합성(13장 참조)은 애니메이션을 더 매끄럽게 만들어 주지만, 텍스트 편집이나 DOM 수정처럼 레이아웃에 영향을 주는 상호작용에는 도움이 되지 않습니다. 다행히 레이아웃 트리를 일종의 캐시로 다루고 바뀌는 부분만 다시 계산함으로써 중복된 레이아웃 작업을 피할 수 있습니다. 이 _무효화(invalidation)_ 기법은 전통적으로 복잡하고 버그가 생기기 쉽지만, 원칙에 입각한 접근과 단순한 추상화를 사용해 다룰 만하게 만들어 보겠습니다.

## 콘텐츠 편집하기

13장에서 우리는 합성을 사용해 `transform`이나 `opacity` 같은 CSS 속성을 매끄럽게 애니메이션했습니다. 하지만 `width`나 `font-size` 같은 _레이아웃 유발_ 속성은 이런 식으로 애니메이션할 수 없었는데, 그것들이 _디스플레이 리스트_ 뿐 아니라 _레이아웃 트리_ 도 바꾸기 때문입니다. 레이아웃 유발 속성을 애니메이션하지 않는 것이 최선이기는 하지만, 레이아웃 트리를 바꾸는 많은 사용자 상호작용은 반응성이 좋아야 합니다.

좋은 예 하나가 텍스트 편집입니다. 사람들은 꽤 빠르게 타이핑하므로 몇 프레임의 지연조차 거슬립니다. 그런데 편집은 HTML 트리를, 따라서 레이아웃 트리를 바꿉니다. 지금 우리 브라우저가 하듯이 레이아웃 트리를 처음부터 다시 만드는 것은 복잡한 페이지에서 매우 느릴 수 있습니다. 예를 들어 우리 브라우저에서 [이 장의 웹 버전](https://browser.engineering/invalidation.html)을 불러와 이 문단 뒤에 나오는 입력 상자에 타이핑해 보세요… _너무_ 느리다는 것을 알게 될 것입니다. `render`에만 1.7초가 걸립니다(그림 1 참조)![^1]

![그림 1: 무효화 최적화가 전혀 없는 상태에서 타이핑하는 예.](example16-input-no-optimizations.png)

*그림 1: 무효화 최적화가 전혀 없는 상태에서 타이핑하는 예.*

`input` 요소에 타이핑하는 것은 특수 처리할 수도 있겠지만,[^2] 그럴 수 없는 다른 텍스트 편집 API도 있습니다. 예를 들어 `contenteditable` 속성은 어떤 요소든 편집 가능하게 만듭니다.[^3]

> **데모**
>
> 이 _서식이 적용된_ **텍스트** 를 클릭해 편집해 보세요. 리치 텍스트까지 편집됩니다!

우리 브라우저에 `contenteditable`의 가장 기본적인 버전을 구현해 봅시다. 유용한 기능이기도 하고 무효화를 시험하기에도 좋습니다. 우선 `contenteditable` 속성을 가진 요소가 포커스 가능해지도록 해야 합니다.[^4]

```python
def is_focusable(node):
    # ...
    elif "contenteditable" in node.attributes:
        return True
    # ...
```

편집 가능한 노드에 포커스하고 나면 타이핑이 그것을 편집해야 합니다. 실제 브라우저라면 커서 이동을 비롯한 온갖 복잡한 문제를 다루겠지만, 저는 단순하게 각 글자를 편집 가능한 요소의 마지막 텍스트 노드에 추가하겠습니다. 먼저 그 텍스트 노드를 찾아야 합니다.

```python
class Frame:
    def keypress(self, char):
        # ...
        elif self.tab.focus and \
            "contenteditable" in self.tab.focus.attributes:
            text_nodes = [
               t for t in tree_to_list(self.tab.focus, [])
               if isinstance(t, Text)
            ]
            if text_nodes:
                last_text = text_nodes[-1]
            else:
                last_text = Text("", self.tab.focus)
                self.tab.focus.children.append(last_text)
```

편집 가능한 요소에 텍스트 자식이 없으면 새로 만든다는 점에 주의하세요. 그다음 입력된 글자를 그 요소에 추가합니다.

```python
class Frame:
    def keypress(self, char):
        elif self.tab.focus and \
            "contenteditable" in self.tab.focus.attributes:
            # ...
            last_text.text += char
            self.set_needs_render()
```

이것만으로 편집이 동작하지만, 요소가 포커스되어 있음을 확인하고 편집이 어디로 들어갈지 보여 주는 커서를 그려 주면 편리합니다. `BlockLayout`에서 그렇게 합시다.

```python
class BlockLayout:
    def paint(self):
        # ...
        if self.node.is_focused \
            and "contenteditable" in self.node.attributes:
            text_nodes = [
                t for t in tree_to_list(self, [])
                if isinstance(t, TextLayout)
            ]
            if text_nodes:
                cmds.append(DrawCursor(text_nodes[-1],
                    text_nodes[-1].width))
            else:
                cmds.append(DrawCursor(self, 0))
        # ...
```

여기서 `DrawCursor`는 그저 `DrawLine`을 감싼 것입니다.

```python
def DrawCursor(elt, offset):
    x = elt.x + offset
    return DrawLine(x, elt.y, x, elt.y + elt.height, "red", 1)
```

이 래퍼를 `InputLayout`에서도 쓰는 편이 좋겠습니다.

```python
class InputLayout(EmbedLayout):
    def paint(self):
        if self.node.is_focused and self.node.tag == "input":
            cmds.append(DrawCursor(self, self.font.measureText(text)))
```

이제 여러분의 브라우저에서 [이 장의 페이지](https://browser.engineering/invalidation.html)에 있는 예제를 편집할 수 있지만, 키를 누를 때마다 1초 넘게 걸려서 편집 경험이 답답할 것입니다. 그러니 그것을 빠르게 만드는 작업을 해 봅시다.

### 더 알아보기

텍스트 편집은 캐럿 어피니티(긴 줄이 단어 중간에서 줄바꿈될 때 커서가 어느 줄에 있는지), 유니코드 처리, [양방향 텍스트](http://unicode.org/faq/bidi.html), 텍스트 서식과 편집의 혼합 같은 까다로운 개념까지 포함하면 [대단히 어렵습니다](https://lord.io/text-editing-hates-you-too/). 그러니 브라우저가 이 모든 복잡함을 구현해 `contenteditable` 뒤에 숨겨 준다는 것은 좋은 일입니다.

## 왜 무효화인가?

근본적으로 우리 브라우저에서 이 페이지를 편집하는 것이 느린 이유는 페이지가 꽤 크기 때문입니다. 결국 느린 것은 키 입력을 처리하는 일이 아닙니다. `Text` 노드에 글자를 덧붙이는 데는 거의 시간이 들지 않습니다. 시간이 드는 것은 그 뒤에 페이지 전체를 다시 렌더링하는 일입니다.

우리는 크고 복잡한 페이지에서도 상호작용이 빠르기를 바라므로, 페이지를 다시 렌더링하는 데 걸리는 시간이 _페이지의 크기_ 가 아니라 _변경의 크기_ 에 비례하기를 바랍니다. 저는 이를 _증분 성능의 원칙_ 이라고 부르며, 크고 복잡한 웹 애플리케이션을 다루는 데 결정적으로 중요합니다. 텍스트 편집을 빠르게 만들어 줄 뿐 아니라, 개발자가 페이지 전체의 내용을 고려하지 않고 한 번에 하나의 변경만 생각하며 성능을 다룰 수 있다는 뜻이기도 합니다. 그러므로 증분 성능은 복잡한 애플리케이션에 필수적입니다.

하지만 증분 성능의 원칙은 우리 브라우저 구현을 정말로 크게 제약하기도 합니다. 예를 들어 레이아웃 트리 전체를 _순회하는_ 것만으로도 변경이 아니라 페이지 전체에 비례하는 시간이 들 것이므로, 그조차 할 여유가 없습니다.

증분 성능을 달성하려면 최초 렌더링과 이후의 재렌더링을 다르게 생각해야 합니다.[^5] 페이지가 처음 로드될 때 렌더링은 페이지 크기에 비례하는 시간이 걸립니다. 하지만 그 최초 렌더링을 캐시로 다루겠습니다. 이후의 렌더링은 그 캐시의 일부를 _무효화_ 하고 다시 계산해 변경 크기에 비례하는 시간이 걸리되 페이지 대부분은 건드리지 않습니다.[^6] 실제 브라우저에서는 렌더링 파이프라인의 모든 단계가 증분적이어야 하지만, 이 장은 레이아웃에 집중합니다.[^7]

이 캐시-무효화 접근의 열쇠는 변경의 영향을 추적하는 것입니다. `style` 속성 같은 페이지의 한 부분이 바뀌면, 그 요소의 크기처럼 그것에 의존하는 다른 것들도 바뀝니다. 그래서 각 레이아웃 필드 수준까지 내려가는 상세한 _의존성 그래프_ 를 만들고, 그 그래프를 사용해 무엇을 다시 계산할지 판단해야 합니다. 이는 우리의 `needs_style`과 `needs_layout` 플래그를 훨씬 크게 확장한 것과 비슷합니다. 그래서 이 장의 대부분은 의존성 그래프에서 의존성을 추적하는 것과, 그것을 돕는 추상화를 만드는 것에 관한 이야기입니다. 그 추상화를 사용하려면 레이아웃 엔진을 상당히 리팩터링해야 합니다. 하지만 레이아웃을 증분화하면 레이아웃에서 가장 비싼 두 부분, 즉 레이아웃 트리를 만드는 것과 레이아웃 필드를 계산하기 위해 그것을 순회하는 것을 건너뛸 수 있습니다. 다 끝나고 나면 텍스트 편집 같은 작은 변경에 대해 재레이아웃이 1밀리초 미만이 될 것입니다.

### 더 알아보기

증분 성능의 원칙은 브라우저를 좋은 플랫폼으로 만드는 요소 중 하나입니다. 웹이 _선언적_ 이라는 점을 떠올려 보세요. 웹 페이지는 자신이 어떻게 보이는지 _기술_ 하는 데만 관여하고, 그 기술을 구현하는 것은 브라우저의 몫입니다. 우리 브라우저 엔지니어에게 그것은 한 무더기의 복잡함을 만들어 냅니다. 하지만 웹 전체를 생각해 보세요. 브라우저 엔지니어뿐 아니라 웹 개발자와 사용자도 관여합니다. 브라우저에 복잡한 무효화 알고리즘을 구현하면 웹 개발자는 더 흥미로운 애플리케이션을 만드는 데 집중할 수 있고 사용자는 더 좋고 반응성 좋은 경험을 얻습니다. 선언적인 웹은 무효화 알고리즘을 한 번만 작성하면 자동으로 모두에게 이득이 되게 해 줍니다.

## 멱등성

이 캐시-무효화 아이디어를 구현하려면 첫 번째 장애물은 우리 브라우저가 레이아웃 단계를 실행할 때마다 레이아웃 트리를 처음부터 다시 만든다는 점입니다.

```python
class Frame:
    def render(self):
        if self.needs_layout:
            self.document = DocumentLayout(self.nodes, self)
            self.document.layout(self.frame_width, self.tab.zoom)
            # ...
```

새 `DocumentLayout`으로 처음부터 시작함으로써 우리는 옛 레이아웃 정보를 모두 무시하고 새로 시작합니다. 본질적으로 트리 전체를 _무효화_ 하는 것이죠. 그러니 첫 번째 최적화는 그것을 피하고 최대한 많은 레이아웃 객체를 재사용하는 것이어야 합니다. 그러면 메모리 할당 시간을 아낄 뿐 아니라, 옛 레이아웃 정보를 남겨 둠으로써 캐시-무효화 접근을 가능하게 합니다.

그런데 코딩으로 바로 뛰어들기 전에 레이아웃 객체가 어떻게 만들어지는지 살펴봅시다. 브라우저 코드에서 모든 레이아웃 클래스 이름이 끝나는 `Layout`을 검색해 보세요. 레이아웃 객체가 몇 군데에서만 만들어진다는 것을 알 수 있을 것입니다.

- `DocumentLayout` 객체는 `Frame`이 `render`에서 만듭니다.

- `BlockLayout` 객체는 다음 중 하나가 만듭니다.

  - `layout`에서 `DocumentLayout`이 만들거나,

  - `layout`에서 `BlockLayout`이 만듭니다.

- `LineLayout` 객체는 `BlockLayout`이 `new_line`에서 만듭니다.

- 나머지 모두는 `BlockLayout`이 `add_inline_child`에서 만듭니다.

`DocumentLayout`부터 시작합시다. 이것은 `render`에서 만들어지며, 두 매개변수 `nodes`와 `self`는 매번 같습니다. 즉 매번 똑같은 `DocumentLayout`이 만들어집니다.[^8] 낭비죠. `DocumentLayout`을 `load`에서 한 번만 만듭시다.

```python
class Frame:
    def load(self, url, payload=None):
        # ...
        self.document = DocumentLayout(self.nodes, self)
        self.set_needs_render()

    def render(self):
        if self.needs_layout:
            self.document.layout(self.frame_width, self.tab.zoom)
            # ...
```

이어서 `DocumentLayout`이 `BlockLayout`을 만드는 곳을 봅시다.

```python
class DocumentLayout:
    def layout(self, width, zoom):
        child = BlockLayout(self.node, self, None, self.frame)
        # ...
```

다시 한번 생성자 매개변수가 바뀔 수 없으므로, 이 레이아웃 객체를 다시 만드는 것도 다음과 같이 건너뛸 수 있습니다.

```python
class DocumentLayout:
    def layout(self, width, zoom):
        if not self.children:
            child = BlockLayout(self.node, self, None, self.frame)
        else:
            child = self.children[0]
        # ...
```

다만 아직 이 변경으로 브라우저를 실행하지는 마세요! 레이아웃 객체를 재사용하면 같은 객체에 대해 `layout`을 여러 번 실행하게 됩니다. `layout`은 그렇게 동작하도록 만들어지지 않았고, 그러면 온갖 이상한 동작이 생깁니다. 예를 들어 `DocumentLayout`이 자식 `BlockLayout`을 만든 뒤 그것을 `children` 배열에 _덧붙입니다(append)_.

```python
class DocumentLayout:
    def layout(self, width, zoom):
        # ...
        self.children.append(child)
        # ...
```

그런데 같은 자식을 두 번 이상 `append`하고 싶지는 않습니다!

여기서의 문제는 _멱등성(idempotence)_ 이라고 합니다. `layout`을 반복 호출해도 상태가 반복해서 바뀌어서는 안 됩니다. 더 형식적으로 말하면, 같은 입력과 의존성으로 두 번 연달아 호출했을 때 같은 결과가 나오면 그 함수는 멱등입니다. 필드에 값을 대입하는 것은 멱등입니다. 두 번째로 같은 값을 대입하는 것은 아무 일도 하지 않으니까요. 하지만 `append` 같은 메서드는 멱등이 아닙니다.

멱등이 아닌 메서드 호출을 모두 고쳐야 합니다. `DocumentLayout`에서는 `append` 대신 대입으로 바꿀 수 있습니다.

```python
class DocumentLayout:
    def layout(self, width, zoom):
        # ...
        self.children = [child]
        # ...
```

`BlockLayout`도 자신의 `children` 배열에 `append`를 호출합니다. `layout`에서 `children` 배열을 초기화함으로써 고칠 수 있습니다. 블록 경우와 인라인 경우에 각각 초기화 코드를 넣겠습니다.

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            self.children = []
            # ...
        else:
            self.children = []
            # ...
```

이렇게 하면 `BlockLayout`의 `layout` 함수가 멱등이 되는데, 호출할 때마다 새 `children` 배열에서 다시 시작하기 때문입니다.

브라우저를 실행해 보기 전에, 다른 모든 `layout` 메서드를 훑어보며 멱등이 아닐 수 있는 하위 호출을 적어 봅시다. 제가 찾은 것은 다음과 같습니다.[^9]

- `new_line`에서 `BlockLayout`이 자신의 `children` 배열에 덧붙입니다.

- `add_inline_child`에서 `BlockLayout`이 어떤 `LineLayout` 자식의 `children` 배열에 덧붙입니다.

- `add_inline_child`에서 `BlockLayout`이 `get_font`를 호출하고, `TextLayout`과 `InputLayout` 메서드도 그렇게 합니다.

- 사실상 모든 레이아웃 메서드가 `dpx`를 호출합니다.

`new_line`과 `add_inline_child` 메서드는 `children` 배열을 초기화하는 `layout`을 통해서만 호출되므로 멱등성을 깨지 않습니다. `get_font` 함수는 캐시 역할을 하므로 여러 번 호출해도 같은 폰트 객체를 반환하여 멱등성이 유지됩니다. 그리고 `dpx`는 그저 계산을 할 뿐이므로 같은 입력에 대해 항상 같은 결과를 반환합니다. 다시 말해 이제 우리의 모든 `layout` 메서드는 멱등입니다.

따라서 같은 객체에 대해 `layout`을 여러 번 호출해도 안전합니다. 바로 지금 우리가 하고 있는 일이죠. 더 일반적으로, 멱등 함수가 _몇 번_ 호출되는지는 중요하지 않으므로 _중복 호출을 건너뛸_ 수 있습니다! 그래서 멱등성이 이 장 나머지의 토대가 되며, 이 장은 온통 중복 작업을 건너뛰는 이야기입니다.

### 더 알아보기

HTTP에도 [멱등성 개념](https://developer.mozilla.org/en-US/docs/Glossary/Idempotent)이 있지만, HTTP에는 클라이언트와 서버가 모두 관여하므로 여기서 이야기하는 것과 미묘하게 다릅니다. HTTP에서 멱등성은 요청이 응답이 아니라 서버 상태에 미치는 영향만을 다룹니다. 그래서 예를 들어 같은 페이지를 `GET`으로 두 번 요청하면 (페이지가 바뀌었다면) 다른 응답이 나올 수 있지만, 서버를 전혀 변경하지 않았으므로 그 요청은 여전히 멱등입니다. 또한 HTTP 멱등성은 클라이언트가 볼 수 있는 상태만 다루므로, 예를 들어 첫 번째 `GET` 요청은 캐시로 가고 두 번째는 그러지 않을 수도 있고, 각각이 별도의 로그 항목을 추가할 수도 있습니다.

## 의존성

지금까지 우리는 레이아웃 객체를 두 개만 재사용하고 있습니다. `DocumentLayout`과 루트 `BlockLayout`입니다. 여기서 만들어지는 다른 `BlockLayout`들을 봅시다.

```python
class BlockLayout:
    def layout(self):
        self.children = []
        # ...
        if mode == "block":
            previous = None
            for child in self.node.children:
                next = BlockLayout(child, self, previous, self.frame)
                self.children.append(next)
                previous = next
        # ...
```

이 코드는 루트 `BlockLayout`을 만드는 코드보다 조금 더 복잡합니다. `child`와 `previous` 인자가 `node.children`에서 오는데, 그 `children` 배열은 `contenteditable` 편집이나 `innerHTML` 호출의 결과로 바뀔 수 있습니다.[^10] 게다가 이 코드가 실행되기라도 하려면 노드의 `layout_mode`가 `block`이어야 하는데, `layout_mode` 자체도 노드의 `children`을 읽습니다.[^11] 그래서 `BlockLayout`을 언제 다시 만들어야 하는지 알기가 더 어렵습니다.

멱등성이란 _같은 입력과 의존성으로_ 함수를 다시 호출하면 같은 결과가 나온다는 뜻이었음을 떠올려 보세요. 여기서는 입력이 바뀔 수 있으므로, _노드의 `children` 필드가 바뀌지 않았을 때만_ 중복 재실행을 피할 수 있습니다. 그러니 그 `children` 필드가 바뀌었는지 알 방법이 필요합니다. 더티 플래그를 쓰겠습니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.children_dirty = True
```

더티 플래그는 `needs_layout`이나 `needs_draw`처럼 전에도 보았지만, 레이아웃은 더 복잡하므로 더티 플래그에 대해 좀 더 엄밀하게 생각해야 합니다.

모든 더티 플래그는 특정 필드를 _보호합니다_. 이 플래그는 `BlockLayout`의 `children` 필드를 보호합니다. 더티 플래그에는 생애 주기가 있습니다. 설정되고, 확인되고, 초기화될 수 있습니다. 더티 플래그는 `True`로 시작하며, 그 필드의 입력이나 의존성이 바뀔 때 `True`로 설정되어 _보호되는 필드_ 를 사용할 수 없다고 표시합니다. 그다음 보호되는 필드를 사용하기 전에 더티 플래그를 반드시 확인해야 합니다. 플래그는 보호되는 필드가 다시 계산될 때만 `False`로 초기화됩니다.

그럼 `children_dirty` 플래그를 이런 식으로 분석해 봅시다. 더티 플래그는 그것이 보호하는 필드의 _의존성_ 이 바뀌면 설정되어야 합니다. 이 경우 더티 플래그는 `BlockLayout`의 `children` 필드를 보호하는데, 그 필드는 다시 연관된 `Element`의 `children` 필드에 의존합니다. 즉 `Element`의 `children` 필드가 수정될 때마다 연관된 `BlockLayout`의 더티 플래그를 설정해야 합니다.

```python
class JSContext:
    def innerHTML_set(self, handle, s, window_id):
        # ...
        obj = elt.layout_object
        while not isinstance(obj, BlockLayout):
            obj = obj.parent
        obj.children_dirty = True
```

마찬가지로 `contenteditable` 요소를 편집할 때마다 더티 플래그를 설정해야 합니다. 그것도 노드의 `children`에 영향을 줄 수 있기 때문입니다.

```python
class Frame:
    def keypress(self, char):
        elif self.tab.focus and \
            "contenteditable" in self.tab.focus.attributes:
            # ...
            obj = self.tab.focus.layout_object
            while not isinstance(obj, BlockLayout):
                obj = obj.parent
            obj.children_dirty = True
```

보호되는 필드의 _모든_ 의존성이 더티 플래그를 설정하는 것이 중요합니다. 어떤 필드가 어떤 다른 필드에 의존하는지 늘 경계해야 하므로 이는 어려울 수 있습니다. 하지만 더티 플래그 설정을 잊으면 때때로 보호되는 필드를 다시 계산하지 못해 페이지를 잘못 표시하게 됩니다. 보통 이런 버그는 예측할 수 없는 레이아웃 결함처럼 보이며 디버깅이 아주 어려울 수 있으니 조심해야 합니다.

어쨌든 이제 더티 플래그를 설정하고 있으니, 다음 단계는 보호되는 필드를 사용하기 전에 그것을 확인하는 것입니다. `BlockLayout`은 `children` 필드를 세 곳에서 사용합니다. 모든 자식에 대해 `layout`을 재귀 호출할 때, 자신의 `height`를 계산할 때, 자신을 `paint`할 때입니다. 각 자리에 확인을 추가합시다.

```python
class BlockLayout:
    def layout(self):
        # ...
        
        assert not self.children_dirty
        for child in self.children:
            child.layout()
            
        assert not self.children_dirty
        self.height = sum([child.height for child in self.children])

    def paint(self, display_list):
        assert not self.children_dirty
        # ...
```

이 단언(assertion)들은 절대 발동되지 않아야 하니 건너뛰고 싶어질 수 있지만, 이렇게 방어적으로 코딩하면 버그를 더 일찍 잡고 디버깅하기도 쉬워집니다. 필드를 잘못된 순서로 무효화하거나 실제로 중요한 계산을 건너뛰기가 아주 쉬운데, 적어도 장난감 브라우저를 디버깅할 때는 미묘하게 잘못된 렌더링보다는 충돌이 나는 편이 낫습니다![^12]

마지막으로, 필드가 다시 계산되면 더티 플래그를 초기화해야 합니다. 여기서는 `children` 배열을 다시 계산했을 때 플래그를 초기화합니다.

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            # ...
            self.children_dirty = False
        else:
            # ...
            self.children_dirty = False
```

이제 더티 플래그의 세 부분이 모두 갖춰졌으니, 브라우저를 실행해 [이 장의 페이지](https://browser.engineering/invalidation.html)에서 시험해 볼 수 있을 것입니다. 텍스트를 편집하거나 `innerHTML`을 호출해도 단언 실패가 보이지 않아야 합니다. 조금씩 작업하고 자주 테스트하세요. 디버깅이 쉬워집니다.

이제 `children_dirty` 플래그가 올바르게 동작하니, 그것에 의존해 중복 작업을 피할 수 있습니다. `children`이 더럽지 않다면 `BlockLayout` 자식들을 다시 만들 필요가 없습니다.

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            if self.children_dirty:
                # ...
                self.children_dirty = False
```

그 가장 안쪽 `if` 안에 `print` 문을 넣으면 `BlockLayout` 자식이 만들어질 때마다 콘솔 출력이 보일 것입니다. 텍스트를 편집하면서 시험해 보세요. 전혀 일어나지 않아야 하고, 편집이 조금 더 매끄러워질 것입니다.

### 더 알아보기

"컴퓨터 과학에서 가장 어려운 두 가지 문제는 캐시 무효화와 이름 짓기"라는 [필 칼턴의 말](https://www.karlton.org/2017/12/naming-things-hard/)을 들어 본 적이 있다면, 더티 플래그를 점점 더 많이 관리하는 것이 복잡성을 키운다는 것을 아실 것입니다. 필은 한때 Netscape에서 일했으므로(공식 직함은 "[수석 잔소리꾼](https://www.karlton.org/karlton/)"이었습니다) 저는 그가 레이아웃 무효화 이야기를 하면서 그 말을 하는 장면을 상상하곤 합니다.

## 보호되는 필드

`children_dirty` 같은 더티 플래그는 레이아웃 무효화의 전통적인 접근법이지만 단점이 있습니다. 그것들을 올바르게 사용하려면 필드 사이의 의존성에 주의하고 각 필드를 언제 읽고 쓰는지 알아야 합니다. 그리고 더티 플래그를 확인하거나 설정하는 것을 잊기 쉬워서 찾기 어려운 버그로 이어집니다. 우리의 단순한 브라우저에서는 아마 해낼 수 있겠지만, 실제 브라우저의 레이아웃 시스템은 훨씬 복잡해서 실수를 피하기가 거의 불가능해집니다.

더 나은 접근법이 있습니다. 우선 더티 플래그와 그것이 보호하는 필드를 하나의 객체로 합쳐 봅시다.

```python
class ProtectedField:
    def __init__(self):
        self.value = None
        self.dirty = True
```

그러면 어떤 더티 플래그가 어떤 필드를 보호하는지 분명해집니다. 기존 더티 플래그를 `ProtectedField`로 대체합시다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.children = ProtectedField()
        # ...
```

다음으로 더티 플래그 생애 주기의 각 단계마다 메서드를 추가합시다. 보호되는 필드의 더티 플래그를 설정하는 것을 `mark`한다고 하겠습니다.

```python
class ProtectedField:
    def mark(self):
        if self.dirty: return
        self.dirty = True
```

이른 반환을 눈여겨보세요. 이미 더러운 필드를 표시하는 것은 아무 일도 하지 않습니다. 나중에 이 점이 중요해집니다. 이제 `innerHTML_set`과 `keypress`에서 `mark`를 호출하세요.

```python
class JSContext:
    def innerHTML_set(self, handle, s, window_id):
        # ...
        obj.children.mark()

class Frame:
    def keypress(self, char):
        elif self.tab.focus and \
            "contenteditable" in self.tab.focus.attributes:
            # ...
            obj.children.mark()
```

`ProtectedField`의 값을 "`get`"하기 전에 더티 플래그를 확인합시다.

```python
class ProtectedField:
    def get(self):
        assert not self.dirty
        return self.value
```

이제 `layout`을 비롯한 여러 곳에서 `get`으로 `children` 필드를 읽을 수 있습니다.

```python
class BlockLayout:
    def layout(self):
        # ...
        for child in self.children.get():
            child.layout()

        self.height = \
            sum([child.height for child in self.children.get()])
```

`get`의 좋은 점은 더티 플래그 연산을 자동화해서 잊을 수 없게 만든다는 것입니다. 코드도 조금 더 읽기 좋아집니다.

마지막으로 더티 플래그를 초기화하기 위해, 필드를 "`set`"할 때 호출자가 새 값을 넘기게 합시다. 이렇게 하면 더티 플래그와 값이 함께 갱신되는 것이 보장됩니다.

```python
class ProtectedField:
    def set(self, value):
        self.value = value
        self.dirty = False
```

안타깝게도 `set`을 쓰려면 리팩터링이 조금 필요합니다. 예를 들어 `BlockLayout`에서는 지역 변수에 자식 배열을 만든 다음 마지막에 `children` 필드를 `set`해야 합니다.

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            if self.children.dirty:
                children = []
                previous = None
                for child in self.node.children:
                    next = BlockLayout(
                        child, self, previous, self.frame)
                    children.append(next)
                    previous = next
                self.children.set(children)
```

하지만 그 이득은, `get`과 마찬가지로 `set`도 더티 플래그 연산을 자동화해서 망치기 어렵게 만든다는 것입니다. 덕분에 레이아웃을 더 빠르게 만들기 위해 더 복잡하고 야심 찬 무효화 알고리즘을 생각해 볼 수 있게 됩니다.

### 더 알아보기

의존성을 바꾸면서 어떤 필드의 더티 플래그 설정을 잊는 것을 기술적으로 [_과소 무효화(under-invalidation)_](https://developer.chrome.com/docs/chromium/layoutng/#under-invalidation)라고 합니다. 이는 특정 변경이 마침내 "먹히려면" 여러 번 일어나야 하는 버그를 흔히 일으킵니다. 다시 말해 이런 종류의 버그는 뜻하지 않은 비멱등성을 만들어 냅니다! 이런 버그는 아주 특정한 변경 순서를 만들어야만 보통 드러나기 때문에 [찾기 어렵습니다](https://developer.chrome.com/docs/chromium/layoutng/#correctness).

## 재귀적 무효화

`ProtectedField` 클래스를 활용해 인라인 레이아웃이 일어날 때마다 모든 `LineLayout`과 그 자식들을 다시 만드는 것을 피해 봅시다. 모든 것은 여기서 시작합니다.

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            # ...
        else:
            self.children = []
            self.new_line()
            self.recurse(self.node)
```

`new_line`과 `recurse` 메서드, 그리고 그것들이 호출하는 `word`, `input`, `iframe`, `image`, `add_inline_child` 같은 헬퍼들이 줄바꿈을 처리합니다. 너비를 확인하고 새 줄을 만드는 등의 일을 하죠. `children` 필드가 더럽지 않다면 그 모든 것을 건너뛰고 싶지만, 이는 블록 레이아웃보다 조금 더 어렵습니다. 줄바꿈 중에 여러 다른 필드가 읽히고, `children` 필드가 그 모두에 의존하기 때문입니다.

그 모든 필드를 `ProtectedField`로 바꾸는 것은 만만치 않은 작업이 될 것입니다. 거의 모든 메서드가 읽는 `zoom`부터 시작해 조금씩 해 나가겠습니다.

`zoom`은 처음에 `DocumentLayout`에서 설정됩니다.

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.zoom = ProtectedField()
        # ...

    def layout(self, width, zoom):
        # ...
        self.zoom.set(zoom)
        # ...
```

각 `BlockLayout`도 자신만의 `zoom` 필드를 갖는데, 그것을 보호할 수 있습니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.zoom = ProtectedField()
        # ...
```

다만 `BlockLayout`에서 `zoom` 값은 부모의 `zoom` 필드에서 옵니다. 다음과 같이 쓰고 싶어질 수 있습니다.

```python
class BlockLayout:
    def layout(self):
        parent_zoom = self.parent.zoom.get()
        self.zoom.set(parent_zoom)
        # ...
```

하지만 더티 플래그를 쓸 때는 항상 (`mark`로) 무효화하고, (`get`으로) 확인하고, (`set`으로) 초기화하는 것을 생각해야 한다는 점을 떠올려 보세요. `get`과 `set`은 추가했는데, 누가 `zoom` 더티 플래그를 _mark_ 할까요?[^13]

필드의 의존성이 바뀔 때 그 필드의 더티 플래그를 표시합니다. 예를 들어 `innerHTML_set`과 `keypress`는 HTML 트리를 바꾸고 레이아웃 트리의 `children` 필드가 그것에 의존하므로, 그 핸들러들이 `children` 필드에 `mark`를 호출합니다. 자식의 `zoom` 필드가 부모의 `zoom` 필드에 의존하므로, `zoom` 필드가 바뀌면 모든 자식을 표시해야 합니다. 그래서 `DocumentLayout`에서는 다음과 같이 해야 합니다.

```python
class DocumentLayout:
    def layout(self, width, zoom):
        # ...
        self.zoom.set(zoom)
        child.zoom.mark()
        # ...
```

마찬가지로 자식이 여럿인 `BlockLayout`에서는 다음과 같이 해야 합니다.

```python
class BlockLayout:
    def layout(self):
        # ...
        for child in self.children.get():
            child.zoom.mark()
```

그런데 이제 다시 수동으로 메서드를 호출하며 호출을 잊지 않으려 애쓰는 상황으로 돌아왔습니다. 우리에게 필요한 것은 매끄러운 무언가입니다. 필드를 `set`하면 그것에 의존하는 모든 필드가 자동으로 표시되어야 합니다.

그러려면 각 `ProtectedField`가 자신에게 의존하는 모든 필드를 추적해야 하는데, 이를 `invalidations`라고 부르겠습니다.

```python
class ProtectedField:
    def __init__(self):
        # ...
        self.invalidations = set()
```

예를 들어 자식의 `zoom` 필드를 부모의 `zoom` 필드의 `invalidations`에 추가할 수 있습니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.parent.zoom.invalidations.add(self.zoom)
```

그다음 `mark` 호출을 자동화하기 위해 각 무효화 대상을 표시하는 `notify` 메서드를 추가합시다.

```python
class ProtectedField:
    def notify(self):
        for field in self.invalidations:
            field.mark()
```

그러면 `set`이 자동으로 `notify`를 호출할 수 있습니다.

```python
class ProtectedField:
    def set(self, value):
        self.notify()
        self.value = value
        self.dirty = False
```

진전이지만, 애초에 무효화 대상 추가를 잊을 수 있다는 문제는 남아 있습니다. 조금 더 자동화할 수 있습니다. 생각해 보세요. 자식의 `zoom`이 _왜_ 부모의 것에 의존해야 할까요? 자식의 것을 계산할 때 부모의 `zoom`을 `get`하기 때문입니다. 그러니 무효화 대상 추가를 `get`의 일부로 할 수 있습니다! 읽히는 필드가 바뀌면 무효화할 필드를 위한 `notify` 매개변수를 가진 `get`의 변형 `read`를 만듭시다.

```python
class ProtectedField:
    def read(self, notify):
        self.invalidations.add(notify)
        return self.get()
```

이제 `zoom` 계산은 `read`만 쓰면 되고, 모든 표시와 의존성 로직이 자동으로 처리됩니다.

```python
class BlockLayout:
    def layout(self):
        parent_zoom = self.parent.zoom.read(notify=self.zoom)
        self.zoom.set(parent_zoom)
```

사실 부모의 값을 그대로 복사하는 이 패턴은 꽤 흔하므로 그것을 위한 지름길을 추가합시다.

```python
class ProtectedField:
    def copy(self, field):
        self.set(field.read(notify=self))

class BlockLayout:
    def layout(self):
        self.zoom.copy(self.parent.zoom)
        # ...
```

`BlockLayout`은 `input`, `image`, `iframe`, `word`, `add_inline_child` 메서드 안에서도 `zoom` 필드를 읽는데, 이들은 모두 `children` 필드를 계산하는 일의 일부입니다. 그 메서드들에서는 `read`를 사용해 zoom 값을 가져오면서 동시에 zoom 값이 바뀌면 `children` 필드를 무효화할 수 있습니다.

```python
class BlockLayout:
    def input(self, node):
        zoom = self.zoom.read(notify=self.children)
        # ...
```

위에서 언급한 다른 메서드들에도 똑같이 하세요. 또한 (이제 꽤 많아진!) 다른 모든 레이아웃 객체 타입의 `zoom` 필드도 보호하되, 쓰기에는 `copy`를, `get` 자리에는 `read`를 사용하세요. 브라우저를 실행해 확대 수준을 올리거나 내려도 아무것도 죽지 않는지 확인해 제대로 했는지 점검하세요.

그런데 `zoom` 필드를 보호한다고 해서 브라우저가 빨라지지는 않았습니다. 여전히 확대 수준을 복사해 나르고 있고, 게다가 이제 더티 플래그를 확인하고 무효화 대상을 갱신하는 추가 작업까지 하고 있습니다. 하지만 `zoom` 필드를 보호했다는 것은 확대 수준이 바뀔 때 `children`과 그것에 의존하는 다른 필드들을 무효화할 수 있다는 뜻이며, 이는 `LineLayout`과 `TextLayout` 요소를 언제 다시 만들어야 하는지 알려 주는 데 도움이 됩니다.

### 더 알아보기

실제 브라우저는 (적어도 지금은) `ProtectedField` 같은 자동 의존성 추적을 사용하지 않습니다. 한 가지 이유는 성능입니다. `ProtectedField`는 많은 객체와 메서드 호출을 더하며, 과도하게 사용하면 성능을 오히려 나쁘게 만들기 쉽습니다. 너무 많은 보호 필드를 무효화해 연쇄적인 작업을 만들어 낼 수도 있습니다. 마지막으로 대부분의 브라우저 엔진 코드베이스에는 오래된 코드가 많고, 그것들을 새 접근 방식으로 리팩터링하려면 많은 시간이 걸립니다.

## 너비 보호하기

줄바꿈이 의존하는 또 다른 필드는 `width`입니다. 그것도 `ProtectedField`로 바꾸되, 새 `read` 메서드도 함께 써 봅시다. `zoom`과 마찬가지로 `width`도 처음에 `DocumentLayout`에서 설정됩니다.

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.width = ProtectedField()
        # ...

    def layout(self, width, zoom):
        # ...
        self.width.set(width - 2 * dpx(HSTEP, zoom))
        # ...
```

그다음 `BlockLayout`이 부모로부터 복사합니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.zoom = ProtectedField()
        # ...

    def layout(self):
        # ...
        self.width.copy(self.parent.width)
        # ...
```

`width` 필드는 줄바꿈 중에 읽힙니다. 예를 들어 `add_inline_child`는 새 줄을 추가할지 결정하는 데 그것이 필요합니다. `read`로 그 의존성을 설정하겠습니다.

```python
class BlockLayout:
    def add_inline_child(self, node, w, child_class,
                         frame, word=None):
        width = self.width.read(notify=self.children)
        if self.cursor_x + w > width:
            self.new_line()
        # ...
```

그런데 새 줄을 추가할지 여부에 대한 결정은 `add_inline_child`의 입력인 `w`에도 의존한다는 점을 눈여겨보세요. `add_inline_child`의 호출자들을 살펴보면 대부분의 경우 이 인자가 `zoom`에만 의존하지만 `word`에서는 폰트 객체에 의존한다는 것을 알 수 있습니다.

```python
class BlockLayout:
    def word(self, node, word):
        zoom = self.zoom.read(notify=self.children)
        node_font = font(node.style, zoom)
        w = node_font.measureText(word)
        self.add_inline_child(
            node, w, TextLayout, self.frame, word)
```

폰트가 노드의 `style`에 의존하며, `style`은 예를 들어 `style_set` 함수를 통해 바뀔 수 있다는 점에 주의하세요. 이를 처리하려면 `style`을 보호해야 합니다.

```python
class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.style = ProtectedField()
        # ...

class Text:
    def __init__(self, text, parent):
        # ...
        self.style = ProtectedField()
        # ...
```

`style` 필드는 `style` 메서드에서 계산되는데, 이 메서드는 여러 단계에 걸쳐 새 `style` 딕셔너리를 계산합니다. 그 새 딕셔너리를 지역 변수에 만들고 마지막에 `set`합시다.

```python
def style(node, rules, frame):
    old_style = node.style.value
    new_style = {}
    # ...
    node.style.set(new_style)

    for child in node.children:
        style(child, rules, frame)
```

`style` 안에서 한 경로가 부모 노드의 style을 읽습니다. 이런 경우 의존성을 표시해야 합니다.

```python
def style(node, rules, frame):
    for property, default_value in INHERITED_PROPERTIES.items():
        if node.parent:
            parent_style = node.parent.style.read(notify=node.style)
            new_style[property] = parent_style[property]
        else:
            new_style[property] = default_value
```

그러면 `style_set`이 `style` 필드를 표시할 수 있습니다.[^14]

```python
class JSContext:
    def style_set(self, handle, s, window_id):
        # ...
        elt.style.mark()
```

마지막으로 `word`(그리고 `add_inline_child`의 비슷한 코드)에서 `style` 필드에 의존할 수 있습니다.

```python
class BlockLayout:
    def word(self, node, word):
        # ...
        style = self.children.read(node.style)
        node_font = font(style, zoom)
        # ...
```

`style` 필드의 다른 모든 사용처가 `read`나 `get`을 쓰도록 하세요. 어느 쪽인지는 꽤 분명할 것입니다.

이제 줄바꿈 중에 읽히는 모든 필드를 보호했습니다. 즉 `children` 필드의 더티 플래그가 이제 줄바꿈을 건너뛸 수 있는지를 올바르게 추적합니다. 그것을 활용합시다.

```python
class BlockLayout:
    def layout(self):
        # ...
        if mode == "block":
            if self.children.dirty:
                # ...
        else:
            if self.children.dirty:
                # ...
```

또한 이제 `children`을 `set`을 통해서만 수정하도록 해야 합니다. 이는 현재 `children` 필드에 `append`하는 `add_inline_child`와 `new_line`에 문제가 됩니다. 몇 가지 해결책이 가능하지만, 편의를 위해[^15] 두 번째의 보호되지 않는 필드 `temp_children`을 사용해 자식 목록을 만든 다음, 마지막에 그것을 `children` 필드의 새 값으로 `set`하겠습니다.

```python
class BlockLayout:
    def layout(self):
        # ...
        if mode == "block":
            # ...
        else:
            if self.children.dirty:
                self.temp_children = []
                self.new_line()
                self.recurse(self.node)
                self.children.set(self.temp_children)
                self.temp_children = None
```

다 쓰고 나면 `temp_children`을 초기화해서 코드의 다른 부분이 실수로 그것을 쓰지 않도록 한다는 점에 주의하세요. 이렇게 하면 `new_line`이 `temp_children`을 수정할 수 있고, 그것이 결국 `children`의 값이 됩니다.

```python
class BlockLayout:
    def new_line(self):
        self.previous_word = None
        self.cursor_x = 0
        last_line = self.temp_children[-1] \
            if self.temp_children else None
        new_line = LineLayout(self.node, self, last_line)
        self.temp_children.append(new_line)
```

`add_inline_child`에서도 비슷한 일을 하고 싶을 것입니다.

```python
class BlockLayout:
    def add_inline_child(self, node, w, child_class,
                         frame, word=None):
        # ...
        line = self.temp_children[-1]
        # ...
```

이 수정들 덕분에 이제 우리 브라우저는 레이아웃 트리의 어떤 부분도 바뀌지 않는 한 다시 만들지 않으며, 그러면 재레이아웃이 어느 정도 빨라질 것입니다. 알맞은 `read`와 `get` 호출을 추가해 왔다면 여러분의 브라우저가 거의 동작할 것입니다. 까다로운 경우가 하나 있습니다. 보호되는 `children` 필드와 보호되지 않는 것을 모두 다룰 수 있는 `tree_to_list`입니다. 저는 타입 검사로 이를 고쳤습니다.

```python
def tree_to_list(tree, list):
    # ...
    children = tree.children
    if isinstance(children, ProtectedField):
        children = children.get()
    for child in children:
        tree_to_list(child, list)
    # ...
```

이 모든 변경을 마치면 브라우저가 다시 동작하고, 이제 대부분의 요소에 대해 줄 레이아웃을 건너뛰게 됩니다.

이제 보호되는 필드가 꽤 많아졌지만, 더티 플래그를 바탕으로 다시 계산을 건너뛰는 것은 `children`뿐이라는 점에 주의하세요. `children`을 다시 계산하는 것은 느리지만 대부분의 다른 필드는 계산이 정말 빠르기 때문입니다. 더티 플래그를 확인하는 데도 시간이 들고 코드도 어수선해지므로, 그럴 만한 가치가 있을 때만 하고 싶습니다.

### 더 알아보기

실제 브라우저에서 레이아웃 단계는 때때로 둘로 나뉩니다. 먼저 레이아웃 트리를 구성하고, 그다음 별도의 [프래그먼트 트리](https://developer.chrome.com/docs/chromium/renderingng-data-structures/#the_immutable_fragment_tree)를 구성합니다.[^16] Chromium에서 프래그먼트 트리는 불변이며, 무효화는 더티 플래그를 쓰는 대신 이전 프래그먼트 트리와 새 프래그먼트 트리를 비교함으로써 이루어집니다. 다만 그 효과는 이 책이 설명하는 것과 꽤 비슷합니다.

## 인라인 요소의 너비

이 시점에서 `BlockLayout`에는 보호되는 `width` 필드가 있지만 다른 레이아웃 객체 타입에는 없습니다. 나중에 필요하니 그것을 고칩시다. `LineLayout`은 꽤 쉽습니다.

```python
class LineLayout:
    def __init__(self, node, parent, previous):
        # ...
        self.width = ProtectedField()
        # ...

    def layout(self):
        # ...
        self.width.copy(self.parent.width)
        # ...
```

`TextLayout`에서는 다시 `font`를 처리해야 합니다(따라서 `width`가 `style`에 의존하게 됩니다).

```python
class TextLayout:
    def __init__(self, node, word, parent, previous):
        # ...
        self.width = ProtectedField()
        # ...

    def layout(self):
        # ...
        style = self.width.read(self.node.style)
        zoom = self.width.read(self.zoom)
        self.font = font(style, zoom)
        self.width.set(self.font.measureText(self.word))
        # ...
```

`EmbedLayout`에서는 `width` 필드를 보호하기만 하면 됩니다.

```python
class EmbedLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.width = ProtectedField()
        # ...
```

`x` 위치를 계산하는 `layout` 메서드에도 `width` 참조가 있습니다. 지금은 여기에 그냥 `get`을 써도 됩니다.

마지막으로 여러 종류의 대체 콘텐츠가 있습니다. `InputLayout`에서 너비는 확대 수준에만 의존합니다.

```python
class InputLayout(EmbedLayout):
    def layout(self):
        # ...
        zoom = self.zoom.read(notify=self.width)
        self.width.set(dpx(INPUT_WIDTH_PX, zoom))
        # ...
```

`IframeLayout`과 `ImageLayout`은 아주 비슷한데, 너비가 확대 수준과 요소의 `width`, `height` 속성에 의존합니다. 그러니 그 속성들이 JavaScript에서 바뀌면 `width` 필드를 무효화해야 합니다.

```python
class JSContext:
    def setAttribute(self, handle, attr, value, window_id):
        # ...
        obj = elt.layout_object
        if isinstance(obj, IframeLayout) or \
           isinstance(obj, ImageLayout):
            if attr == "width" or attr == "height":
                obj.width.mark()
```

그 밖에는 `IframeLayout`과 `ImageLayout`도 `InputLayout`과 똑같이 처리됩니다. 코드를 검색해 항상 `get`과 `read` 같은 메서드를 통해서만 `width`와 상호작용하는지 확인하고, `contenteditable` 같은 사용자 상호작용 테스트를 포함해 브라우저가 동작하는지 점검하세요.

### 더 알아보기

여기서 정의한 `ProtectedField` 클래스는 [모나드](https://en.wikipedia.org/wiki/Monad_(functional_programming))의 한 종류입니다. 모나드는 [Haskell](https://www.haskell.org/) 같은 프로그래밍 언어에서 쓰이는 프로그래밍 패턴입니다. 간단히 말해 모나드는 계산의 단계들을 연결하는 방식을 기술하지만, 그 구체적인 내용은 [악명 높게 혼란스럽습니다](https://wiki.haskell.org/Monad_tutorials_timeline). 다행히 이 장에서는 모나드 일반을 생각할 필요 없이 `ProtectedField`만 생각하면 됩니다.

## 레이아웃 필드 무효화하기

이왕 하는 김에 `x`, `y`, `height`를 포함한 나머지 모든 레이아웃 필드도 보호합시다. 그것을 마치고 나면 불필요한 순회를 건너뛰어 레이아웃을 더욱 빠르게 만드는 이야기를 할 준비가 됩니다.

`width`와 마찬가지로 `DocumentLayout`과 `BlockLayout`부터 시작합시다. 먼저 `x`와 `y` 위치입니다. `DocumentLayout`에서는 그냥 `set`을 쓰면 됩니다.

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.x = ProtectedField()
        self.y = ProtectedField()
        # ...

    def layout(self, width, zoom):
        # ...
        self.x.set(dpx(HSTEP, zoom))
        self.y.set(dpx(VSTEP, zoom))
        # ...
```

`BlockLayout`의 `x` 위치는 그저 부모의 `x` 위치이므로 그냥 `copy`하면 됩니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.x = ProtectedField()
        # ...

    def layout(self):
        # ...
        self.x.copy(self.parent.x)
        # ...
```

다만 `y` 위치는 때때로 `previous` 형제를 참조합니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.y = ProtectedField()

    def layout(self):
        # ...
        if self.previous:
            prev_y = self.previous.y.read(notify=self.y)
            prev_height = self.previous.height.read(notify=self.y)
            self.y.set(prev_y + prev_height)
        else:
            self.y.copy(self.parent.y)
        # ...
```

`height`도 해 봅시다. `DocumentLayout`에서는 자식의 높이를 읽기만 하면 됩니다.

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.height = ProtectedField()
        # ...

    def layout(self, width, zoom):
        # ...
        self.height.copy(child.height)
```

`BlockLayout`도 비슷하되 여러 자식을 순회한다는 점만 다릅니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.height = ProtectedField()
        # ...

    def layout(self):
        # ...
        children = self.children.read(notify=self.height)
        new_height = sum([
            child.height.read(notify=self.height)
            for child in children
        ])
        self.height.set(new_height)
```

이 마지막 코드 블록에서 먼저 `children` 필드를 `read`한 다음, 자식 목록을 순회하며 각각의 `height` 필드를 `read`한다는 점에 주의하세요. 앞선 레이아웃 필드들과 달리 `height` 필드는 부모가 아니라 자식들의 필드에 의존합니다(그림 2 참조).

더티 플래그만이 증분 성능을 달성하는 유일한 방법은 아닙니다. 또 다른 선택지는 _델타_ 를 추적하는 것입니다. 예를 들어 [Adapton](http://adapton.org/) 프로젝트에서는 입력을 출력으로 변환하는 각 계산이 입력 델타를 출력 델타로 변환할 수도 있습니다. ## 인라인 레이아웃 보호하기

`LineLayout`, `TextLayout`, `EmbedLayout`의 필드들도 보호해야 하는데, 그것들의 `layout` 메서드는 조금 다르게 동작합니다. 물론 이 레이아웃 객체들도 각각 `x`, `y`, `height` 필드를 갖지만, 다른 레이아웃 객체들이 사용하는 `font`, `ascent`, `descent` 필드도 계산합니다. 이 모두를 보호해야 합니다. 이제 `ProtectedField` 경험이 꽤 쌓였으니 모든 필드를 한 번에 처리하겠습니다.

`TextLayout`부터 시작합시다.

```python
class TextLayout:
    def __init__(self, node, word, parent, previous):
        # ...
        self.x = ProtectedField()
        self.y = ProtectedField()
        self.height = ProtectedField()
        self.font = ProtectedField()
        self.ascent = ProtectedField()
        self.descent = ProtectedField()
        # ...
```

이 필드들을 `layout`에서 계산해야 합니다. 폰트 관련 필드들은 모두 꽤 간단합니다.

```python
class TextLayout:
    def layout(self):
        # ...

        zoom = self.zoom.read(notify=self.font)
        style = self.node.style.read(notify=self.font)
        self.font.set(font(style, zoom))

        f = self.font.read(notify=self.width)
        self.width.set(f.measureText(self.word))

        f = self.font.read(notify=self.ascent)
        self.ascent.set(f.getMetrics().fAscent * 1.25)

        f = self.font.read(notify=self.descent)
        self.descent.set(f.getMetrics().fDescent * 1.25)

        f = self.font.read(notify=self.height)
        self.height.set(linespace(f) * 1.25)
```

`width`가 `zoom`과 `style`을 직접 읽는 대신 `font` 필드를 읽도록 바꿨다는 점에 주의하세요. `f`를 반복해서 계산하는 것이 조금 이상해 _보이기는_ 하지만, 그 각각의 `read` 호출이 한 레이아웃 필드가 다른 필드에 대해 갖는 의존성을 설정한다는 점을 기억하세요. 저는 각 `f`가 그 필드의 계산에 국한된 것이라고 생각하기를 좋아합니다.

`TextLayout`의 _x_ 위치도 계산해야 합니다. 이는 이전 형제의 폰트, _x_ 위치, 너비를 쓸 수 있습니다.

```python
class TextLayout:
    def layout(self):
        # ...
        if self.previous:
            prev_x = self.previous.x.read(notify=self.x)
            prev_font = self.previous.font.read(notify=self.x)
            prev_width = self.previous.width.read(notify=self.x)
            self.x.set(
                prev_x + prev_font.measureText(' ') + prev_width)
        else:
            self.x.copy(self.parent.x)
```

`EmbedLayout`도 기본적으로 동일합니다. 그 하위 클래스로는 `InputLayout`이 다음과 같습니다.

```python
class InputLayout(EmbedLayout):
    def layout(self):
        super().layout()
        zoom = self.zoom.read(notify=self.width)
        self.width.set(dpx(INPUT_WIDTH_PX, zoom))

        font = self.font.read(notify=self.height)
        self.height.set(linespace(font))

        height = self.height.read(notify=self.ascent)
        self.ascent.set(-height)
        self.descent.set(0)
```

그리고 `ImageLayout`은 다음과 같습니다. 여기에는 `img_height` 필드가 있는데, 저는 이것을 `height`를 계산하는 중간 단계로 보고 보호하지 않겠습니다.

```python
class ImageLayout(EmbedLayout):
    def layout(self):
        # ...
        font = self.font.read(notify=self.height)
        self.height.set(max(self.img_height, linespace(font)))

        height = self.height.read(notify=self.ascent)
        self.ascent.set(-height)
        self.descent.set(0)
```

마지막으로 `IframeLayout`이 높이를 계산하는 방식은 다음과 같으며 간단합니다.

```python
class IframeLayout(EmbedLayout):
    def layout(self):
        # ...
        zoom = self.zoom.read(notify=self.height)
        if height_attr:
            self.height.set(dpx(int(height_attr) + 2, zoom))
        else:
            self.height.set(dpx(IFRAME_HEIGHT_PX + 2, zoom))
        # ...
```

`height` 속성이 바뀌면 `height` 필드도 무효화해야 합니다.

```python
class JSContext:
    def setAttribute(self, handle, attr, value, window_id):
        if isinstance(obj, IframeLayout) or \
           isinstance(obj, ImageLayout):
            if attr == "width" or attr == "height":
                # ...
                obj.height.mark()
```

이것으로 모든 인라인 레이아웃 객체를 다뤘습니다. 남은 것은 `LineLayout`뿐입니다. `x`와 `y`는 다음과 같습니다.

```python
class LineLayout:
    def __init__(self, node, parent, previous):
        # ...
        self.x = ProtectedField()
        self.y = ProtectedField()
        # ...

    def layout(self):
        # ...
        self.x.copy(self.parent.x)
        if self.previous:
            prev_y = self.previous.y.read(notify=self.y)
            prev_height = self.previous.height.read(notify=self.y)
            self.y.set(prev_y + prev_height)
        else:
            self.y.copy(self.parent.y)
        # ...
```

다만 `height`는 조금 복잡합니다. 모든 자식에 걸친 최대 어센트와 디센트를 계산하고 그것으로 `height`와 자식들의 `y`를 설정하기 때문입니다. 이 코드를 다루는 가장 단순한 방법은 `LineLayout`에 최대 어센트와 디센트를 저장할 `ascent`와 `descent` 필드를 추가하고, `height`와 자식들의 `y` 필드가 그것들에 의존하게 하는 것이라고 생각합니다.

보호되는 필드를 선언하는 것부터 시작해 그렇게 해 봅시다.

```python
class LineLayout:
    def __init__(self, node, parent, previous):
        # ...
        self.ascent = ProtectedField()
        self.descent = ProtectedField()
```

그다음 `layout`에서 먼저 자식이 없는 경우를 처리하겠습니다.

```python
class LineLayout:
    def layout(self):
        # ...
        if not self.children:
            self.height.set(0)
            return
```

`children` 필드를 `read`할 필요가 없다는 점에 주의하세요. `LineLayout`에서 그 필드는 보호되지 않습니다. `LineLayout`이 만들어질 때 `BlockLayout`이 채워 넣고 그 뒤로는 절대 수정되지 않기 때문입니다.

다음으로 최대 어센트와 디센트를 계산합시다.

```python
class LineLayout:
    def layout(self):
        # ...
        self.ascent.set(max([
            -child.ascent.read(notify=self.ascent)
            for child in self.children
        ]))

        self.descent.set(max([
            child.descent.read(notify=self.descent)
            for child in self.children
        ]))
```

다음으로 각 자식의 `y` 위치를 다시 계산할 수 있습니다.

```python
class LineLayout:
    def layout(self):
        # ...
        for child in self.children:
            new_y = self.y.read(notify=child.y)
            new_y += self.ascent.read(notify=child.y)
            new_y += child.ascent.read(notify=child.y)
            child.y.set(new_y)
```

마지막으로 줄의 높이를 다시 계산합니다.

```python
class LineLayout:
    def layout(self):
        # ...
        max_ascent = self.ascent.read(notify=self.height)
        max_descent = self.descent.read(notify=self.height)
        self.height.set(max_ascent + max_descent)
```

이 변경들의 결과로 이제 모든 레이아웃 객체 필드가 보호됩니다. 전과 마찬가지로 이 필드들의 모든 사용처가 `read`와 `get`을 쓰는지, `contenteditable` 중에도 브라우저가 여전히 실행되는지 확인하세요. 스크롤 오프셋을 제한하는 것처럼 `Frame`과 `Tab` 안에서 `height`와 `y`를 쓰는 몇몇 곳도 이제 고쳐야 할 것입니다.

## 변화 없는 갱신 건너뛰기

이제 레이아웃 필드가 꽤 많아졌으니, 실제로 얼마나 많은 무효화가 일어나고 있는지 봅시다. 어떤 필드가 다시 계산되는지 보기 위해 `ProtectedField`의 `set` 메서드 안에 `print` 문을 추가하세요.

```python
class ProtectedField:
    def set(self, value):
        if self.value != None:
            print("Change", self)
        self.notify()
        self.value = value
        self.dirty = False
```

`if` 검사는 최초 페이지 레이아웃 중에는 출력하지 않게 하므로, 우리 무효화 최적화가 얼마나 잘 동작하는지만 보여 줍니다. 출력이 적을수록 바뀌는 필드가 적고 더 많은 작업을 건너뛸 수 있다는 뜻입니다.

(이 장 같은) 큰 웹 페이지에서 `contenteditable`로 텍스트를 편집해 보세요. _화면 가득_ 출력이, 수천 줄의 알아보기 힘든 내용이 쏟아질 것입니다. 왜 그런지 이해하기가 조금 어려우니, `ProtectedField`에 보기 좋은 출력 형태와 디버깅용 새 `name` 매개변수를 추가합시다.[^19]

```python
class ProtectedField:
    def __init__(self, obj, name):
        self.obj = obj
        self.name = name
        # ...

    def __repr__(self):
        return "ProtectedField({}, {})".format(
            self.obj.node if hasattr(self.obj, "node") else self.obj,
            self.name)
```

모든 `ProtectedField`에 다음과 같이 이름을 붙이세요.

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.zoom = ProtectedField(self, "zoom")
        self.width = ProtectedField(self, "width")
        self.height = ProtectedField(self, "height")
        self.x = ProtectedField(self, "x")
        self.y = ProtectedField(self, "y")
```

출력을 다시 보면 이제 두 단계가 보일 것입니다. 먼저 `style` 재계산이 많습니다.

Change ProtectedField('Twitter', style)

...
```

Change ProtectedField(<body>, zoom)
Change ProtectedField(<body>, y)
Change ProtectedField(<header>, zoom)
Change ProtectedField(<header>, y)
...
```

이것들을 고쳐 봅시다. 먼저 `style`을 다뤄 보죠. `style`이 반복해서 다시 계산되는 이유는 그저 더럽지 않아도 다시 계산하기 때문입니다. 더럽지 않으면 건너뜁시다.

```python
def style(node, rules, frame):
    if node.style.dirty:
        # ...

    for child in node.children:
        style(child, rules, frame)
```

이제 style 재계산이 거의 없을 것입니다. 그런데 저 레이아웃 필드 재계산들은 어떨까요? 왜 일어나는 걸까요? 여기서 가장 먼저 다시 계산되는 필드는 `zoom`이고, 그것은 다시 `DocumentLayout`으로 거슬러 올라갑니다.

```python
class DocumentLayout:
    def layout(self, width, zoom):
        self.zoom.set(zoom)
        # ...
```

페이지를 배치할 때마다 zoom 매개변수를 `set`하는데, 사용자가 확대하거나 축소했을 수 있으므로 그렇게 해야 합니다. 하지만 필드를 `set`할 때마다 그것에 의존하는 모든 필드에 통지합니다. 이 두 가지가 합쳐져 우리는 매 프레임마다 `zoom` 필드와 `zoom`에 의존하는 모든 것을 다시 계산하고 있습니다.

이 모든 것을 낭비로 만드는 것은 `zoom`이 보통 바뀌지 않는다는 점입니다. 그러니 값이 바뀌지 않았다면 의존 필드에 통지하지 말아야 합니다.

```python
class ProtectedField:
    def set(self, value):
        if value != self.value:
            self.notify()
        # ...
```

이 변경은 안전합니다. 새 값이 옛 값과 같다면 하류의 계산들이 실제로 바뀔 필요가 없기 때문입니다. 이 작은 조정으로 필드 변경 횟수가 최소로 줄어들 것입니다.

```
Change ProtectedField(<html lang="en-US" xml:lang="en-US">, zoom)
Change ProtectedField(<div class="demo" ...>, children)
Change ProtectedField(<div class="demo" ...>, height)
```

여기서 일어나는 일은 (새 텍스트를 반영하기 위해 반드시 해야 하는) `contenteditable` 요소의 `children` 재생성과, (줄이 더 늘어났을 경우를 대비해 필요한) 그 `height`가 바뀌지 않았는지 확인하는 것뿐입니다.

편집도 이제 더 빠릿하게 느껴질 것입니다. 원래 1.7초 대신 약 0.6초입니다(그림 3 참조). 나아졌지만 여전히 좋지는 않습니다.[^20]

브라우저 레이아웃에서 우리가 하고 있는 캐싱과 무효화는 컴퓨터 과학 전반에 비슷한 것들이 있습니다. 예를 들어 어떤 데이터베이스는 [증분 뷰 유지(incremental view maintenance)](https://wiki.postgresql.org/wiki/Incremental_View_Maintenance)를 사용해 데이터베이스 항목이 추가되거나 수정될 때 흔한 질의의 결과를 캐시하고 갱신합니다. [Make](https://en.wikipedia.org/wiki/Make_(software)) 같은 빌드 시스템도 바뀐 객체만 다시 컴파일하려 하고, [스프레드시트](https://lord.io/spreadsheets/)도 바뀌었을 수 있는 수식만 다시 계산하려 합니다. 브라우저가 요구하는 구체적인 절충은 특이할 수 있지만, 문제와 핵심 알고리즘은 보편적입니다.

## 순회 건너뛰기

이제 모든 레이아웃 필드가 보호되므로, 더티 플래그를 확인해 다시 계산이 필요한지 알 수 있습니다. 하지만 그 모든 더티 플래그를 확인하려면 모든 레이아웃 객체를 _방문_ 해야 하는데, 그것은 오래 걸릴 수 있습니다. 대신 더티 플래그를 사용해 방문해야 할 레이아웃 객체 수를 최소화해야 합니다.

기본 아이디어는 이런 질문을 중심으로 합니다. 주어진 노드에 대해 `layout`을 호출할 필요가 있기는 할까요? `layout` 메서드는 세 가지 일을 합니다. 자식 레이아웃 객체를 만들고, 레이아웃 속성을 계산하고, `layout`을 더 호출하며 재귀합니다. 이 단계들은 다음의 경우 건너뛸 수 있습니다.

- 자식 레이아웃 객체를 만들 필요가 없을 때, 즉 `children` 필드가 더럽지 않을 때

- 레이아웃 필드가 더럽지 않아서 다시 계산할 필요가 없을 때

- `layout`을 재귀 호출할 필요가 없을 때

마지막 조건에 대한 더티 플래그는 아직 없으니 추가합시다. 어떤 자손이든 더러운 `ProtectedField`를 갖고 있는지 추적하므로 `has_dirty_descendants`라고 부르겠습니다.[^21]

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.has_dirty_descendants = False
```

다른 모든 종류의 레이아웃 객체에도 이것을 추가하세요.

이제 어떤 더티 플래그든 설정되면 `has_dirty_descendants` 플래그를 설정해야 합니다. `ProtectedField`에 추가적인 (그리고 선택적인[^22]) `parent` 매개변수를 두어 그렇게 할 수 있습니다.

```python
class ProtectedField:
    def __init__(self, obj, name, parent=None):
        # ...
        self.parent = parent
```

각 레이아웃 객체 타입의 모든 `ProtectedField`에 이 매개변수를 반드시 넘기세요. 예를 들어 `BlockLayout`은 다음과 같습니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...    
        self.children = ProtectedField(self, "children", self.parent)
        self.zoom = ProtectedField(self, "zoom", self.parent)
        self.width = ProtectedField(self, "width", self.parent)
        self.height = ProtectedField(self, "height", self.parent)
        self.x = ProtectedField(self, "x", self.parent)
        self.y = ProtectedField(self, "y", self.parent)
```

그다음 `mark`나 `notify`가 호출될 때마다 `parent` 사슬을 따라 올라가며 자손 플래그를 설정합니다.

```python
class ProtectedField:
    def set_ancestor_dirty_flags(self):
        parent = self.parent
        while parent and not parent.has_dirty_descendants:
            parent.has_dirty_descendants = True
            parent = parent.parent

    def mark(self):
        # ...
        self.set_ancestor_dirty_flags()
```

자손 플래그가 이미 설정되어 있으면 `while` 루프가 일찍 빠져나간다는 점에 주의하세요. _그_ 플래그를 설정한 쪽이 이미 모든 조상의 자손 더티 플래그를 설정했기 때문입니다.[^23]

`layout` 뒤에는 자손 플래그를 지워야 합니다.

```python
class BlockLayout:
    def layout(self):
        # ...
        for child in self.children.get():
            child.layout()

        self.has_dirty_descendants = False    
```

이제 자손 더티 플래그가 생겼으니, 그것을 사용해 재귀 호출을 포함해 `layout`을 건너뜁시다.

```python
class BlockLayout:
    def layout(self):
        if not self.layout_needed(): return
        # ...
```

여기서 `layout_needed` 메서드는 모든 더티 플래그를 확인하기만 합니다.

```python
class BlockLayout:
    def layout_needed(self):
        if self.zoom.dirty: return True
        if self.width.dirty: return True
        if self.height.dirty: return True
        if self.x.dirty: return True
        if self.y.dirty: return True
        if self.children.dirty: return True
        if self.has_dirty_descendants: return True
        return False
```

다른 모든 종류의 레이아웃 객체에도 똑같이 하세요. `DocumentLayout`에서는 조금 조심해야 합니다. 프레임 너비와 확대 수준을 인자로 받으므로, 해당 `Frame` 변수가 바뀌면 `DocumentLayout`의 그 필드들을 `mark`해야 합니다.[^24]

```python
class IframeLayout(EmbedLayout):
    def layout(self):
        if self.node.frame and self.node.frame.loaded:
            # ...
            self.node.frame.document.width.mark()
```

확대 수준은 `Tab`에서 바뀝니다.

```python
class Tab:
    def zoom_by(self, increment):
        # ...
        for id, frame in self.window_id_to_frame.items():
            frame.document.zoom.mark()

    def reset_zoom(self):
        # ...
        for id, frame in self.window_id_to_frame.items():
            frame.document.zoom.mark()
```

불필요한 `layout` 메서드를 건너뛰면 눈에 띄는 속도 향상이 있어야 합니다. 이제 작은 레이아웃은 갱신에 약 7ms가 걸리고 편집이 훨씬 매끄러워집니다.[^25][^26]

### 더 알아보기

`ProtectedField`는 [관찰자 패턴(observer pattern)](https://en.wikipedia.org/wiki/Observer_pattern)과 비슷합니다. 관찰자 패턴에서는 어떤 상태가 바뀔 때 한 코드 조각이 콜백을 실행합니다. 이 패턴은 [UI 프레임워크에서 흔합니다](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/KeyValueObserving/KeyValueObserving.html). 보통 이런 관찰자들은 의존 결과를 _즉시_ 다시 계산하지만, 우리 콜백인 `mark`와 `notify`는 그저 나중에 정리할 더티 플래그를 설정할 뿐입니다. 즉 우리 무효화 알고리즘은 일종의 [_지연_ 관찰자](https://en.wikipedia.org/wiki/Lazy_evaluation)입니다. 지연은 갱신을 묶어 처리함으로써 성능에 도움이 됩니다.

## 세밀한 스타일 무효화

안타깝게도 무효화를 추가하는 과정에서 우리는 뜻하지 않게 매끄러운 애니메이션을 망가뜨렸습니다. 기본 문제는 이렇습니다. 예를 들어 JavaScript를 통해 요소의 `opacity`나 `transform` 속성이 바뀐다고 합시다. 그 속성은 레이아웃 유발이 아니므로 전적으로 합성으로 애니메이션되어야 _합니다_. 하지만 어떤 스타일 속성이든 바뀌면 `Element`의 `style` 필드가 무효화되고, 그것이 다시 `children` 필드를 무효화해 레이아웃 트리가 다시 만들어집니다. 좋지 않죠.

궁극적으로 여기서 핵심 문제는 너무 성긴 `ProtectedField` 때문에 생기는 _과잉_ 무효화입니다. 예를 들어 `children` 필드는 `style` 딕셔너리 전체가 아니라 그중 몇몇 폰트 관련 필드에만 의존합니다. `style`이 딕셔너리의 `ProtectedField`가 아니라 `ProtectedField`의 딕셔너리여야 합니다.

```python
class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.style = dict([
            (property, ProtectedField(self, property))
            for property in CSS_PROPERTIES
        ])
        # ...
```

`Text`에도 같은 변경을 하세요. `CSS_PROPERTIES` 딕셔너리는 우리가 지원하는 각 CSS 속성과 그 기본값을 담습니다.

```python
CSS_PROPERTIES = {
    "font-size": "inherit", "font-weight": "inherit",
    "font-style": "inherit", "color": "inherit",
    "opacity": "1.0", "transition": "",
    "transform": "none", "mix-blend-mode": None,
    "border-radius": "0px", "overflow": "visible",
    "outline": "none", "background-color": "transparent",
    "image-rendering": "auto",
}
```

JavaScript에서 `style` 속성을 설정할 때는 새 `dirty_style` 함수를 호출해 모든 필드를 무효화하겠습니다.

```python
def dirty_style(node):
    for property, value in node.style.items():
        value.mark()

class JSContext:
    def style_set(self, handle, s, window_id):
        # ...
        dirty_style(elt)
        # ...
```

하지만 그것이 전부는 아닙니다. `:focus` 같은 의사 클래스에 영향을 줄 수 있는 다른 코드도 style을 무효화합니다.

```python
class Frame:
    def focus_element(self, node):
        # ...
        if self.tab.focus:
            # ...
            dirty_style(self.tab.focus)
        if node:
             #...
            dirty_style(node)
```

마찬가지로 `style`에서는 노드의 스타일 속성 중 _하나라도_ 더러우면 그 노드의 스타일을 다시 계산해야 합니다.

```python
def style(node, rules, frame):
    needs_style = any([field.dirty for field in node.style.values()])
    if needs_style:
        # ...
    for child in node.children:
        style(child, rules, frame)
```

기존 코드에 맞추기 위해 `old_style`과 `new_style`은 그냥 속성을 값에 대응시키게 하겠습니다.

```python
def style(node, rules, frame):
    if needs_style:
        old_style = dict([
            (property, field.value)
            for property, field in node.style.items()
        ])
        new_style = CSS_PROPERTIES.copy()
        # ...
```

그다음 상속을 해석할 때, 우리 스타일의 한 필드가 부모 스타일의 한 필드에 구체적으로 의존하게 합니다.

```python
def style(node, rules, frame):
    if needs_style:
        for property, default_value in INHERITED_PROPERTIES.items():
            if node.parent:
                parent_field = node.parent.style[property]
                parent_value = \
                    parent_field.read(notify=node.style[property])
                new_style[property] = parent_value
```

백분율 폰트 크기를 해석할 때도 마찬가지입니다.

```python
def style(node, rules, frame):
    if needs_style:
        if new_style["font-size"].endswith("%"):
            if node.parent:
                parent_field = node.parent.style["font-size"]
                parent_font_size = \
                    parent_field.read(notify=node.style["font-size"])
```

그다음 `new_style`이 모두 계산되고 나면 노드 `style`의 모든 필드를 개별적으로 설정합니다.

```python
def style(node, rules, frame):
    if needs_style:
        # ...
        for property, field in node.style.items():
            field.set(new_style[property])
```

이제 브라우저의 나머지 부분이 세밀한 style 필드를 쓰도록 갱신하기만 하면 됩니다. 대부분 `style.get()[property]`를 `style[property].get()`으로 바꾸는 일입니다.

```python
def paint_visual_effects(node, cmds, rect):
    opacity = float(node.style["opacity"].get())
    blend_mode = node.style["mix-blend-mode"].get()
    translation = parse_transform(node.style["transform"].get())

    if node.style["overflow"].get() == "clip":
        border_radius = float(node.style["border-radius"].get()[:-2])
        # ...
    
    # ...
```

다만 `font` 메서드는 손을 조금 봐야 합니다. 지금까지 우리는 노드의 `style`을 읽어 `font`에 넘겼습니다.

```
class BlockLayout:
    def word(self, node, word):
        zoom = self.children.read(self.zoom)
        style = self.children.read(node.style)
        node_font = font(style, zoom)
        # ...
```

이제 style의 서로 다른 세 속성을 읽어야 하므로 그 방식은 통하지 않습니다. 간결하게 유지하기 위해 무효화할 필드를 인자로 넘기도록 `font`를 다시 쓰겠습니다.

```python
def font(css_style, zoom, notify):
    weight = css_style['font-weight'].read(notify)
    style = css_style['font-style'].read(notify)
    try:
        size = float(css_style['font-size'].read(notify)[:-2]) * 0.75
    except:
        size = 16
    font_size = dpx(size, zoom)
    return get_font(font_size, weight, style)
```

이제 줄바꿈 중에 폰트를 요청할 때 `notify` 매개변수로 그냥 `self.children`을 넘기면 됩니다.

```python
class BlockLayout:
    def word(self, node, word):
        zoom = self.zoom.read(notify=self.children)
        node_font = font(node.style, zoom, notify=self.children)
        # ...
```

마찬가지로 우리가 계산하는 것이 `font` 필드라면 그것을 넘깁니다.

```python
class TextLayout:
    def layout(self):
        if self.font.dirty:
            zoom = self.zoom.read(notify=self.font)
            self.font.set(font(
                self.node.style, zoom, notify=self.font))
```

`font` 메서드의 다른 모든 사용처도 이 새 인터페이스로 반드시 갱신하세요. 이 "목적지 전달 방식(destination-passing style)"은 헬퍼 메서드에 무효화를 추가하는 흔한 방법입니다.

마지막으로, 이제 `style`에 세밀한 무효화를 추가했으니 애니메이션을 처리할 때 애니메이션되는 속성만 무효화할 수 있습니다.

```python
class Tab:
    def run_animation_frame(self, scroll):
        for (window_id, frame) in self.window_id_to_frame.items():
            for node in tree_to_list(frame.nodes, []):
                for (property_name, animation) in \
                    node.animations.items():
                    value = animation.animate()
                    if value:
                        node.style[property_name].set(value)
                        # ...
```

`opacity`나 `transform` 같은 속성이 바뀌면 (이 속성들은 어떤 레이아웃 필드에도 영향을 주지 않으므로) 어떤 레이아웃 필드도 무효화되지 않고, 따라서 애니메이션은 다시 레이아웃을 완전히 건너뛰게 됩니다.

### 더 알아보기

CSS 스타일은 선택자가 어떤 요소에 매치되는지에 의존하며, 페이지가 바뀌면 그것도 무효화되어야 할 수 있습니다.[^27] 브라우저는 페이지의 모든 선택자에 대해 선택자 매칭을 다시 하지 않도록 영리한 알고리즘을 갖고 있습니다. 예를 들어 Chromium은 각 선택자에 대해 [_무효화 집합(invalidation set)_](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/core/css/style-invalidation.md?pli=1#)을 구성하는데, 이는 어떤 선택자–요소 매치를 다시 확인해야 하는지 알려 줍니다. `:has()` 같은 새 선택자는 [더 복잡한](https://blogs.igalia.com/blee/posts/2023/05/31/how-blink-invalidates-styles-when-has-in-use.html) 무효화 전략을 요구하지만, 이 복잡함은 빠른 재스타일링에 필수적입니다.

## 의존성 분석하기

`ProtectedField` 추상화 덕분에 레이아웃은 이제 꽤 빠르고 올바릅니다. 하지만 대부분의 의존성이 `read`를 통해 암묵적으로 설정되기 때문에, 주어진 연산에서 궁극적으로 어떤 필드가 무효화될지 알기 어렵습니다. 그래서 어떤 연산이 빠르고 어떤 연산이 느린지 이해하기 어려운데, 새 스타일과 레이아웃 기능을 추가할수록 더욱 그렇습니다. 이 _감사 가능성(auditability)_ 문제는 실제 브라우저에서도 일어납니다. 결국 실제 브라우저는 수천 줄이 아니라 수백만 줄에 이르고 수천 개의 CSS 속성을 지원합니다. 그 의존성 그래프는 우리 브라우저의 것보다 극적으로 복잡합니다.

그러므로 의존성 그래프를 더 쉽게 볼 수 있으면 좋겠습니다. 다만 그 일의 규모에 대한 감을 잡으려면 그림 5를 보세요. 그 과정에서 그 그래프의 모양에 대한 _불변식(invariant)_ 을 한곳에 모을 수도 있습니다. 그러면 앞으로 우발적인 버그에 대해 브라우저가 [단단해지고](https://en.wikipedia.org/wiki/Hardening_(computing)) 성능도 개선됩니다.

![그림 5: 우리 브라우저의 레이아웃 필드에 대한 의존성 다이어그램. 단순화했는데도 이미 꽤 복잡합니다.](protected-field-dependencies-bottom-2.gif)

*그림 5: 우리 브라우저의 레이아웃 필드에 대한 의존성 다이어그램. 단순화했는데도 이미 꽤 복잡합니다.*

쉬운 첫걸음은 각 `ProtectedField`의 의존성을 명시적으로 나열하는 것입니다. 이를 선택적 생성자 매개변수로 만들 수 있습니다.

```python
class ProtectedField:
    def __init__(self, obj, name, parent=None, dependencies=None):
        # ...
        if dependencies != None:
            for dependency in dependencies:
                dependency.invalidations.add(self)
```

게다가 의존성이 생성자로 넘어오면 `ProtectedField`를 "얼릴(freeze)" 수 있어서, `read`가 더 이상 새 의존성을 추가하지 않고 그것들이 선언되었는지 확인만 하게 됩니다.

```python
class ProtectedField:
    def __init__(self, obj, name, parent=None, dependencies=None):
        # ...
        self.frozen_dependencies = (dependencies != None)
        if dependencies != None:
            for dependency in dependencies:
                dependency.invalidations.add(self)

    def read(self, notify):
        if notify.frozen_dependencies:
            assert notify in self.invalidations
        else:
            self.invalidations.add(notify)

        return self.get()
```

예를 들어 `DocumentLayout`에서는 이제 그 필드들에 외부 의존성이 없으며 따라서 명시적으로 `mark`되어야 한다는 사실을 분명히 할 수 있습니다.[^28]

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.zoom = ProtectedField(self, "zoom", None, [])
        self.width = ProtectedField(self, "width", None, [])
        self.x = ProtectedField(self, "x", None, [])
        self.y = ProtectedField(self, "y", None, [])
        self.height = ProtectedField(self, "height")
```

다만 `height`에는 의존성 매개변수가 빠져 있다는 점에 주의하세요. `DocumentLayout`의 높이는 자식의 높이에 의존하는데, 그 자식은 `layout`이 호출될 때까지 존재하지 않습니다. 이런 "하향" 의존성 때문에 모든 `ProtectedField`를 생성 시점에 얼릴 수는 없습니다. 하지만 얼리는 보호 필드가 많아질수록 의존성 그래프를 감사하기 쉬워집니다.

`BlockLayout`의 `zoom`, `width`, `x`, `y` 필드도 얼릴 수 있습니다. `y`의 경우 레이아웃 객체에 이전 형제가 있는지에 따라 의존성이 달라집니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        if self.previous:
            y_dependencies = [self.previous.y, self.previous.height]
        else:
            y_dependencies = [self.parent.y]
        self.y = ProtectedField(
            self, "y", self.parent, y_dependencies)
        # ...
```

`DocumentLayout`과 같은 이유로 `BlockLayout`의 `height`는 생성자에서 얼릴 수 없습니다. 하지만 `children` 필드가 계산되자마자 얼릴 수는 _있습니다_. 그것을 하는 `set_dependencies` 메서드를 추가합시다.[^29]

```python
class ProtectedField:
    def set_dependencies(self, dependencies):
        for dependency in dependencies:
            dependency.invalidations.add(self)
        self.frozen_dependencies = True
```

이제 `DocumentLayout`에서 `height`를 얼릴 수 있습니다.

```python
class DocumentLayout:
    def layout(self, width, zoom):
        if not self.children:
            child = BlockLayout(self.node, self, None, self.frame)
            self.height.set_dependencies([child.height])
```

`BlockLayout`에서도 비슷합니다.

```python
class BlockLayout:
    def layout(self):
        # ...
        if mode == "block":
            if self.children.dirty:
                # ...
                self.children.set(children)

                height_dependencies = \
                   [child.height for child in children]
                height_dependencies.append(self.children)
                self.height.set_dependencies(height_dependencies)
        else:
            if self.children.dirty:
                # ...
                self.children.set(self.temp_children)

                height_dependencies = \
                   [child.height for child in self.temp_children]
                height_dependencies.append(self.children)
                self.height.set_dependencies(height_dependencies)
```

다른 레이아웃 객체들도 자기 필드를 얼릴 수 있습니다. `TextLayout`, `EmbedLayout`과 그 하위 클래스에서는 모든 것을 얼릴 수 있습니다.

```python
class TextLayout:
    def __init__(self, node, word, parent, previous):
        # ...
        self.zoom = ProtectedField(self, "zoom", self.parent,
            [self.parent.zoom])
        self.font = ProtectedField(self, "font", self.parent,
            [self.zoom,
             self.node.style['font-weight'],
             self.node.style['font-style'],
             self.node.style['font-size']])
        self.width = ProtectedField(self, "width", self.parent,
            [self.font])
        self.height = ProtectedField(self, "height", self.parent,
            [self.font])
        self.ascent = ProtectedField(self, "ascent", self.parent,
            [self.font])
        self.descent = ProtectedField(self, "descent", self.parent,
            [self.font])
        if self.previous:
            x_dependencies = [self.previous.x, self.previous.font,
            self.previous.width]
        else:
            x_dependencies = [self.parent.x]
        self.x = ProtectedField(self, "x", self.parent,
            x_dependencies)
        self.y = ProtectedField(self, "y", self.parent,
            [self.ascent, self.parent.y, self.parent.ascent])
```

`LineLayout`에서는 줄이 만들어지고 배치되는 다소 복잡한 방식 때문에, `ascent`와 `descent`를 얼리는 것을 `layout`이 처음 호출될 때까지 미뤄야 합니다.

```python
class LineLayout:
    def __init__(self, node, parent, previous):
        # ...
        self.initialized_fields = False
        self.ascent = ProtectedField(self, "ascent", self.parent)
        self.descent = ProtectedField(self, "descent", self.parent)
        # ...

    def layout(self):
        if not self.initialized_fields:
            self.ascent.set_dependencies(
               [child.ascent for child in self.children])
            self.descent.set_dependencies(
               [child.descent for child in self.children])
            self.initialized_fields = True
        # ...
```

마지막 레이아웃 클래스는 `EmbedLayout`입니다. 여기서 의존성은 두 가지만 빼면 간단합니다. 첫째, `TextLayout`과 마찬가지로 `x`는 이전 것이 있다면 그 `x`에 의존합니다. 둘째, 종횡비 때문에 `height`가 `width`에 의존합니다.

```python
class EmbedLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.zoom = ProtectedField(self, "zoom", self.parent,
            [self.parent.zoom])
        self.font = ProtectedField(self, "font", self.parent,
           [self.zoom,
            self.node.style['font-weight'],
            self.node.style['font-style'],
            self.node.style['font-size']])
        self.width = ProtectedField(self, "width", self.parent,
            [self.zoom])
        self.height = ProtectedField(self, "height", self.parent,
            [self.zoom, self.font, self.width])
        self.ascent = ProtectedField(self, "ascent", self.parent,
            [self.height])
        self.descent = ProtectedField(
            self, "descent", self.parent, [])
        if self.previous:
            x_dependencies = \
                [self.previous.x, self.previous.font,
                 self.previous.width]
        else:
            x_dependencies = [self.parent.x]
        self.x = ProtectedField(
            self, "x", self.parent, x_dependencies)
        self.y = ProtectedField(self, "y", self.parent,
            [self.ascent,self.parent.y, self.parent.ascent])
```

심지어 모든 style 필드도 얼릴 수 있습니다! 유일한 복잡한 점은 `innerHTML`이 요소의 부모를 바꾼다는 것이므로, style 딕셔너리를 동적으로 만듭시다. 생성자에서는 `None`으로 초기화합니다.

```python
class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.style = None

class Text:
    def __init__(self, text, parent):
        # ...
        self.style = None
```

그다음 `style`이 처음 호출될 때 설정합니다.

```python
def style(node, rules, frame):
    if not node.style:
        init_style(node)
```

`init_style` 안에서 각 style 필드의 의존성을 얼려야 합니다. 쉽습니다. 상속되는 필드만 의존성을 갖습니다.

```python
def init_style(node):
    node.style = dict([
            (property, ProtectedField(node, property, None,
                [node.parent.style[property]] \
                    if node.parent and \
                        property in INHERITED_PROPERTIES \
                    else []))
            for property in CSS_PROPERTIES
        ])
```

`children`을 제외한 모든 레이아웃 필드와 style 필드를 얼림으로써, 레이아웃 객체 타입의 생성자만 봐도 우리 브라우저의 의존성 그래프를 잘 파악할 수 있게 되었습니다. 좋은 일이며, 스타일과 레이아웃 기능을 더 추가할 때 순환과 긴 의존성 사슬을 피하는 데 도움이 됩니다.

그런데 실제 브라우저에 필요할 법한 최대 성능을 얻으려면 이점이 하나 더 있습니다. 이 근사한 `ProtectedField`들은 오버헤드를 많이 더하는데, 주로 메모리를 더 차지하고 함수 호출을 더 요구하기 때문입니다. 실제로 이 장은 아마 여러분의 브라우저를 _최초_ 페이지 로드에서 꽤 느리게 만들었을 것입니다.[^30] 그중 일부는 `assert`를 건너뛰어 개선할 수 있지만,[^31] 이상적인 상태는 분명 아닙니다.

다행히 컴파일 타임 코드 생성과 매크로 같은 기법을 사용하면 `ProtectedField` 객체를 뒤에서 직선적인 코드로 바꿀 수 있습니다. 특정 `ProtectedField`를 설정하면 정적으로 알려진 무효화 대상들의 더티 플래그를 설정할 수 있고, 더티 플래그를 레이아웃 객체 안에 인라인할 수 있으며, `read` 함수는 의존성이 선언되었는지 컴파일 타임에 확인할 수 있습니다.[^32] 그런 기법은 이 책의 범위를 넘어서지만, 그것을 탐구하는 것은 고급 연습문제로 남겨 두었습니다.

### 더 알아보기

실제 브라우저도 이 장의 `ProtectedField` 추상화처럼 버그를 잡기 위해 단언을 사용합니다. 다만 사용자에게 브라우저가 느려지지 않도록, 필수적이지 않은 단언은 최종 사용자가 실행하는 _릴리스 빌드_ 에서는 "컴파일되어 빠집니다". _디버그 빌드_ 는 브라우저 엔지니어가 디버깅하거나 새 기능을 개발할 때, 그리고 자동화 테스트에서 사용하는 것입니다. 디버그 빌드에는 [새니타이저](https://firefox-source-docs.mozilla.org/tools/sanitizer/index.html) 같은 디버깅 기능도 함께 컴파일되고, 릴리스 빌드는 대신 [_프로파일 기반 최적화_](https://blog.chromium.org/2020/08/chrome-just-got-faster-with-profile.html) 같은 무거운 최적화를 사용합니다.

- 좋은 브라우저는 증분 성능의 원칙을 지향합니다. 변경의 비용은 페이지 전체의 크기가 아니라 변경의 크기에 비례해야 합니다.

- 캐시 무효화는 어렵고 오류가 생기기 쉬우므로, `ProtectedField` 같은 신중한 추상화가 정당화됩니다.

- 무효화는 할당, 계산, 심지어 객체 순회까지 건너뛰는 데 쓸 수 있습니다.

## 연습문제

**16-1 _요소 비우기_.** 인자 없이 호출될 때의 [`replaceChildren` DOM 메서드](https://developer.mozilla.org/en-US/docs/Web/API/Element/replaceChildren)를 구현하세요. 이 메서드는 주어진 요소의 모든 자식을 삭제해야 합니다. 무효화를 제대로 처리하도록 하세요.

**16-2 _레이아웃 단계 보호하기_.** `Frame`의 `document` 필드를 `ProtectedField`로 만들어 `needs_style`과 `needs_layout` 더티 플래그를 대체하세요. 애니메이션이 여전히 올바르게 동작하는지 확인하세요. `opacity`나 `transform`의 애니메이션은 레이아웃을 유발해서는 안 되고, 다른 속성의 애니메이션은 유발해야 합니다.

**16-3 _자식 옮기기_.** 여러 인자와 함께 호출될 때의 [`replaceChildren` DOM 메서드](https://developer.mozilla.org/en-US/docs/Web/API/Element/replaceChildren)를 구현하세요. 여기서 인자들은 문서의 다른 곳에 있는 요소들이며,[^33] 현재 부모에서 제거된 뒤 이 요소에 붙습니다. 무효화를 제대로 처리하도록 하세요.

**16-4 _style을 위한 자손 플래그_.** `style` 정보에 대한 자손 더티 플래그를 추가해서, `style` 단계가 스타일이 바뀌지 않은 노드는 순회하지 않아도 되게 하세요.

**16-5 _브라우저 크기 조절_.** 어쩌면 연습문제 2-3에서 브라우저 크기 조절 지원을 구현했을 수도 있습니다. (그리고 SDL로 전환하면서 그 지원을 버렸을 가능성이 큽니다.) 브라우저 크기 조절 지원을 다시 구현하세요. `SDL_CreateWindow`에 `SDL_WINDOW_RESIZABLE` 플래그를 넘기고 `SDL_WINDOWEVENT_RESIZED` 이벤트를 들어야 합니다. 무효화가 동작하는지 확인하세요. 창 크기를 조절하면 페이지 크기도 조절되어야 합니다. 무효화가 크기 조절을 빠르게 만드는 데 얼마나 도움이 되나요? 세로와 가로 크기 조절 모두 테스트해 보세요.

**16-6 _자식 매칭하기_.** 연습문제 9-2에서 아직 하지 않았다면 [`appendChild` 메서드](https://developer.mozilla.org/en-US/docs/Web/API/Node/appendChild) 지원을 추가하세요. `appendChild`의 흥미로운 점은, 레이아웃 객체의 `children` 필드를 바꾸기는 _하지만_ 오직 끝에 새 자식을 추가하는 방식으로만 바꾼다는 것입니다. 이 경우 기존 레이아웃 객체 자식들을 모두 유지할 수 있습니다. 적어도 블록 모드 `BlockLayout`의 경우에 이 최적화를 적용하세요.

**16-7 _`previous` 무효화_.** 연습문제 9-2에서 아직 하지 않았다면 [`insertBefore` 메서드](https://developer.mozilla.org/en-US/docs/Web/API/Node/insertBefore) 지원을 추가하세요. `appendChild`와 마찬가지로 가능하면 레이아웃 객체를 다시 만들지 않고 싶습니다. 다만 이 메서드는 레이아웃 객체의 `previous` 필드도 바꿀 수 있습니다. 모든 블록 모드 `BlockLayout`에서 그 필드를 보호하고, 레이아웃 트리를 최대한 다시 만들지 않도록 하세요.

**16-8 _`:hover` 의사 클래스_.** 마우스가 [올려져 있는](https://developer.mozilla.org/en-US/docs/Web/CSS/:hover) 요소를 식별하는 `:hover` 의사 클래스가 있습니다. 마우스 호버 이벤트를 활성 `Tab`에 보내고 히트 테스팅으로 어떤 요소 위에 마우스가 있는지 알아내 이를 구현하세요. 이 히트 테스트에서 [강제 레이아웃](https://browser.engineering/scheduling.html#threaded-style-and-layout)을 유발하지 않도록 해 보세요. 한 가지 방법은 `Tab`에 `pending_hover`를 저장해 두고 `render` 중 `layout` 이후에 히트 테스트를 실행한 다음, 호버된 요소의 스타일을 무효화하기 위해 _한 번 더_ 렌더링하는 것입니다.

**16-9 _`ProtectedField` 없애기_.** 이 장 마지막 절에서 언급했듯이, 이 모든 `ProtectedField` 객체를 만드는 것은 실제 브라우저에는 너무 비쌉니다. 객체를 아예 만들지 않는 방법을 찾아보세요. 브라우저를 구현하는 데 쓰는 언어에 따라 도움이 되는 컴파일 타임 매크로를 쓸 수 있을 수도 있습니다. Python에서는 `ProtectedField`의 API 모양을 객체 지향이 아니라 함수형으로 바꾸는 리팩터링이 필요할 수 있습니다.

**16-10 _paint 최적화하기_.** 텍스트 입력에 대해 레이아웃을 빠르게 만든 뒤에도 paint는 여전히 고통스러울 만큼 느립니다. 프레임 사이에 디스플레이 리스트를 저장하고, 각 레이아웃 객체마다 paint가 필요한지에 대한 더티 플래그를 추가하고, 매번 다시 만드는 대신 디스플레이 리스트를 변경함으로써 이를 고치세요.
