현대 브라우저는 사용자 입력을 처리하고, 원격 파일을 요청하고, 여러 콜백을 실행하고, 궁극적으로 화면에 렌더링해야 하며, 그 모든 것을 빠르고 반응성 좋게 유지하면서 해내야 합니다. 그러려면 브라우저가 처리해야 할 일을 추적하는 통일된 작업(task) 추상화가 필요합니다. 게다가 브라우저의 일은 여러 CPU 스레드에 나뉘어야 하고, 서로 다른 스레드가 작업을 병렬로 실행해 반응성을 최대화해야 합니다.

## 작업과 작업 큐

지금까지 우리 브라우저가 하는 일의 대부분은 스크롤, 버튼 누르기, 링크 클릭 같은 사용자 동작에서 비롯되었습니다. 하지만 우리 브라우저가 실행하는 웹 애플리케이션이 점점 정교해지면서, 원격 서버에 질의하고, 애니메이션을 보여 주고, 나중에 쓸 정보를 미리 가져오기 시작합니다. 사용자는 느리고 신중해서 동작 사이에 브라우저가 따라잡을 긴 틈을 남겨 주지만, 애플리케이션은 매우 요구가 많을 수 있습니다. 이는 관점의 전환을 요구합니다. 이제 브라우저에는 끝없이 이어지는 작업의 큐가 있습니다.

현대 브라우저는 멀티태스킹하고, 우선순위를 매기고, 중복을 제거함으로써 이 현실에 적응합니다. 브라우저가 할 수 있는 모든 일, 즉 페이지 로드, 스크립트 실행, 사용자 동작에 대한 반응은 나중에 실행될 수 있는 _작업(task)_ 으로 바뀝니다. 여기서 작업이란 그저 실행할 수 있는 함수(와 그 인자)일 뿐입니다.

```python
class Task:
    def __init__(self, task_code, *args):
        self.task_code = task_code
        self.args = args

    def run(self):
        self.task_code(*self.args)
        self.task_code = None
        self.args = None
```

생성자 인자와 `task_code` 호출에 쓰인 특별한 `*args` 문법을 눈여겨보세요. 이 문법은 `Task`를 임의 개수의 인자로 생성할 수 있으며 그 인자들이 리스트 `args`로 제공된다는 뜻입니다. 그리고 `*args`로 함수를 호출하면 그 리스트가 다시 여러 인자로 풀립니다.

작업의 요점은 한 시점에 만들어 두었다가 나중에 어떤 작업 실행기(task runner)가 스케줄링 알고리즘에 따라 실행할 수 있다는 것입니다.[^1] 우리 브라우저에서 작업 실행기는 작업을 선입선출 큐에 저장합니다.

```python
class TaskRunner:
    def __init__(self):
        self.tab = tab
        self.tasks = []

    def schedule_task(self, task):
        self.tasks.append(task)
```

작업을 실행할 때가 되면, 우리 작업 실행기는 큐에서 첫 번째 작업을 꺼내 실행하기만 하면 됩니다.[^2]

```python
class TaskRunner:
    def run(self):
        if len(self.tasks) > 0:
            task = self.tasks.pop(0)
            task.run()
```

그 작업들을 실행하려면 `TaskRunner`의 `run` 메서드를 호출해야 하는데, 이는 메인 이벤트 루프에서 할 수 있습니다.

```python
class Tab:
    def __init__(self):
        self.task_runner = TaskRunner(self)
```

```python
def mainloop(browser):
    while True:
        # ...
        browser.active_tab.task_runner.run()
```

`TaskRunner` 덕분에 우리는 서로 다른 작업이 정확히 언제 처리될지 고를 수 있습니다. 여기서 저는 브라우저가 실행하는 모든 `Task` 사이에 사용자 이벤트를 확인하도록 했는데, 이렇게 하면 작업이 많을 때 브라우저의 반응성이 좋아집니다. 또한 활성 탭의 작업만 실행하도록 했는데, 이는 배경 탭이 우리 브라우저를 느리게 만들 수 없다는 뜻입니다.

이 간단한 작업 실행기가 있으면 이제 작업을 큐에 넣어 두었다가 나중에 실행할 수 있습니다. 예를 들어 지금은 웹 페이지를 로드할 때 우리 브라우저가 렌더링 단계를 하기 전에 모든 스크립트를 내려받아 실행합니다. 그 때문에 페이지 로드가 느려집니다. 스크립트 실행을 위한 작업을 만들어 이를 고칠 수 있습니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        for script in scripts:
            # ...
            try:
                header, body = script_url.request(url)
            except:
                continue
            task = Task(self.js.run, script_url, body)
            self.task_runner.schedule_task(task)
```

이제 우리 브라우저는 `load`가 완료되고 이벤트 루프가 다시 돌아온 뒤에야 스크립트를 실행합니다. 그리고 실행할 스크립트가 많다면 페이지가 로드되는 동안 사용자 이벤트도 처리할 수 있게 됩니다.

### 더 알아보기

JavaScript는 브라우저 [바깥에서도](https://nodejs.dev/learn/the-nodejs-event-loop) 작업 기반 [이벤트 루프](https://developer.mozilla.org/en-US/docs/Web/JavaScript/EventLoop)를 사용합니다. 예를 들어 JavaScript는 메시지 전달을 사용하고, [비동기](https://developer.mozilla.org/en-US/docs/Web/JavaScript/EventLoop#never_blocking) API로 입출력을 처리하며, 실행 완료(run-to-completion) 의미론을 가집니다. 물론 이 프로그래밍 모델은 초기 브라우저 구현에서 자라 나온 것이며, 이제는 브라우저를 작업 중심으로 설계해야 할 또 하나의 중요한 이유가 되었습니다.

## 타이머와 `setTimeout`

작업은 미래의 어느 시점에 함수를 실행해 달라고 요청하는 여러 JavaScript API를 지원하는 자연스러운 방법이기도 _합니다_. 예를 들어 [`setTimeout`](https://developer.mozilla.org/en-US/docs/Web/API/setTimeout)은 지금부터 몇 밀리초 뒤에 JavaScript 함수를 실행하게 해 줍니다. 다음 코드는 1초 뒤에 콘솔에 "Callback"을 출력합니다.

```
function callback() { console.log('Callback'); }
setTimeout(callback, 1000);
```

[9장](https://browser.engineering/scripts.html#event-handling)의 `addEventListener`와 마찬가지로, 콜백을 JavaScript 변수에 저장하고 Python 쪽 코드가 그것을 호출할 수 있는 핸들을 만들어 `setTimeout`을 구현하겠습니다.

```javascript
SET_TIMEOUT_REQUESTS = {}

function setTimeout(callback, time_delta) {
    var handle = Object.keys(SET_TIMEOUT_REQUESTS).length;
    SET_TIMEOUT_REQUESTS[handle] = callback;
    call_python("setTimeout", handle, time_delta)
}
```

내보낸 `setTimeout` 함수는 타이머를 만들고, 요청된 시간만큼 기다린 다음, JavaScript 런타임에게 콜백을 실행해 달라고 요청합니다. 그 마지막 부분은 `__runSetTimeout`을 통해 일어납니다.[^3]

```javascript
function __runSetTimeout(handle) {
    var callback = SET_TIMEOUT_REQUESTS[handle]
    callback();
}
```

이제 이 API의 Python 쪽을 구현해 봅시다. Python의 [`threading`](https://docs.python.org/3/library/threading.html) 모듈에 있는 [`Timer`](https://docs.python.org/3/library/threading.html#timer-objects) 클래스를 쓸 수 있습니다. 사용법은 다음과 같습니다.[^4]

```
import threading
def callback():
    # ...
threading.Timer(1.0, callback).start()
```

이 코드는 지금부터 1초 뒤에 `callback`을 실행합니다. 간단하죠! 그런데 `threading.Timer`는 콜백을 _새 Python 스레드에서_ 실행하며, 이는 많은 어려움을 불러옵니다. 콜백이 그냥 `evaljs`를 직접 호출할 수는 없습니다. 그러면 두 Python 스레드에서 동시에 JavaScript가 실행되는데, 이는 좋지 않습니다.[^5] 그래서 우회책으로, 콜백은 `__runSetTimeout`을 호출하는 새 `Task`를 작업 큐에 추가하겠습니다. 이는 콜백이 지연될 수 있다는 단점이 있지만, JavaScript가 항상 메인 스레드에서만 실행된다는 뜻이기도 합니다.

구현해 봅시다.

```python
SETTIMEOUT_JS = "__runSetTimeout(dukpy.handle)"

class JSContext:
    def __init__(self, tab):
        # ...
        self.interp.export_function("setTimeout",
            self.setTimeout)

    def dispatch_settimeout(self, handle):
        self.interp.evaljs(SETTIMEOUT_JS, handle=handle)

    def setTimeout(self, handle, time):
        def run_callback():
            task = Task(self.dispatch_settimeout, handle)
            self.tab.task_runner.schedule_task(task)
        threading.Timer(time / 1000.0, run_callback).start()
```

하지만 이것도 아직 완전히 옳지는 않습니다. 이제 두 스레드가 `task_runner`에 접근합니다. 작업을 실행하는 기본 스레드와 작업을 추가하는 타이머 스레드입니다. 이는 온갖 나쁜 일을 일으킬 수 있는 [경쟁 조건](https://en.wikipedia.org/wiki/Race_condition)이므로, 한 번에 한 스레드만 `task_runner`에 접근하도록 해야 합니다.

그러기 위해 한 번에 한 스레드만 잡을 수 있는 [`Condition`](https://docs.python.org/3/library/threading.html#threading.Condition) 객체를 사용합니다. 각 스레드는 `task_runner`를 읽거나 쓰기 전에 `condition`을 획득하려고 시도해 동시 접근을 피합니다.[^6]

`Condition` 클래스는 사실 [`Lock`](https://docs.python.org/3/library/threading.html#threading.Lock)에 어떤 상태 조건이 일어날 때까지 _기다릴_ 수 있는 기능을 더한 것입니다. 지금 당장 할 일이 더 없다면 `condition`을 획득한 다음 `wait`를 호출하세요. 그러면 스레드가 그 코드 줄에서 멈춥니다. `schedule_task`에서처럼 할 일이 더 들어오면, `notify_all` 호출이 `wait`를 호출했던 스레드를 깨웁니다.

```python
class TaskRunner:
    def __init__(self, tab):
        # ...
        self.condition = threading.Condition()

    def schedule_task(self, task):
        self.condition.acquire(blocking=True)
        self.tasks.append(task)
        self.condition.notify_all()
        self.condition.release()

    def run(self):
        task = None
        self.condition.acquire(blocking=True)
        if len(self.tasks) > 0:
            task = self.tasks.pop(0)
        self.condition.release()
        if task:
            task.run()
```

락을 쓸 때는 결국 락을 반드시 해제하는 것, 그리고 가능한 한 짧은 시간만 잡고 있는 것이 아주 중요합니다. 예를 들어 위 코드는 `task`를 실행하기 전에 락을 해제합니다. 작업이 큐에서 제거된 뒤에는 다른 스레드가 그것에 접근할 수 없으므로, 작업이 실행되는 동안 락을 잡고 있을 필요가 없기 때문입니다.

이제 `setTimeout` 코드는 스레드 안전하지만 아직 또 다른 버그가 있습니다. 한 페이지에서 다른 페이지로 이동하면, 이전 페이지에서 아직 대기 중이던 `setTimeout` 콜백이 여전히 실행되려 할 수 있습니다. 이는 `JSContext`에 `discarded` 필드를 추가하고 새 페이지를 로드할 때 그것을 설정함으로써 쉽게 막을 수 있습니다.

```python
class JSContext:
    def __init__(self, tab):
        # ...
        self.discarded = False

    def dispatch_settimeout(self, handle):
        if self.discarded: return
        self.interp.evaljs(SETTIMEOUT_JS, handle=handle)
```

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        if self.js: self.js.discarded = True
        self.js = JSContext(self)
        # ...
```

### 더 알아보기

안타깝게도 현재 Python에는 [전역 인터프리터 락](https://wiki.python.org/moin/GlobalInterpreterLock)(GIL)이 있어서 Python 스레드는 진정으로 병렬 실행되지 않습니다. Python의 이 아쉬운 한계는 우리 브라우저에는 어느 정도 영향을 주지만 실제 브라우저에는 그렇지 않으므로, 이 장에서는 대체로 GIL이 없는 척하겠습니다. 어쩌면 미래의 Python 버전에서는 [그것이 없어질지도](https://peps.python.org/pep-0703/) 모릅니다. 전역 인터프리터 락이 있어도 우리는 여전히 락이 필요한데, Python 스레드가 바이트코드 연산 사이나 C 라이브러리 호출 중에 양보할 수 있기 때문입니다. 즉 동시 접근과 경쟁 조건이 여전히 가능합니다.[^7]

## 오래 사는 스레드

스레드는 브라우저 멀티태스킹을 추가하는 데도 쓸 수 있습니다. 예를 들어 [10장](https://browser.engineering/security.html#cross-site-requests)에서 우리는 스크립트가 서버에 요청할 수 있게 해 주는 `XMLHttpRequest` 클래스를 구현했습니다. 하지만 우리 구현에서는 요청이 끝나기를 기다리는 동안 브라우저 전체가 멈춰 버립니다. 이는 명백히 나쁩니다.[^8] Python의 `Thread` 클래스를 쓰면 더 잘할 수 있습니다.

```
threading.Thread(target=callback).start()
```

이 코드는 새 스레드를 만들고 곧바로 반환합니다. 그러면 `callback`이 새 스레드에서 병렬로 실행되고, 최초의 스레드는 그 뒤의 코드를 계속 실행합니다.

스레드를 사용해 비동기 `XMLHttpRequest` 호출을 구현하겠습니다. 구체적으로는 브라우저가 스레드를 시작해 그 스레드에서 요청을 하고 응답을 파싱한 다음, 응답을 스크립트로 돌려보내는 `Task`를 예약하도록 하겠습니다.

`setTimeout`과 마찬가지로 콜백을 JavaScript 쪽에 저장하고 핸들로 참조하겠습니다.

```javascript
XHR_REQUESTS = {}

function XMLHttpRequest() {
    this.handle = Object.keys(XHR_REQUESTS).length;
    XHR_REQUESTS[this.handle] = this;
}
```

이제 스크립트가 `XMLHttpRequest` 객체의 `open` 메서드를 호출할 때 `is_async` 플래그가 참일 수 있도록 허용하겠습니다.[^9]

```javascript
XMLHttpRequest.prototype.open = function(method, url, is_async) {
    this.is_async = is_async;
    this.method = method;
    this.url = url;
}
```

`send` 메서드는 `is_async` 플래그와 핸들을 함께 보내야 합니다.

```javascript
XMLHttpRequest.prototype.send = function(body) {
    this.responseText = call_python("XMLHttpRequest_send",
        this.method, this.url, body, this.is_async, this.handle);
}
```

브라우저 쪽에서 `XMLHttpRequest_send` 핸들러는 세 부분으로 이루어집니다. 첫 번째 부분은 URL을 해석하고 보안 검사를 합니다.

```python
class JSContext:
    def XMLHttpRequest_send(
        self, method, url, body, isasync, handle):
        full_url = self.tab.url.resolve(url)
        if not self.tab.allowed_request(full_url):
            raise Exception("Cross-origin XHR blocked by CSP")
        if full_url.origin() != self.tab.url.origin():
            raise Exception(
                "Cross-origin XHR request not allowed")
```

그다음 요청을 하고 콜백 실행을 위한 작업을 큐에 넣는 함수를 정의하겠습니다.

```python
class JSContext:
    def XMLHttpRequest_send(
        self, method, url, body, isasync, handle):
        # ...
        def run_load():
            headers, response = full_url.request(self.tab.url, body)
            task = Task(self.dispatch_xhr_onload, response, handle)
            self.tab.task_runner.schedule_task(task)
            return response
```

그 작업이 `dispatch_xhr_onload`를 실행한다는 점에 주의하세요. 이 함수는 곧 정의하겠습니다.

마지막으로 `is_async` 플래그에 따라 브라우저는 이 함수를 곧바로 호출하거나 새 스레드에서 호출합니다.

```python
class JSContext:
    def XMLHttpRequest_send(
        self, method, url, body, isasync, handle):
        # ...
        if not isasync:
            return run_load()
        else:
            threading.Thread(target=run_load).start()
```

비동기인 경우 `XMLHttpRequest_send` 메서드가 스레드를 시작하고 곧바로 반환한다는 점에 주의하세요. 그 스레드는 요청이 끝날 때까지 브라우저의 주된 일과 병렬로 실행됩니다.[^10]

결과를 JavaScript로 되돌려 주기 위해 `dispatch_xhr_onload`에서 `__runXHROnload` 함수를 호출하겠습니다.

```python
XHR_ONLOAD_JS = "__runXHROnload(dukpy.out, dukpy.handle)"

class JSContext:
    def dispatch_xhr_onload(self, out, handle):
        if self.discarded: return
        do_default = self.interp.evaljs(
            XHR_ONLOAD_JS, out=out, handle=handle)
```

`__runXHROnload` 메서드는 그저 `XHR_REQUESTS`에서 해당 객체를 꺼내 그 `onload` 함수를 호출합니다. 이 함수가 비동기 `XMLHttpRequest`의 표준 콜백입니다.

```javascript
function __runXHROnload(body, handle) {
    var obj = XHR_REQUESTS[handle];
    var evt = new Event('load');
    obj.responseText = body;
    if (obj.onload)
        obj.onload(evt);
}
```

보시다시피 작업은 브라우저뿐 아니라 브라우저에서 실행되는 애플리케이션도 작업을 나중으로 미룰 수 있게 해 줍니다.

### 더 알아보기

`XMLHttpRequest`는 웹이 진화하도록 돕는 데 핵심적인 역할을 했습니다. 1990년대에는 링크를 클릭하거나 폼을 제출하려면 새 페이지를 로드해야 했습니다. `XMLHttpRequest`가 있으니 웹 페이지가 훨씬 더 동적인 애플리케이션처럼 동작할 수 있게 되었습니다. GMail이 유명한 초기 사례 중 하나입니다.[^11] 요즘은 상태를 갱신하는 데 페이지 로드 대신 DOM 조작을 사용하는 웹 애플리케이션을 [단일 페이지 앱](https://en.wikipedia.org/wiki/Single-page_application)이라고 부릅니다. 단일 페이지 앱은 더 대화형이고 복잡한 웹 앱을 가능하게 했고, 그것이 다시 브라우저의 속도와 반응성을 더 중요하게 만들었습니다.

## 렌더링의 박자

작업에는 몇몇 JavaScript API를 구현하는 것 이상의 의미가 있습니다. 무언가가 `Task`가 되고 나면 그것이 언제 실행될지는 작업 실행기가 제어합니다. 어쩌면 지금, 어쩌면 나중에, 어쩌면 초당 최대 한 번, 심지어 활성 페이지와 비활성 페이지에 서로 다른 속도로, 또는 우선순위에 따라서 말이죠. 브라우저가 서로 다른 사용 사례에 최적화된 여러 작업 실행기를 가질 수도 있습니다.

지금은 브라우저가 어떤 JavaScript 콜백을 실행할지 우선순위를 매긴다거나, 왜 JavaScript 작업을 고정된 박자로 실행하고 싶어 하는지 이해하기 어려울 수 있습니다. 하지만 JavaScript 외에도 브라우저는 페이지를 렌더링해야 하며, [2장](https://browser.engineering/graphics.html#framebudget)에서 보았듯이 우리는 브라우저가 디스플레이 하드웨어가 새로 고칠 수 있는 것과 정확히 같은 속도로 페이지를 렌더링하기를 바랍니다. 대부분의 컴퓨터에서 이는 초당 60번, 즉 프레임당 16ms입니다. 하지만 오늘날의 컴퓨터로도 그렇게 높은 프레임 레이트를 유지하기는 꽤 어렵고, 우리의 장난감 브라우저에는 분명 너무 높은 기준입니다.

그러니 초당 30프레임, 즉 각 프레임당 33ms를 새로 고침 목표로 정합시다.[^12]

```python
REFRESH_RATE_SEC = .033
```

이제 프레임 하나를 그리는 일은 `Tab`과 `Browser`로 나뉩니다. `Tab`은 디스플레이 리스트를 계산하기 위해 `render`를 호출해야 합니다. 그다음 `Browser`는 그 디스플레이 리스트를 (그리고 크롬 디스플레이 리스트도) 래스터화하고 그려야 합니다. 그 `Browser` 작업들을 별도의 메서드로 만듭시다.

```python
class Browser:
    def raster_and_draw(self):
        self.raster_chrome()
        self.raster_tab()
        self.draw()
```

그런데 사용자는 한 번에 한 탭만 보므로 _모든_ 탭이 매 프레임마다 자신을 다시 그릴 필요는 없습니다. _활성_ 탭만 다시 그리면 됩니다. 따라서 언제 화면을 갱신할지 제어해야 하는 것은 개별 `Tab`이 아니라 `Browser`입니다. 그러니 활성 탭을 `render`하는 작업을 예약하는 `schedule_animation_frame` 메서드[^13]를 작성합시다.

```python
class Browser:
    def __init__(self):
        self.animation_timer = None

    def schedule_animation_frame(self):
        def callback():
            active_tab = self.active_tab
            task = Task(active_tab.render)
            active_tab.task_runner.schedule_task(task)
            self.animation_timer = None
        if not self.animation_timer:
            self.animation_timer = \
                threading.Timer(REFRESH_RATE_SEC, callback)
            self.animation_timer.start()
```

이 과정은 브라우저를 시작할 때 시동을 걸 수 있습니다. 최상위 루프에서 활성 탭의 작업을 실행한 뒤, 그 작업이 렌더링 작업이었을 경우를 대비해 브라우저는 래스터화하고 그려야 합니다.

```python
def mainloop(browser):
    while True:
        # ...
        browser.active_tab.task_runner.run()
        browser.raster_and_draw()
        browser.schedule_animation_frame()
```

추가된 `schedule_animation_frame` 호출은 루프를 돌 때마다 일어납니다. 하지만 `self.animation_timer`가 `None`인지 검사하기 때문에, 33ms 뒤에야 일어나는 `callback` 호출이 있고 나서야 효과가 있습니다. 따라서 우리가 원한 대로 33ms마다 새 렌더링 작업을 예약하게 됩니다.

### 더 알아보기

특정 새로 고침 빈도가 특별한 것은 아닙니다. 어떤 디스플레이는 초당 72번 새로 고치고, [그보다 더 자주 새로 고치는](https://www.intel.com/content/www/us/en/gaming/resources/highest-refresh-rate-gaming.html) 디스플레이도 점점 흔해지고 있습니다. 영화는 흔히 초당 24프레임으로 촬영되고([48프레임을 주장하는 감독](https://www.extremetech.com/extreme/128113-why-movies-are-moving-from-24-to-48-fps)도 있습니다), 텔레비전 프로그램은 전통적으로 초당 30프레임을 씁니다. 실제 프레임 레이트보다 일관성이 더 중요한 경우가 많습니다. 일정한 초당 24프레임이 60과 24 사이를 오가는 것보다 훨씬 부드러워 보일 수 있습니다.

## 더티 플래그로 최적화하기

이것을 여러분의 컴퓨터에서 실행하면 CPU 사용량이 치솟고 배터리가 닳기 시작할 가능성이 큽니다. 우리가 매 프레임마다 `render`를 호출하고 있어서, 브라우저가 이제 끊임없이 요소에 스타일을 주고, 레이아웃 트리를 만들고, 디스플레이 리스트를 페인트하기 때문입니다. 그 일의 대부분은 낭비인데, 대부분의 프레임에서 웹 페이지는 전혀 바뀌지 않았으므로 옛 스타일, 레이아웃 트리, 디스플레이 리스트가 새것만큼이나 잘 동작했을 것이기 때문입니다.

_더티 플래그(dirty flag)_ 를 사용해 이를 고칩시다. 더티 플래그란 어떤 복잡한 자료 구조가 최신 상태인지 알려 주는 상태 조각입니다. 우리는 `render`를 실행해야 하는지 알고 싶으므로, 더티 플래그의 이름을 `needs_render`라고 합시다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.needs_render = False

    def set_needs_render(self):
        self.needs_render = True

    def render(self):
        if not self.needs_render: return
        # ...
        self.needs_render = False
```

이 플래그의 이점 하나는, 이제 HTML이 바뀌었을 때 `render`를 직접 호출하는 대신 `needs_render`를 설정하면 된다는 것입니다. `render`는 여전히 일어나지만 나중에 일어납니다. 이는 스크립트를 더 빠르게 만들어 주는데, 특히 스크립트가 페이지를 여러 번 수정할 때 그렇습니다. DOM을 바꿀 때 `innerHTML_set`, `load`, `click`, `keypress`에서 이렇게 바꾸세요. 예를 들어 `load`에서는 다음과 같이 합니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.set_needs_render()
```

그리고 `innerHTML_set`에서는 다음과 같이 합니다.

```python
class JSContext:
    def innerHTML_set(self, handle, s):
        # ...
        self.tab.set_needs_render()
```

`render` 호출이 더 있습니다. 전부 찾아서 고쳐야 합니다… 다만 `click`은 좀 더 자세히 살펴봅시다.

이제 무언가가 바뀌었을 때 즉시 렌더링하지 않습니다. 즉 어떤 메서드가 호출될 때 레이아웃 트리(와 스타일)가 낡은 상태일 수 있습니다. 보통은 문제가 되지 않지만 한 가지 중요한 경우에는 문제가 됩니다. 바로 클릭 처리입니다. 어떤 객체가 클릭되었는지 알아내려면 레이아웃 트리를 읽어야 하므로 레이아웃 트리가 최신이어야 하기 때문입니다. 이를 고치기 위해 `click`의 맨 위에 `render` 호출을 추가하세요.

```python
class Tab:
    def click(self, x, y):
        self.render()
        # ...
```

우리 구현의 또 다른 문제는, 활성 탭이 작업을 실행할 때마다 브라우저가 `raster_and_draw`를 한다는 것입니다. 하지만 때로는 그 작업이 웹 페이지를 건드리지 않는 JavaScript를 실행하는 것뿐이어서 `raster_and_draw` 호출이 낭비입니다.

또 다른 더티 플래그로 이를 피할 수 있습니다. 그것을 `needs_raster_and_draw`라고 부르겠습니다.[^14]

```python
class Browser:
    def __init__(self):
        self.needs_raster_and_draw = False

    def set_needs_raster_and_draw(self):
        self.needs_raster_and_draw = True

    def raster_and_draw(self):
        if not self.needs_raster_and_draw:
            return
        # ...
        self.needs_raster_and_draw = False
```

`Browser`가 브라우저 크롬의 무언가를 바꿀 때마다, 또는 `Tab`이 자신의 렌더링을 바꿀 때마다 `set_needs_raster_and_draw`를 호출해야 합니다. 브라우저 크롬은 이벤트 핸들러가 바꿉니다.

```python
class Browser:
    def handle_click(self, e):
        if e.y < self.chrome.bottom:
            # ...
            self.set_needs_raster_and_draw()

    def handle_key(self, char):
        if self.chrome.keypress(char):
            # ...
            self.set_needs_raster_and_draw()

    def handle_enter(self):
        if self.chrome.enter():
            # ...
            self.set_needs_raster_and_draw()
```

여기서 `enter`가 무언가를 했는지 반환하도록 작은 변경이 필요합니다.

```python
class Chrome:
    def enter(self):
        if self.focus == "address bar":
            self.browser.active_tab.load(URL(self.address_bar))
            self.focus = None
            return True
        return False
```

그리고 `Tab`도 `render`를 실행한 뒤 이 플래그를 설정해야 합니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.browser = browser
        
    def render(self):
        # ...
        self.browser.set_needs_raster_and_draw()
```

`Tab`을 생성할 때 `browser` 매개변수를 넘겨야 합니다.

```python
class Browser:
    def new_tab(self, url):
        new_tab = Tab(self, HEIGHT - self.chrome.bottom)
        # ...
```

이제 렌더링 파이프라인은 필요할 때만 실행되고, 브라우저는 다시 받아들일 만한 성능을 갖게 되었을 것입니다.

### 더 알아보기

이렇게 예약되고 작업에 기반한 렌더링 접근법은 복잡한 대화형 애플리케이션을 실행하는 데 필수적이지만, 그런 웹 애플리케이션이 널리 퍼진 지 한참 뒤인 2010년대에 이르러서야 모든 현대 브라우저가 그것을 채택했습니다. 그것은 보통 방대한 브라우저 코드베이스를 대대적으로 리팩터링해야 했기 때문입니다. 예를 들어 Chromium은 [최근에야](https://developer.chrome.com/docs/chromium/renderingng) 이 모델을 활용하기 위한 작업을 100% 마쳤습니다. 물론 (늘 그렇듯) 아직 할 일이 남아 있지만요.

## 프레임 애니메이션하기

일정한 렌더링 박자를 유지하는 큰 이유 하나는 애니메이션이 부드럽게 실행되게 하기 위해서입니다. 웹 페이지는 [`requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/window/requestAnimationFrame) API로 그런 애니메이션을 설정할 수 있습니다. 이 API는 브라우저가 렌더링 파이프라인을 실행하기 직전에 스크립트가 코드를 실행할 수 있게 해 주어, 애니메이션을 최대한 부드럽게 만듭니다. 사용법은 다음과 같습니다.

```
function callback() { /* Modify DOM */ }
requestAnimationFrame(callback);
```

`requestAnimationFrame`을 호출함으로써 이 코드는 두 가지 일을 합니다. 렌더링 작업을 예약하고, 브라우저가 그 렌더링 작업 _맨 처음에_, 브라우저 렌더링 코드보다 앞서 `callback`을 호출하도록 요청하는 것입니다. 덕분에 웹 페이지 작성자는 페이지를 바꾸고 그것이 곧바로 렌더링되리라고 확신할 수 있습니다.

이 JavaScript API의 구현은 간단합니다. 전과 마찬가지로 콜백은 JavaScript 쪽에 저장합니다.

```javascript
RAF_LISTENERS = [];

function requestAnimationFrame(fn) {
    RAF_LISTENERS.push(fn);
    call_python("requestAnimationFrame");
}
```

`JSContext`에서 그 메서드가 호출되면 새 렌더링 작업을 예약해야 합니다.

```python
class JSContext:
    def __init__(self, tab):
        # ...
        self.interp.export_function("requestAnimationFrame",
            self.requestAnimationFrame)
```

```python
    def requestAnimationFrame(self):
        task = Task(self.tab.render)
        self.tab.task_runner.schedule_task(task)
```

그다음 실제로 `render`가 호출될 때 다음과 같이 JavaScript를 다시 호출해야 합니다.

```python
class Tab:
    def render(self):
        if not self.needs_render: return
        self.js.interp.evaljs("__runRAFHandlers()")
        # ...
```

이 `__runRAFHandlers` 함수는 조금 까다롭습니다.

```javascript
function __runRAFHandlers() {
    var handlers_copy = RAF_LISTENERS;
    RAF_LISTENERS = [];
    for (var i = 0; i < handlers_copy.length; i++) {
        handlers_copy[i]();
    }
}
```

`__runRAFHandlers`가 콜백을 하나라도 실행하기 전에 `RAF_LISTENERS`를 빈 배열로 초기화해야 한다는 점에 주의하세요. 콜백 중 하나가 스스로 `requestAnimationFrame`을 호출할 수 있기 때문입니다. 그런 콜백 도중에 이런 일이 일어나면, 명세는 _두 번째_ 애니메이션 프레임이 예약되어야 한다고 말합니다. 즉 _현재_ 프레임의 콜백을 _다음_ 프레임의 콜백과 분리해 저장해야 합니다.

이 상황은 예외적인 경우처럼 보일 수 있지만, 사실 매우 중요합니다. 페이지가 _애니메이션_ 을 실행하는 방식이 바로 이것, 즉 한 프레임 뒤에 또 한 프레임을 반복적으로 예약하는 것이기 때문입니다. 예를 들어 다음은 간단한 카운터 "애니메이션"입니다.

```javascript
var count = 0;
function callback() {
    var output = document.querySelectorAll("div")[1];
    output.innerHTML = "count: " + (count++);
    if (count < 100)
        requestAnimationFrame(callback);
}
requestAnimationFrame(callback);
```

이 스크립트는 렌더링 이벤트 루프에서 100개의 애니메이션 프레임 작업을 실행하게 합니다. 그동안 우리 브라우저는 0에서 99까지 세는 애니메이션을 표시합니다. 이 예제 웹 페이지를 우리 HTTP 서버에서 제공하세요.

```python
def do_request(session, method, url, headers, body):
    elif method == "GET" and url == "/count":
        return "200 OK", show_count()
# ...
def show_count():
    out = "<!doctype html>"
    out += "<div>";
    out += "  Let's count up to 99!"
    out += "</div>";
    out += "<div>Output</div>"
    out += "<script src=/eventloop.js></script>"
    return out
```

이것을 불러와 0에서 99까지의 애니메이션을 확인해 보세요.

지금까지의 구현에는 결함이 하나 있습니다. 부주의한 코더가 `requestAnimationFrame`을 여러 번 호출해 예상보다 많은 애니메이션 프레임을 예약할 수 있다는 점입니다. 나중에 다른 JavaScript 작업이 나타나면 아주아주 많은 프레임만큼 지연될 수 있습니다.

다행히 렌더링은 특별해서, 두 개의 렌더링 작업이 연달아 오는 것은 결코 말이 되지 않습니다. 그 사이에 페이지가 바뀌지 않았을 테니까요. 렌더링 작업이 두 개가 되는 것을 피하기 위해, 렌더링 작업을 실제로 예약해야 하는지를 나타내는 `needs_animation_frame`이라는 더티 플래그를 `Browser`에 추가하겠습니다.

```python
class Browser:
    def __init__(self):
        self.needs_animation_frame = True
```

```python
    def schedule_animation_frame(self):
        # ...
        if self.needs_animation_frame and not self.animation_timer:
            # ...
```

탭은 애니메이션 프레임이 요청되면 `needs_animation_frame` 플래그를 설정합니다.

```python
class JSContext:
    def requestAnimationFrame(self):
        self.tab.browser.set_needs_animation_frame(self.tab)

class Tab:
    def set_needs_render(self):
        # ...
        self.browser.set_needs_animation_frame(self)

class Browser:
    def set_needs_animation_frame(self, tab):
        if tab == self.active_tab:
            self.needs_animation_frame = True
```

`set_needs_animation_frame`은 활성 탭에서 호출되었을 때만 실제로 더티 플래그를 설정한다는 점에 주의하세요. 이는 비활성 탭이 활성 탭을 방해할 수 없도록 보장합니다. 스크립트가 애니메이션 프레임을 너무 많이 예약하는 것을 막는 것 외에도, 이 체계는 우리 브라우저가 지속적으로 초당 30프레임보다 느리게 실행되더라도 렌더링 작업의 큐가 끝없이 커지지 않게 해 줍니다.

### 더 알아보기

`requestAnimationFrame` API가 있기 전에는 개발자들이 `setTimeout`으로 그것을 흉내 냈습니다. 이것도 애니메이션을 (대략) 고정된 박자로 실행하기는 했지만, 브라우저의 렌더링 루프와 맞춰지지 않았기 때문에 콜백과 렌더링 사이에 이벤트가 처리되어 불필요한 렌더링 단계가 한 번 더 강제될 수 있었습니다. `requestAnimationFrame`은 이를 피할 뿐 아니라, 웹 페이지 탭이나 창이 배경으로 가거나 최소화되거나 다른 이유로 제한될 때 브라우저가 렌더링 작업을 끌 수 있게 해 주면서도, 작업을 클라우드에 저장하는 것 같은 다른 배경 작업은 계속 허용합니다.

## 렌더링 프로파일링

이제 33ms마다 렌더링 작업을 예약하는 체계를 갖췄습니다. 그런데 렌더링이 끝나는 데 33ms보다 오래 걸리면 어떻게 될까요? 이 질문에 답하기 전에, 브라우저를 계측해서 실제로 렌더링에 얼마나 많은 시간이 쓰이는지 측정해 봅시다. 결과가 뜻밖일 때가 많으므로 최적화하기 전에 항상 측정하는 것이 중요합니다.

브라우저를 계측하기 위해, [Chrome의 `chrome://tracing`](https://www.chromium.org/developers/how-tos/trace-event-profiling-tool/), [Firefox Profiler](https://profiler.firefox.com/), [Perfetto UI](https://ui.perfetto.dev/)가 사용하는 [JSON](https://www.json.org/) 트레이싱 형식을 출력하게 합시다.[^15]

우선 실제 파일과 형식을 클래스로 감싸 봅시다.

```python
class MeasureTime:
    def __init__(self):
        self.file = open("browser.trace", "w")
```

트레이스 파일은 그저 트레이스 이벤트의 리스트를 담은 `traceEvents` 필드[^16]가 있는 JSON 객체입니다.

```python
class MeasureTime:
    def __init__(self):
        # ...
        self.file.write('{"traceEvents": [')
```

각 트레이스 이벤트에는 여러 필드가 있습니다. `ph`와 `name` 필드가 이벤트 타입을 정의합니다. 예를 들어 `ph`를 `M`으로, `name`을 `process_name`으로 설정하면 표시되는 프로세스 이름을 바꿀 수 있습니다.

```python
class MeasureTime:
    def __init__(self):
        # ...
        ts = time.time() * 1000000
        self.file.write(
            '{ "name": "process_name",' +
            '"ph": "M",' +
            '"ts": ' + str(ts) + ',' +
            '"pid": 1, "cat": "__metadata",' +
            '"args": {"name": "Browser"}}')
        self.file.flush()
```

새 이름("Browser")은 `args`로 전달되고 나머지 필드는 필수입니다. 우리 브라우저에는 프로세스가 하나뿐이므로 프로세스 ID로 그냥 `1`을 넘기고, 메타데이터 트레이스 이벤트이므로 `cat`egory는 `__metadata`여야 합니다. `ts` 필드는 타임스탬프를 저장합니다. 이것이 첫 이벤트이므로 트레이스 전체의 시작 시간을 정하게 되니, 실제 현재 시각을 넣는 것이 중요합니다.

브라우저를 시작할 때 이 `MeasureTime` 객체를 만들어 여러 브라우저 구성 요소가 얼마나 걸리는지 측정하는 데 쓰겠습니다.

```python
class Browser:
    def __init__(self):
        self.measure = MeasureTime()
```

이제 브라우저가 흥미로운 일을 할 때마다 트레이스 이벤트를 추가합시다. 우리가 특히 원하는 것은 어떤 흥미로운 계산의 시작과 끝을 표시하는 `B`와 `E` 이벤트입니다. 최초의 트레이스 이벤트가 있으므로, 이후의 모든 트레이스 이벤트 앞에는 쉼표가 와야 합니다.

```python
class MeasureTime:
    def time(self, name):
        ts = time.time() * 1000000
        self.file.write(
            ', { "ph": "B", "cat": "_",' +
            '"name": "' + name + '",' +
            '"ts": ' + str(ts) + ',' +
            '"pid": 1, "tid": 1}')
        self.file.flush()
```

여기서 `time`의 `name` 인자는 어떤 종류의 계산이 시작되는지 설명해야 하며, 대응하는 `stop` 이벤트에 넘기는 이름과 일치해야 합니다.

```python
class MeasureTime:
    def stop(self, name):
        ts = time.time() * 1000000
        self.file.write(
            ', { "ph": "E", "cat": "_",' +
            '"name": "' + name + '",' +
            '"ts": ' + str(ts) + ',' +
            '"pid": 1, "tid": 1}')
        self.file.flush()
```

탭 렌더링은 그냥 `time`과 `stop`을 호출해 측정할 수 있습니다.

```python
class Tab:
    def render(self):
        if not self.needs_render: return
        self.browser.measure.time('render')
        # ...
        self.browser.measure.stop('render')
```

`raster_and_draw`와 JavaScript를 실행하기 위해 `evaljs`를 호출하는 모든 코드에도 똑같이 하세요.

마지막으로, 트레이싱을 마칠 때(즉 브라우저 창을 닫을 때) 파일이 유효한 JSON 파일로 남게 하고 싶습니다.

```python
class MeasureTime:
    def finish(self):
        self.file.write(']}')
        self.file.close()

class Browser:
    def handle_quit(self):
        # ...
        self.measure.finish()
```

그런데 제가 쓸 때마다 조심스럽게 `flush`한다는 점을 눈여겨보세요. 이렇게 하면 브라우저가 죽더라도 디버깅에 도움이 될 모든 로그 이벤트가 이미 디스크에 안전하게 저장되어 있게 됩니다.[^17]

우리 브라우저는 픽셀을 복사하는 데 많은 시간을 씁니다. 그래서 [서피스 최적화](https://browser.engineering/visual-effects.html#optimizing-surface-use)가 중요한 것입니다! 연습문제 11-3을 완료했다면 더 빠를 텐데, `tab_surface`를 더 작게 만드는 것도 크게 도움이 되기 때문입니다. 현대 브라우저는 한 걸음 더 나아가 훨씬 많은 병렬성을 쓸 수 있는 [GPU에서](https://skia.org/docs/user/api/skcanvas_creation/#gpu) 래스터화와 그리기를 수행합니다. 그렇더라도 복잡한 페이지에서는 래스터화와 그리기가 정말로 많은 시간을 잡아먹기도 합니다. 13장에서 이를 더 파고들겠습니다.

## 두 개의 스레드

물론 한 가지 선택지는 래스터화와 그리기를, 심지어 렌더링까지 최적화하는 것이고, [13장](https://browser.engineering/animations.html)에서 그렇게 하겠습니다. 하지만 또 다른 선택지가 있는데, 복잡하지만 그만한 가치가 있고 모든 주요 브라우저가 하는 방식입니다. 바로 다중 스레드 구조를 채택해 렌더링 단계를 래스터화·그리기 단계와 병렬로 수행하는 것입니다. 이렇게 하면 렌더링 파이프라인이 빨라질 뿐 아니라(85ms에서 62ms로 줄어듭니다) 비용이 큰 `raster_and_draw` 작업이 한쪽에서 실행되는 동안 다른 쪽에서 JavaScript를 실행할 수도 있습니다.

우리의 두 스레드를 _브라우저 스레드_[^18] 와 _메인 스레드_[^19] 라고 부릅시다. 브라우저 스레드는 `Browser` 클래스에 대응하며 래스터화와 그리기를 처리합니다. 브라우저 크롬과의 상호작용도 처리합니다. 반면 메인 스레드는 `Tab`에 대응하며 스크립트 실행, 자원 로딩, 렌더링과 함께 이벤트 핸들러와 콜백 실행 같은 관련 작업을 처리합니다. 탭을 하나 이상 열어 두었다면 (탭마다 하나씩) 여러 개의 메인 스레드가 있지만 브라우저 스레드는 하나뿐입니다.

다중 스레드 구조는 까다로우니 계획을 좀 세워 봅시다.

우선 이미 존재하는 스레드 하나, 즉 브라우저를 시작할 때 실행되는 스레드가 브라우저 스레드가 됩니다. 탭을 만들 때마다 메인 스레드를 만들겠습니다. 이 두 스레드는 이벤트를 처리하고 화면에 그리기 위해 통신해야 합니다.

브라우저 스레드가 이벤트를 알리기 위해 메인 스레드와 통신해야 할 때는 메인 스레드의 `TaskRunner`에 작업을 넣습니다.[^20] 메인 스레드는 애니메이션 프레임을 요청하고 래스터화·그리기를 위한 디스플레이 리스트를 보내기 위해 브라우저 스레드와 통신해야 하는데, 메인 스레드는 이를 `browser`의 두 메서드를 통해 합니다. 애니메이션 프레임을 요청하는 `set_needs_animation_frame`과 디스플레이 리스트를 보내는 `commit`입니다.

따라서 프레임 하나를 렌더링하는 전체 제어 흐름은 다음과 같습니다.

1. 메인 스레드에서 실행되는 코드가 `set_needs_animation_frame`으로 애니메이션 프레임을 요청합니다. 이벤트 핸들러에 대한 반응이거나 `requestAnimationFrame` 때문일 수 있습니다.

2. 브라우저 스레드 이벤트 루프가 메인 스레드 `TaskRunner`에 애니메이션 프레임을 예약합니다.

3. 메인 스레드가 자신이 맡은 렌더링 부분을 실행한 다음 `browser.commit`을 호출합니다.

4. 브라우저 스레드가 디스플레이 리스트를 래스터화하고 화면에 그립니다.

이 설계를 구현해 봅시다. 우선 각 `TaskRunner`에 `Thread`를 추가하는데, 이것이 탭의 메인 스레드가 됩니다. 이 스레드는 루프를 돌면서 작업 큐에서 작업을 꺼내 실행해야 합니다. 그 루프는 `TaskRunner`의 `run` 메서드 안에 넣겠습니다.

```python
class TaskRunner:
    def __init__(self, tab):
        # ...
        self.main_thread = threading.Thread(
            target=self.run,
            name="Main thread",
        )

    def start_thread(self):
        self.main_thread.start()
```

제가 스레드에 이름을 붙인다는 점에 주의하세요. 이는 디버깅에 도움이 되는 좋은 습관입니다. 브라우저 스레드에도 이름을 붙입시다.

```python
class Browser:
    def __init__(self):
        # ...
        threading.current_thread().name = "Browser thread"
```

최상위 `while True` 루프에서 `run` 호출을 제거하세요. 이제 그 루프는 브라우저 스레드에서 실행될 것이기 때문입니다. 그리고 `run`은 자신만의 루프를 갖게 됩니다.

```python
class TaskRunner:
    def run(self):
        while True:
            # ...
```

이 루프는 영원히 돌기 때문에 메인 스레드는 무기한 살아 있게 됩니다. 그래서 브라우저가 종료되면 메인 스레드에게도 종료해 달라고 요청해야 합니다.

```python
class Browser:
    def handle_quit(self):
        for tab in self.tabs:
            tab.task_runner.set_needs_quit()
```

`set_needs_quit` 메서드는 `TaskRunner`가 루프를 돌 때마다 확인하는 플래그를 설정합니다.

```python
class TaskRunner:
    def set_needs_quit(self):
        self.condition.acquire(blocking=True)
        self.needs_quit = True
        self.condition.notify_all()
        self.condition.release()

    def run(self):
        while True:
            self.condition.acquire(blocking=True)
            needs_quit = self.needs_quit
            self.condition.release()
            if needs_quit:
                return
    
            # ...
    
            self.condition.acquire(blocking=True)
            if len(self.tasks) == 0 and not self.needs_quit:
                self.condition.wait()
            self.condition.release()
```

할 일이 남아 있지 않다면 `run` 루프 끝에서 `condition.wait`를 호출하는 것이 중요합니다. 그러지 않으면 그 스레드가 CPU를 많이 잡아먹는 경향이 있고, 게다가 끊임없이 `condition`을 획득하고 해제하게 됩니다. 이 헛수고는 컴퓨터를 느리게 만들 뿐 아니라, 두 스레드가 락을 두고 경쟁하기 때문에 `Timer`의 콜백이 불규칙한 시점에 일어나게 만듭니다.[^21]

`Browser`는 더 이상 `Tab`의 어떤 메서드도 호출해서는 안 됩니다. 대신 이벤트를 처리하려면 메인 스레드에 작업을 예약해야 합니다. 예를 들어 로딩은 다음과 같습니다.

```python
class Browser:
    def schedule_load(self, url, body=None):
        self.active_tab.task_runner.clear_pending_tasks()
        task = Task(self.active_tab.load, url, body)
        self.active_tab.task_runner.schedule_task(task)
```

새 페이지를 로드하기 전에 대기 중인 작업을 모두 비워야 합니다. 그 이전 작업들은 이제 무효이기 때문입니다.

```python
class TaskRunner:
    def clear_pending_tasks(self):
        self.condition.acquire(blocking=True)
        self.tasks.clear()
        self.condition.release()
```

또한 `new_tab`을 락을 획득하는 버전과 획득하지 않는 버전(`new_tab_internal`)으로 나눠야 합니다.

```python
class Browser:
    def new_tab(self, url):
        self.lock.acquire(blocking=True)
        self.new_tab_internal(url)
        self.lock.release()

    def new_tab_internal(self, url):
        new_tab = Tab(self, HEIGHT - self.chrome.bottom)
        self.tabs.append(new_tab)
        self.set_active_tab(new_tab)
        self.schedule_load(url)
```

이렇게 하면 `Chrome`의 `click` 메서드처럼 이미 락을 잡고 있는 메서드가 `new_tab_internal`을 직접 호출할 수 있습니다.[^22]

```python
class Chrome:
    def click(self, x, y):
        if self.newtab_rect.contains(x, y):
            self.browser.new_tab_internal(
                URL("https://browser.engineering/"))

    def enter(self):
        if self.focus == "address bar":
            self.browser.schedule_load(URL(self.address_bar))
```

이벤트 핸들러도 대체로 비슷하지만, 브라우저 크롬에 영향을 주는 이벤트와 탭에 영향을 주는 이벤트를 조심해서 구분해야 합니다. 예를 들어 `handle_click`을 생각해 봅시다. 사용자가 브라우저 크롬을 클릭했다면 브라우저 스레드에서 바로 처리하면 됩니다. 하지만 웹 페이지를 클릭했다면 메인 스레드에 작업을 예약해야 합니다.

```python
class Browser:
    def handle_click(self, e):
        self.lock.acquire(blocking=True)
        if e.y < self.chrome.bottom:
             # ...
        else:
            # ...
            tab_y = e.y - self.chrome.bottom
            task = Task(self.active_tab.click, e.x, tab_y)
            self.active_tab.task_runner.schedule_task(task)
        self.lock.release()
```

`keypress`도 같은 논리를 따릅니다.

```python
class Browser:
    def handle_key(self, char):
        if not (0x20 <= ord(char) < 0x7f): return
        if self.chrome.keypress(char):
            # ...
        elif self.focus == "content":
            task = Task(self.active_tab.keypress, char)
            self.active_tab.task_runner.schedule_task(task)
```

`Browser`에서 `Tab`으로 가는 다른 모든 호출에도 똑같이 하세요.

이제 브라우저 스레드가 메인 스레드에게 무엇을 할지 알려 줍니다. 반대 방향의 통신은 조금 더 미묘합니다.

### 더 알아보기

원래 스레드는 선점형 멀티태스킹을 통해 _반응성_ 을 개선하는 메커니즘이었지만, 요즘은 휴대폰조차 코어가 여러 개이므로 브라우저가 _처리량_ 을 늘리는 데도 쓰입니다. 하지만 CPU 아키텍처는 서로 다르고, 브라우저 엔지니어(여러분 같은!)는 상황에 맞게 하드웨어 병렬성을 더 쓰거나 덜 써야 합니다. 예를 들어 어떤 기기는 다른 기기보다 [CPU 코어](https://en.wikipedia.org/wiki/Multi-core_processor)가 많고, 어떤 기기는 배터리 사용에 더 민감하며, 무선 라디오를 청취하는 것 같은 시스템 프로세스가 브라우저가 실제로 쓸 수 있는 병렬성을 제한할 수도 있습니다.

## 디스플레이 리스트 커밋하기

우리에겐 이미 `set_needs_animation_frame` 메서드가 있지만, `Tab`이 디스플레이 리스트 생성을 마쳤을 때 호출할 수 있는 `commit` 메서드도 필요합니다. 그리고 래스터화·그리기 코드를 자세히 보면, 디스플레이 리스트를 그리려면 (브라우저 크롬을 갱신하기 위한) URL, (알맞은 크기의 서피스를 할당하기 위한) 문서 높이, (서피스의 올바른 부분을 그리기 위한) 스크롤 위치도 알아야 한다는 것을 알 수 있습니다.

이 데이터를 저장할 간단한 클래스를 만듭시다.

```python
class CommitData:
    def __init__(self, url, scroll, height, display_list):
        self.url = url
        self.scroll = scroll
        self.height = height
        self.display_list = display_list
```

애니메이션 프레임을 실행할 때 `Tab`은 이 객체 중 하나를 만들어 `commit`에 넘겨야 합니다. `render`가 너무 복잡해지지 않도록 이것을 새로운 `run_animation_frame` 메서드에 넣고, `__runRAFHandlers`도 거기로 옮깁시다.[^23]

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.browser = browser

    def run_animation_frame(self):
        self.js.interp.evaljs("__runRAFHandlers()")
        self.render()
        commit_data = CommitData(
            self.url, self.scroll, document_height, \
            self.display_list)
        self.display_list = None
        self.browser.commit(self, commit_data)
```

`CommitData` 객체를 메인 스레드에서 브라우저 스레드로 보내는 것이라고 생각하세요. 즉 메인 스레드는 더 이상 그것에 접근해서는 안 되며, 그래서 `display_list` 필드를 초기화하는 것입니다. 이제 `Browser`가 `run_animation_frame`을 예약해야 합니다.

```python
class Browser:
    def schedule_animation_frame(self):
        def callback():
            # ...
            task = Task(self.active_tab.run_animation_frame)
            # ...
```

`Browser` 쪽에서 새로운 `commit` 메서드는 자신이 받은 모든 데이터를 읽어 내고 필요에 따라 `set_needs_raster_and_draw`를 호출해야 합니다. 이 호출은 다른 스레드에서 오므로 락을 획득해야 합니다. 또 하나 중요한 단계는, 다음 커밋이 일어난 _뒤에야_ `animation_timer` 객체를 비우는 것입니다. 그러지 않으면 여러 렌더링 작업이 동시에 큐에 들어갈 수 있습니다. 마지막으로 모든 `CommitData`를 저장하세요. `scroll`은 `active_tab_scroll`에, `url`은 `active_tab_url`에 저장하고, 추가로 `height`와 (있다면) `display_list`도 저장합니다.

```python
class Browser:
    def __init__(self):
        self.lock = threading.Lock()

        self.active_tab_url = None
        self.active_tab_scroll = 0
        self.active_tab_height = 0
        self.active_tab_display_list = None

    def commit(self, tab, data):
        self.lock.acquire(blocking=True)
        if tab == self.active_tab:
            self.active_tab_url = data.url
            self.active_tab_scroll = data.scroll
            self.active_tab_height = data.height
            if data.display_list:
                self.active_tab_display_list = data.display_list
            self.animation_timer = None
            self.set_needs_raster_and_draw()
        self.lock.release()
```

`Chrome` 클래스가 이 새 `url` 필드를 쓰도록 반드시 갱신하세요. 브라우저 스레드에서 실행되는 크롬이 메인 스레드에서 실행되는 탭에서 읽어 오는 것을 원하지 않기 때문입니다.

`commit`은 메인 스레드에서 호출되지만 브라우저 스레드의 락을 획득한다는 점에 주의하세요. 그 결과 `commit`은 두 스레드가 동시에 "멈춰 있는" 중요한 시점입니다.[^24] 또한 브라우저 스레드가 비활성 탭에서 `commit`을 받는 것도 가능하므로,[^25] 커밋된 데이터를 복사하기 전에 `tab` 매개변수를 활성 탭과 비교한다는 점에도 주의하세요.

이제 브라우저 락이 생겼으니, 브라우저 스레드가 자신의 변수에 접근할 때마다 락을 획득해야 합니다. 예를 들어 `set_needs_animation_frame`에서는 다음과 같이 합니다.

```python
class Browser:
    def set_needs_animation_frame(self, tab):
        self.lock.acquire(blocking=True)
        # ...
        self.lock.release()
```

`schedule_animation_frame`에서는 콜백 안과 밖 양쪽에서 해야 합니다.

```python
class Browser:
    def schedule_animation_frame(self):
        def callback():
            self.lock.acquire(blocking=True)
            # ...
            self.lock.release()
            # ...
        self.lock.acquire(blocking=True)
        # ...
        self.lock.release()
```

`raster_and_draw`, `handle_down`, `handle_click`, `handle_key`, `handle_enter`에도 락을 추가하세요.

또한 메인 스레드가 브라우저 스레드가 래스터화하고 그릴 수 있는 것보다 빠르게 렌더링하는 것도 원하지 않습니다. 그러니 래스터화와 그리기가 끝난 뒤에만 애니메이션 프레임을 예약해야 합니다.[^26] 다행히 그것이 바로 우리가 하고 있는 일입니다.

```python
def mainloop(browser):
    while True:
        # ...
        browser.raster_and_draw()
        browser.schedule_animation_frame()
```

이것으로 끝입니다. 이제 한 스레드에서 렌더링을, 다른 스레드에서 래스터화와 그리기를 하게 되었습니다!

### 더 알아보기

Python의 GIL 때문에 Python에서 스레딩은 _처리량_ 을 늘려 주지는 않지만, 예를 들어 브라우저가 래스터화하고 그리는 동안 메인 스레드에서 JavaScript 작업을 실행하는 식으로 _반응성_ 은 높일 수 있습니다. Python 라이브러리에 링크된 외부 C/C++ 코드를 실행하는 동안 전역 인터프리터 락을 끄는 것도 가능합니다. Skia는 스레드 안전하지만 DukPy와 SDL은 그렇지 않을 수 있고, GIL을 놓아 주는 것 같지도 않습니다. 만약 그렇게 한다면 JavaScript나 래스터화·그리기가 브라우저의 나머지 부분과 진정으로 병렬 실행될 수 있고 성능도 개선될 것입니다.

## 스레드 프로파일링

이제 스레드가 두 개가 되었으니, 우리가 만드는 트레이스에서 이를 시각화할 수 있으면 좋겠습니다. 다행히 Chrome 트레이싱 형식은 그것을 지원합니다. 우선 `MeasureTime` 메서드들을 스레드 안전하게 만들어 어느 스레드에서든 호출할 수 있게 합시다.

```python
class MeasureTime:
    def __init__(self):
        self.lock = threading.Lock()
        # ...

    def time(self, name):
        self.lock.acquire(blocking=True)
        # ...
        self.lock.release()

    def stop(self, name):
        self.lock.acquire(blocking=True)
        # ...
        self.lock.release()

    def finish(self):
        self.lock.acquire(blocking=True)
        # ...
        self.lock.release()
```

다음으로, 모든 트레이스 이벤트에서 `tid` 필드에 실제 스레드 ID를 제공하고 싶은데, 이는 `threading` 라이브러리의 `get_ident`를 호출해 얻을 수 있습니다.

```python
class MeasureTime:
    def time(self, name):
        # ...
        tid = threading.get_ident()
        self.file.write(
            ', { "ph": "B", "cat": "_",' +
            '"name": "' + name + '",' +
            '"ts": ' + str(ts) + ',' +
            '"pid": 1, "tid": ' + str(tid) + '}')
        # ...
```

`stop`에서도 똑같이 하세요. 트레이스를 마칠 때 메타데이터 이벤트를 추가하면 사람이 읽을 수 있는 스레드 이름도 표시할 수 있습니다.[^27]

```python
class MeasureTime:
    def finish(self):
        self.lock.acquire(blocking=True)
        for thread in threading.enumerate():
            self.file.write(
                ', { "ph": "M", "name": "thread_name",' +
                '"pid": 1, "tid": ' + str(thread.ident) + ',' +
                '"args": { "name": "' + thread.name + '"}}')
        # ...
```

이제 카운팅 애니메이션으로 새 트레이스를 만들어 트레이싱 도구 중 하나에 불러오면 그림 3과 비슷한 것이 보일 것입니다(예시 트레이스를 내려받으려면 [여기](https://browser.engineering/examples/example12-count-two-threads.trace)를 클릭하세요).

이 장에서 소개한 트레이싱 시스템은 실제 브라우저에서 그대로 가져온 것입니다. 브라우저 엔지니어들은 여러 상황에서 브라우저의 성능 특성을 이해하고, 병목을 찾고, 고치기 위해 매일 이것을 사용합니다. 이런 도구가 없었다면 브라우저는 최근 몇 년간 이룬 성능 도약을 많이 해내지 못했을 것입니다. 좋은 디버깅 도구는 소프트웨어 공학에 필수적입니다!

## 스레드 기반 스크롤

메인 스레드를 브라우저 스레드와 분리하면 메인 스레드가 브라우저를 크게 느리게 만들지 않으면서 많은 JavaScript를 실행할 수 있습니다. 하지만 정말 느린 JavaScript가 브라우저를 느리게 만드는 것은 여전히 가능합니다. 예를 들어 우리 카운터가 다음과 같은 인위적인 지연을 추가한다고 상상해 봅시다.

```javascript
function callback() {
    for (var i = 0; i < 5e6; i++);
    // ...
}
```

이제 카운터가 한 번 똑딱일 때마다 인위적인 멈춤이 생기고, 그동안 메인 스레드는 JavaScript를 실행하느라 묶여 있습니다. 즉 어떤 이벤트에도 반응할 수 없습니다. 예를 들어 아래쪽 방향키를 누르고 있으면 스크롤이 뚝뚝 끊기고 짜증스러울 것입니다. 이것을 직접 해 보고 얼마나 짜증스러운지 확인해 보시길 권합니다. 현대 브라우저에는 보통 이런 종류의 끊김이 없기 때문입니다.[^29]

이를 고치려면 메인 스레드가 아니라 브라우저 스레드가 스크롤을 처리해야 합니다. 이는 보기보다 어려운데, 스크롤 오프셋이 (사용자가 스크롤할 때) 브라우저와 (새 페이지를 로드하거나 JavaScript로 문서 높이를 바꿀 때) 메인 스레드 양쪽의 영향을 받을 수 있기 때문입니다. 이제 브라우저 스레드와 메인 스레드가 병렬로 실행되므로, 스크롤 오프셋에 대해 서로 의견이 다를 수 있습니다.

우리가 할 수 있는 최선은 스크롤 오프셋을 두 개, 브라우저 스레드에 하나 메인 스레드에 하나 두는 것입니다. 중요한 점은, 브라우저 스레드의 스크롤 오프셋은 브라우저가 가진 디스플레이 리스트 사본을 가리키고, 메인 스레드의 스크롤 오프셋은 메인 스레드의 디스플레이 리스트를 가리키며 이 둘이 조금 다를 수 있다는 것입니다. 브라우저 스레드가 렌더링할 때 메인 스레드로 스크롤 오프셋을 보내되, 새 프레임이 요구한다면 메인 스레드가 그 스크롤 오프셋을 _덮어쓸_ 수 있게 하겠습니다.

구현해 봅시다. 우선 `Browser`에 `active_tab_scroll` 변수를 저장하고 사용자가 스크롤할 때 그것을 갱신해야 합니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.active_tab_scroll = 0

    def clamp_scroll(self, scroll):
        height = self.active_tab_height
        maxscroll = height - (HEIGHT - self.chrome.bottom)
        return max(0, min(scroll, maxscroll))

    def handle_down(self):
        self.lock.acquire(blocking=True)
        if not self.active_tab_height:
            self.lock.release()
            return
        self.active_tab_scroll = self.clamp_scroll(
            self.active_tab_scroll + SCROLL_STEP)
        self.set_needs_raster_and_draw()
        self.needs_animation_frame = True
        self.lock.release()
```

이 코드는 새 스크롤 오프셋으로 화면을 다시 그리기 위해 `set_needs_raster_and_draw`를 호출하고, 메인 스레드가 앞으로 비동기적으로 스크롤 오프셋을 받도록 `needs_animation_frame`도 설정합니다. 브라우저 스레드가 이미 스크롤을 처리했더라도, 클릭 처리 같은 API가 그것에 의존하므로 새 값을 곧 메인 스레드에 동기화하는 것이 여전히 중요합니다.

사용자가 탭을 전환할 때도 스크롤 오프셋이 바뀌어야 하지만, 이 경우에는 아직 올바른 스크롤 오프셋을 알지 못합니다. 다른 탭의 새 디스플레이 리스트를 커밋하려면 메인 스레드가 실행되어야 하고, 그 시점에 새 스크롤 오프셋도 갖게 됩니다. (`load`와 `handle_click`의) 탭 전환을 그저 새 애니메이션 프레임을 예약하기만 하는 새 메서드 `set_active_tab`으로 옮기세요.[^30]

```python
class Browser:
    def set_active_tab(self, tab):
        self.active_tab = tab
        self.active_tab_scroll = 0
        self.active_tab_url = None
        self.needs_animation_frame = True
        self.animation_timer = None
```

지금까지는 브라우저 스레드의 스크롤 오프셋만 갱신하고 있습니다. 하지만 결국 메인 스레드도 스크롤 오프셋을 알아야 `commit`에 되돌려 줄 수 있습니다. 그러니 `Browser`가 `run_animation_frame`을 위한 렌더링 작업을 만들 때 스크롤 오프셋을 넘겨야 합니다. 그러면 `run_animation_frame` 함수가 다른 무엇을 하기 전에 그 스크롤 오프셋을 저장할 수 있습니다. `run_animation_frame`에 `scroll` 매개변수를 추가하세요.

```python
class Browser:
    def schedule_animation_frame(self):
        # ...
        def callback():
            self.lock.acquire(blocking=True)
            scroll = self.active_tab_scroll
            self.needs_animation_frame = False
            task = Task(self.active_tab.run_animation_frame, scroll)
            self.active_tab.task_runner.schedule_task(task)
            self.lock.release()
        # ...
```

하지만 메인 스레드도 스크롤 오프셋을 수정할 수 있어야 합니다. 메인 스레드가 그렇게 했는지 추적하는 `scroll_changed_in_tab` 플래그를 추가하고, `scroll_changed_in_tab`이 이미 참이 아닐 때만 브라우저 스레드의 스크롤 오프셋을 저장하겠습니다.[^31]

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.scroll_changed_in_tab = False

    def run_animation_frame(self, scroll):
        if not self.scroll_changed_in_tab:
            self.scroll = scroll
        # ...
```

새 페이지를 로드할 때나 브라우저 스레드의 스크롤 오프셋이 페이지 아래쪽을 넘어갔을 때 `scroll_changed_in_tab`을 설정하겠습니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.scroll = 0
        self.scroll_changed_in_tab = True

    def clamp_scroll(self, scroll):
        height = math.ceil(self.document.height + 2*VSTEP)
        maxscroll = height - self.tab_height
        return max(0, min(scroll, maxscroll))

    def run_animation_frame(self, scroll):
        # ...
        self.browser.commit(self, commit_data)
        self.scroll_changed_in_tab = False

    def render(self):
        # ...
        clamped_scroll = self.clamp_scroll(self.scroll)
        if clamped_scroll != self.scroll:
            self.scroll_changed_in_tab = True
        self.scroll = clamped_scroll
        # ...
```

메인 스레드가 브라우저의 스크롤 오프셋을 덮어쓰지 _않았다면_, 커밋 데이터에서 스크롤 오프셋을 `None`으로 설정하겠습니다.

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        scroll = None
        if self.scroll_changed_in_tab:
            scroll = self.scroll
        commit_data = CommitData(
            self.url, scroll, document_height, \
            self.display_list)
        # ...
```

이 경우 브라우저 스레드는 스크롤 오프셋을 무시할 수 있습니다.

```python
class Browser:
    def commit(self, tab, data):
        if tab == self.active_tab:
            # ...
            if data.scroll != None:
                self.active_tab_scroll = data.scroll
```

이것으로 끝입니다! 이제 카운팅 데모를 해 보면 인위적인 멈춤 중에도 스크롤할 수 있을 것입니다. [여기](https://browser.engineering/examples/example12-count-with-scroll.trace)에 스레드 기반 스크롤이 동작하는 트레이스가 있는데(래스터화와 그리기가 이제 때때로 메인 스레드 작업과 동시에 일어나는 것을 눈여겨보세요), 그림 4에 시각화되어 있습니다.

### 더 알아보기

실제 브라우저의 스크롤은 우리가 여기서 구현한 것보다 _훨씬_ 더 나아갑니다. 예를 들어 실제 브라우저에서 JavaScript는 [`scroll`](https://developer.mozilla.org/en-US/docs/Web/API/Document/scroll_event) 이벤트를 듣고 `preventDefault`를 호출해 스크롤을 취소할 수 있습니다. 그리고 [`background-attachment: fixed`](https://developer.mozilla.org/en-US/docs/Web/CSS/background-attachment) 같은 일부 렌더링 기능은 브라우저 스레드에서 구현하기 어렵습니다.[^32] 그래서 대부분의 실제 브라우저는 스레드 기반 스크롤과 비스레드 스크롤을 모두 구현하고, 이런 고급 기능이 사용되면 비스레드 스크롤로 되돌아갑니다.[^33] 이런 우려는 [새 JavaScript API](https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener#passive)를 이끌어 내기도 합니다.

## 스레드 기반 스타일과 레이아웃

이제 브라우저 스레드와 메인 스레드가 분리되었고 일부 연산이 브라우저 스레드에서 수행되므로, 우리 브라우저의 스레드 구조는 실제 브라우저의 그것을 닮기 시작했습니다.[^34] 그런데 왜 더 많은 브라우저 구성 요소를 더 많은 스레드로 옮기지 않을까요? 그러면 브라우저가 더 빨라지지 않을까요?

한마디로, 그렇습니다. 현대 브라우저에는 [수십 개의 스레드](https://developer.chrome.com/docs/chromium/renderingng-architecture#process_and_thread_structure)가 있고, 이들이 함께 브라우저를 더 빠르고 반응성 좋게 만들어 줍니다. 예를 들어 래스터화와 그리기는 종종 자신만의 스레드에서 실행되어, 새 프레임이 준비되는 동안에도 브라우저 스레드가 이벤트를 처리할 수 있게 합니다. 마찬가지로 현대 브라우저에는 보통 네트워크나 입출력(I/O) 스레드 모음이 있어서, 네트워크나 파일 시스템과의 모든 상호작용을 메인 스레드 밖으로 옮깁니다.

반면 브라우저의 어떤 부분들은 쉽게 스레드로 나눌 수 없습니다. 예를 들어 렌더링 파이프라인의 앞쪽 부분인 스타일, 레이아웃, 페인트를 생각해 봅시다. 우리 브라우저에서 이들은 메인 스레드에서 실행됩니다. 그런데 이들을 자신만의 스레드로 옮길 수 있을까요?

원칙적으로는 그렇습니다. 브라우저가 반드시 _해야_ 하는 유일한 일은 모든 웹 API 명세를 올바르게 구현하는 것, 그리고 스크립트와 `requestAnimationFrame` 콜백이 완료된 뒤 화면에 그리는 것입니다. 명세는 이를 "[렌더링 갱신하기(update-the-rendering)](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering)" 단계라고 부르며 자세히 설명합니다. 이 단계들은 스타일이나 레이아웃을 전혀 언급하지 않습니다. 스타일과 레이아웃은 페인트와 그리기와 마찬가지로 브라우저의 구현 세부 사항이기 때문입니다. 명세의 렌더링 갱신하기 단계는 화면에 그리기 전에 일어나야 하는, _JavaScript가 관찰 가능한_ 것들입니다.

그렇지만 실제로 현재 어떤 현대 브라우저도 스타일이나 레이아웃을 메인 스레드가 아닌 스레드에서 실행하지 않습니다.[^35] 이유는 간단합니다. 스타일이나 레이아웃 상태를 질의할 수 있는 JavaScript API가 많기 때문입니다. 예를 들어 [`getComputedStyle`](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle)은 먼저 스타일을 계산해야 하고, [`getBoundingClientRect`](https://developer.mozilla.org/en-US/docs/Web/API/Element/getBoundingClientRect)는 먼저 레이아웃을 해야 합니다.[^36] 웹 페이지가 이런 API 중 하나를 호출했는데 스타일이나 레이아웃이 최신이 아니라면, 그 자리에서 바로 계산해야 합니다. 이런 계산을 _강제 스타일_ 또는 _강제 레이아웃_ 이라고 합니다. 아직 계산되지 않았다면 어쩌면 33ms 뒤가 아니라 지금 당장 스타일이나 레이아웃이 일어나도록 "강제"되는 것입니다. 이런 강제 스타일·레이아웃 상황 때문에 브라우저는 메인 스레드에서 스타일과 레이아웃을 계산할 수 있어야 합니다.[^37]

이 긴장을 해소하는 한 가지 방법은, 웹 페이지가 스크롤에 `preventDefault`를 하지 않으면 스레드 기반 스크롤을 낙관적으로 수행하는 것과 비슷하게, 스타일과 레이아웃을 낙관적으로 메인 스레드 밖으로 옮기는 것입니다. 좋은 생각일까요? 어쩌면요. 하지만 강제 스타일과 레이아웃은 JavaScript 실행 때문에만 생기는 것이 아닙니다. 한 가지 예가 우리의 `click` 구현인데, 히트 테스팅에 앞서 강제 렌더링을 유발합니다.

```python
class Tab:
    def click(self, x, y):
        self.render()
        # ...
```

히트 테스팅을 메인 스레드 밖으로 옮기거나, 더 오래된 버전의 레이아웃 트리에 대해 히트 테스팅을 하거나, 다른 기술적 해법을 찾는 것이 가능하기는 합니다(다만 매우 어렵습니다). 그러니 스타일과 레이아웃을 "낙관적으로" 메인 스레드 밖으로 옮기는 것이 _불가능하지는_ 않지만 _어려운_ 것은 맞습니다. 그렇긴 해도 브라우저 개발자들은 언제나 더 빠르게 만들 방법을 찾고 있으므로, 저는 미래의 어느 시점에 스타일과 레이아웃이 자신만의 스레드로 옮겨지리라 예상합니다. 어쩌면 그 일을 할 사람이 여러분일지도 모릅니다.

### 더 알아보기

브라우저 렌더링 파이프라인은 그래픽과 게임의 영향을 강하게 받았습니다. 고성능 게임 상당수는 이벤트 루프로 구동되며, 이벤트마다 [장면 그래프(scene graph)](https://en.wikipedia.org/wiki/Scene_graph)를 갱신하고, 장면 그래프를 디스플레이 리스트로 변환한 다음, 디스플레이 리스트를 픽셀로 변환합니다. 하지만 게임에서는 프로그래머가 어떤 장면 그래프가 주어질지 _미리_ 알고 있어서 그래픽 파이프라인을 그 그래프에 맞게 조율할 수 있습니다. 게임은 시작할 때 고도로 최적화된 코드와 미리 렌더링된 데이터를 CPU와 GPU 메모리에 올려 둘 수 있습니다. 반면 브라우저는 임의의 웹 페이지를 처리해야 하고 무언가를 최적화하는 데 시간을 많이 쓸 수 없습니다. 이는 매우 다른 절충을 만들어 내며, 브라우저가 게임보다 덜 화려하고 덜 매끄럽게 느껴지는 이유이기도 합니다.

## 요약

이 장에서는 현대 브라우저의 핵심에 있는 두 스레드 렌더링 시스템을 살펴보았습니다. 기억해야 할 핵심은 다음과 같습니다.

- 브라우저는 일을 작업 큐로 정리하며, JavaScript 실행, 사용자 입력 처리, 페이지 렌더링 같은 작업들이 있습니다.

- 목표는 30Hz의 박자로 일관되게 프레임을 화면에 생성하는 것이며, 이는 각 애니메이션 프레임을 그리는 데 33ms 예산이 있다는 뜻입니다.

- 브라우저에는 렌더링에 관여하는 두 개의 핵심 스레드가 있습니다.

- 메인 스레드는 JavaScript와 특별한 렌더링 작업을 실행합니다.

- 브라우저 스레드는 디스플레이 리스트를 화면에 그리고, 입력 이벤트를 처리·디스패치하며, 스크롤을 수행합니다.

- 메인 스레드는 두 스레드를 동기화하는 `commit`을 통해 브라우저 스레드와 통신합니다.

또한 두 스레드 사이에서 작업을 옮기는 것이 얼마나 어려운지도 보았습니다. 브라우저 스레드에서 스크롤할 때의 어려움이나, 강제 스타일·레이아웃 때문에 렌더링 파이프라인을 JavaScript로부터 완전히 격리하기 어렵다는 점이 그렇습니다.

## 연습문제

**12-1 _`setInterval`_.** [`setInterval`](https://developer.mozilla.org/en-US/docs/Web/API/WindowOrWorkerGlobalScope/setInterval)은 `setTimeout`과 비슷하지만 [`clearInterval`](https://developer.mozilla.org/en-US/docs/Web/API/WindowOrWorkerGlobalScope/clearInterval)이 호출될 때까지 주어진 박자로 반복 실행됩니다. 이 API들을 구현하세요. 비용이 큰 렌더링 파이프라인 작업을 하는 `requestAnimationFrame`도 함께 쓰는 페이지에서 여러 박자로 `setInterval`을 반드시 테스트하세요. `setInterval` 작업의 실제 타이밍을 기록해 보세요. 박자가 얼마나 일정한가요?

**12-2 _작업 타이밍_.** 작업이 실행될 때마다 트레이스 이벤트를 추가하도록 `Task`를 수정하세요. 이 트레이스 이벤트에 좋은 이름을 붙이는 것이 좋습니다. 한 가지 방법은 `task_code`의 `__name__` 필드를 쓰는 것인데, 이는 작업이 실행하는 Python 함수의 이름을 알려 줍니다.

**12-3 _시계 기반 프레임 타이밍_.** 지금 우리 브라우저는 각 애니메이션 프레임을 이전 프레임이 완료된 뒤 정확히 33ms 후에 예약합니다. 이는 실제로 33ms보다 느린 애니메이션 프레임 박자로 이어집니다. 프레임 사이의 고정 지연 대신 절대 시각을 사용해 애니메이션 프레임을 예약함으로써 우리 브라우저에서 이를 고치세요. 또한 래스터화와 그리기 _뒤가_ 아니라 _앞에_ 일어나는 메인 스레드 애니메이션 프레임 예약도 구현해, 두 스레드가 동시에 애니메이션 작업을 할 수 있게 하세요.

**12-4 _스케줄링_.** 더 많은 종류의 복잡한 작업이 이벤트 큐에 들어오면서, 렌더링 박자를 최대한 33ms에 가깝게 유지하고 작업 기아(starvation)도 피하도록 작업을 신중하게 스케줄링할 필요가 커집니다. 이 두 요구를 균형 잡는 우선순위 체계를 가진 작업 스케줄러를 구현하세요. 렌더링 작업과 입력 처리에 우선순위를 주고, `setTimeout` 같은 JavaScript API에서 궁극적으로 비롯되는 작업의 우선순위는 낮추되 완전히 굶기지는 마세요. `setTimeout` 기반 작업을 잔뜩 만들어 시스템에 부담을 주는 웹 페이지에서 시험해 보세요.

**12-5 _스레드 기반 로딩_.** 페이지를 로드할 때 우리 브라우저는 현재 각 스타일 시트나 스크립트 자원이 차례로 로드되기를 기다립니다. 이는 불필요하게 느리며, 특히 네트워크가 나쁠 때 그렇습니다. 대신 브라우저가 모든 네트워크 요청을 병렬로 보내게 만드세요. 다만 스타일 같은 자원은 여전히 소스 순서대로 처리해야 합니다. `Thread`의 `join` 메서드가 편리할 수 있는데, 이 메서드는 `join`되는 스레드가 완료될 때까지 `join`을 호출한 스레드를 막습니다.

**12-6 _네트워킹 스레드_.** 실제 브라우저에는 보통 네트워킹(과 그 밖의 I/O)을 위한 별도의 스레드가 있습니다. 메인 스레드와 비슷한 방식으로 이 스레드에 작업이 추가됩니다. 세 번째 _네트워킹_ 스레드를 구현하고 모든 네트워킹 작업을 거기에 넣으세요.

**12-7 _최적화된 스케줄링_.** 복잡한 웹 페이지에서는 브라우저가 원하는 박자를 따라잡지 못할 수 있습니다. 헛되이 따라잡으려 애쓰며 CPU를 계속 붙잡고 있는 대신, 이전 프레임들을 바탕으로 브라우저의 실제 박자를 추정하는 _프레임 시간 추정기_ 를 구현하고 `schedule_animation_frame`을 그에 맞게 조정하세요. 이렇게 하면 복잡한 페이지는 무작위로 느려지는 대신 일관되게 느려집니다.

**12-8 _래스터·그리기 스레드_.** 지금은 브라우저 스레드가 래스터화하거나 그리는 중에 입력 이벤트가 도착하면 그 이벤트가 즉시 처리되지 않습니다. [래스터화와 그리기가 느리기](#렌더링-프로파일링) 때문에 이는 특히 문제입니다. 브라우저 스레드가 제어하는 별도의 래스터·그리기 스레드를 추가해 이를 고치세요. 래스터·그리기 스레드가 일하는 동안 브라우저 스레드는 입력 이벤트를 처리할 수 있어야 합니다. 조심하세요. SDL은 스레드 안전하지 않으므로, SDL을 직접 사용하는 모든 단계는 여전히 브라우저 스레드에서 일어나야 합니다.

[^19]: 여기서는 실제 브라우저가 흔히 쓰는 이름을 따르고 있습니다. (JavaScript가 때때로 [다른 스레드](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API)에서 실행될 수 있으므로) "DOM" 스레드가 더 나은 이름일 수도 있습니다.

[^20]: 왜 메인 스레드는 `TaskRunner`로 브라우저 스레드와 통신하지 않는지 궁금할 수 있습니다. 그렇게 할 수도 있습니다. 여기서는 한 방향으로만 하기로 했는데, JavaScript의 예측 불가능한 성격과 알 수 없는 DOM 크기 때문에 브라우저에서 메인 스레드가 일반적으로 "가장 느린" 스레드이기 때문입니다.

[^21]: 이 코드를 제거하고 관찰해 보세요. 타이머가 꽤 불규칙해질 것입니다.

[^22]: 경쟁 조건과 교착 상태를 피하면서 락을 쓰는 일은 꽤 어려울 수 있습니다!

[^23]: 왜 새 메서드 대신 `render`를 재사용하지 않을까요? `render` 메서드는 필요할 때 스타일, 레이아웃, 페인트를 갱신하는 것에 관한 것이기 때문입니다. `render`는 모든 프레임마다 호출되지만 `click`에서도 호출되며, 실제 브라우저에서는 다른 여러 곳에서도 호출됩니다. 반면 `run_animation_frame`은 프레임에 대해서만 호출되므로, `render`가 아니라 그것이 RAF 핸들러를 실행하고 `commit`을 호출합니다.

[^24]: 그래서 커밋은 병렬성과 반응성을 최대화하기 위해 최대한 빨라야 합니다. 현대 브라우저에서 커밋 최적화는 꽤 어려운데, 스레드 사이에 데이터를 캐시하고 보내는 방식이 훨씬 정교하기 때문입니다.

[^25]: 비활성 탭도 마지막 애니메이션 프레임 하나를 처리하고 있을 수 있기 때문입니다.

[^26]: 파이프라인 끝의 속도로 파이프라인 앞의 속도를 제어하는 기법을 _역압(back pressure)_ 이라고 합니다.

[^27]: 우리 브라우저는 탭을 닫을 수 없으므로, 트레이스가 `finish`될 때까지 모든 스레드가 남아 있다는 점에 주의하세요. 탭을 닫을 수 있다면 스레드 이름을 다소 다르게 처리해야 할 것입니다.

[^28]: 다만 이 경우 두 스레드가 작업을 동시에 실행하고 있지는 _않습니다_. 모든 JavaScript 작업이 브라우저 스레드가 예약하는 `requestAnimationFrame` 콜백이고, 그것들은 브라우저 스레드가 래스터화와 그리기 작업을 마친 뒤에야 시작되기 때문입니다. 연습문제 12-8이 그 문제를 다룹니다.

[^29]: 여러분의 컴퓨터에서 1초 정도 멈추도록 루프 상한을 조정하세요.

[^30]: 두 호출자 모두 이미 락을 잡고 있으므로 이 메서드는 락을 획득할 필요가 없다는 점에 주의하세요.

[^31]: 두 스레드 스크롤에는 예외 사례가 많은데, 이 장을 쓰면서 예상하지 못했던 것들도 있습니다. 예를 들어 로드는 스크롤을 0으로 강제해야 한다는 것이 꽤 분명하지만(브라우저가 뒤로 가기 이동에 대해 [스크롤 복원](https://developer.mozilla.org/en-US/docs/Web/API/History/scrollRestoration)을 구현하지 않는 한 말이죠!), 스크롤 제한(clamp) 뒤에 브라우저 스크롤이 일어나 그것을 다시 제한된 영역 안으로 되돌리는 경우는 어떨까요? 브라우저를 두 스레드로 나눔으로써 우리는 동시성과 분산 상태의 모든 어려움을 끌어들인 것입니다.

[^32]: 우리 브라우저는 이런 기능을 전혀 지원하지 않으므로 이런 어려움을 겪지 않습니다. 그것도 하나의 전략입니다. 예를 들어 2020년까지 Android의 Chromium 기반 브라우저는 `background-attachment: fixed`를 지원하지 않았습니다.

[^33]: 사실 실제 브라우저는 필요할 때만 비스레드 스크롤로 되돌아갑니다. 예를 들어 `scroll` 이벤트 리스너가 `preventDefault`를 호출할 때만 스레드 기반 스크롤을 끌 수도 있습니다.

[^34]: 이제 많은 브라우저가 브라우저 스레드와 메인 스레드의 일부를 서로 다른 프로세스에서 실행하는데, 이는 보안과 오류 처리에 이점이 있습니다.

[^35]: 어떤 브라우저는 스타일과 레이아웃 _안에서_ 여러 스레드를 사용합니다. [Servo](https://en.wikipedia.org/wiki/Servo_(software)) 연구용 브라우저가 이 분야의 선구자로, 완전히 병렬적인 스타일·레이아웃·페인트 단계를 시도했습니다. Servo의 일부 코드는 이제 Firefox의 일부입니다. 그렇지만 스타일이나 다른 단계가 내부적으로 스레드를 쓴다 해도, 그 단계들이 예를 들어 JavaScript 실행과 동시에 일어나지는 않습니다.

[^36]: 레이아웃보다 렌더링 파이프라인의 더 뒤쪽에 있는 것의 상태를 읽어 오게 해 주는 JavaScript API는 없으며, 그 덕분에 파이프라인의 뒤쪽 절반을 다른 스레드로 옮길 수 있었습니다.

[^37]: 아니면 메인 스레드가 브라우저 스레드에게 그 일을 강제할 수도 있겠지만 그것은 더 나쁩니다. 컴포지터 스레드에 일을 강제하면, 어떻게든 그것을 피하려고 훨씬 더 많은 일을 하지 않는 한 스크롤이 뚝뚝 끊기게 되기 때문입니다.
