## JavaScript 실행

현대 웹 브라우저의 상당 부분은 매우 높은 성능을 내는 JavaScript 구현체입니다. 오늘날 주요 브라우저는 모두 JavaScript를 실행하는 데 그치지 않고, 런타임 타입 분석을 이용해 실행 중에 저수준 기계어 코드로 컴파일합니다. 여기에 더해 히든 클래스(hidden class) 같은 기법으로 JavaScript가 명시적으로 제공하지 않는 구조를 추론해 내어 메모리 사용량과 가비지 컬렉션 부담을 낮춥니다. 그뿐만 아니라 현대 브라우저는 WebAssembly도 실행합니다. WebAssembly는 하드웨어에 독립적인 바이트코드 형식으로, 다른 여러 프로그래밍 언어가 컴파일 대상으로 삼을 수 있으며 언젠가는 웹에서 JavaScript와 대등한 위치에 오를지도 모릅니다.

이 책은 JavaScript 엔진을 직접 만드는 대신 DukPy를 사용합니다. 이렇게 선택한 이유는, JavaScript 실행이 현대 브라우저의 핵심이기는 하지만 그 기법이 Python, Lua, Java 같은 다른 언어의 실행 방식과 상당히 비슷하기 때문입니다. 현대 JavaScript 엔진의 내부를 배우는 가장 좋은 방법은 프로그래밍 언어 구현에 관한 책을 읽는 것입니다.

## 텍스트 및 그래픽 렌더링

텍스트 렌더링은 겉보기보다 훨씬 복잡합니다. 글자마다 너비와 높이가 다릅니다. 발음 구별 부호는 글자 위에 겹쳐 쌓아야 할 수도 있습니다. 합자(ligature)나 (필기체 폰트의) _셰이핑(shaping)_ 처럼, 글자가 다른 글자 옆에 놓이면 모양이 바뀌기도 합니다. 어떤 언어는 오른쪽에서 왼쪽으로, 또는 위에서 아래로 쓰입니다. 여기에 커닝(kerning)이나 변형자(variant) 같은 타이포그래피 기능도 있습니다. 그중에서도 가장 복잡한 것은 _힌팅(hinting)_ 인데, 이는 폰트 안에 내장된 작은 컴퓨터 프로그램으로 폰트를 이산적인 픽셀 격자에 더 잘 맞도록 수정합니다. 텍스트 렌더링은 물론 Skia에 영향을 주지만, 화면에서 콘텐츠의 크기와 위치를 결정하기 때문에 레이아웃에도 영향을 미칩니다.

더 넓게 보면 그래픽 전반이 상당히 복잡합니다! 우리 브라우저는 Skia를 사용하는데, 이는 Chromium을 비롯한 몇몇 브라우저가 실제로 사용하는 래스터화 엔진입니다. 하지만 우리는 Skia가 실제로 어떻게 동작하는지에 대해서는 거의 이야기하지 않았고, 실제로 그 내부는 꽤 복잡합니다. Skia는 텍스트를 렌더링할 뿐 아니라 사실상 모든 CPU와 GPU에서 온갖 종류의 블렌딩과 효과를 빠르고 높은 품질로 적용합니다. 실제 브라우저에서는 이것이 더욱 복잡해져서, 정교한 합성(compositing) 시스템, 그래픽 프로세스 보안 샌드박싱, 플랫폼별 폰트 및 OS 합성 통합 등이 얽힙니다. 게다가 [Canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API), [WebGL](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API), [WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API) 같은 저수준 JavaScript 노출 API를 구현하는 데도 엄청난 추가 노력이 들어갑니다.

이 주제를 책에서 건너뛴 이유는, (그래픽의) Skia나 (텍스트의) Harfbuzz 같은 라이브러리와 여러 시스템 라이브러리에 이미 고품질 구현이 제공되고 있어서 브라우저 고유의 영역이라고 보기 어렵기 때문입니다. 다만 여기에는 이 주제만 전문적으로 다루는 책이 필요할 만큼의 깊이가 있습니다.

## 연결 보안과 프라이버시

오늘날 웹 브라우저에는 AES-GCM, ChaCha20, HMAC-SHA512처럼 어리둥절한 이름을 가진 정교한 암호화 프로토콜 모음이 함께 탑재되어 있습니다. 이 프로토콜들은 네트워크 패킷을 읽거나 쓸 수 있는 악의적인 행위자로부터 사용자를 보호합니다. 가장 큰 틀에서 보면 연결 보안은 ([1장](https://browser.engineering/http.html)에 잠깐 등장했던) TLS 프로토콜을 통해 확립되며, 암호학자, 인증 기관, 오픈 소스 프로젝트로 이루어진 생태계에 의해 유지됩니다.

TLS에 대한 깊이 있는 논의를 건너뛰기로 한 이유는, 완전성과 검증에 대해 이 책이 취하는 다소 격식 없는 태도가 실제 보안 엔지니어링과는 양립할 수 없기 때문입니다. 최소한으로 축약된 불완전한 TLS는 곧 망가지고 안전하지 않은 TLS이며, 이는 원래 의도한 목표에 어긋날 뿐 아니라 교육적으로도 역효과를 냅니다. 현대 암호학과 네트워크 보안을 배우는 가장 좋은 방법은 그 주제를 다룬 책을 읽는 것입니다.

[웹에서의 프라이버시](https://developer.mozilla.org/en-US/docs/Web/Privacy) 역시 제가 건너뛴 중요한 주제입니다. 어떤 면에서 보안과 프라이버시는 서로 관련이 있고 (분명 서로를 보완하기도 하지만) 같은 것은 아닙니다. 그리고 웹에서의 프라이버시는 [서드파티 쿠키](https://developer.mozilla.org/en-US/docs/Web/HTTP/Cookies#third-party_cookies), [핑거프린팅](https://developer.mozilla.org/en-US/docs/Glossary/Fingerprinting), 광고를 지원하는 API가 있어야 하는지에 대한 논쟁처럼 여전히 유동적입니다. 이 주제를 건너뛴 이유는 기본 개념 상당수가 아직 정리되지 않았기 때문입니다. 프라이버시의 기준이 무엇인지, 그리고 그 안에서 정부, 브라우저 개발자, 웹사이트 제작자, 사용자가 각각 어떤 역할을 해야 하는지가 아직 합의되지 않았습니다.

## 네트워크 캐싱과 미디어

캐싱은 네트워크 요청 대부분을 아예 건너뛰게 만들어 속도를 높여 줍니다. 그런데 캐싱을 단순한 최적화 이상으로 만드는 것은, HTTP 자체가 캐싱을 가능하게 하도록 설계되어 있다는 점입니다. 네트워크 캐시를 구현해 보면 HTTP에 대한 이해가 크게 깊어집니다. 그렇지만 이 책의 네트워킹 부분은 이미 충분히 길고, 책을 쓰는 동안 캐시가 없어서 곤란했던 적도 없었기 때문에 이 주제는 빼기로 했습니다.

또한 오늘날 네트워크 대역폭과 배터리 수명의 대부분을 비디오 재생과 화상 회의가 차지하고 있기 때문에, 실시간 비디오 인코딩·디코딩·렌더링에는 어마어마한 복잡성의 세계가 펼쳐져 있습니다. 실제 브라우저에는 이런 서비스와 API에 전념하는 큰 팀이 있고, 전 세계의 많은 연구자가 비디오 압축을 연구합니다. 비디오 코덱은 매력적인 주제이지만 이 역시 브라우저 고유의 영역은 아니어서 이 책에서는 완전히 건너뛰었으니, 코덱을 다룬 전문 서적을 읽어 보시길 권합니다.

## 더 정교한 레이아웃 모드

실제 브라우저가 사용하는 레이아웃 알고리즘은 이 책에서 다룬 것보다 훨씬 정교해서, 플로팅 레이아웃, 위치 지정 요소, 플렉스 박스, 그리드, 테이블 등의 기능을 포함합니다. 이러한 레이아웃 모드를 구현하는 일은 복잡하며, 특히 속도와 증분 성능까지 얻고자 한다면 세심함과 정교함이 필요합니다. 여기서 중요한 기법으로는 다단계 레이아웃[^1]과 측정·배치(measure-layout) 단계가 있으며, 좋은 성능을 내려면 까다로운 캐싱 전략이 필수적입니다.

더 정교한 레이아웃을 이 책에서 건너뛴 이유는, 여기서 설명한 단순한 레이아웃 알고리즘조차 이미 상당히 복잡한 데다, 실제 레이아웃 알고리즘에는 오래된 표준과 하위 호환성에서 비롯된 우발적 복잡성이 많이 얽혀 있는데 그런 이야기를 길게 하고 싶지 않았기 때문입니다.

## 브라우저 UI와 개발자 도구

실제 브라우저는 우리 브라우저보다 _훨씬_ 더 복잡하고 강력한 "브라우저 UI"를 갖추고 있습니다. 여기서 브라우저 UI란 URL을 입력하고 탭을 확인하는 등, 웹 페이지를 둘러싼 크롬(chrome) 부분을 뜻합니다. 실제로 브라우저 팀 인력의 상당수는 "웹 플랫폼" 자체가 아니라 바로 이 부분에만 매달립니다. 또한 현대 브라우저의 다중 프로세스 구조 때문에 동기적인 OS API와 상호작용하기가 어려운데, 이는 [14장](https://browser.engineering/accessibility.html#the-accessibility-tree)에서 접근성을 다루며 살펴본 바 있습니다. 여기에 더해 (적어도 데스크톱) 많은 브라우저는 개발자가 브라우저 UI를 확장할 수 있게 해 주는 강력한 [확장 프로그램 API](https://en.wikipedia.org/wiki/Browser_extension)를 지원합니다. 이를 돕기 위해 브라우저 UI는 종종 HTML로 구현되어 브라우저 자신이 렌더링합니다.

또한 어떤 형태로든 디버깅 보조 도구가 없다면 복잡한 웹 앱을 만드는 것은 거의 불가능하기 때문에, 실제 브라우저에는 모두 디버거가 내장되어 있습니다. 믿기 어렵겠지만 꽤 오랜 기간 웹 개발자들은 그저 [console.log 디버깅](https://en.wikipedia.org/wiki/Debugging#printf_debugging)에 의존했습니다(콘솔을 쉽게 볼 방법이 없던 시절에는 alert 디버깅까지 했습니다!). [Firebug](https://en.wikipedia.org/wiki/Firebug_(software)) 같은 초창기 웹 디버거는 흑백에서 컬러로 넘어가는 것 같은 느낌을 주었습니다. 그리고 AJAX 요청 확인, JavaScript 코드 한 줄씩 실행하기, 요소 검사 같은 기능들이 여러 브라우저에서 각각 만들어졌고, 결국 오늘날의 통합 개발자 도구로 한데 모였습니다.

이 주제를 건너뛴 이유는, 브라우저 UI의 과제 상당수가 다른 UI의 과제와 다르지 않기 때문입니다. 디자인, 사용성, 복잡성 등이 그렇습니다. 그것만 다루면 지루한 책이 되었을 것입니다. 개념적으로 꽤 흥미로운 디버거조차도, 쓸 만하게 만들려면 상당한 양의 UI 작업이 뒷받침되어야만 비로소 유용해집니다. 아쉽게도 개발자 도구를 다룬 책은 제가 아는 바 없지만, 기본적인 사용자 인터페이스 개발을 다룬 책은 많습니다.

## 테스팅

실제 브라우저는 시간이 흘러도 품질을 유지하고 개선하기 위해 놀라울 만큼 인상적인 테스트 기법들을 발전시켜 왔습니다. 전체적으로 수십만 개에 달하는 [단위 테스트](https://en.wikipedia.org/wiki/Unit_testing)와 [통합 테스트](https://en.wikipedia.org/wiki/Integration_testing) 묶음을 갖추고 있습니다. 최근에는 견고한 [크로스 브라우저 테스트](https://wpt.fyi)에 많은 관심이 쏠리고 있는데, 이는 하나의 자동화된 테스트를 모든 브라우저에서 실행하여 동일한 입력에 대해 모두 동일하게 동작하는지 검증할 수 있게 해 줍니다. 또한 이제는 핵심 기능에 대해 브라우저들이 이 목표를 얼마나 잘 달성하고 있는지 측정하는 연례 [상호 운용성](https://wpt.fyi/interop-2023)[^2] 벤치마크도 있습니다. 테스팅의 이면에는 이러한 테스트를 지속적으로 효율적으로 실행하고 테스트를 쉽게 작성할 수 있도록 방대한 [프레임워크](https://web-platform-tests.org/)를 제공하는, 코드와 인프라의 또 다른 세계가 있습니다.

## 각주

[^1]: 이 책에서도 다단계 레이아웃을 조금은 사용합니다. 한 줄 안의 단어들에 대해 첫 번째 단계에서 `x`, `width`, `height`를 계산한 뒤, 별도의 단계에서 베이스라인을 기준으로 `y`를 계산하는 부분이 그렇습니다. 다만 이를 다단계 레이아웃의 예로 자세히 설명하지는 않았으며, 실제 브라우저는 훨씬 더 복잡한 레이아웃 단계들의 집합을 가지고 있습니다.
