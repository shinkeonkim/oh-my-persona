## 폼은 어떻게 동작하는가

HTML 폼에는 몇 가지 움직이는 부품이 있습니다.

첫째, HTML에는 `form` 요소가 있고 그 안에 `input` 요소[^1]가 들어가며, 이 `input` 요소는 사용자가 편집할 수 있습니다. 그래서 폼은 다음과 같이 작성될 수 있습니다(결과는 그림 1 참조).

```
<form action="/submit" method="post">
    <p>Name: <input name=name value=1></p>
    <p>Comment: <input name=comment value=2></p>
    <p><button>Submit!</button></p>
</form>
```

![그림 1: 우리 브라우저에 표시된 예제 폼.](forms-screenshot.png)

*그림 1: 우리 브라우저에 표시된 예제 폼.*

이 폼에는 `name`과 `comment`라는 두 개의 텍스트 입력 상자가 들어 있습니다. 사용자가 이 페이지에 오면 그 상자들을 클릭해 값을 편집할 수 있습니다. 그다음 폼 끝의 버튼을 클릭하면, 브라우저는 모든 이름–값 쌍을 모아 (`method` 속성이 지시하는 대로) HTTP `POST` 요청으로 묶어서, `form` 요소의 `action` 속성이 지정한 URL로 보냅니다. 상대 URL의 평소 규칙이 적용되므로 이 경우에는 `/submit`입니다. 그 `POST` 요청은 다음과 같은 모습입니다.

```
POST /submit HTTP/1.0
Host: example.org
Content-Length: 16

name=1&comment=2
```

다시 말해 이미 살펴본 보통의 `GET` 요청과 매우 비슷하되, 본문이 있다는 점만 다릅니다. 본문이 있는 HTTP 응답은 이미 보셨지만, 요청에도 본문이 있을 수 있습니다. `Content-Length` 헤더에 주목하세요. 이 헤더는 `POST` 요청에서 필수입니다. 서버는 평소처럼 웹 페이지로 이 요청에 응답하고, 브라우저는 늘 하던 일을 그대로 합니다.

폼을 구현하려면 HTTP `POST` 구현부터 `input` 요소를 그리는 새로운 레이아웃 객체, 버튼 클릭 처리에 이르기까지 브라우저의 여러 부분을 확장해야 합니다. 그래서 폼은 앞으로 몇 장에 걸친 우리의 목표, 즉 브라우저를 애플리케이션 플랫폼으로 바꾸는 일의 훌륭한 출발점이 됩니다. 자, 전부 구현해 봅시다!

### 더 알아보기

HTML 폼은 [HTML+](https://www.w3.org/MarkUp/htmlplus_paper/htmlplus.html)에서 처음 표준화되었는데, HTML+는 테이블, 수식, 이미지 주위를 감싸는 텍스트도 제안했습니다. 놀랍게도 이 세 기술 모두 살아남았지만 완전히 다른 표준에 담겼습니다. 테이블은 [RFC 1942](https://datatracker.ietf.org/doc/html/rfc1942)에, 수식은 [MathML](https://www.w3.org/Math/)에, 떠 있는 이미지는 [CSS 1.0](https://www.w3.org/TR/REC-CSS1/#floating-elements)에 말이죠.

## 위젯 렌더링하기

먼저 사용자가 입력할 입력 영역을 그려 봅시다.[^2] 입력 영역은 인라인 콘텐츠로, 텍스트 옆에 줄 단위로 배치됩니다. 그러니 입력을 지원하려면 새로운 종류의 레이아웃 객체가 필요한데, 이를 `InputLayout`이라고 부르겠습니다. `TextLayout`을 복사해 템플릿으로 쓰되 몇 가지를 빠르게 고쳐야 합니다.

첫째, `InputLayout`에는 `word` 인자가 없습니다.

```python
class InputLayout:
    def __init__(self, node, parent, previous):
        self.node = node
        self.children = []
        self.parent = parent
        self.previous = previous
```

둘째, `input` 요소는 보통 고정된 너비를 갖습니다.

```python
INPUT_WIDTH_PX = 200

class InputLayout:
    def layout(self):
        # ...
        self.width = INPUT_WIDTH_PX
        # ...
```

`input`과 `button` 요소는 사용자가 쉽게 찾을 수 있도록 시각적으로 구분되어야 합니다. 우리 브라우저의 스타일 지정 능력은 제한적이므로 배경색으로 그렇게 합시다.

```css
input {
    font-size: 16px; font-weight: normal; font-style: normal;
    background-color: lightblue;
}
button {
    font-size: 16px; font-weight: normal; font-style: normal;
    background-color: orange;
}
```

브라우저가 `InputLayout`을 페인트할 때는 배경을 그려야 합니다.

```python
class InputLayout:
    def paint(self):
        cmds = []
        bgcolor = self.node.style.get("background-color",
                                      "transparent")
        if bgcolor != "transparent":
            rect = DrawRect(self.self_rect(), bgcolor)
            cmds.append(rect)
        return cmds
```

그다음 입력 요소의 텍스트 내용을 가져와야 합니다.

```python
class InputLayout:
    def paint(self):
        # ...
        if self.node.tag == "input":
            text = self.node.attributes.get("value", "")
        elif self.node.tag == "button":
            if len(self.node.children) == 1 and \
               isinstance(self.node.children[0], Text):
                text = self.node.children[0].text
            else:
                print("Ignoring HTML contents inside button")
                text = ""
        # ...
```

`<button>` 요소는 원칙적으로 텍스트 노드뿐 아니라 복잡한 HTML도 담을 수 있다는 점에 주의하세요. 그것은 이 장에서 다루기에는 너무 복잡하므로, 그런 경우에는 브라우저가 경고를 출력하고 텍스트를 건너뛰게 하겠습니다.[^3] 마지막으로 그 텍스트를 그립니다.

```python
class InputLayout:
    def paint(self):
        # ...
        color = self.node.style["color"]
        cmds.append(
            DrawText(self.x, self.y, text, self.font, color))
        return cmds
```

책의 이 지점에 이르면 레이아웃 객체를 여러 번 보셨을 테니, 이런 변경은 간단히 넘어가겠습니다. 요점은 새로운 레이아웃 객체가 브라우저를 확장하는 흔한 방법 중 하나라는 것입니다.

이제 `InputLayout`을 몇 개 만들어야 하는데, 이는 `BlockLayout`에서 할 수 있습니다.

```python
class BlockLayout:
    def recurse(self, node):
        if isinstance(node, Text):
            # ...
        else:
            if node.tag == "br":
                self.new_line()
            elif node.tag == "input" or node.tag == "button":
                self.input(node)
            else:
                for child in node.children:
                    self.recurse(child)
```

마지막으로, 이 새로운 `input` 메서드는 `text` 메서드와 비슷하게 새 레이아웃 객체를 만들어 현재 줄에 추가합니다.[^4]

```python
class BlockLayout:
    def input(self, node):
        w = INPUT_WIDTH_PX
        if self.cursor_x + w > self.width:
            self.new_line()
        line = self.children[-1]
        previous_word = line.children[-1] if line.children else None
        input = InputLayout(node, line, previous_word)
        line.children.append(input)

        weight = node.style["font-weight"]
        style = node.style["font-style"]
        if style == "normal": style = "roman"
        size = int(float(node.style["font-size"][:-2]) * .75)
        font = get_font(size, weight, style)

        self.cursor_x += w + font.measure(" ")
```

그런데 사실 블록과 인라인 형제가 섞이는 문제를 우리가 해결하기로 한 방식([5장](https://browser.engineering/layout.html#layout-modes) 참조) 때문에 복잡한 점이 몇 가지 더 있습니다. 하나는 노드에 자식이 없으면 블록 요소라고 가정한다는 점입니다. 그런데 `<input>` 요소는 자식이 없지만 올바르게 그려지려면 반드시 인라인 레이아웃이어야 합니다. 마찬가지로 `<button>`은 자식이 있지만 그 자식들은 특별하게 처리됩니다.[^5]

"inline"을 반환하는 두 번째 조건을 추가하도록 `layout_mode`를 다음과 같이 바꾸면 이를 고칠 수 있습니다.

```python
class BlockLayout:
    def layout_mode(self):
        # ...
        elif self.node.children or self.node.tag == "input":
            return "inline"
        # ...
```

두 번째 문제는, 역시 블록 형제가 있는 탓에 때때로 `<input>`이나 `<button>` 요소가 `BlockLayout`을 만들고(그 안에 다시 `InputLayout`을 만들고) 만다는 것입니다. 이 경우 배경을 두 번 그리고 싶지 않으므로, 새로운 `should_paint` 메서드를 통해 `BlockLayout`에서 배경 그리기를 건너뛰는 간단한 로직을 추가합시다.[^6]

```python
class BlockLayout:
    # ...
    def should_paint(self):
        return isinstance(self.node, Text) or \
            (self.node.tag != "input" and self.node.tag !=  "button")
```

다른 모든 레이아웃 객체 타입에는 그냥 `True`를 반환하는 간단한 `should_paint` 메서드를 추가하세요. 이제 `should_paint`를 기준으로 객체 그리기를 건너뛸 수 있습니다.

```python
def paint_tree(layout_object, display_list):
    if layout_object.should_paint():
        display_list.extend(layout_object.paint())
    # ...
```

이 변경으로 브라우저는 이제 `input`과 `button` 요소를 파란색과 주황색 직사각형으로 그릴 것입니다.

### 더 알아보기

버튼은 내용을 감싸지만 입력 영역은 그렇지 않은 이유는, 버튼이 이미지, 스타일이 적용된 텍스트, 또는 다른 콘텐츠를 담을 수 있기 때문입니다. 실제 브라우저에서는 이것이 [`inline-block`](https://developer.mozilla.org/en-US/docs/Web/CSS/display) 디스플레이 모드에 의존합니다. 이는 블록 요소를 텍스트 줄 안에 넣는 방법입니다. 텍스트 입력에 더 가까운 옛 `<input type=button>` 문법도 있습니다.

## 위젯과 상호작용하기

`input` 요소가 렌더링되게 만들었지만 아직 그 내용을 편집할 수는 없습니다. 하지만 물론 그것이 핵심이죠! 그러니 `input` 요소가 주소창처럼 동작하게 만듭시다. 클릭하면 비워지고 거기에 입력할 수 있게 말이죠.

비우는 것은 쉽습니다. `Tab`의 `click` 메서드 안에 경우를 하나 더 추가하면 됩니다.

```python
class Tab:
    def click(self, x, y):
        while elt:
            # ...
            elif elt.tag == "input":
                elt.attributes["value"] = ""
            # ...
```

그런데 이것을 시험해 보면 클릭해도 `input` 요소가 실제로 비워지지 않는 것을 알게 됩니다. 위 코드가 HTML 트리를 갱신하기는 하지만, 변경이 화면에 나타나려면 레이아웃 트리를 갱신하고 그다음 디스플레이 리스트도 갱신해야 하기 때문입니다.

지금은 레이아웃 트리와 디스플레이 리스트가 `load`에서 계산되지만, 우리는 페이지 전체를 다시 로드하고 싶지는 않습니다. 그저 스타일 지정, 레이아웃, 페인트, 그리기 단계만 다시 하고 싶습니다. 이 단계들을 통틀어 _렌더링_ 이라고 합니다. 그러니 이 단계들을 `render`라는 새로운 `Tab` 메서드로 떼어 냅시다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.render()

    def render(self):
        style(self.nodes, sorted(self.rules, key=cascade_priority))
        self.document = DocumentLayout(self.nodes)
        self.document.layout()
        self.display_list = []
        paint_tree(self.document, self.display_list)
```

이 코드가 동작하려면 `load` 메서드의 지역 변수였던 `nodes`와 `rules`를 `Tab`의 새 필드로 바꿔야 합니다. 스타일 지정은 `load`에서 `render`로 옮겨졌지만 스타일 시트를 내려받는 일은 옮겨지지 않았다는 점에 주의하세요. 입력할 때마다 스타일 시트를 다시 내려받지는[^7] 않으니까요!

이제 `input` 요소를 클릭해 그 내용을 비울 때, `render`를 호출해 `input`이 비워진 상태로 페이지를 다시 그려야 합니다. 입력 요소 바깥을 클릭했을 때도 `render`를 호출해야 하는데, 그 과정에서 입력 요소의 포커스를 해제했을 수 있기 때문입니다.

```python
class Tab:
    def click(self, x, y):
        while elt:
            elif elt.tag == "input":
                elt.attributes["value"] = ""
                return self.render()
        self.render()
```

여기까지가 `input` 영역을 클릭하는 것입니다. 하지만 타이핑은 더 어렵습니다. [7장에서 주소창을 구현한 방식](https://browser.engineering/chrome.html)을 떠올려 보세요. 우리는 나중에 키 입력을 보낼 수 있도록 무엇을 클릭했는지 기억하는 `focus` 필드를 추가했습니다. 입력 영역에도 그런 `focus` 필드 같은 것이 필요하지만, 입력 영역은 `Browser`가 아니라 `Tab` 안에 있으므로 더 복잡해집니다.

당연히 각 `Tab`에 `focus` 필드가 필요합니다. 최근에 어떤 텍스트 입력란을 클릭했는지(클릭한 것이 있다면) 기억하기 위해서죠.

```python
class Tab:
    def __init__(self):
        # ...
        self.focus = None
```

이제 입력 요소를 클릭하면 `focus`를 설정해야 합니다(포커스할 것을 찾지 못했다면 포커스를 해제해야 합니다).

```python
class Tab:
    def click(self, x, y):
        self.focus = None
        # ...
        while elt:
            elif elt.tag == "input":
                self.focus = elt
                # ...
```

하지만 키보드 입력은 `Tab`이 아니라 `Browser`가 처리한다는 점을 기억하세요. 그렇다면 `Browser`는 키보드 이벤트를 언제 `Tab`으로 보내야 하는지 어떻게 알까요? `Browser`도 자신의 `focus` 필드에 그것을 기억해야 합니다!

다시 말해 웹 페이지를 클릭하면 `Browser`는 사용자가 브라우저 크롬이 아니라 페이지와 상호작용하고 있다는 것을 기억하도록 `focus` 필드를 갱신합니다. 그리고 그렇다면 브라우저 크롬의 포커스를 해제("블러")해야 합니다.

```python
class Chrome:
    def blur(self):
        self.focus = None
```

```python
class Browser:
    def handle_click(self, e):
        if e.y < self.chrome.bottom:
            self.focus = None
            # ...
        else:
            self.focus = "content"
            self.chrome.blur()
            # ...
        self.draw()
```

브라우저 크롬의 클릭에 해당하는 `if` 분기는 `focus`를 해제하는데, 이는 포커스가 더 이상 페이지 내용에 있지 않으며 따라서 키 입력이 `Chrome`으로 보내진다는 뜻입니다.

키 입력이 일어나면 `Browser`는 그것을 주소창으로 보내거나 활성 탭의 `keypress` 메서드를 호출합니다(아무것도 포커스되어 있지 않다면 둘 다 하지 않습니다).

```python
class Browser:
    def handle_key(self, e):
        # ...
        if self.chrome.keypress(e.char):
            self.draw()
        elif self.focus == "content":
            self.active_tab.keypress(e.char)
            self.draw()
```

여기서 브라우저 크롬이 키를 소비했다면 참을 반환하도록 `keypress`를 바꿨습니다.

```python
class Chrome:
    def keypress(self, char):
        if self.focus == "address bar":
            self.address_bar += char
            return True
        return False
```

그러면 그 `keypress` 메서드는 탭의 `focus` 필드를 사용해 해당 문자를 올바른 텍스트 입력란에 넣습니다.

```python
class Tab:
    def keypress(self, char):
        if self.focus:
            self.focus.attributes["value"] += char
            self.render()
```

여기서 `draw` 대신 `render`를 호출한다는 점에 주의하세요. 웹 페이지를 수정했으므로 단순히 화면에 다시 그리는 것이 아니라 디스플레이 리스트를 다시 생성해야 하기 때문입니다.

계층적 포커스 처리는 그래픽 위젯을 조합하는 데 중요한 패턴입니다. 웹 페이지가 `iframe`[^8]으로 서로 안에 내장될 수 있는 실제 브라우저에서는 포커스 트리가 임의로 깊어질 수 있습니다.

이제 `input` 요소에서 사용자 입력이 동작합니다. 다음으로 넘어가기 전에 마지막으로 손볼 것이 하나 있습니다. `Tab`의 `render` 메서드에서 텍스트 커서를 그리는 일입니다. 이는 생각보다 어려운 것으로 드러납니다. 커서는 포커스된 노드의 `InputLayout`이 그려야 하는데, 그 말은 각 노드가 자신이 포커스되었는지 여부를 알아야 한다는 뜻입니다.

```python
class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.is_focused = False
```

`Text` 노드에도 같은 필드를 추가하세요. `Text` 노드는 절대 포커스되지 않고 커서도 그리지 않지만, `Text`와 `Element`가 같은 필드를 갖는 편이 더 편리합니다. 이 값은 포커스를 입력 요소로 옮길 때 설정하겠습니다.

```python
class Tab:
    def click(self, x, y):
        if self.focus:
            self.focus.is_focused = False
        while elt:
            elif elt.tag == "input":
                elt.attributes["value"] = ""
                self.focus = elt
                elt.is_focused = True
                return self.render()
```

현재 포커스된 요소가 계속 커서를 그리지 않도록 그 요소의 포커스를 해제해야 한다는 점에 주의하세요. 어쨌든 이제 `input` 요소가 포커스되어 있으면 커서를 그릴 수 있습니다.

```python
class InputLayout:
    def paint(self):
        # ...
        if self.node.is_focused:
            cx = self.x + self.font.measure(text)
            cmds.append(DrawLine(
                cx, self.y, cx, self.y + self.height, "black", 1))
        # ...
```

이제 텍스트 입력란을 클릭하고, 거기에 입력하고, 그 값을 수정할 수 있습니다. 다음 단계는 이제 다 채워진 폼을 제출하는 것입니다.

### 더 알아보기

`InputLayout`이 텍스트 커서를 그리게 하는 이 접근 방식은 [11장](https://browser.engineering/visual-effects.html)에서 보게 되듯이 커서에 시각 효과를 적용할 수 있게 해 줍니다. 하지만 모든 브라우저가 이렇게 하는 것은 아닙니다. 예를 들어 Chrome은 커서가 [전역적으로 스타일링](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/editing/frame_caret.h?q=framecaret&ss=chromium)될 수 있도록 전역 [포커스된 요소](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/dom/document.h;l=881;drc=80def040657db16e79f59e7e3b27857014c0f58d)를 추적합니다.

## 폼 제출하기

폼은 `button`을 클릭해 제출합니다. 그러니 `click`의 커다란 `while` 루프에 조건을 하나 더 추가합시다.

```python
class Tab:
    def click(self, x, y):
        while elt:
            # ...
            elif elt.tag == "button":
                # ...
            # ...
```

버튼을 찾았으면 HTML 트리를 거슬러 올라가며 그 버튼이 속한 폼을 찾아야 합니다.

```python
elif elt.tag == "button":
    while elt:
        if elt.tag == "form" and "action" in elt.attributes:
            return self.submit_form(elt)
        elt = elt.parent
```

그러면 `submit_form` 메서드가 모든 입력 요소를 찾고, 올바른 방식으로 인코딩하고, `POST` 요청을 보내는 일을 맡습니다. 먼저 `form`의 모든 자손을 훑어 `input` 요소를 찾습니다.

```python
class Tab:
    def submit_form(self, elt):
        inputs = [node for node in tree_to_list(elt, [])
                  if isinstance(node, Element)
                  and node.tag == "input"
                  and "name" in node.attributes]
```

그 각각의 `input` 요소에 대해 `name` 속성과 `value` 속성을 뽑아내고 둘 다 _폼 인코딩_ 해야 합니다. 폼 인코딩은 HTTP `POST` 요청에서 이름–값 쌍이 형식화되는 방식입니다. 기본적으로는 이렇습니다. 이름, 그다음 등호, 그다음 값. 그리고 이름–값 쌍들은 앰퍼샌드로 구분됩니다.

```python
class Tab:
    def submit_form(self, elt):
        # ...
        body = ""
        for input in inputs:
            name = input.attributes["name"]
            value = input.attributes.get("value", "")
            body += "&" + name + "=" + value
        body = body[1:]
```

여기서 `body`는 처음에 앞쪽에 `&`가 하나 더 붙어 있는데, 마지막 줄에서 그것을 제거합니다.

자, 이런 특별한 문법을 볼 때마다 물어야 합니다. 이름이나 값 안에 등호나 앰퍼샌드가 들어 있으면 어떻게 될까요? 그래서 실제로 "퍼센트 인코딩"은 모든 특수 문자를 퍼센트 기호와 그 문자의 16진 코드로 대체합니다. 예를 들어 공백은 `%20`이 되고 마침표는 `%2e`가 됩니다. Python은 `urllib.parse` 모듈의 `quote`로 퍼센트 인코딩 함수를 제공합니다.[^9]

```python
for input in inputs:
    # ...
    name = urllib.parse.quote(name)
    value = urllib.parse.quote(value)
    # ...
```

이제 `submit_form`이 요청 본문을 만들었으니 `POST` 요청을 해야 합니다. 이 책임은 요청을 처리하는 `load` 함수에 넘기겠습니다.

```python
def submit_form(self, elt):
    # ...
    url = self.url.resolve(elt.attributes["action"])
    self.load(url, body)
```

`load`의 새로운 `payload` 인자는 그다음 `request`로 전달됩니다.

```python
def load(self, url, payload=None):
    # ...
    body = url.request(payload)
    # ...
```

`request`에서는 이 새 인자를 사용해 `GET` 요청과 `POST` 요청 중 무엇을 할지 결정합니다.

```python
class URL:
    def request(self, payload=None):
        # ...
        method = "POST" if payload else "GET"
        # ...
        request = "{} {} HTTP/1.0\r\n".format(method, self.path)
        # ...
```

`POST` 요청이라면 `Content-Length` 헤더가 필수입니다.

```python
class URL:
    def request(self, payload=None):
        # ...
        if payload:
            length = len(payload.encode("utf8"))
            request += "Content-Length: {}\r\n".format(length)
        # ...
```

`Content-Length`는 페이로드의 바이트 길이이며, 이는 글자 수와 같지 않을 수 있다는 점에 주의하세요.[^10] 마지막으로 헤더 다음에 페이로드 자체를 보냅니다.

```python
class URL:
    def request(self, payload=None):
        # ...
        if payload: request += payload
        s.send(request.encode("utf8"))
        # ...
```

이것이 `POST` 요청이 전송되는 방식입니다. 그러면 서버는 HTML 페이지로 응답하고 브라우저는 완전히 평소대로 그것을 렌더링합니다.[^11] 폼에 대해서는 기본적으로 이것이 전부입니다!

### 더 알아보기

대부분의 폼 제출은 여기서 설명한 폼 인코딩을 사용하지만, (`<input type=file>`을 사용하는) 파일 업로드가 있는 폼은 각 키–값 쌍에 대한 (파일 이름이나 파일 타입 같은) 메타데이터를 포함하는 [다른 인코딩](https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods/POST)을 사용합니다. 잘 알려지지 않은 [`text/plain` 인코딩](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#text/plain-encoding-algorithm) 옵션도 있는데, 이는 이스케이프를 전혀 하지 않아서 표준조차 사용을 권하지 않습니다.

## 웹 앱은 어떻게 동작하는가

그렇다면… 웹 애플리케이션(웹 앱)은 폼을 어떻게 사용할까요? 브라우저에서 애플리케이션을 사용할 때, 유권자 등록을 하든 사촌 아기 사진을 보든 이메일을 확인하든, 보통[^12] 두 개의 프로그램이 관여합니다. 브라우저에서 실행되는 클라이언트 코드와 서버에서 실행되는 서버 코드입니다. 애플리케이션에서 무언가를 클릭하거나 어떤 동작을 하면 클라이언트 코드가 실행되고, 그 코드가 HTTP 요청을 통해 서버로 데이터를 보냅니다.

예를 들어 간단한 게시판 애플리케이션을 상상해 봅시다. 서버는 게시판의 상태, 즉 누가 무엇을 올렸는지를 저장하고 그 상태를 갱신하는 로직을 갖고 있습니다. 하지만 페이지와의 실제 상호작용, 즉 글을 그리고 사용자가 새 글을 입력하게 하는 일은 모두 브라우저에서 일어납니다. 두 구성 요소 모두 필요합니다.

브라우저와 서버는 HTTP로 상호작용합니다. 브라우저는 먼저 현재 게시판을 로드하기 위해 서버에 `GET` 요청을 합니다. 사용자는 브라우저와 상호작용해 새 글을 입력하고 (예를 들어 폼을 통해) 서버에 제출합니다. 그러면 브라우저는 서버에 `POST` 요청을 하고, 이는 서버에게 게시판 상태를 갱신하라고 지시합니다. 그다음 서버는 사용자가 보는 것을 브라우저가 갱신하게 해야 합니다. 폼의 경우 서버는 `POST` 요청에 대한 응답으로 새 HTML 페이지를 보냅니다. 이 과정이 그림 2에 나와 있습니다.

![그림 2: 다중 페이지 애플리케이션의 요청과 응답 주기.](forms-mpa-2.gif)

*그림 2: 다중 페이지 애플리케이션의 요청과 응답 주기.*

폼은 이 요청–응답 주기에 대한 단순하고 최소한의 소개이며, 브라우저 애플리케이션이 어떻게 동작하는지 알아보는 좋은 입문입니다. 폼은 모든 브라우저에 구현되어 있고 수십 년간 존재해 왔습니다. 요즘 많은 웹 애플리케이션은 폼 요소를 사용하되 동기적인 `POST` 요청을 JavaScript가 주도하는 비동기 요청으로 대체합니다.[^13] 이렇게 하면 HTTP 요청에 걸리는 시간을 감춰서 애플리케이션이 더 빠릿하게 느껴집니다. 그 빠릿함의 대가로 그 JavaScript 코드가 이제 오류를 처리하고, 입력을 검증하고, 로딩 시간을 표시해야 합니다. 어느 쪽이든 폼의 동기적 사용과 비동기적 사용 모두 클라이언트 코드와 서버 코드라는 같은 원리에 기반합니다.

### 더 알아보기

`GET`과 `POST` 외에도 [`PUT`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods/PUT)(없으면 생성), [`DELETE`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods/DELETE), 그리고 덜 알려진 `CONNECT`와 `TRACE` 같은 요청 타입이 있습니다. 2010년에는 [`PATCH` 메서드](https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods/PATCH)가 [RFC 5789](https://datatracker.ietf.org/doc/html/rfc5789)에 표준화되었습니다. 새 메서드는 HTTP의 표준 확장 메커니즘으로 의도되었고 일부 프로토콜은 이런 방식으로 만들어졌지만([WebDav](https://en.wikipedia.org/wiki/WebDAV)의 `PROPFIND`, `MOVE`, `LOCK` 메서드처럼), 이것이 웹 자체를 확장하는 지속적인 방법이 되지는 못했고 HTTP 2.0과 3.0은 새 메서드를 전혀 추가하지 않았습니다.

## POST 요청 받기

요청/응답 주기를 더 잘 이해하기 위해 간단한 웹 서버를 작성해 봅시다. 이 서버는 온라인 방명록[^14]을 구현할 것인데, 일종의 열린 익명 댓글 스레드 같은 것입니다. 이 책은 웹 _브라우저_ 공학에 관한 책이므로 웹 서버 구현을 그렇게 깊이 다루지는 않겠습니다. 다만 애플리케이션의 서버 쪽이 어떻게 동작하는지는 보여 드리고 싶습니다.

웹 서버는 웹 브라우저와는 별개의 프로그램이므로 새 파일을 시작합시다. 서버가 해야 할 일은 다음과 같습니다.

- 소켓을 열고 연결을 기다립니다.

- 받은 HTTP 요청을 파싱합니다.

- 그 요청에 HTML 웹 페이지로 응답합니다.

소켓을 여는 것부터 시작합시다. 브라우저에서와 마찬가지로 TCP를 사용해 인터넷 스트리밍 소켓을 만들어야 합니다.

```python
import socket
s = socket.socket(
    family=socket.AF_INET,
    type=socket.SOCK_STREAM,
    proto=socket.IPPROTO_TCP)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
```

`setsockopt` 호출은 선택 사항입니다. 보통 어떤 프로그램이 소켓을 열어 둔 채 죽으면, OS는 짧은 기간 동안 그 포트를 재사용하지 못하게 막습니다.[^15] 서버를 개발할 때는 이것이 성가시죠. `SO_REUSEADDR` 옵션과 함께 `setsockopt`를 호출하면 OS가 그 포트를 즉시 재사용할 수 있게 됩니다.

이제 이 소켓으로 (다른 서버에 연결하기 위한) `connect`를 호출하는 대신, 다른 컴퓨터가 연결해 오기를 기다리는 `bind`를 호출하겠습니다.

```python
s.bind(('', 8000))
s.listen()
```

먼저 `bind` 호출을 봅시다. 첫 번째 인자는 누가 이 서버_에_ 연결할 수 있는지를 지정합니다. 빈 문자열은 누구나 연결할 수 있다는 뜻입니다. 두 번째 인자는 다른 컴퓨터가 우리 서버와 통신할 때 사용해야 하는 포트인데, 저는 `8000`을 골랐습니다. 1024 미만의 포트는 관리자 권한이 필요하므로 80은 쓸 수 없지만, 어떤 이유로든 여러분 컴퓨터에서 8000번 포트가 이미 사용 중이라면 다른 것을 골라도 됩니다.

마지막으로 `bind` 호출 뒤의 `listen` 호출은 우리가 연결을 받을 준비가 되었다고 OS에 알려 줍니다.

실제로 그 연결들을 받기 위해, 연결마다 한 번씩 도는 루프에 들어갑니다. 루프 맨 위에서 새 연결을 기다리기 위해 `s.accept`를 호출합니다.

```python
while True:
    conx, addr = s.accept()
    handle_connection(conx)
```

혼란스럽게도 그 연결 객체 역시 소켓입니다. 그 하나의 연결에 해당하는 소켓이죠. 소켓으로 무엇을 해야 하는지는 알고 있습니다. 내용을 읽고 HTTP 메시지를 파싱하면 됩니다. 하지만 서버에서는 브라우저에서보다 조금 까다롭습니다. 서버는 연결이 닫힐 때까지 소켓에서 그냥 읽을 수가 없기 때문입니다. 브라우저는 서버를 기다리고 있어서 연결을 닫지 않으니까요.

그래서 소켓에서 한 줄씩 읽어야 합니다. 먼저 요청 줄을 읽습니다.

```python
def handle_connection(conx):
    req = conx.makefile("b")
    reqline = req.readline().decode('utf8')
    method, url, version = reqline.split(" ", 2)
    assert method in ["GET", "POST"]
```

그다음 빈 줄에 도달할 때까지 헤더를 읽으면서 딕셔너리에 모읍니다.

```python
def handle_connection(conx):
    # ...
    headers = {}
    while True:
        line = req.readline().decode('utf8')
        if line == '\r\n': break
        header, value = line.split(":", 1)
        headers[header.casefold()] = value.strip()
```

마지막으로 본문을 읽는데, `Content-Length` 헤더가 얼마나 읽어야 하는지 알려 줄 때만 읽습니다(그래서 그 헤더가 `POST` 요청에서 필수인 것입니다).

```python
def handle_connection(conx):
    # ...
    if 'content-length' in headers:
        length = int(headers['content-length'])
        body = req.read(length).decode('utf8')
    else:
        body = None
```

이제 서버는 응답으로 웹 페이지를 생성해야 합니다. 그 부분은 나중에 다루고, 지금은 `do_request` 호출 뒤로 추상화해 둡시다.

```python
def handle_connection(conx):
    # ...
    status, body = do_request(method, url, headers, body)
```

그러면 서버는 이 페이지를 브라우저로 되돌려 보냅니다.

```python
def handle_connection(conx):
    # ...
    response = "HTTP/1.0 {}\r\n".format(status)
    response += "Content-Length: {}\r\n".format(
        len(body.encode("utf8")))
    response += "\r\n" + body
    conx.send(response.encode('utf8'))
    conx.close()
```

전체 구조는 그림 3에 정리되어 있습니다. 우리 구현은 모두 꽤 뼈대뿐입니다. 우리 서버는 브라우저가 HTTP 1.0으로 말하고 있는지 확인하지 않고, `Content-Length` 말고는 어떤 헤더도 돌려보내지 않으며, TLS를 지원하지도 않습니다. 다시 말하지만, 이 책은 웹 _브라우저_ 책입니다. 이 정도면 충분합니다.

## 웹 페이지 생성하기

지금까지의 서버 코드는 모두 "상용구"입니다. 어떤 웹 애플리케이션이든 비슷한 코드를 갖게 됩니다. 반면 우리 서버를 방명록으로 만들어 주는 것은 `do_request` 안에서 일어나는 일입니다. 이 함수는 방명록 상태를 저장하고, HTML 페이지를 생성하고, `POST` 요청에 응답해야 합니다.

방명록 항목은 Python 리스트에 저장합시다. 보통 웹 애플리케이션은 서버를 재시작해도 상태를 잃지 않도록 데이터베이스 같은 _영속적인_ 상태를 사용하지만, 우리 방명록이 그 정도로 견고할 필요는 없습니다.

```python
ENTRIES = [ 'Pavel was here' ]
```

다음으로 `do_request`는 그 항목들을 보여 주는 HTML을 출력해야 합니다.

```python
def do_request(method, url, headers, body):
    out = "<!doctype html>"
    for entry in ENTRIES:
        out += "<p>" + entry + "</p>"
    return "200 OK", out
```

이것은 확실히 "최소한의" HTML이니, 우리 브라우저가 암묵적 태그를 넣어 주고 기본 스타일도 갖고 있다는 게 다행입니다! 이 최소한의 웹 서버를 실행하고, 실행 중인 상태에서 브라우저를 `http://localhost:8000/`으로 보내 시험해 볼 수 있습니다. 여기서 `localhost`는 여러분 컴퓨터가 자기 자신을 부르는 이름이고 `8000`은 앞서 고른 포트입니다. 방명록 항목 하나가 보여야 합니다.

그런데 이 웹 서버를 디버깅하는 동안에는 이 책의 브라우저 대신 실제 웹 브라우저로 상호작용하는 편이 아마 나을 것입니다. 그래야 서버 버그를 다루는 동안 브라우저 버그를 걱정하지 않아도 되니까요. 하지만 이 서버는 실제 브라우저와 장난감 브라우저 모두를 지원합니다.

방문자가 방명록에 글을 쓸 수 있도록 폼을 사용하겠습니다.

```python
def do_request(method, url, headers, body):
    # ...
    out += "<form action=add method=post>"
    out +=   "<p><input name=guest></p>"
    out +=   "<p><button>Sign the book!</button></p>"
    out += "</form>"
    # ...
```

이 폼이 제출되면 브라우저는 `http://localhost:8000/add`로 `POST` 요청을 보냅니다. 그러니 서버는 이 제출에 반응해야 합니다. 즉 `do_request`가 두 종류의 요청, 일반 브라우징과 폼 제출을 처리하게 됩니다. 이 두 종류의 요청을 서로 다른 함수로 분리합시다.

먼저 현재의 `do_request`를 `show_comments`로 이름을 바꿉니다.

```python
def show_comments():
    # ...
    return out
```

그러면 `do_request` 함수는 어떤 요청에 어떤 함수를 호출할지 결정하는 역할을 맡게 됩니다.

```python
def do_request(method, url, headers, body):
    if method == "GET" and url == "/":
        return "200 OK", show_comments()
    elif method == "POST" and url == "/add":
        params = form_decode(body)
        return "200 OK", add_entry(params)
    else:
        return "404 Not Found", not_found(url, method)
```

`/add`로 `POST` 요청이 들어오면 첫 단계는 요청 본문을 디코딩하는 것입니다.

```python
def form_decode(body):
    params = {}
    for field in body.split("&"):
        name, value = field.split("=", 1)
        name = urllib.parse.unquote_plus(name)
        value = urllib.parse.unquote_plus(value)
        params[name] = value
    return params
```

여기서 `unquote` 대신 `unquote_plus`를 사용한다는 점에 주의하세요. 브라우저는 공백을 인코딩하는 데 플러스 기호를 쓸 수도 있기 때문입니다. 그러면 `add_entry` 함수는 `guest` 매개변수를 찾아 그 내용을 새 방명록 항목으로 추가합니다.

```python
def add_entry(params):
    if 'guest' in params:
        ENTRIES.append(params['guest'])
    return show_comments()
```

"404" 응답도 추가했습니다. 우리 방명록의 소박한 스타일에 맞춰, 404 페이지는 다음과 같습니다.

```python
def not_found(url, method):
    out = "<!doctype html>"
    out += "<h1>{} {} not found!</h1>".format(method, url)
    return out
```

시험해 보세요! 서버를 재시작하고, 브라우저에서 열고, 방명록을 몇 번 갱신할 수 있어야 합니다. 실제 웹 브라우저에서도 방명록을 사용할 수 있어야 합니다.

## 연습문제

**8-1 _Enter 키_.** 대부분의 브라우저에서는 텍스트 입력란 안에 있을 때 "Enter" 또는 "Return" 키를 누르면 그 입력란이 속한 폼이 제출됩니다. 이 기능을 여러분의 브라우저에 추가하세요.

**8-2 _`GET` 폼_.** 폼은 `POST` 요청뿐 아니라 `GET` 요청으로도 제출할 수 있습니다. `GET` 요청에서는 폼 인코딩된 데이터가 URL 끝에 붙고 물음표로 경로와 구분됩니다. `/search?q=hi`처럼요. `GET` 폼 제출에는 본문이 없습니다. `GET` 폼 제출을 구현하세요.

**8-3 _블러_.** 지금은 텍스트 입력란 안을 클릭한 다음 주소창 안을 클릭하면 화면에 커서가 두 개 나타납니다. 이를 고치기 위해 각 `Tab`에 포커스된 모든 것의 포커스를 해제하는 `blur` 메서드를 추가하고, 포커스를 바꾸기 전에 그 메서드를 호출하세요.

**8-4 _체크박스_.** HTML에서 `input` 요소는 `type` 속성을 가집니다. `checkbox`로 설정되면 `input` 요소는 체크박스처럼 보입니다. `checked` 속성이 설정되어 있으면 체크된 상태이고, 그렇지 않으면 체크되지 않은 상태입니다.[^16] 폼이 제출될 때 체크박스의 `name=value` 쌍은 체크되어 있을 때만 포함됩니다. (체크박스에 `value` 속성이 없으면 기본값은 문자열 `on`입니다.)

**8-5 _요청 재전송_.** `GET`과 `POST` 요청을 구분하는 이유 중 하나는, `GET` 요청은 _멱등적_(기본적으로 읽기 전용)이어야 하는 반면 `POST` 요청은 웹 서버 상태를 바꾼다고 가정되기 때문입니다. 즉 `GET` 요청으로 "뒤로" 가는 것(요청을 다시 하는 것)은 안전하지만, `POST` 요청으로 "뒤로" 가는 것은 나쁜 생각입니다. 각 URL에 접근할 때 어떤 메서드를 사용했는지, 그리고 `POST` 본문이 있었다면 그 본문도 기록하도록 브라우저 방문 기록을 바꾸세요. `POST`로 요청했던 URL로 뒤로 갈 때는 사용자에게 폼을 다시 제출할지 물어보세요. 아니라고 하면 뒤로 가지 말고, 그렇다고 하면 이전과 같은 본문으로 `POST` 요청을 보내세요.

**8-6 _게시판_.** 지금 우리 웹 서버는 단순한 방명록입니다. 주제(topic) 지원을 추가해 간단한 게시판으로 확장하세요. 각 주제는 자신만의 URL과 자신만의 메시지 목록을 가져야 합니다. 예를 들어 `/cooking`은 (요리에 관한) 글들의 페이지여야 하고, 그 페이지의 폼을 통해 제출된 댓글은 `/cars`가 아니라 `/cooking`에 갔을 때만 보여야 합니다. `/`의 홈페이지에서는 사용 가능한 주제 목록과 각 주제 페이지로 가는 링크를 보여 주세요. 사용자가 새 주제를 추가할 수 있게도 만드세요.

**8-7 _영속성_.** 서버의 방명록 항목 목록을 파일로 뒷받침해서, 서버를 재시작해도 데이터를 잃지 않게 만드세요.

**8-8 _풍부한 버튼_.** 버튼이 임의의 요소를 자식으로 담을 수 있게 하고 올바르게 렌더링하세요. 자식들은 밖으로 흘러나오지 않고 버튼 안에 담겨야 합니다. 그러면 버튼이 아주 커질 수도 있습니다. 다른 버튼이나 입력 영역이나 링크를 담은 버튼 같은 예외 사례들을 생각해 보고, 실제 브라우저가 어떻게 하는지 시험해 보세요.

**8-9 _HTML 크롬_.** 실제 브라우저에서 브라우저 크롬은 폰트 크기, 여백, 외곽선, 그림자, 아이콘 등 까다로운 세부 사항으로 꽤 복잡합니다. 그래서 우리 레이아웃 엔진을 그대로 재사용하고 싶어집니다. 새 탭 버튼과 뒤로 가기 버튼에는 `<button>` 요소를, 주소창에는 `<input>` 요소를, 탭 이름에는 `<a>` 요소를 사용해 이를 구현하세요. 현재 크롬과 정확히 똑같아 보이지는 않겠지만(예를 들어 외곽선은 [14장](https://browser.engineering/accessibility.html)까지 기다려야 합니다), 기본 CSS를 조정하면 그럭저럭 봐 줄 만하게 만들 수 있을 것입니다.[^17]

## 각주

[^1]: `select`나 `textarea`처럼 `input`과 비슷한 다른 요소들도 있습니다. 동작 방식은 충분히 비슷하며, 드롭다운이나 여러 줄 입력처럼 서로 다른 종류의 사용자 컨트롤을 나타낼 뿐입니다.

[^2]: 대부분의 애플리케이션은 입력 영역이 그 OS의 다른 애플리케이션과 비슷해 보이도록 OS 라이브러리를 사용해 입력 영역을 그립니다. 하지만 브라우저는 애플리케이션 스타일 지정에 대한 통제권이 많이 필요하므로, 흔히 자신만의 입력 영역을 직접 그립니다.

[^3]: 연습문제 8-8을 보세요.

[^4]: 사실 너무 비슷해서 `w`를 계산하는 방식만 다릅니다. [15장](https://browser.engineering/embeds.html)에 이를 때까지는 이 코드를 리팩터링하고 싶은 유혹을 참겠습니다.

[^5]: 이 상황은 우리 브라우저에서 이 요소들에만 해당하는데, 이는 인라인 맥락 안에서 특별한 페인팅 동작을 가진 유일한 요소들이기 때문입니다. 이 둘은 [원자적 인라인(atomic inline)](https://www.w3.org/TR/CSS2/visuren.html#inline-boxes)의 예이기도 합니다.

[^6]: ([5장](https://browser.engineering/layout.html#block-layout) 참조) 익명 블록 박스의 존재 때문에만 이런 상황에 빠진다는 점을 떠올려 보세요. 또한 우리 브라우저가 인라인 페인팅의 모든 복잡함을 완전히 구현하지 않는 다른 여러 방식이 있다는 점도 짚어 둘 만합니다. 한 예로, 배경색이 서로 다른 중첩 인라인을 올바르게 페인트하지 못합니다. 실제 브라우저에서 인라인 레이아웃과 페인트는 매우 복잡합니다.

[^7]: 사실 웹 페이지에 대한 어떤 변경은 기존 `link` 노드를 삭제하거나 새로 만들 수 있습니다. 실제 브라우저는 이에 올바르게 반응해서, 삭제된 `link` 노드에 해당하는 규칙을 제거하거나 새 `link` 노드가 만들어지면 새 스타일 시트를 내려받습니다. 이를 제대로 하기는 까다롭고, 입력 영역에 타이핑하는 것으로는 그런 변경이 절대 생길 수 없으니 우리 브라우저에서는 건너뛰겠습니다.

[^8]: `iframe` 요소는 한 웹 페이지를 다른 웹 페이지 안에 작은 창처럼 내장할 수 있게 해 줍니다. [15장](https://browser.engineering/embeds.html)에서 더 이야기하겠습니다.

[^9]: 원한다면 Python의 `ord`와 `hex` 함수를 사용해 직접 `percent_encode` 함수를 작성할 수도 있습니다. 저는 편의를 위해 표준 함수를 쓰고 있습니다. [1장](https://browser.engineering/http.html)에서라면 이런 라이브러리 함수를 쓰는 것이 핵심 개념을 가렸겠지만, 이 시점에서 퍼센트 인코딩은 필요하기는 해도 개념적으로 흥미롭지는 않습니다.

[^10]: 많은 언어의 문자가 여러 바이트를 차지하기 때문입니다.

[^11]: 사실 브라우저는 `POST`로 요청한 페이지로 "뒤로" 가는 것을 특별하게 취급하므로(연습문제 8-5 참조), `POST` 요청에 리다이렉트로 응답하는 것이 흔합니다.

[^12]: 여기서는 일반적인 이야기를 하고 있습니다. 서버가 없는 브라우저 애플리케이션도 있고, 클라이언트 코드가 극히 단순하고 거의 모든 코드가 서버에 있는 경우도 있습니다.

[^13]: 2000년대 초 비동기 HTTP 요청의 도입은 [웹 2.0](https://en.wikipedia.org/wiki/Web_2.0)이라 불리는 혁신적인 새 웹 애플리케이션의 물결을 불러왔습니다.

[^14]: 1990년대에 아주 유행했습니다. 댓글을 달 대상이 있기도 전에 존재했던 댓글 스레드였죠.

[^15]: 프로세스가 죽으면 연결 반대편의 컴퓨터는 즉시 그 사실을 알지 못합니다. 다른 프로세스가 같은 포트를 열면, 이제는 죽어 버린 옛 프로세스로 향하던 데이터를 받을 수도 있습니다.

[^16]: 엄밀히 말하면 `checked` 속성은 [페이지가 로드될 때의 체크박스 상태에만 영향을 줍니다](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/checkbox#attr-checked). 체크박스를 체크하거나 해제하는 것은 이 속성에 영향을 주지 않고 내부 상태를 조작합니다.

[^17]: 실제로 브라우저들은 이 구현 경로를 여러 번 걸어갔습니다. 메인 웹 레이아웃 엔진에서 크게 영감을 받거나 그 일부를 재사용하는 브라우저 크롬용 레이아웃 엔진을 만든 것이죠. [Firefox에도 하나 있었고](https://en.wikipedia.org/wiki/XUL), [Chrome에도 하나 있습니다](https://www.chromium.org/developers/webui/). 다만 브라우저 크롬은 그리기가 아주 빠르고 반응성이 좋아야 하기 때문에, 이런 접근은 성패가 엇갈렸습니다.
