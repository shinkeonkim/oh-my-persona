지금까지 우리는 브라우저를 웹 애플리케이션 개발을 위한 효과적인 플랫폼으로 만드는 데 집중했습니다. 하지만 궁극적으로 브라우저는 [_사용자_ 에이전트](https://browser.engineering/intro.html#the-role-of-the-browser)입니다. 즉 사용자가 웹 애플리케이션에 접근하고 그것을 사용하도록 가능한 모든 방식으로 도와야 한다는 뜻입니다. 그래서 브라우저는 [선언적](https://browser.engineering/intro.html#browser-code-concepts) UI와 HTML·CSS의 유연함을 활용해 터치, 키보드, 음성으로 웹 페이지와 상호작용할 수 있게 해 주는 다양한 [_접근성_](https://developer.mozilla.org/en-US/docs/Learn/Accessibility/What_is_accessibility) 기능을 제공합니다.

## 접근성이란 무엇인가?

접근성이란 사용자가 웹 페이지와 상호작용하는 방식을 더 쓰기 쉽게 바꾸거나 맞춤 설정할 수 있다는 뜻입니다.[^1] 웹의 독특하게 유연한 핵심 기술 덕분에 브라우저는 사용자가 웹 페이지의 렌더링을 맞춤 설정하고, 키보드나 음성으로, 또는 어떤 보조 소프트웨어를 사용해 웹 페이지와 상호작용할 수 있게 해 주는 많은 접근성 기능을 제공합니다.[^2]

물론 맞춤 설정을 하는 이유는 그 맞춤 설정만큼이나 다양합니다. 세계보건기구는 세계 인구의 무려 15%가 어떤 형태로든 장애를 갖고 있으며 그중 상당수가 심각하거나 영구적이라는 [사실을 밝혔습니다](https://www.who.int/publications/i/item/9789241564182). 그들 거의 모두가 이 장에서 설명하는 접근성 기능에서 큰 도움을 얻을 수 있습니다. 특정한 사람에게 장애가 심각할수록 이 기능들은 그들에게 더욱 결정적으로 중요해집니다.

접근성이 필요한 상황 중에는 왔다가 가는 것도 있습니다. 예를 들어 제 아들이 태어났을 때,[^3] 아내와 저는 번갈아 아기를 돌봤고 저는 결국 밤에 일하는 시간이 많아졌습니다. 소중한 수면을 최대한 확보하기 위해 화면이 덜 밝기를 바랐고, 많은 웹사이트가 다크 모드를 제공한다는 것에 감사했습니다. 나중에는 두 손이 아기를 안느라 바쁠 때 음성으로 메모하는 것이 편리하다는 것을 알게 되었습니다. 그리고 아기를 재우려 할 때는 TV를 음소거하고 자막을 읽는 것이 영화를 보는 최고의 방법이라는 것도 알게 되었습니다.

이런 접근성 도구를 사용한 근본적인 이유는 일시적이었습니다. 하지만 다른 용도는 더 오래가거나 영구적일 수도 있습니다. 예를 들어 저는 유아차를 끌고 산책하기를 훨씬 편하게 만들어 주는 [연석 경사로](https://en.wikipedia.org/wiki/Curb_cut)에 늘 감사합니다.[^4] 그리고 제 친척들 상당수처럼 저도 나이가 들면서 시력이 나빠져 컴퓨터의 글자 크기를 영구적으로 크게 설정해야 할 가능성이 큽니다. 더 심각하고 영구적인 장애를 위해서는 [스크린 리더](https://www.afb.org/blindness-and-low-vision/using-technology/assistive-technology-products/screen-readers) 같은 고급 도구가 있습니다.[^5] 이런 도구는 배우고 효과적으로 사용하기까지 시간이 걸리지만, 그것이 필요한 사람들에게는 삶을 바꿔 놓습니다.

접근성은 사소한 편의 제공부터 고급 접근성 도구까지 전체 스펙트럼을 아우릅니다.[^6] 그런데 물리적이든 디지털이든 모든 종류의 접근성 작업에서 얻는 핵심 교훈 하나는, 일단 접근성 도구가 만들어지면 창의적인 사람들이 그 도구의 설계자가 예상하지 못한 온갖 상황에서 그것이 도움이 된다는 것을 알아낸다는 점입니다. 다크 모드는 업무용 메일 앱과 개인용 메일 앱을 구별하는 데 도움이 되고, 웹 페이지 확대는 웹 페이지 전체를 종이 한 장에 인쇄하는 데 도움이 되며, 키보드 단축키는 일괄 처리 모드가 없는 웹 애플리케이션에 비슷한 주문을 여러 건 넣을 때 근육 기억을 활용하게 해 줍니다.

게다가 접근성은 웹을 탄생시킨 것과 같은 [원칙](https://browser.engineering/intro.html)에서 나옵니다. 사용자 제어, 다중 모드 콘텐츠, 상호 운용성이 그것입니다. 이 원칙들 덕분에 웹은 모든 종류의 브라우저와 운영체제에서 접근 가능해졌고, _바로 그 같은 원칙_ 이 마찬가지로 웹을 모든 유형과 능력의 사람들에게 접근 가능하게 만듭니다.

### 더 알아보기

미국, 영국, 유럽연합을 비롯한 많은 나라에서 웹사이트 접근성은 많은 경우 법적으로 요구됩니다. 예를 들어 미국 정부 웹사이트는 [1973년 재활법 개정안(이후 개정 포함)](https://www.access-board.gov/law/ra.html)의 [508조](https://www.access-board.gov/law/ra.html#section-508-federal-electronic-and-information-technology)와 그에 딸린 [규정](https://www.access-board.gov/ict/)에 따라 접근 가능해야 합니다. 정부가 아닌 웹사이트도 [미국 장애인법](https://www.ada.gov/ada_intro.htm)에 따라 접근 가능해야 하지만, 대부분 법원에서 판단되고 있기 때문에 그 법적 요구가 실무적으로 정확히 무엇을 뜻하는지는 [아직 분명하지 않습니다](https://www.americanbar.org/groups/law_practice/publications/law_practice_magazine/2022/jf22/vu-launey-egan/). 영국에서는 [2010년 평등법](https://www.siteimprove.com/glossary/uk-accessibility-laws/)이 웹사이트에 대해 비슷한 규칙을 세웠고, 2018년에는 정부 웹사이트에 더 엄격한 규칙이 추가되었습니다. 유럽연합의 비슷한 법으로는 [유럽 접근성법](https://ec.europa.eu/social/main.jsp?catId=1202)이 있습니다.

## 확대

가장 단순한 접근성 문제부터 시작합시다. 화면의 텍스트가 너무 작아 읽기 어려운 문제입니다. 이는 우리 중 많은 이가 언젠가 마주할 문제이며, 아마도 가장 흔한 사용자 장애 문제일 것입니다. 이를 해결하는 가장 단순하고 효과적인 방법은 폰트와 요소의 크기를 키우는 것입니다. 이 접근법을 _확대(zoom)_[^7] 라고 하며, 모든 CSS 크기가 지정된 비율만큼 커지거나 작아진 것처럼 페이지를 배치하는 것을 뜻합니다.

이를 구현하려면 먼저 확대를 유발할 방법이 필요합니다. 대부분의 브라우저에서 그것은 `Ctrl-+`, `Ctrl--`, `Ctrl-0` 키입니다. `Ctrl` 수정자 키를 쓰면 확대 기능을 유발하지 않고 텍스트 입력란에 `+`, `-`, `0`을 입력할 수 있습니다.

수정자 키를 처리하려면 이벤트 루프에서 "키 누름"과 "키 뗌" 이벤트를 모두 듣고 `Ctrl` 키가 눌려 있는지 저장해야 합니다.

```python
def mainloop(browser):
    # ...
    ctrl_down = False
    while True:
        if sdl2.SDL_PollEvent(ctypes.byref(event)) != 0:
            elif event.type == sdl2.SDL_KEYDOWN:
                # ...
                elif event.key.keysym.sym == sdl2.SDLK_RCTRL or \
                    event.key.keysym.sym == sdl2.SDLK_LCTRL:
                    ctrl_down = True                
             elif event.type == sdl2.SDL_KEYUP:
                if event.key.keysym.sym == sdl2.SDLK_RCTRL or \
                    event.key.keysym.sym == sdl2.SDLK_LCTRL:
                    ctrl_down = False
                # ...
```

이제 `Ctrl` 키가 눌린 상태의 "키 누름" 이벤트를 위한 분기를 키 처리 코드에 둘 수 있습니다.

```python
def mainloop(browser):
    while True:
        if sdl2.SDL_PollEvent(ctypes.byref(event)) != 0:
            elif event.type == sdl2.SDL_KEYDOWN:
                if ctrl_down:
                     if event.key.keysym.sym == sdl2.SDLK_EQUALS:
                         browser.increment_zoom(True)
                     elif event.key.keysym.sym == sdl2.SDLK_MINUS:
                         browser.increment_zoom(False)
                     elif event.key.keysym.sym == sdl2.SDLK_0:
                         browser.reset_zoom()
                # ...
```

여기서 `increment_zoom`의 인자는 늘려야 하는지(`True`) 줄여야 하는지(`False`)를 나타냅니다.

`Browser` 코드는 그저 메인 스레드 작업을 통해 `Tab`에 위임합니다.

```python
class Browser:
    # ...
    def increment_zoom(self, increment):
        task = Task(self.active_tab.zoom_by, increment)
        self.active_tab.task_runner.schedule_task(task)

    def reset_zoom(self):
        task = Task(self.active_tab.reset_zoom)
        self.active_tab.task_runner.schedule_task(task)
```

마지막으로 `Tab`은 이 명령들에 반응해 새로운 `zoom` 속성을 조정합니다. 이 값은 `1`에서 시작하며 웹 페이지의 모든 "CSS 크기"에 대한 곱셈 인자 역할을 합니다.[^8]

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.zoom = 1

    def zoom_by(self, increment):
        if increment:
            self.zoom *= 1.1
            self.scroll *= 1.1
        else:
            self.zoom *= 1/1.1
            self.scroll *= 1/1.1
        self.scroll_changed_in_tab = True
        self.set_needs_render()

    def reset_zoom(self):
        self.scroll /= self.zoom
        self.zoom = 1
        self.scroll_changed_in_tab = True
        self.set_needs_render()
```

확대가 끝난 뒤 화면을 다시 그리기 위해 확대할 때 `needs_render` 플래그를 설정해야 한다는 점에 주의하세요. 또한 페이지를 확대할 때 스크롤 위치도 조정해야 하고,[^9] 새 페이지로 이동할 때는 확대 수준을 초기화해야 한다는 점도 주의하세요.

```python
class Tab:
    def load(self, url, payload=None):
        self.zoom = 1
        # ...
```

`zoom` 인자는 모든 CSS 크기에 곱해져야 하므로 레이아웃 중에 그것에 접근할 수 있어야 합니다. 몇 가지 방법이 있지만, 쉬운 방법 하나는 `DocumentLayout`의 `layout`에 매개변수로 넘기는 것입니다.

```python
class DocumentLayout:
    def layout(self, zoom):
        self.zoom = zoom
        child = BlockLayout(self.node, self, None)
        # ...
```

```python
class Tab:
    def render(self):
        if self.needs_layout:
            # ...
            self.document.layout(self.zoom)
            # ...
```

다른 모든 레이아웃 객체도 `layout`에서 부모로부터 복사한 `zoom` 필드를 가질 수 있습니다. 다음은 `BlockLayout`이고, 다른 레이아웃 클래스도 똑같이 해야 합니다.

```python
class BlockLayout:
    def layout(self):
        self.zoom = self.parent.zoom
        # ...
```

이제 여러 메서드가 `zoom`을 반영해 폰트 크기를 조정해야 합니다. `zoom`으로 크기를 조절하는 것은 흔한 연산이므로 헬퍼 메서드 `dpx`로 감싸 봅시다.[^10]

```python
def dpx(css_px, zoom):
    return css_px * zoom
```

`dpx`를 단순한 헬퍼 메서드가 아니라 _CSS 픽셀_ (CSS 선언에 지정된 단위)에서 _장치 픽셀_ (실제로 화면에 그려지는 것)로의 단위 변환이라고 생각하세요. 실제 브라우저에서 이 메서드는 고DPI 디스플레이 같은 차이도 반영할 수 있습니다.

`BlockLayout`의 `text`와 `input` 메서드, 그리고 `InputLayout`에서 폰트 크기를 조정하기 위해 이 변환을 하겠습니다.

```python
class BlockLayout:
    def word(self, node, word):
        # ...
        px_size = float(node.style["font-size"][:-2])
        size = dpx(px_size * 0.75, self.zoom)
        # ...

    def input(self, node):
        # ...
        px_size = float(node.style["font-size"][:-2])
        size = dpx(px_size * 0.75, self.zoom)
        # ...
```

```python
class InputLayout:
    def layout(self):
        # ...
        px_size = float(self.node.style["font-size"][:-2])
        size = dpx(px_size * 0.75, self.zoom)
        # ...
```

`TextLayout`의 폰트 크기에도 마찬가지입니다.[^11]

```python
class TextLayout:
    # ...
    def layout(self):
        # ...
        px_size = float(self.node.style["font-size"][:-2])
        size = dpx(px_size * 0.75, self.zoom)
```

그리고 텍스트 상자의 고정된 `INPUT_WIDTH_PX`에도요.

```python
class BlockLayout:
    # ...
    def input(self, node):
        w = dpx(INPUT_WIDTH_PX, self.zoom)  
```

마지막으로 확대를 반영해야 하는 까다로운 곳이 `DocumentLayout` 안에 있습니다. 여기에는 두 종류의 길이가 있습니다. 전체 `WIDTH`와, 페이지 가장자리 주위의 `HSTEP`/`VSTEP` 여백입니다. `WIDTH`는 애플리케이션 창 자체의 크기에서 오므로 장치 픽셀로 측정되며 변환할 필요가 없습니다. 하지만 `HSTEP`/`VSTEP`은 페이지 레이아웃의 일부이므로 CSS 픽셀이며 변환해야 _합니다_.

```python
class DocumentLayout:
    def layout(self, zoom):
        # ...
        self.width = WIDTH - 2 * dpx(HSTEP, self.zoom)
        self.x = dpx(HSTEP, self.zoom)
        self.y = dpx(VSTEP, self.zoom)
        child.layout()
        self.height = child.height
```

이제 시험해 보세요. `Ctrl-+`를 누를 때마다 모든 폰트가 약 10% 커지고, `Ctrl--`를 누를 때마다 10% 줄어들어야 합니다. 커진 텍스트는 여전히 화면 가장자리에서 알맞게 줄바꿈되어야 하고, CSS 길이도 텍스트와 똑같이 크기가 조절되어야 합니다. 텍스트를 더 쉽게 읽는 데 훌륭합니다.

### 더 알아보기

고해상도 화면에서 CSS 픽셀은 확대와 [`devicePixelRatio`](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio) 인자 양쪽에 의해 크기가 조절됩니다.[^13] 이 인자는 (예전 데스크톱 디스플레이 상당수가 그랬듯이) [1인치당](https://en.wikipedia.org/wiki/Dots_per_inch) 대략 96 CSS 픽셀이 되도록 장치 픽셀의 크기를 조절합니다. 예를 들어 초기 iPhone은 1인치당 163픽셀이었고, 그 기기의 브라우저는 `devicePixelRatio`로 2를 사용해 96 CSS 픽셀이 192 장치 픽셀, 즉 약 1.17인치에 해당했습니다.[^14] 이 크기 조절은 기기가 여러 디스플레이에 연결되어 있을 때 특히 까다롭습니다. 창이 저해상도 디스플레이에서 고해상도 디스플레이로 옮겨 가거나(그래서 `devicePixelRatio`가 바뀌거나), 심지어 해상도가 다른 두 디스플레이에 걸쳐 있을 수도 있기 때문입니다.

## 다크 모드

또 하나의 유용한 시각적 변화는 더 어두운 색을 사용하는 것인데, 이는 빛에 특히 민감하거나, 밤에 기기를 쓰거나, 그저 더 어두운 색 배합을 선호하는 사용자를 돕습니다. 이 브라우저 _다크 모드_ 기능은 브라우저 크롬과 웹 페이지 자체 모두를 검은 배경에 흰 텍스트를 쓰도록 전환하고, 그 밖의 배경색도 더 어둡게 조정해야 합니다.[^15]

이벤트 루프에서 `Ctrl-d`로 다크 모드를 유발하겠습니다.

```python
def mainloop(browser):
    while True:
        if sdl2.SDL_PollEvent(ctypes.byref(event)) != 0:
            elif event.type == sdl2.SDL_KEYDOWN:
                if ctrl_down:
                    # ...
                    elif event.key.keysym.sym == sdl2.SDLK_d:
                        browser.toggle_dark_mode()
```

다크 모드가 활성일 때는 브라우저 크롬과 웹 페이지 내용을 모두 다르게 그려야 합니다. 브라우저 크롬이 조금 더 쉬우니 그것부터 시작합시다. 다크 모드가 활성인지 나타내는 `dark_mode` 필드부터 시작하겠습니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.dark_mode = False

    def toggle_dark_mode(self):
        self.dark_mode = not self.dark_mode
```

이제 `dark_mode`가 설정되면 `raster_chrome`의 모든 색을 뒤집기만 하면 됩니다. 전경색과 배경색을 재사용할 수 있도록 변수에 저장합시다.

```python
class Browser:
    def raster_chrome(self):
        if self.dark_mode:
            background_color = skia.ColorBLACK
        else:
            background_color = skia.ColorWHITE
        canvas.clear(background_color)
        # ...
```

마찬가지로 `Chrome`의 `paint`에서도 알맞은 전경색을 써야 합니다.

```python
class Chrome:
    def paint(self):
        if self.browser.dark_mode:
            color = "white"
        else:
            color = "black"
```

그다음 모든 곳에서 `black` 대신 `color`를 쓰기만 하면 됩니다. `paint`에서 그렇게 바꾸세요.[^16]

이제 웹 페이지 내용도 라이트 모드에서 다크 모드로 바뀌기를 바랍니다. 우선 사용자가 다크 모드를 요청하면 `Tab`에 알려 줍시다.

```python
class Browser:
    # ...
    def toggle_dark_mode(self):
        # ...
        self.dark_mode = not self.dark_mode
        task = Task(self.active_tab.set_dark_mode, self.dark_mode)
        self.active_tab.task_runner.schedule_task(task)
```

그리고 `Tab`에서는 이렇게 합니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.dark_mode = browser.dark_mode

    def set_dark_mode(self, val):
        self.dark_mode = val
        self.set_needs_render()
```

다크 모드 설정이 뒤집히면 사용자가 실제로 새 색을 보도록 페이지를 다시 렌더링해야 한다는 점에 주의하세요. 그런 맥락에서 탭을 바꿀 때도 다크 모드를 설정해야 합니다. 모든 탭이 다크이거나 라이트여야 하니까요.

```python
class Browser:
   def set_active_tab(self, tab):
        # ...
        task = Task(self.active_tab.set_dark_mode, self.dark_mode)
        self.active_tab.task_runner.schedule_task(task)
```

이제 페이지의 색이 어떻게든 다크 모드에 의존해야 합니다. 가장 바꾸기 쉬운 것은 브라우저가 설정하는 기본 텍스트 색과 문서의 배경색입니다. 예를 들어 기본 텍스트 색은 `INHERITED_PROPERTIES` 딕셔너리에서 오므로, 다크 모드에 따라 그냥 수정하면 됩니다.

```python
class Tab:
    # ...
    def render(self):
        if self.needs_style:
            if self.dark_mode:
                INHERITED_PROPERTIES["color"] = "white"
            else:
                INHERITED_PROPERTIES["color"] = "black"
            style(self.nodes,
                sorted(self.rules, key=cascade_priority))
```

그리고 페이지의 배경은 `Browser`가 `draw` 메서드에서 그리므로, 그것을 다크 모드에 의존하게 만들 수 있습니다.

```python
class Browser:
    # ...
    def draw(self):
        # ...
        if self.dark_mode:
            canvas.clear(skia.ColorBLACK)
        else:
            canvas.clear(skia.ColorWHITE)
```

이제 브라우저를 열고 다크 모드로 전환하면 그림 3처럼 검은 배경에 흰 텍스트가 보일 것입니다.

### 더 알아보기

브라우저가 아무것도 모르는 페이지의 색을 정말로 바꿔서는 안 됩니다. 페이지의 테마와 충돌하면 가독성에 끔찍한 결과가 생길 수 있으니까요! 대신 웹 페이지는 `color-scheme` [`meta` 태그](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/meta/name)나 [CSS 속성](https://developer.mozilla.org/en-US/docs/Web/CSS/color-scheme)으로 다크 모드 지원을 [알립니다](https://blogs.windows.com/msedgedev/2021/06/16/dark-mode-html-form-controls/). 브라우저는 그 메타 태그의 존재로 다크 모드를 적용해도 안전한지 판단합니다. `color-scheme`이 표준화되기 전에도 웹 페이지는 원칙적으로 [대체 스타일 시트](https://developer.mozilla.org/en-US/docs/Web/CSS/Alternative_style_sheets)로 대안적인 색 배합을 제공할 수 있었지만, 이를 지원하는 브라우저가 거의 없었고(주요 브라우저 중에서는 Firefox뿐이었습니다) 흔히 쓰이지도 않았습니다.

## 다크 모드 맞춤 설정

우리의 단순한 다크 모드 구현은 배경 위에 텍스트만 있는 페이지에서는 잘 동작합니다. 하지만 보기 좋은 다크 모드를 위해서는 페이지의 다른 모든 색도 조정해야 합니다. 예를 들어 버튼과 입력 요소는 아마 더 어두운 배경색이 필요할 것이고, 웹 개발자가 페이지에 쓴 색들도 마찬가지입니다.

이를 지원하기 위해 CSS는 [미디어 쿼리](https://developer.mozilla.org/en-US/docs/Web/CSS/Media_Queries/Using_media_queries)를 사용합니다. 이는 기본적으로 CSS 규칙 몇 개를 어떤 조건을 가진 `if` 문으로 감싸는 특별한 문법입니다. 조건이 참이면 그 CSS 규칙이 사용되고, 거짓이면 무시됩니다. `prefers-color-scheme` 조건은 다크 모드를 확인합니다. 예를 들어 다음 CSS는 다크 모드에서만 `<div>`가 검은 배경에 흰 텍스트를 갖게 합니다.

```
@media (prefers-color-scheme: dark) {
  div { background-color: black; color: white; }
}
```

웹 개발자는 자신의 스타일 시트에서 `prefers-color-scheme` 쿼리를 사용해 사용자의 요청에 맞게 색 선택을 조정할 수 있지만, 우리도 브라우저 기본 스타일 시트에서 `prefers-color-scheme` 미디어 쿼리를 사용해 링크, 버튼, 텍스트 입력란의 기본 색을 조정할 수 있습니다.

```css
@media (prefers-color-scheme: dark) {
  a { color: lightblue; }
  input { background-color: #2222FF; }
  button { background-color: #992500; }
}
```

여기서 저는 파랑과 주황이라는 전반적인 색 배합을 유지하면서도 읽기 쉽도록 흰 전경 텍스트와 최대한의 대비를 보장하는 아주 구체적인 16진수 색을 골랐습니다. 최대한의 대비([“AAA”](https://accessibleweb.com/rating/aaa/) 등급)를 보장하는 색을 고르는 것이 중요합니다. [이 도구](https://webaim.org/resources/contrastchecker/)가 전경색과 배경색의 대비를 확인하는 데 편리합니다.

미디어 쿼리를 구현하려면 우선 이 문법을 파싱하는 것부터 시작해야 합니다.

```python
class CSSParser:
    def media_query(self):
        self.literal("@")
        assert self.word() == "media"
        self.whitespace()
        self.literal("(")
        self.whitespace()
        prop, val = self.pair([")"])
        self.whitespace()
        self.literal(")")
        return prop, val
```

그다음 `parse`에서 현재 색 배합을 추적하고 `@media` 규칙에 들어가고 나올 때마다 그것을 조정합니다.[^17]

```python
class CSSParser:
    def parse(self):
        # ...
        media = None
        self.whitespace()
        while self.i < len(self.s):
            try:
                if self.s[self.i] == "@" and not media:
                    prop, val = self.media_query()
                    if prop == "prefers-color-scheme" and \
                        val in ["dark", "light"]:
                        media = val
                    self.whitespace()
                    self.literal("{")
                    self.whitespace()
                elif self.s[self.i] == "}" and media:
                    self.literal("}")
                    media = None
                    self.whitespace()
                else:
                    # ...
                    rules.append((media, selector, body))
```

규칙 목록이 선택자와 본문뿐 아니라 그 규칙들의 색 배합도 저장하도록 수정했다는 점에 주의하세요. 색 배합과 무관하게 적용되면 `None`, 다크 모드 전용이면 `dark`, 라이트 모드 전용이면 `light`입니다. 이렇게 하면 `style` 함수가 적용되지 않는 규칙을 무시할 수 있습니다.

```python
def style(node, rules, tab):
    # ...
    for media, selector, body in rules:
        if media:
            if (media == "dark") != tab.dark_mode: continue
        # ...
```

링크, 텍스트 입력란, 버튼이 많은 이 [웹 페이지](https://browser.engineering/examples/example14-focus.html)[^18]에서 여러분의 브라우저를 시험해 보세요. 이제 다크 모드에서 그것들도 배경이 더 어둡고 전경이 더 밝은 색으로 바뀌는 것을 볼 수 있을 것입니다. 다크 모드에서는 그림 4처럼 보여야 합니다.

### 더 알아보기

`prefers-color-scheme` 외에도 웹 페이지는 미디어 쿼리를 사용해 사용자가 [`prefers-contrast`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-contrast)일 때 대비를 높이거나 낮출 수 있고, 사용자가 [`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)일 때 불필요한 애니메이션을 끌 수 있습니다. 둘 다 특정 장애를 가진 사용자에게 도움이 됩니다. 사용자는 운영체제를 통해 제한된 색 팔레트의 사용을 강제할 수도 있습니다. 웹 페이지는 [`forced-colors`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors) 미디어 쿼리로 이를 감지하거나 (조심해서 쓰세요!) [`forced-color-adjust`](https://developer.mozilla.org/en-US/docs/Web/CSS/forced-color-adjust)로 특정 요소에 대해 그것을 끌 수 있습니다.

## 키보드 내비게이션

지금 우리 브라우저의 기능 대부분은 마우스로 유발됩니다.[^19] 이는 손에 부상이나 장애가 있는 사용자에게 문제이고, 키보드를 선호하는 파워 유저에게도 문제입니다. 그러니 이상적으로는 모든 브라우저 기능이 마우스뿐 아니라 키보드로도 접근 가능해야 합니다. 여기에는 뒤로 가기, URL 입력, 브라우저 종료 같은 브라우저 크롬 상호작용과, 폼 제출, 텍스트 영역 입력, 링크 이동, 페이지의 항목 선택 같은 웹 페이지 상호작용이 모두 포함됩니다.

가장 쉬운 브라우저 크롬부터 시작합시다. 여기서는 사용자가 키보드로 뒤로 가고, 주소창에 입력하고, 탭을 만들고 순환할 수 있게 해야 합니다. 브라우저 종료를 위한 키보드 단축키도 추가하겠습니다.[^20] 일반 타이핑을 방해하지 않도록 이벤트 루프의 이 단축키들에 모두 `Ctrl` 수정자 키를 씁시다. 뒤로 가기는 `Ctrl-Left`, 주소창에 입력하기는 `Ctrl-l`, 새 탭 만들기는 `Ctrl-t`, 다음 탭으로 전환하기는 `Ctrl-Tab`, 브라우저 종료는 `Ctrl-q`입니다.

```python
def mainloop(browser):
    while True:
        if sdl2.SDL_PollEvent(ctypes.byref(event)) != 0:
            elif event.type == sdl2.SDL_KEYDOWN:
                if ctrl_down:
                    # ...
                    elif event.key.keysym.sym == sdl2.SDLK_LEFT:
                        browser.go_back()
                    elif event.key.keysym.sym == sdl2.SDLK_l:
                        browser.focus_addressbar()
                    elif event.key.keysym.sym == sdl2.SDLK_t:
                        browser.new_tab(
                            "https://browser.engineering/")
                    elif event.key.keysym.sym == sdl2.SDLK_TAB:
                        browser.cycle_tabs()
                    elif event.key.keysym.sym == sdl2.SDLK_q:
                        browser.handle_quit()
                        sdl2.SDL_Quit()
                        sys.exit()
                        break
```

여기서 `focus_addressbar`와 `cycle_tabs` 메서드는 새것이지만, 그 내용은 그저 `handle_click`에서 복사한 것입니다.

```python
class Chrome:
    def focus_addressbar(self):
        self.focus = "address bar"
        self.address_bar = ""

class Browser:
    def focus_addressbar(self):
        self.lock.acquire(blocking=True)
        self.chrome.focus_addressbar()
        self.set_needs_raster()
        self.lock.release()

    def cycle_tabs(self):
        self.lock.acquire(blocking=True)
        active_idx = self.tabs.index(self.active_tab)
        new_active_idx = (active_idx + 1) % len(self.tabs)
        self.set_active_tab(self.tabs[new_active_idx])
        self.lock.release()
```

이제 브라우저 크롬의 모든 클릭을 키보드 동작으로 대체할 수 있습니다. 그런데 웹 페이지 자체의 클릭은 어떨까요? 이는 더 까다로운데, 웹 페이지에는 링크가 몇 개든 있을 수 있기 때문입니다. 그래서 표준적인 해법은 사용자가 페이지의 모든 클릭 가능한 것들을 `Tab`으로 훑고 `Enter`를 눌러 실제로 클릭하게 하는 것입니다.[^21]

이를 _포커스_ 구현을 확장해 구현하겠습니다. 우리에겐 이미 각 `Tab`에 어떤 `input` 요소가 키보드 입력을 받고 있는지 나타내는 `focus` 속성이 있습니다. 버튼과 링크도 포커스될 수 있게 합시다. 물론 그것들은 키보드 입력을 받지 않지만, 사용자가 `Enter`를 누르면 버튼을 누르거나 링크로 이동하겠습니다.

이벤트 루프에서 그 키들을 바인딩하는 것부터 시작하겠습니다.

```python
def mainloop(browser):
    while True:
        if sdl2.SDL_PollEvent(ctypes.byref(event)) != 0:
            elif event.type == sdl2.SDL_KEYDOWN:
                # ...
                elif event.key.keysym.sym == sdl2.SDLK_RETURN:
                    browser.handle_enter()
                elif event.key.keysym.sym == sdl2.SDLK_TAB:
                    browser.handle_tab()
```

이 줄들은 `if ctrl_down` 블록 안에 들어가지 않는다는 점에 주의하세요. 우리가 바인딩하는 것은 `Ctrl-Tab`과 `Ctrl-Enter`가 아니라 `Tab`과 `Enter`이기 때문입니다. `Browser`에서는 이 키들을 활성 탭의 `enter`와 `advance_tab` 메서드로 전달하기만 합니다.[^22]

```python
class Browser:
    def handle_tab(self):
        self.focus = "content"
        task = Task(self.active_tab.advance_tab)
        self.active_tab.task_runner.schedule_task(task)

    def handle_enter(self):
        # ...
        elif self.focus == "content":
            task = Task(self.active_tab.enter)
            self.active_tab.task_runner.schedule_task(task)
        # ...
```

`advance_tab` 메서드부터 시작합시다. 이 메서드가 호출될 때마다 브라우저는 포커스를 다음 포커스 가능한 것으로 옮겨야 합니다. 그러려면 먼저 어떤 요소가 포커스 가능한지 정의해야 합니다.

```python
def is_focusable(node):
    return node.tag in ["input", "button", "a"]

class Tab:
    def advance_tab(self):
        focusable_nodes = [node
            for node in tree_to_list(self.nodes, [])
            if isinstance(node, Element) and is_focusable(node)]
```

다음으로 `advance_tab`에서는 현재 포커스된 요소가 이 목록의 어디에 있는지 알아내 포커스를 그다음으로 옮겨야 합니다.

```python
class Tab:
    def advance_tab(self):
        # ...
        if self.focus in focusable_nodes:
            idx = focusable_nodes.index(self.focus) + 1
        else:
            idx = 0
```

마지막으로 선택된 요소에 포커스를 주기만 하면 됩니다. 마지막 포커스 가능한 노드에 도달했다면(또는 애초에 포커스 가능한 노드가 없었다면), 페이지의 포커스를 해제하고 주소창으로 포커스를 옮기겠습니다.

```python
class Tab:
    def advance_tab(self):
        if idx < len(focusable_nodes):
            self.focus = focusable_nodes[idx]
        else:
            self.focus = None
            self.browser.focus_addressbar()
        self.set_needs_render()
```

이제 요소가 포커스되었으니 사용자가 `Enter`를 눌러 그것과 상호작용할 수 있어야 합니다. 정확히 어떤 동작을 하는지는 (링크 이동, 버튼 누르기, 텍스트 입력란 비우기 등) 제각각이므로, 이를 요소를 "활성화(activate)"한다고 부르겠습니다.

```python
class Tab:
    def enter(self):
        if not self.focus: return
        self.activate_element(self.focus)
```

`activate_element` 메서드는 요소 종류에 따라 다른 일을 합니다.

```python
class Tab:
    def activate_element(self, elt):
        if elt.tag == "input":
            elt.attributes["value"] = ""
            self.set_needs_render()
        elif elt.tag == "a" and "href" in elt.attributes:
            url = self.url.resolve(elt.attributes["href"])
            self.load(url)
        elif elt.tag == "button":
            while elt:
                if elt.tag == "form" and "action" in elt.attributes:
                    self.submit_form(elt)
                elt = elt.parent
```

이 활성화 코드는 모두 `Tab`의 `click` 메서드에서 복사한 것입니다. 텍스트 입력란에 포커스가 있을 때 `Enter`를 누르면 텍스트 입력란이 비워진다는 점에 주의하세요. 대부분의 브라우저에서는 대신 그것을 담은 폼이 제출됩니다. 이 특이 동작은 우리 브라우저가 `Backspace` 키를 [구현하지 않은 것](https://browser.engineering/forms.html#interacting-with-widgets)(8.3절)에 대한 우회책입니다.

이제 `click` 메서드는 `activate_element`를 직접 호출하도록 다시 쓸 수 있습니다.

```python
class Tab:
    def click(self, x, y):
        # ...
        while elt:
            if isinstance(elt, Text):
                pass
            elif is_focusable(elt):
                self.focus = elt
                self.activate_element(elt)
                return
            elt = elt.parent
```

또한 이제 어떤 요소든 포커스될 수 있으므로, `keypress`는 입력하기 전에 `input` 요소가 포커스되어 있는지 확인해야 합니다.

```python
class Tab:
    def keypress(self, char):
        if self.focus and self.focus.tag == "input":
            if not "value" in self.focus.attributes:
                self.activate_element(self.focus)
            # ...
```

빈 `value` 속성을 만들기 위해 `activate_element`를 호출했습니다.

마찬가지로 `InputLayout`은 포커스된 어떤 요소에 대해서든 커서를 그렸습니다. 이제 `button` 요소도 포커스될 수 있으므로 더 조심해야 합니다.

```python
class InputLayout:
    def paint(self):
        # ...
        if self.node.is_focused and self.node.tag == "input":
            # ...
        # ...
```

마지막으로, 요소를 활성화하면 때때로 폼이 제출되거나 새 페이지로 이동해서 우리가 포커스하고 있던 요소가 더 이상 존재하지 않게 된다는 점에 주의하세요. 이 경우 포커스를 반드시 지워야 합니다.

```python
class Tab:
    def load(self, url, payload=None):
        self.focus = None
        # ...
```

이제 링크, 버튼, 텍스트 입력란에 포커스할 수 있게 되었습니다. 그런데 다른 모든 브라우저 기능과 마찬가지로, 웹 페이지 작성자가 이것을 맞춤 설정할 수 있어야 하는지 물어볼 가치가 있습니다. 키보드 내비게이션의 경우, 작성자는 (대부분의 사용자에게는 잡음일 뿐인 섹션 제목의 "고유 링크"처럼) 특정 링크가 포커스되지 않기를 바라거나, 사용자가 포커스 가능한 항목을 훑는 순서를 바꾸고 싶어 할 수 있습니다.

브라우저는 이를 가능하게 하기 위해 `tabindex` HTML 속성을 지원합니다. `tabindex` 속성은 숫자입니다. `tabindex`가 음수인 요소는 포커스될 수 없고, `tabindex` 값이 더 작은 요소가 더 큰 요소나 `tabindex`가 아예 없는 요소보다 앞에 옵니다. 이를 구현하려면 포커스 가능한 요소들을 탭 인덱스로 정렬해야 하므로 탭 인덱스를 반환하는 함수가 필요합니다.

```python
def get_tabindex(node):
    tabindex = int(node.attributes.get("tabindex", "9999999"))
    return 9999999 if tabindex == 0 else tabindex
```

기본값 "9999999"는 `tabindex` 속성이 없는 요소가 있는 요소보다 뒤에 정렬되도록 하는 꼼수입니다. 이제 `advance_tab`에서 `get_tabindex`로 정렬할 수 있습니다.

```python
class Tab:
    def advance_tab(self):
        focusable_nodes = [node
            for node in tree_to_list(self.nodes, [])
            if isinstance(node, Element) and is_focusable(node)]
        focusable_nodes.sort(key=get_tabindex)
        # ...
```

Python의 정렬은 "안정적(stable)"이므로, `tabindex`가 같은 두 요소는 `focusable_nodes`에서 상대적 위치가 바뀌지 않습니다.

또한 `tabindex`가 음수가 아닌 요소는 링크나 버튼이나 텍스트 입력란이 아니어도 자동으로 포커스 가능해집니다. 그 요소가 `click` 이벤트를 듣고 있을 수 있으므로 이는 유용합니다. 이를 지원하기 위해 먼저 `is_focusable`이 `tabindex`를 고려하도록 확장합시다.

```python
def is_focusable(node):
    if get_tabindex(node) < 0:
        return False
    elif "tabindex" in node.attributes:
        return True
    else:
        return node.tag in ["input", "button", "a"]
```

[포커스 예제](https://browser.engineering/examples/example14-focus.html)에 대해 `focusable_nodes`를 출력해 보면 다음과 같이 나와야 합니다.

```
[<a tabindex="1" href="/">,
 <button tabindex="2">,
 <div tabindex="3">,
 <div tabindex="12">,
 <input>,
 <a href="http://browser.engineering">]
```

또한 요소가 활성화될 때 `click` 이벤트를 반드시 보내야 합니다. 요소를 클릭하는 것과 마찬가지로, 요소를 활성화하는 것도 JavaScript에서 `preventDefault`로 취소할 수 있다는 점에 주의하세요.

```python
class Tab:
    def enter(self):
        if not self.focus: return
        if self.js.dispatch_event("click", self.focus): return
        self.activate_element(self.focus)
```

이제 브라우저와 웹 페이지 내용 양쪽에 대해 설정 가능한 키보드 내비게이션을 갖췄습니다. 그리고 그 과정에서 새 코드는 거의 쓰지 않았고, 대부분 기존 메서드의 코드를 새로운 독립 메서드로 옮겼을 뿐입니다. 키보드 내비게이션이 우리 브라우저 구현을 복잡하게 만든 것이 아니라 단순하게 만들었다는 사실은 흔한 결과입니다. 접근성을 개선하는 일은 흔히 기존 개념을 일반화하고 다듬는 일이며, 그 결과 전반적으로 더 유지 보수하기 좋은 코드가 됩니다.

### 더 알아보기

요소가 활성화될 때 특별한 `activate` 이벤트가 아니라 `click` 이벤트를 보내는 이유는 무엇일까요? Internet Explorer는 실제로 특별한 `activate` 이벤트를 [사용했고](https://docs.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa742710(v=vs.85)), 다른 브라우저들은 [DOMActivate](https://w3c.github.io/uievents/#event-type-DOMActivate) 이벤트를 보내곤 했습니다. 하지만 현대 표준은 요소가 클릭이 아니라 키보드로 활성화되었더라도 `click` 이벤트를 보내도록 요구합니다. 개발자가 접근성을 별로 생각하지 않고 `click` 이벤트 리스너만 등록할 때 이렇게 하는 편이 더 잘 동작합니다.

## 포커스 표시하기

우리의 키보드 단축키 덕분에 이제 사용자는 키보드로 어떤 링크, 버튼, 텍스트 입력란에도 닿을 수 있습니다. 하지만 이것으로 웹사이트를 돌아다녀 보면 어떤 요소가 포커스되어 있는지 알기가 조금 어렵습니다. 텍스트 입력에 쓰는 커서와 비슷한 시각적 표시가 있으면, 눈으로 볼 수 있는 사용자가 원하는 요소에 도달했는지 아니면 `Tab`을 더 눌러야 하는지 알 수 있어 도움이 될 것입니다. 대부분의 브라우저에서 이 시각적 표시는 포커스된 요소를 둘러싸는 _포커스 링(focus ring)_ 입니다.

포커스 링을 구현하기 위해 텍스트 커서에 쓰는 것과 같은 메커니즘을 쓰겠습니다. 지금 텍스트 커서는 `InputLayout`의 `paint` 메서드에서 수직선을 그려 추가된다는 점을 떠올려 보세요. 포커스된 요소 주위에 사각형을 그리기 위해 그 메서드에 `paint_outline` 호출을 추가하겠습니다.

```python
def paint_outline(node, cmds, rect, zoom):
    if not node.is_focused: return
    cmds.append(DrawOutline(rect, "black", 1))
```

이 `is_focused` 플래그는 `Tab`의 `focus` 필드를 바꾸는 데 앞으로 쓸 새 `focus_element` 메서드에서 설정합니다(`is_focused`를 직접 설정하던 기존 코드도 `focus_element`를 호출하도록 갱신해야 합니다).

```python
class Tab:
    def focus_element(self, node):
        if self.focus:
            self.focus.is_focused = False
        self.focus = node
        if node:
            node.is_focused = True
```

외곽선 페인팅은 서브트리 위에 그려지므로 `paint_effects`에서 일어나야 합니다.

```python
class InputLayout:
    def paint_effects(self, cmds):
        cmds = paint_visual_effects(self.node, cmds, self.self_rect())
        paint_outline(self.node, cmds, self.self_rect(), self.zoom)
        return cmds
```

안타깝게도 링크를 다루는 것은 조금 더 복잡합니다. 하나의 `<a>` 요소가 여러 개의 `TextLayout` 객체에 대응하므로, 코드를 넣을 레이아웃 객체가 하나로 정해지지 않기 때문입니다. 게다가 그 `TextLayout`들이 여러 줄에 걸쳐 나뉘어 있을 수 있어서 포커스 링을 하나 이상 그리고 싶을 수도 있습니다. 이를 우회하기 위해 포커스 링을 `LineLayout`에서 그립시다. 각 `LineLayout`은 포커스된 자식 `TextLayout`을 모두 찾아 그것들 전체를 둘러싸는 사각형을 그립니다.

```python
class LineLayout:
    def paint_effects(self, cmds):
        outline_rect = skia.Rect.MakeEmpty()
        outline_node = None
        for child in self.children:
            if child.node.parent.is_focused:
                outline_rect.join(child.self_rect())
                outline_node = child.node.parent
        if outline_node:
            paint_outline(
                outline_node, cmds, outline_rect, self.zoom)
        return cmds
```

사용자가 `tabindex`로 어떤 요소든 포커스 가능하게 만들 수 있으므로 `BlockLayout`에도 `paint_outline` 호출을 추가해야 합니다.[^23]

이제 페이지에서 `Tab`을 누르면 포커스된 요소가 검은 외곽선으로 강조되는 것이 보일 것입니다. 그리고 링크가 여러 줄에 걸쳐 있다면, 우리 브라우저가 무엇에 포커스되어 있는지 명확히 하기 위해 여러 개의 포커스 사각형을 쓰는 것을 볼 수 있습니다.

문제가 하나 있습니다. 포커스된 요소가 화면 밖으로 스크롤되어 있으면 여전히 무엇이 포커스되었는지 알 방법이 없습니다. 이를 고치려면 사용자가 그것으로 탭할 때 자동으로 화면 안으로 스크롤해야 합니다.

이는 조금 까다로운데, 요소가 화면 밖에 있는지 판단하려면 레이아웃이 필요하기 때문입니다. 그래서 즉시 스크롤하는 대신 `Tab`에 새로운 `needs_focus_scroll` 비트를 설정하겠습니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.needs_focus_scroll = False

    def focus_element(self, node):
        if node and node != self.focus:
            self.needs_focus_scroll = True
```

그러면 `run_animation_frame`이 플래그를 초기화하기 전에 알맞게 스크롤할 수 있습니다.

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        if self.needs_focus_scroll and self.focus:
            self.scroll_to(self.focus)
        self.needs_focus_scroll = False
        # ...
```

실제로 스크롤하려면 포커스된 노드에 해당하는 레이아웃 객체를 찾아야 합니다.

```python
class Tab:
    def scroll_to(self, elt):
        objs = [
            obj for obj in tree_to_list(self.document, [])
            if obj.node == self.focus
        ]
        if not objs: return
        obj = objs[0]
```

그다음 그것으로 스크롤합니다.

```python
class Tab:
    def scroll_to(self, elt):
        # ...

        if self.scroll < obj.y < self.scroll + self.tab_height:
            return

        document_height = math.ceil(self.document.height + 2*VSTEP)
        new_scroll = obj.y - SCROLL_STEP
        self.scroll = self.clamp_scroll(new_scroll)
        self.scroll_changed_in_tab = True
```

여기서 저는 객체가 화면 위쪽에서 `SCROLL_STEP` 픽셀 떨어지도록 스크롤 위치를 옮기고 있지만, 실제 브라우저는 위로 스크롤할 때와 아래로 스크롤할 때 다른 로직을 쓸 가능성이 큽니다.

이제 포커스 외곽선이 기본적으로 동작하고, [포커스 예제](https://browser.engineering/examples/example14-focus.html)에서 시험해 보면 화면 안으로 스크롤도 됩니다. 그림 5는 제가 탭을 눌러 "this is a link" 요소에 포커스한 뒤의 모습입니다.

그런데 이상적으로는 포커스 표시가 맞춤 설정 가능해서, 웹 페이지 작성자가 포커스된 요소를 확실히 눈에 띄게 만들 수 있어야 합니다. CSS에서 그것은 `:focus` [의사 클래스](https://developer.mozilla.org/en-US/docs/Web/CSS/Pseudo-classes)로 합니다. 기본적으로 다음과 같은 선택자를 쓸 수 있다는 뜻입니다.

```
div:focus { ... }
```

그러면 그 선택자는 현재 포커스된 `<div>` 요소에만 적용됩니다.[^24]

이를 구현하려면 이 새로운 종류의 선택자를 파싱해야 합니다. `selector`가 태그 이름과 가능한 의사 클래스를 파싱하는 새 `simple_selector` 서브루틴을 호출하도록 바꿉시다.

```python
class CSSParser:
    def selector(self):
        out = self.simple_selector()
        # ...
        while self.i < len(self.s) and self.s[self.i] != "{":
            descendant = self.simple_selector()
            # ...
```

`simple_selector`에서 파서는 먼저 태그 이름을 파싱하고, 그다음 콜론과 의사 클래스 이름이 뒤따르는지 확인합니다.

```python
class CSSParser:
    def simple_selector(self):
        out = TagSelector(self.word().casefold())
        if self.i < len(self.s) and self.s[self.i] == ":":
            self.literal(":")
            pseudoclass = self.word().casefold()
            out = PseudoclassSelector(pseudoclass, out)
        return out
```

`PseudoclassSelector`는 다른 선택자를 감쌉니다.

```python
class PseudoclassSelector:
    def __init__(self, pseudoclass, base):
        self.pseudoclass = pseudoclass
        self.base = base
        self.priority = self.base.priority
```

매칭은 간단합니다.

```python
class PseudoclassSelector:
    def matches(self, node):
        if not self.base.matches(node):
            return False
        if self.pseudoclass == "focus":
            return node.is_focused
        else:
            return False
```

알 수 없는 의사 클래스는 그냥 아무것에도 매치되지 않습니다.

이제 포커스된 요소에 스타일을 줄 수 있습니다. 하지만 이상적으로는 요소뿐 아니라 포커스 외곽선 자체도 맞춤 설정할 수 있으면 좋겠습니다. 그것은 CSS [`outline` 속성](https://developer.mozilla.org/en-US/docs/Web/CSS/outline)을 지원함으로써 할 수 있는데, (두께 3픽셀의 빨간 외곽선에 대해) 다음과 같이 생겼습니다.[^25]

```
outline: 3px solid red;
```

이를 두께와 색으로 파싱할 수 있습니다.

```python
def parse_outline(outline_str):
    if not outline_str: return None
    values = outline_str.split(" ")
    if len(values) != 3: return None
    if values[1] != "solid": return None
    return int(values[0][:-2]), values[2]
```

그다음 파싱된 외곽선을 그립니다.

```python
def paint_outline(node, cmds, rect, zoom):
    outline = parse_outline(node.style.get("outline"))
    if not outline: return
    thickness, color = outline
    cmds.append(DrawOutline(rect, color, dpx(thickness, zoom)))
```

더 좋은 것은, 기본 2픽셀 검은 외곽선을 다음과 같이 브라우저 기본 스타일 시트로 옮길 수 있다는 것입니다.

```css
input:focus { outline: 2px solid black; }
button:focus { outline: 2px solid black; }
div:focus { outline: 2px solid black; }
```

게다가 이제 다크 모드가 유발되었을 때 외곽선을 흰색으로 만들 수 있는데, 검은 배경에서 눈에 띄려면 이것이 중요합니다.

```css
@media (prefers-color-scheme: dark) {
input:focus { outline: 2px solid white; }
button:focus { outline: 2px solid white; }
div:focus { outline: 2px solid white; }
a:focus { outline: 2px solid white; }
}
```

마지막으로, 우리의 모든 `paint` 메서드가 외곽선을 그릴 때 `is_focused` 대신 `parse_outline`을 쓰도록 바꾸세요. 다음은 `LineLayout`입니다.

```python
class LineLayout:
    def paint_effects(self, cmds):
        # ...
        for child in self.children:
            outline_str = child.node.parent.style.get("outline")
            if parse_outline(outline_str):
                outline_rect.join(child.self_rect())
                outline_node = child.node.parent
```

### 더 알아보기

포커스 표시가 그 아래 웹 페이지와 [좋은 대비](https://www.w3.org/TR/WCAG21/#contrast-minimum)를 이루어 사용자가 자신이 어디로 탭했는지 분명히 볼 수 있게 하는 것이 필수적입니다. 기본 포커스 표시가 페이지나 요소 배경과 비슷해 보인다면 [약간의 주의](https://darekkay.com/blog/accessible-focus-indicator/)가 필요할 수 있습니다. 예를 들어 어두운 배경과 밝은 배경 모두에서 보이는 포커스 표시를 보장하려면 흰색과 검은색 [외곽선 두 개](https://blogs.windows.com/msedgedev/2019/10/15/form-controls-microsoft-edge-chromium/)를 그리는 것이 가장 좋을 수 있습니다. 직접 설계한다면 [웹 콘텐츠 접근성 지침](https://www.w3.org/WAI/standards-guidelines/wcag/)이 대비에 관한 안내를 제공합니다.

## 접근성 트리

확대, 다크 모드, 포커스 표시는 세밀한 것을 보기 어려운 사용자를 돕지만, 화면을 전혀 볼 수 없는 사용자는[^26] 보통 스크린 리더를 대신 사용합니다. 이름이 거의 다 설명해 줍니다. 스크린 리더는 화면의 텍스트를 소리 내어 읽어 주어, 사용자가 보지 않고도 무엇이 쓰여 있는지 알 수 있게 합니다.

그렇다면 스크린 리더는 무엇을 말해야 할까요? 극복해야 할 큰 어려움이 기본적으로 두 가지 있습니다.

첫째, 웹 페이지에는 텍스트 외에도 스크린 리더 사용자에게 재현해 주어야 하는 시각적 힌트가 들어 있습니다. 예를 들어 포커스가 `<input>`이나 `<button>` 요소에 있을 때, 이 사용자들은 연한 파란색이나 주황색 배경을 볼 수 없으므로 스크린 리더가 그 사실을 말해 주어야 합니다.

둘째, 스크린 리더를 들을 때 사용자는 자신이 관심 있는 페이지 부분으로 브라우저를 안내할 수 있어야 합니다.[^27] 예를 들어 사용자는 헤더와 내비게이션 메뉴를 건너뛰거나, 관심 있는 문단에 도달할 때까지 페이지 대부분을 건너뛰고 싶어 할 수 있습니다. 하지만 자신에게 관심 있는 부분에 도달하고 나면 그것이 읽히기를 원할 수 있고, 어떤 문장이나 구절이 특히 복잡하다면 스크린 리더가 그것을 다시 읽어 주기를 바랄 수 있습니다.

이 모든 것을 지원하기 위해 브라우저는 페이지를 트리로 구조화하고 그 트리를 사용해 스크린 리더와 상호작용합니다. 트리의 상위 계층은 문단, 제목, 내비게이션 메뉴 같은 항목을 나타내고, 하위 계층은 텍스트, 링크, 버튼을 나타냅니다.[^30]

이는 아마 HTML과 아주 비슷하게 들릴 텐데, 실제로 꽤 비슷합니다! 하지만 HTML 트리가 레이아웃 트리와 정확히 일치하지 않듯이, 이 트리와도 정확히 일치하지는 않습니다. 예를 들어 어떤 HTML 요소(`<div>` 같은)는 스크린 리더 사용자에게는 무의미한 스타일 지정을 위해 콘텐츠를 묶습니다. 반대로 어떤 HTML 요소는 화면에서는 보이지 않지만[^31] 스크린 리더 사용자에게는 의미가 있을 수 있습니다. 그래서 브라우저는 스크린 리더 내비게이션을 지원하기 위해 별도의 [접근성 트리](https://developer.mozilla.org/en-US/docs/Glossary/Accessibility_tree)를 만듭니다.

우리 브라우저에 접근성 트리를 구현해 봅시다. 이는 레이아웃 직후의 렌더링 단계에서 만들어집니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.needs_accessibility = False
        self.accessibility_tree = None

    def render(self):
        # ...
        if self.needs_layout:
            # ...
            self.needs_accessibility = True
            self.needs_paint = True
            self.needs_layout = False

        if self.needs_accessibility:
            self.accessibility_tree = AccessibilityNode(self.nodes)
            self.accessibility_tree.build()
            self.needs_accessibility = False
```

접근성 트리는 `AccessibilityNode`로 만들어집니다.

```python
class AccessibilityNode:
    def __init__(self, node):
        self.node = node
        self.children = []
```

`AccessibilityNode`의 `build` 메서드가 접근성 트리를 재귀적으로 만듭니다. 그러기 위해 HTML 트리를 순회하며 각 노드가 접근성 트리에서 어떤 "역할(role)"을 하는지 결정합니다. `<div>` 같은 어떤 요소는 역할이 없어서 접근성 트리에 나타나지 않고, `<input>`, `<a>`, `<button>` 같은 요소는 기본 역할을 가집니다.[^32] 노드의 역할은 태그 이름으로부터 계산하거나, 특별한 `role` 속성이 있다면 그것으로부터 계산할 수 있습니다.

```python
class AccessibilityNode:
    def __init__(self, node):
        # ...
        if isinstance(node, Text):
            if is_focusable(node.parent):
                self.role = "focusable text"
            else:
                self.role = "StaticText"
        else:
            if "role" in node.attributes:
                self.role = node.attributes["role"]
            elif node.tag == "a":
                self.role = "link"
            elif node.tag == "input":
                self.role = "textbox"
            elif node.tag == "button":
                self.role = "button"
            elif node.tag == "html":
                self.role = "document"
            elif is_focusable(node):
                self.role = "focusable"
            else:
                self.role = "none"
```

접근성 트리를 만들려면 HTML 트리를 재귀적으로 훑기만 하면 됩니다. 그 과정에서 역할이 `none`인 노드는 건너뛰되 그 자식으로는 여전히 재귀합니다.

```python
class AccessibilityNode:
    def build(self):
        for child_node in self.node.children:
            self.build_internal(child_node)

    def build_internal(self, child_node):
        child = AccessibilityNode(child_node)
        if child.role != "none":
            self.children.append(child)
            child.build()
        else:
            for grandchild_node in child_node.children:
                self.build_internal(grandchild_node)
```

### 더 알아보기

([Chromium 같은](https://www.chromium.org/developers/design-documents/multi-process-architecture/)) 다중 프로세스 브라우저에는 OS와 인터페이스하는 브라우저 프로세스가 있고, 웹 페이지를 로드하는 렌더 프로세스들이 있습니다. 스크린 리더 API는 동기적이므로 Chromium은 접근성 트리의 사본을 [두 개 저장하며](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/accessibility/browser/how_a11y_works_2.md), 하나는 브라우저에 하나는 각 렌더러에 두고 둘 사이의 변경만 주고받습니다. Chromium 이전의 Microsoft Edge를 비롯한 일부 브라우저가 쓰는 대안적 설계는 각 렌더 프로세스를 운영체제의 접근성 API 요청에 직접 연결하는 것입니다. 이렇게 하면 접근성 트리를 중복 저장할 필요가 없지만, 개별 탭에 운영체제를 노출하는 것은 보안 문제로 이어질 수 있습니다.

## 스크린 리더

보통 스크린 리더는 브라우저와는 별개의 애플리케이션이며,[^33] 브라우저는 OS별 API를 통해 그것과 통신합니다. 이 책을 플랫폼 독립적으로 유지하고 스크린 리더가 접근성 트리와 어떻게 상호작용하는지 더 명확히 보여 주기 위해, 스크린 리더 지원에 대한 논의에서는 대신 브라우저에 직접 통합된 최소한의 스크린 리더를 다루겠습니다.

그런데 우리 내장 스크린 리더는 `Browser`에 있어야 할까요, 아니면 각 `Tab`에 있어야 할까요? 현대 브라우저는 대체로 `Browser` 같은 것에서 스크린 리더와 대화하므로 우리도 그렇게 하겠습니다.[^34] 그러니 가장 먼저 할 일은 탭의 접근성 트리를 브라우저 스레드로 보내는 것입니다. 이는 [12장](https://browser.engineering/scheduling.html#committing-a-display-list)에서 소개한 커밋 개념의 자연스러운 확장입니다. 먼저 `CommitData`에 트리를 추가하겠습니다.

```python
class CommitData:
    def __init__(self, url, scroll, height, display_list,
            composited_updates, accessibility_tree):
        # ...
        self.accessibility_tree = accessibility_tree
```

그다음 `run_animation_frame`에서 그것을 보냅니다.

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        commit_data = CommitData(
            self.accessibility_tree,
            # ...
        # ...
        self.accessibility_tree = None

class Browser:
    def commit(self, tab, data):
        # ...
        self.accessibility_tree = data.accessibility_tree

    def clear_data(self):
        # ...
        self.accessibility_tree = None
```

디스플레이 리스트와 마찬가지로 데이터 경쟁을 피하기 위해 브라우저 스레드로 보낸 뒤 `accessibility_tree` 필드를 비운다는 점에 주의하세요.

이제 트리가 브라우저 스레드에 있으니 스크린 리더를 구현합시다. 보통 스크린 리더는 텍스트를 소리 내어 읽는데, 흔히 일반적인 말하기 속도보다 훨씬 빠릅니다. 그것은 건너뛰고(오디오 믹싱과 재생에 관한 온갖 복잡한 문제가 따라오니까요) 스크린 리더가 말할 텍스트를 화면에 출력하기만 하겠습니다.[^35]

다음 라이브러리를 사용해 텍스트를 오디오 파일로 변환하고 재생할 수 있습니다.

```python
def speak_text(text):
    print("SPEAK:", text)
```

우선 스크린 리더를 켜고 끄는 키 바인딩이 필요합니다. 실제 운영체제는 보통 더 잘 알려지지 않은 단축키를 쓰지만, 저는 이벤트 루프에서 `Ctrl-a`로 스크린 리더를 켜겠습니다.

`toggle_accessibility` 메서드는 `Tab`에 접근성이 켜졌다고 알려 줍니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.needs_accessibility = False
        self.accessibility_is_on = False

    def set_needs_accessibility(self):
        if not self.accessibility_is_on:
            return
        self.needs_accessibility = True
        self.needs_draw = True

    def toggle_accessibility(self):
        self.lock.acquire(blocking=True)
        self.accessibility_is_on = not self.accessibility_is_on
        self.set_needs_accessibility()
        self.lock.release()
```

```python
class Browser:
    def composite_raster_and_draw(self):
        # ...
        if self.needs_accessibility:
            self.update_accessibility()
```

그렇다면 스크린 리더는 무엇을 말해야 할까요? 그것은 사실 브라우저가 정할 일이 아닙니다. 스크린 리더는 독립적인 애플리케이션이고, 흔히 사용자가 많이 설정해 두며, 스스로 결정할 수 있습니다. 다만 간단한 디버깅 보조 도구로, 페이지가 로드되면 웹 페이지 전체를 말하는 스크린 리더를 작성하겠습니다. 물론 실제 스크린 리더는 그보다 훨씬 유연합니다.

문서 전체를 말하려면 각 `AccessibilityNode`를 어떻게 말할지 알아야 합니다. 이는 `Tab`에서 결정해야 하는데, 텍스트에 브라우저 스레드가 접근할 수 없는 DOM 콘텐츠가 포함되기 때문입니다. 그러니 `AccessibilityNode`에 `text` 필드를 추가하고 `build`에서 노드의 역할과 주변 DOM 문맥에 따라 설정합시다. 텍스트 노드의 경우 그냥 그 텍스트이고, 그 밖에는 요소 태그와 포커스 여부를 설명합니다.

```python
class AccessibilityNode:
    def __init__(self, node):
        # ...
        self.text = ""

    def build(self):
        for child_node in self.node.children:
            self.build_internal(child_node)

        if self.role == "StaticText":
            self.text = repr(self.node.text)
        elif self.role == "focusable text":
            self.text = "Focusable text: " + self.node.text
        elif self.role == "focusable":
            self.text = "Focusable element"
        elif self.role == "textbox":
            if "value" in self.node.attributes:
                value = self.node.attributes["value"]
            elif self.node.tag != "input" and self.node.children and \
                 isinstance(self.node.children[0], Text):
                value = self.node.children[0].text
            else:
                value = ""
            self.text = "Input box: " + value
        elif self.role == "button":
            self.text = "Button"
        elif self.role == "link":
            self.text = "Link"
        elif self.role == "alert":
            self.text = "Alert"
        elif self.role == "document":
            self.text = "Document"

        if self.node.is_focused:
            self.text += " is focused"
```

```python
class Browser:
    def __init__(self):
        # ...
        self.has_spoken_document = False

    def update_accessibility(self):
        if not self.accessibility_tree: return

        if not self.has_spoken_document:
            self.speak_document()
            self.has_spoken_document = True

    def speak_document(self):
        text = "Here are the document contents: "
        tree_list = tree_to_list(self.accessibility_tree, [])
        for accessibility_node in tree_list:
            new_text = accessibility_node.text
            if new_text:
                text += "\n"  + new_text

        speak_text(text)
```

문서 전체를 말하는 일은 한 번만 일어납니다. 하지만 사용자는 페이지를 둘러보는 동안 피드백이 필요할 수 있습니다. 예를 들어 사용자가 한 요소에서 다른 요소로 탭할 때, 자신이 무엇과 상호작용하고 있는지 알 수 있도록 새 요소가 읽히기를 바랄 수 있습니다.

그러려면 브라우저 스레드가 어떤 요소가 포커스되었는지 알아야 합니다. 그것을 `CommitData`에 추가합시다.

```python
        self.focus = focus
```

그러면 `tab_focus`가 `last_tab_focus`와 같지 않을 때 포커스가 옮겨졌고 포커스된 노드를 말할 때라는 것을 알 수 있습니다. 변경은 다음과 같습니다.

```python

        # ...

            self.tab_focus != self.last_tab_focus:

                    self.focus_a11y_node, "element focused ")
```

`speak_node` 메서드는 `speak_document`와 비슷하지만 노드 하나만 말합니다.

```python
class Browser:
    def speak_node(self, node, text):
        text += node.text
        if text and node.children and \
            node.children[0].role == "StaticText":
            text += " " + \
            node.children[0].text

        if text:
            speak_text(text)
```

실제 스크린 리더에는 훨씬 더 많은 것이 있습니다. 랜드마크, 서로 다른 단위로 텍스트 탐색하기, 요청 시 텍스트 반복하기 등이죠. 그런 기능들은 접근성 트리와 여러 노드의 역할을 다양하게 활용합니다. 하지만 이 책의 초점은 스크린 리더 자체가 아니라 브라우저이므로, 이 장의 나머지에서는 접근성을 지원하는 추가 브라우저 기능에 집중합시다.

### 더 알아보기

접근성 트리는 스크린 리더만을 위한 것이 아닙니다. 예를 들어 어떤 사용자는 음성 출력 대신, 또는 그것에 더해 [점자 디스플레이](https://en.wikipedia.org/wiki/Refreshable_braille_display) 같은 촉각 출력을 선호합니다. 출력 장치는 꽤 다르지만, 접근성 트리에는 여전히 페이지에 어떤 콘텐츠가 있는지, 그것과 상호작용할 수 있는지, 그 상태는 무엇인지 등의 모든 정보가 담겨 있습니다. 게다가 모든 출력 장치에 같은 접근성 트리를 사용하므로, (점자 디스플레이와 스크린 리더처럼) 둘 이상의 _보조 기술_ 을 사용하는 사용자도 일관된 정보를 받게 됩니다.

## 접근 가능한 알림

스크립트는 디스플레이 리스트와 직접 상호작용하지 않듯이 접근성 트리와도 직접 상호작용하지 않습니다. 다만 스크린 리더 사용자에게 더 나은 경험을 주기 위해, 스크립트가 페이지에 특정 변경을 하는 _이유_ 를 스크린 리더에 알려 주어야 할 때가 있습니다. 가장 흔한 예는 방금 한 동작이 실패했음을 알려 주는 알림(alert)입니다.[^36] 스크린 리더 사용자에게는 문서의 어디에 삽입되든 그 알림이 즉시 읽혀야 합니다.

`alert` 역할이 이 필요를 해결합니다. 스크린 리더는 사용자가 현재 문서의 어디에 있든 그 역할을 가진 요소를 즉시[^37] 읽습니다. 기본 역할이 `alert`인 HTML 요소는 없으므로, 이는 페이지 작성자가 `role` 속성을 명시적으로 설정해야 한다는 점에 주의하세요.

이제 구현으로 넘어갑시다. 먼저 `setAttribute` 메서드 지원을 추가해 스크립트가 `role` 속성을 바꿀 수 있게 해야 합니다. JavaScript 쪽에서는 그저 브라우저 API를 호출하기만 합니다.

```javascript
Node.prototype.setAttribute = function(attr, value) {
    return call_python("setAttribute", this.handle, attr, value);
}
```

Python 쪽도 꽤 단순합니다.

```python
class JSContext:
    def __init__(self, tab):
        # ...
        self.interp.export_function("setAttribute",
            self.setAttribute)
    # ...

    def setAttribute(self, handle, attr, value):
        elt = self.handle_to_node[handle]
        elt.attributes[attr] = value
        self.tab.set_needs_render()
```

이제 `alert` 역할을 구현할 수 있습니다. 접근성 트리에서 그 역할을 가진 요소를 찾습니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.active_alerts = []

    def update_accessibility(self):
        self.active_alerts = [
            node for node in tree_to_list(
                self.accessibility_tree, [])
            if node.role == "alert"
        ]
        # ...
```

그런데 매 프레임마다 모든 `alert`를 읽을 수는 없습니다. 두 번 읽지 않도록 어떤 요소가 이미 읽혔는지 추적해야 합니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.spoken_alerts = []

    def update_accessibility(self):
        # ...
        for alert in self.active_alerts:
            if alert not in self.spoken_alerts:
                self.speak_node(alert, "New alert")
                self.spoken_alerts.append(alert)
```

`spoken_alerts`가 접근성 트리를 가리키므로, 접근성 트리가 다시 만들어질 때마다 새 트리를 가리키도록 갱신해야 합니다. 합성과 마찬가지로 접근성 트리의 `node` 포인터를 사용해 옛 접근성 트리와 새 접근성 트리의 접근성 노드를 짝지으세요. 이 짝짓기를 `commit` 안에서 _할 수도_ 있지만, 그 메서드는 브라우저 스레드와 메인 스레드 양쪽을 막으므로 최대한 빨라야 합니다. 그러니 `update_accessibility`에서 하는 것이 가장 좋습니다.

```python
class Browser:
    def update_accessibility(self):
        # ...
        new_spoken_alerts = []
        for old_node in self.spoken_alerts:
            new_nodes = [
                node for node in tree_to_list(
                    self.accessibility_tree, [])
                if node.node == old_node.node
                and node.role == "alert"
            ]
            if new_nodes:
                new_spoken_alerts.append(new_nodes[0])
        self.spoken_alerts = new_spoken_alerts
        # ...
```

어떤 노드가 `alert` 역할을 _잃으면_ `spoken_alerts`에서 제거해서, 나중에 다시 `alert` 역할을 얻으면 다시 읽히도록 한다는 점에 주의하세요. 예외적인 경우처럼 들리겠지만, 모든 알림에 요소 하나를 쓰고 (예를 들어) 그 클래스만 숨김에서 보임으로 바꾸는 것은 흔한 패턴입니다.

이제 [이 예제](https://browser.engineering/examples/example14-alert-role.html)를 불러와 버튼을 클릭하면 알림 텍스트가 들릴 것입니다.

### 더 알아보기

`alert` 역할은 ARIA가 "라이브 영역(live region)"이라고 부르는 것의 한 예로, 사용자 동작의 결과로 바뀔 수 있는 페이지 영역입니다. (`status`나 `alertdialog` 같은) 다른 역할들도 있고, `aria-live` 속성으로 "정중함(politeness)"을 설정해 라이브 영역을 더 세밀하게 설정할 수도 있습니다(단정적(assertive) 알림은 사용자를 방해하지만 정중한(polite) 알림은 그러지 않습니다). `aria-atomic`과 `aria-relevant`로 어떤 종류의 변경을 알릴지, `aria-busy`로 라이브 영역이 완료 상태인지 중간 상태인지도 설정할 수 있습니다. 게다가 라이브 영역을 만드는 데는 `aria-live`만 있으면 되고 역할은 필요 없습니다.

## 음성과 시각의 결합

이 장의 작업 덕분에 우리 렌더링 파이프라인은 이제 기본적으로 두 가지 출력을 갖습니다. 시각적 상호작용을 위한 디스플레이 리스트와 스크린 리더 상호작용을 위한 접근성 트리입니다. 많은 사용자는 둘 중 하나만 쓸 것입니다. 하지만 둘을 함께 쓰는 것도 가치가 있을 수 있습니다. 예를 들어 어떤 사용자는 시력이 제한적이어서 웹 페이지의 전체적인 항목은 알아볼 수 있지만 텍스트는 읽지 못할 수 있습니다. 그런 사용자는 마우스로 페이지를 탐색하되, 마우스 아래에 있는 항목을 스크린 리더가 읽어 주기를 바랄 수 있습니다.

그것을 해 봅시다. 이 특정 기능을 구현하려면 각 접근성 노드가 페이지에서의 자기 기하 정보를 알아야 합니다. 그러면 사용자는 스크린 리더에게 ([히트 테스팅](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/accessibility/browser/how_a11y_works_3.md#Hit-testing)을 통해) 마우스 아래에 어떤 객체가 있는지 알아내 소리 내어 읽으라고 지시할 수 있습니다.

기하 정보에 접근하는 것은 까다로운데, 접근성 트리는 HTML 트리에서 생성되는 반면 기하 정보는 레이아웃 트리에서 접근 가능하기 때문입니다. 이를 돕기 위해 각 `Element` 객체에 `layout_object` 포인터를 추가합시다.[^38]

```python
class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.layout_object = None

class Text:
    def __init__(self, text, parent):
        # ...
        self.layout_object = None
```

이제 레이아웃 객체를 만들 때 그 `Element`의 `layout_object` 필드를 채울 수 있습니다. `BlockLayout`에서는 다음과 같습니다.

```python
class BlockLayout:
    def __init__(self, node, parent, previous):
        # ...
        node.layout_object = self
```

다른 모든 종류의 레이아웃 객체 생성자에도 비슷한 코드 줄을 반드시 추가하세요. 그러면 각 `AccessibilityNode`가 레이아웃 객체의 경계를 저장할 수 있습니다.

```python
class AccessibilityNode:
    def __init__(self, node):
        # ...
        self.bounds = self.compute_bounds()

    def compute_bounds(self):
        if self.node.layout_object:
            return [absolute_bounds_for_obj(self.node.layout_object)]
        # ...
```

여기서 `absolute_bounds_for_obj`를 쓴다는 점에 주의하세요. 우리가 관심 있는 경계는 `translate` 같은 변환이 적용된 뒤 화면상의 절대 좌표이기 때문입니다.

그런데 또 다른 복잡한 점이 있습니다. `node.layout_object`가 설정되어 있지 않을 수 있습니다. 예를 들어 텍스트 노드에는 그것이 없습니다.[^39] 마찬가지로 인라인 레이아웃을 가진 노드도 대체로 없습니다. 그래서 트리를 거슬러 올라가 `BlockLayout`을 가진 부모를 찾고, 현재 `node`의 자식인 모든 `LineLayout` 안의 모든 텍스트 노드를 합집합해야 합니다. 그리고 `LineLayout`과 텍스트 노드가 여러 개일 수 있으므로 경계는 `skia.Rect` 객체의 배열이어야 합니다.

```python
class AccessibilityNode:
    def compute_bounds(self):
        # ...
        if isinstance(self.node, Text):
            return []
        inline = self.node.parent
        bounds = []
        while not inline.layout_object: inline = inline.parent
        for line in inline.layout_object.children:
            line_bounds = skia.Rect.MakeEmpty()
            for child in line.children:
                if child.node.parent == self.node:
                    line_bounds.join(skia.Rect.MakeXYWH(
                        child.x, child.y, child.width, child.height))
            bounds.append(line_bounds)
        return bounds
```

그러면 이제 마우스 올림 시 읽기 기능을 구현해 봅시다. 먼저 이벤트 루프에서 마우스 이동 이벤트를 들어야 하는데, SDL에서는 `MOUSEMOTION`이라고 부릅니다.

```python
def mainloop(browser):
    while True:
        if sdl2.SDL_PollEvent(ctypes.byref(event)) != 0:
            # ...
            elif event.type == sdl2.SDL_MOUSEMOTION:
                browser.handle_hover(event.motion)
```

브라우저는 마우스가 올려진 위치를 듣고, 그것이 접근성 노드 위에 있는지 판단하고, 그 노드를 강조해야 합니다. 정상적인 렌더링 박자를 방해하고 싶지 않으므로 `handle_hover`에서는 호버 이벤트를 저장해 두고 `composite_raster_and_draw`에서 호버에 반응하겠습니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.pending_hover = None

    def handle_hover(self, event):
        if not self.accessibility_is_on or \
            not self.accessibility_tree:
            return
        self.pending_hover = (event.x, event.y - self.chrome.bottom)
        self.set_needs_accessibility()
```

사용자가 어떤 노드 위에 마우스를 올리면 두 가지를 하겠습니다. 첫째, 그 경계를 화면에 그립니다. 이는 사용자가 무엇 위에 있는지 보는 데 도움이 되고 디버깅에도 유용합니다. 이는 `paint_draw_list`에서 하는데, 사용자가 올려 둔 접근성 노드를 찾는 것부터 시작합니다(스크롤을 고려해야 한다는 점에 주의하세요).

```python
class Browser:
    def __init__(self):
        # ...
        self.hovered_a11y_node = None

    def paint_draw_list(self):
        # ...
        if self.pending_hover:
            (x, y) = self.pending_hover
            y += self.active_tab_scroll
            a11y_node = self.accessibility_tree.hit_test(x, y)
```

그런데 `a11y_node`의 `a11y`라는 약어는 "a", 숫자 11, "y"로 이루어진 것으로 "accessibility"라는 단어의 흔한 축약입니다.[^40] `hit_test` 함수는 접근성 트리를 재귀합니다.

```python
class AccessibilityNode:
    def contains_point(self, x, y):
        for bound in self.bounds:
            if bound.contains(x, y):
                return True
        return False

    def hit_test(self, x, y):
        node = None
        if self.contains_point(x, y):
            node = self
        for child in self.children:
            res = child.hit_test(x, y)
            if res: node = res
        return node
```

히트 테스트가 끝나고 브라우저가 사용자가 어떤 노드 위에 있는지 알게 되면, 외곽선이 프레임 사이에 유지되도록 이 정보를 `Browser`에 저장하고 외곽선을 그립니다.

```python
class Browser:
    def paint_draw_list(self):
        if self.pending_hover:
            # ...
            if a11y_node:
                self.hovered_a11y_node = a11y_node
            self.pending_hover = None
```

마지막으로 `paint_draw_list` 끝에서 외곽선을 그릴 수 있습니다.

```python
class Browser:
    def paint_draw_list(self):
        # ...
        if self.hovered_a11y_node:
            for bound in self.hovered_a11y_node.bounds:
                self.draw_list.append(DrawOutline(
                    bound,
                    "white" if self.dark_mode else "black", 2))
```

외곽선의 색이 다크 모드가 켜져 있는지에 따라 달라진다는 점에 주의하세요. 높은 대비를 보장하기 위해서입니다.

이제 외곽선이 그려집니다. 하지만 추가로 사용자가 올려 둔 것을 말해 주고 싶습니다. 그러려면 또 다른 플래그 `needs_speak_hovered_node`가 필요한데, 호버가 한 요소에서 다른 요소로 옮겨갈 때마다 설정하겠습니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.needs_speak_hovered_node = False

    def paint_draw_list(self):
        if self.pending_hover:
            if a11y_node:
                if not self.hovered_a11y_node or \
                    a11y_node.node != self.hovered_a11y_node.node:
                    self.needs_speak_hovered_node = True
                # ...
```

보기 흉한 조건문은 두 가지 경우를 처리하기 위해 필요합니다. 이전에 아무것도 호버되지 않은 상태에서 어떤 객체 위로 올리는 경우와, 마우스를 한 객체에서 다른 객체로 옮기는 경우입니다. 두 경우 모두 플래그를 설정하고, 그다음 `update_accessibility`에서 그 플래그를 사용합니다.

```python
class Browser:
    def update_accessibility(self):
        # ...
        if self.needs_speak_hovered_node:
            self.speak_node(self.hovered_a11y_node, "Hit test ")
        self.needs_speak_hovered_node = False
```

이제 접근성 모드를 켜고 페이지 위로 마우스를 움직이면 무엇 위에 있는지에 대해 시각적 피드백과 청각적 피드백을 모두 받을 수 있을 것입니다!

### 더 알아보기

흔한 문제 하나는 웹 페이지 작성자가 맞춤 입력 요소를 만들면서 접근성을 별로 생각하지 않는 것입니다. 그 이유는 내장 입력 요소는 스타일을 주기 어려워서, 작성자들이 더 보기 좋은 것을 직접 만들기 때문입니다.

내장 입력 요소는 흔히 여러 개의 분리된 부분으로 이루어집니다. `file` 입력의 경로와 버튼, `checkbox` 요소의 체크 박스, `select` 드롭다운의 팝업 메뉴 같은 것들이죠. 그리고 CSS는 그런 "복합" 요소에 스타일을 주는 데 (아직) 능하지 않습니다. `::backdrop`이나 `::file-selector-button` 같은 [의사 요소](https://developer.mozilla.org/en-US/docs/Web/CSS/Pseudo-elements)가 도움이 되기는 합니다. 아마 최선의 해결책은 새로운 [완전히 스타일 지정 가능한](https://blogs.windows.com/msedgedev/2022/05/05/styling-select-elements-for-real/) 입력 요소를 위한 [표준](https://open-ui.org/#proposals)일 것입니다.

## 요약

이 장에서는 접근성, 즉 _모든_ 사용자가 웹사이트에 접근하고 상호작용할 수 있게 하는 기능들을 소개하고, 브라우저에서 가장 흔한 접근성 문제 몇 가지를 어떻게 해결하는지 보여 주었습니다. 핵심은 다음과 같습니다.

- HTML의 의미론적이고 선언적인 성격은 접근성 기능을 자연스러운 확장으로 만들어 줍니다.

- 접근성 기능은 흔히 여러 필요를 동시에 충족하며, 거의 모든 사람이 어떤 식으로든 이 기능들에서 이득을 얻습니다.

- 접근성 트리는 디스플레이 리스트와 비슷하며, 브라우저가 스크린 리더를 비롯한 보조 기술과 상호작용하는 것을 이끕니다.

- 다크 모드, 키보드 내비게이션, 외곽선 같은 새 기능은 최대한 쓸모 있으려면 웹 페이지 작성자가 맞춤 설정할 수 있어야 합니다.

이 장의 브라우저를 시험해 보려면 [여기](https://browser.engineering/widgets/lab14-browser.html)를 클릭하세요.

## 연습문제

**14-1 _대비가 좋은 포커스 링_.** 더 두꺼운 흰색 외곽선과 더 얇은 검은색 외곽선 두 개를 사용해 포커스 링과 주변 콘텐츠 사이에 대비가 보장되도록 포커스 표시의 대비를 개선하세요.

**14-2 _focus 메서드와 이벤트_.** JavaScript [`focus()`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/focus) 메서드와 DOM 요소의 대응하는 [`focus`](https://developer.mozilla.org/en-US/docs/Web/API/Element/focus_event), [`blur`](https://developer.mozilla.org/en-US/docs/Web/API/Element/blur_event) 이벤트 지원을 추가하세요. `focus()`가 포커스 가능한 요소에만 효과가 있도록 하세요. 조심하세요. 요소의 위치를 읽기 전에 레이아웃이 최신인지 확인해야 합니다.

**14-3 _읽는 동안 요소 강조하기_.** 문서를 읽는 메서드는 동작하지만, 마우스 호버에서 했던 것과 비슷하게 읽히고 있는 요소를 강조해 주면 좋을 것입니다. 그것을 구현하세요. `speak_document` 메서드를 접근성 포커스를 한 노드씩 옮기고 그것을 말하는 `advance_accessibility` 메서드로 대체하고 싶을 수도 있습니다.

**14-4 _너비 미디어 쿼리_.** 확대하거나 축소하면 CSS 픽셀 단위의 페이지 너비가 바뀝니다. 즉 예전에는 페이지에 편안하게 들어가던 요소들이 더 이상 들어가지 않을 수 있고, 페이지가 충분히 좁아지면 다른 레이아웃이 더 알맞을 수 있습니다. [`max-width` 미디어 쿼리](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/width)는 개발자가 사용 가능한 너비에 따라 페이지에 다르게 스타일을 줄 수 있게 해 주며, CSS 픽셀 단위 페이지 너비가 주어진 길이 이하일 때만 활성화됩니다.[^41] 이 미디어 쿼리를 구현하세요. 확대하거나 축소하면 이 미디어 쿼리가 유발되는지 테스트하세요.

연습문제를 마치면 [이 예제](https://browser.engineering/examples/example14-maxwidth-media.html)가 좁은 화면에서 초록색 텍스트를 보여 주어야 합니다.

**14-5 _혼합 인라인_.** 중첩된 인라인 요소에서 포커스 링이 올바르게 동작하게 만드세요. 예를 들어 `<a>a <b>bold</b> link</a>`에서, 사용자가 그 링크에 포커스하면 포커스 링이 세 단어 전체를 덮어야 하고, 인라인이 여러 줄에 걸치면 여러 개의 사각형으로 덮어야 합니다. 다만 사용자가 `<div tabindex=2>many<br>lines</div>` 같은 블록 수준 요소에 포커스하면 각 줄마다 포커스 링이 아니라 블록 전체에 하나가 있어야 합니다.

**14-6 _스레드화된 접근성_.** 접근성 코드는 현재 브라우저 스레드에서 텍스트를 말하며, 말하는 동안 브라우저 스레드를 막습니다. 이는 쓰기 답답합니다. 말하기를 새로운 접근성 스레드로 옮겨 이를 해결하세요.

**14-7 _고대비 모드_.** 고대비 [forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors) 모드를 구현하세요. 이 모드는 모든 색을 소수의 [고대비](https://www.w3.org/TR/WCAG21/#contrast-minimum) 색 집합 중 하나로 대체해야 합니다.

**14-8 _`focus-visible`_.** 사용자가 링크로 탭했을 때는 아마 포커스 표시를 보여 주고 싶겠지만, 사용자가 그것을 클릭했다면 대부분의 브라우저는 그러지 않습니다. 사용자가 포커스된 요소가 어디인지 알고 있으니까요! 그리고 불필요한 포커스 표시는 보기 흉하거나 주의를 흩뜨릴 수 있습니다. 비슷한 휴리스틱을 구현하세요. 버튼을 클릭하면 포커스는 되지만 포커스 표시는 보이지 않아야 합니다. (버튼을 클릭해도 새 페이지로 이동하지 않도록 폼 바깥에 버튼을 둔 [포커스 예제](https://browser.engineering/examples/example14-focus.html)에서 테스트하세요.) 하지만 입력 요소는 클릭하든 탭하든 포커스 링이 보여야 합니다. [`:focus-visible` 의사 클래스](https://developer.mozilla.org/en-US/docs/Web/CSS/:focus-visible) 지원도 추가하세요. 이는 요소가 포커스되어 있고 _동시에_ 브라우저가 포커스 링을 그렸을 경우에만 적용됩니다(포커스 링이 _보였을(visible)_ 것이라서 그런 이름입니다). 덕분에 맞춤 위젯이 위에서 언급한 유용한 브라우저 휴리스틱을 잃지 않으면서 포커스 링 스타일을 바꿀 수 있습니다.

**14-9 _OS 통합_.** [`accessible_output`](https://pypi.org/project/accessible_output/) Python 라이브러리를 추가하고 그것을 사용해 여러분 OS의 내장 스크린 리더와 직접 통합하세요. 이 장의 예제 몇 가지를 시험해 보고 실제 브라우저와 동작을 비교해 보세요.

**14-10 _`zoom` CSS 속성_.** [`zoom`](https://developer.mozilla.org/en-US/docs/Web/CSS/zoom) CSS 속성 지원을 추가하세요. 이는 확대 접근성 기능과 같은 기능을 웹 개발자에게 노출하며, 지정된 HTML 서브트리에만 적용할 수도 있게 해 줍니다.

**14-11 _소리 내어 말하기_.** 웹 페이지를 실제로 소리 내어 읽는 코드를 추가하세요. [`pyttsx`](https://pypi.org/project/pyttsx3/) 라이브러리는 "논블로킹" 모드로 텍스트를 말할 수 있지만 브라우저 이벤트 루프와의 통합이 조금 필요합니다. 사용자가 노드 위로 마우스를 올리거나 문서를 탭으로 훑을 때 말하기를 반드시 중단시키세요. 작성자가 현재 말하기를 중단시키는 `assertive` 알림이나 그러지 않는 `polite` 알림을 만들 수 있도록 `aria-live` 속성을 구현하세요.
