복잡한 웹 애플리케이션은 상태 사이를 전환할 때 _애니메이션_ 을 사용합니다. 이 애니메이션은 사용자가 상태 변화를 이해하도록 돕고, 갑작스러운 도약을 점진적인 변화로 대체해 시각적 완성도를 높여 줍니다. 하지만 이런 애니메이션을 매끄럽게 실행하려면 브라우저는 각 애니메이션 프레임에 드는 시간을 최소화해야 합니다. 시각 효과를 빠르게 하기 위해 GPU 가속을 쓰고, 렌더링 작업을 최소화하기 위해 합성(compositing)을 써야 합니다.

## JavaScript 애니메이션

[애니메이션](https://en.wikipedia.org/wiki/Animation)이란 정지 그림을 빠르게 연속해서 보여 주어 사람 눈에 _움직임_ 의 착각을 만들어 내는 것입니다.[^1] 전형적인 웹 페이지 애니메이션에는 요소의 색을 바꾸거나, 서서히 나타나거나 사라지게 하거나, 크기를 조절하는 것이 있습니다. 브라우저는 스크롤, 크기 조절, 핀치 줌 같은 사용자 동작에 반응할 때도 애니메이션을 사용합니다. 게다가 (비디오 같은) 어떤 종류의 애니메이션 미디어는 웹 페이지에 포함될 수 있습니다.[^2]

이 장에서는 웹 페이지 요소의 애니메이션에 집중하겠습니다. [12장에서 구현한](https://browser.engineering/scheduling.html#animating-frames) `requestAnimationFrame` API를 사용해 간단한 애니메이션을 작성하는 것부터 시작합시다. 이 메서드는 어떤 JavaScript 코드를 다음 프레임에 실행해 달라고 요청합니다. 여러 프레임에 걸쳐 반복 실행하려면 그 JavaScript 코드가 스스로 `requestAnimationFrame`을 호출하게 하면 됩니다.

```
function run_animation_frame() {
    if (animate())
        requestAnimationFrame(run_animation_frame);
}
requestAnimationFrame(run_animation_frame);
```

그러면 `animate` 함수가 페이지에 작은 변화를 주어 연속적인 변화의 인상을 만들어 냅니다.[^3] `animate`가 하는 일을 바꾸면 어떤 애니메이션이 일어나는지 바꿀 수 있습니다.

예를 들어 요소의 `opacity` 값을 0.1에서 0.999로 매끄럽게 전환해 서서히 나타나게 할 수 있습니다.[^4] 이를 120프레임(약 4초)에 걸쳐 하면 프레임마다 불투명도를 약 0.008씩 늘리게 됩니다.

그러니 텍스트가 들어 있는 이 `div`를 가져와서

```
<div>This text fades</div>
```

그 `opacity`를 조금씩 바꾸는 `animate` 함수를 작성해 봅시다.

```
var div = document.querySelectorAll("div")[0];
var total_frames = 120;
var current_frame = 0;
var change_per_frame = (0.999 - 0.1) / total_frames;
function animate() {
    current_frame++;
    var new_opacity = current_frame * change_per_frame + 0.1;
    div.style = "opacity:" + new_opacity;
    return current_frame < total_frames;
}
```

다음은 그 모습입니다. 버튼을 클릭해 페이드를 시작해 보세요.

> 🔗 대화형 위젯: [example13-opacity-raf.html](https://browser.engineering/examples/example13-opacity-raf.html)

이 애니메이션은 우리 브라우저에서 _거의_ 실행되지만, JavaScript에서 요소의 `style` 속성을 바꾸는 지원을 추가해야 합니다. 그러려면 JavaScript 런타임에서 `Node`의 `style` 속성에 세터를 등록하세요.

```javascript
Object.defineProperty(Node.prototype, 'style', {
    set: function(s) {
        call_python("style_set", this.handle, s.toString());
    }
});
```

그다음 브라우저 안에서 `style_set` 핸들러를 정의합니다.

```python
class JSContext:
    def __init__(self, tab):
        # ...
        self.interp.export_function("style_set", self.style_set)

     def style_set(self, handle, s):
        elt = self.handle_to_node[handle]
        elt.attributes["style"] = s;
        self.tab.set_needs_render()
```

중요한 점은, `style_set` 함수가 브라우저가 새 `style` 매개변수로 웹 페이지를 다시 렌더링하도록 `needs_render` 플래그를 설정한다는 것입니다. 이 변경들로 이제 여러분의 브라우저에서 이 애니메이션을 열어 실행할 수 있을 것입니다.

### 더 알아보기

이 절에서 소개한 애니메이션 패턴은 [2장](https://browser.engineering/graphics.html#creating-windows)에서 처음 소개하고 [12장](https://browser.engineering/scheduling.html#animating-frames)에서 더 발전시킨 _이벤트 루프_ 의 또 다른 예입니다. 이 장에서 새로운 점은, 이제 마침내 의미 있고 실용적인 애니메이션을 실제로 만들 만큼 기술이 쌓였다는 것입니다. 웹에서도 같은 일이 일어났습니다. 제대로 된 애니메이션을 위한 수많은 API가, `requestAnimationFrame` API부터 CSS 네이티브 애니메이션까지, [2010년대](https://en.wikipedia.org/wiki/CSS_animations)에 와서야 등장했습니다.

## GPU 가속

여러분의 브라우저에서 페이드 애니메이션을 시험해 보면 아마 그리 매끄럽지 않다는 것을 알아차릴 것입니다. 놀랄 일은 아닙니다. [12장](https://browser.engineering/scheduling.html#profiling-rendering)에서 단순한 페이지에서도 래스터화와 그리기가 약 62ms, 렌더링이 23ms였다는 것을 보았으니까요.

프레임당 62ms만 해도 우리 브라우저는 겨우 초당 15프레임을 내고 있습니다. 매끄러운 애니메이션을 위해서는 30프레임이 필요합니다! 그러니 래스터화와 그리기를 빠르게 해야 합니다.

그렇게 하는 가장 좋은 방법은 래스터화와 그리기를 [GPU](https://en.wikipedia.org/wiki/Graphics_processing_unit)로 옮기는 것입니다. GPU는 본질적으로 여러분 컴퓨터 안의 칩으로 CPU와 비슷하게 프로그램을 실행하지만, 아주 단순한 프로그램을 대규모 병렬로 실행하는 데 특화되어 있습니다. 화면의 모든 픽셀에 단순한 연산을 병렬로 적용하기 위해 개발되었기 때문입니다. 덕분에 GPU는 단순한 도형을 그리는 데 더 빠르고, 시각 효과를 적용하는 데는 _훨씬_ 더 빠릅니다.

큰 틀에서 GPU에서 래스터화하고 그리려면 우리 브라우저는 다음을 해야 합니다.[^5]

- 디스플레이 리스트를 특수한 GPU 메모리로 _업로드_ 합니다.

- 디스플레이 리스트를 래스터화하고 그리는 GPU 프로그램을 _컴파일_ 합니다.[^6]

- 모든 그리기 명령을 GPU 텍스처로 _래스터화_ 합니다.[^7]

- 그 텍스처를 화면에 _그립니다_.

다행히 SDL과 Skia는 GPU와 이 모든 단계를 지원합니다. 대체로 그것들이 GPU에서 일어나도록 알맞은 매개변수를 넘겨 주기만 하면 됩니다. 그렇게 해 봅시다. 실제 브라우저는 보통 CPU와 GPU 양쪽의 래스터화·그리기를 모두 구현한다는 점에 주의하세요. 어떤 경우에는 CPU 래스터화·그리기가 GPU를 쓰는 것보다 빠를 수 있고, 버그를 우회하기 위해 필요할 수도 있기 때문입니다.[^8] 우리 브라우저에서는 단순함을 위해 항상 GPU를 사용하겠습니다.

먼저 OpenGL 라이브러리를 설치해야 합니다.

```
pip3 install PyOpenGL
```

그리고 import합니다.

```python
import OpenGL.GL
```

이제 SDL이 OpenGL을 쓰도록 설정하고 프로그램 시작/종료 시점에 [GL 컨텍스트](https://www.khronos.org/opengl/wiki/OpenGL_Context)를 시작하고 끝내야 합니다. 우리 목적에서는 그냥 API 상용구라고 생각하면 됩니다.[^9]

```python
class Browser:
    def __init__(self):
        # ...
        self.sdl_window = sdl2.SDL_CreateWindow(b"Browser",
            sdl2.SDL_WINDOWPOS_CENTERED,
            sdl2.SDL_WINDOWPOS_CENTERED,
            WIDTH, HEIGHT,
            sdl2.SDL_WINDOW_SHOWN | sdl2.SDL_WINDOW_OPENGL)

        sdl2.SDL_GL_SetAttribute(sdl2.SDL_GL_CONTEXT_MAJOR_VERSION, 3)
        sdl2.SDL_GL_SetAttribute(sdl2.SDL_GL_CONTEXT_MINOR_VERSION, 2)
        sdl2.SDL_GL_SetAttribute(
            sdl2.SDL_GL_CONTEXT_FORWARD_COMPATIBLE_FLAG, True)
        sdl2.SDL_GL_SetAttribute(sdl2.SDL_GL_CONTEXT_PROFILE_MASK,
                                 sdl2.SDL_GL_CONTEXT_PROFILE_CORE)
        self.gl_context = sdl2.SDL_GL_CreateContext(
            self.sdl_window)
        print(("OpenGL initialized: vendor={}," + \
            "renderer={}").format(
            OpenGL.GL.glGetString(OpenGL.GL.GL_VENDOR),
            OpenGL.GL.glGetString(OpenGL.GL.GL_RENDERER)))

    def handle_quit(self):
        # ...
        sdl2.SDL_GL_DeleteContext(self.gl_context)
        sdl2.SDL_DestroyWindow(self.sdl_window)
```

그 `print` 문은 브라우저가 사용 중인 GPU 벤더와 렌더러를 보여 주는데, 이는 실제로 여러분의 GPU를 쓰고 있는지 확인하는 데 도움이 됩니다. 저는 이 장을 쓰는 데 Chromebook을 쓰고 있어서 다음과 같이 나옵니다.[^10]

```
OpenGL initialized: vendor=b'Red Hat', renderer=b'virgl'
```

이제 Skia가 화면에 직접 그리도록 설정할 수 있습니다. 주문은 다음과 같습니다.[^11]

```python
class Browser:
    def __init__(self):
        # ...
        self.skia_context = skia.GrDirectContext.MakeGL()

        self.root_surface = \
            skia.Surface.MakeFromBackendRenderTarget(
            self.skia_context,
            skia.GrBackendRenderTarget(
                WIDTH, HEIGHT, 0, 0,
                skia.GrGLFramebufferInfo(
                    0, OpenGL.GL.GL_RGBA8)),
                skia.kBottomLeft_GrSurfaceOrigin,
                skia.kRGBA_8888_ColorType,
                skia.ColorSpace.MakeSRGB())
        assert self.root_surface is not None
```

OpenGL을 쓰는 또 다른 이점은 Skia와 SDL 사이에서 데이터를 복사할 필요가 더 이상 없다는 것입니다. 대신 Skia 서피스를 _플러시_ 하고(Skia 서피스는 지연 그리기를 합니다) `SDL_GL_SwapWindow`를 호출해 (OpenGL의 [더블 버퍼링](https://wiki.libsdl.org/SDL_GL_SwapWindow) 때문에) 새 프레임버퍼를 활성화하기만 하면 됩니다.

```python
class Browser:
    def draw(self):
        # ...
        self.root_surface.flushAndSubmit()
        sdl2.SDL_GL_SwapWindow(self.sdl_window)
```

마지막으로 우리 브라우저는 `chrome_surface`와 `tab_surface`를 위한 Skia 서피스도 만듭니다. 이것들은 화면에 직접 그리고 싶지 않으므로 주문이 조금 다릅니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.chrome_surface = skia.Surface.MakeRenderTarget(
                self.skia_context, skia.Budgeted.kNo,
                skia.ImageInfo.MakeN32Premul(
                    WIDTH, math.ceil(self.chrome.bottom)))
        assert self.chrome_surface is not None
```

다시 말하지만 이 변경들은 대체로 상용구라고 생각하면 됩니다. GPU 동작의 세부 사항은 여기서 우리의 초점이 아니니까요.[^12] `tab_surface`에도 (너비와 높이 인자만 다르게) 같은 처리를 반드시 적용하세요.

SDL과 Skia의 철저한 GPU 렌더링 지원 덕분에 우리 브라우저가 GPU에서 래스터화하고 그리는 데 필요한 것은 이것으로 전부입니다. 그리고 예상대로 속도가 크게 개선되었습니다. 제 경우 래스터화와 그리기가 평균 7ms로 개선되었습니다(그림 1 참조).

### 더 알아보기

Skia에서 고속이고 안정적이며 크로스 플랫폼인 GPU 래스터 경로는 몇 년 전에야 생겼습니다.[^13] Chromium 초창기에는 CPU 래스터만 있었습니다. 스크롤은 이 책의 앞부분 장들처럼 콘텐츠를 다시 래스터화하는 방식으로 구현되었습니다. 당시에는 이것이 받아들일 만하다고 여겨졌는데, 전반적으로 컴퓨터가 오늘날보다 훨씬 느렸고, GPU는 훨씬 덜 안정적이었으며, 애니메이션은 덜 빈번했고, Android와 iOS 같은 모바일 플랫폼은 아직 부상하는 중이었기 때문입니다. (사실 초기 버전의 Android에도 GPU 가속이 없었습니다.) Firefox와 Safari도 대체로 마찬가지였지만, Safari는 macOS와 iOS가 지원하는 제한된 수의 GPU만 대상으로 했기 때문에 콘텐츠를 더 쉽게 가속할 수 있었습니다.

GPU 가속 래스터를 구현하는 데는 _많은_ 어려움이 있습니다. 그중에는 수많은 GPU 아키텍처에서 올바르게 동작하게 하는 것, 복잡한 상황이나 오류 상황에서 우아하게 CPU 래스터로 되돌아가는 것, 안티에일리어싱된 복잡한 도형 같은 까다로운 상황에서 콘텐츠를 효율적으로 GPU 래스터화할 방법을 찾는 것이 있습니다. 그러니 우리 브라우저에서 이제야 GPU 가속을 켜는 것이 이상해 보일 수 있지만, 이 또한 브라우저의 진화 시간선을 반영합니다.

## 합성

그렇다면 래스터화·그리기 단계에서 어떻게 일을 덜 할 수 있을까요? 답은 _합성(compositing)_ 이라는 기법인데, 이는 그저 래스터화된 이미지 일부를 GPU에 캐시해 두었다가 나중 프레임에서 재사용한다는 뜻입니다.[^14]

합성을 설명하려면 우리 브라우저의 디스플레이 리스트를 생각해 봐야 하고, 그러려면 그것을 출력해 보는 것이 유용합니다. 예를 들어 `DrawRect`에 대해서는 다음과 같이 출력할 수 있습니다.

```python
class DrawRect:
    def __repr__(self):
        return ("DrawRect(top={} left={} " +
            "bottom={} right={} color={})").format(
            self.top, self.left, self.bottom,
            self.right, self.color)
```

`Blend` 명령은 불투명도나 블렌딩 모드가 넘어오지 않으면 때때로 아무 일도 하지 않습니다. 출력할 때 그것을 표시해 주면 도움이 됩니다.

```python
class Blend:
    def __repr__(self):
        args = ""
        if self.opacity < 1:
            args += ", opacity={}".format(self.opacity)
        if self.blend_mode:
            args += ", blend_mode={}".format(self.blend_mode)
        if not args:
            args = ", <no-op>"
        return "Blend({})".format(args[2:])
```

`print_tree`가 `children` 필드에 의존하므로 모든 페인트 명령에 `children` 필드도 추가해야 합니다. 이제 우리 브라우저의 디스플레이 리스트를 출력할 수 있습니다.

```
class Tab:
    def render(self):
        # ...
        for item in self.display_list:
            print_tree(item)
```

우리 불투명도 예제의 경우, 어느 한 프레임의 디스플레이 리스트(의 핵심 부분)는 다음과 같이 보일 수 있습니다.

```
Blend(alpha=0.119866666667)
  DrawText(text=This)
  DrawText(text=text)
  DrawText(text=fades)
```

다음 프레임에서는 대신 다음과 같이 보일 수 있습니다.

```
Blend(alpha=0.112375)
  DrawText(text=This)
  DrawText(text=text)
  DrawText(text=fades)
```

두 경우 모두, 이 디스플레이 리스트를 래스터화한다는 것은 먼저 세 단어를 `Blend`가 만든 Skia 서피스에 래스터화하고, 그다음 투명도를 적용하면서 그것을 루트 서피스로 복사한다는 뜻입니다. 결정적으로 두 프레임에서 래스터화는 동일하고 복사만 다릅니다. 즉 캐싱으로 속도를 높일 수 있습니다.

아이디어는 먼저 세 단어를 (이번에는 Skia가 아니라 우리가 소유하는) 별도의 서피스에 래스터화해 두는 것입니다. 이것을 _합성 레이어(composited layer)_ 라고 부르며, 나중에 쓰기 위해 저장해 둡니다.

```
Composited Layer:
  DrawText(text=This)
  DrawText(text=text)
  DrawText(text=fades)
```

이제 세 단어를 래스터화하는 대신 `DrawCompositedLayer` 명령으로 합성 레이어를 복사해 오기만 하면 됩니다.

```
Blend(alpha=0.112375)
  DrawCompositedLayer()
```

중요한 점은, 다음 프레임에서 `Blend`는 바뀌지만 `DrawText`는 바뀌지 않으므로 그 프레임에서 우리가 해야 할 일은 `Blend`를 다시 실행하는 것뿐이라는 것입니다.

```
Blend(alpha=0.119866666667)
  DrawCompositedLayer()
```

다시 말해 합성의 아이디어는 디스플레이 리스트를 두 조각으로 나누는 것입니다. 브라우저의 래스터화 단계에서 래스터화되어 캐시되는 합성 레이어 집합과, 브라우저의 그리기 단계에서 그려지며 그 합성 레이어를 사용하는 _그리기 디스플레이 리스트_ 입니다.

합성은 애니메이션의 이후 프레임들이 합성 레이어를 재사용할 때 성능을 개선합니다. 여기서는 프레임 사이의 유일한 차이가 그리기 디스플레이 리스트에 있는 `Blend`이므로 그렇습니다.

디스플레이 리스트를 정확히 어떻게 나눌지는 브라우저에 달려 있습니다. 보통 불투명도 같은 시각 효과는 GPU에서 실행하기가 아주 빠르지만, 도형을 그리는 _페인트 명령_ (우리 브라우저에서는 `DrawText`, `DrawRect`, `DrawRRect`, `DrawLine`)은 더 느릴 수 있습니다.[^15] 애니메이션되는 것은 보통 시각 효과이므로, 브라우저는 대개 애니메이션되는 시각 효과를 그리기 디스플레이 리스트에 남기고 나머지 전부를 합성 레이어로 옮깁니다. 물론 실제 브라우저에서는 하드웨어 성능, GPU 메모리, 애플리케이션 데이터가 모두 이 결정에 영향을 주지만, 무엇이 어디로 가든 합성의 기본 아이디어는 같습니다.

### 더 알아보기

이 절의 불투명도 예제를 자세히 보면, `DrawText` 명령의 `rect`가 텍스트 너비만큼만 넓다는 것을 알 수 있습니다. 반면 `Blend`의 `rect`는 거의 뷰포트만큼 넓습니다. 이 둘이 다른 이유는 텍스트가 필요한 만큼만 넓은 반면, 그것을 담고 있는 블록 요소는 사용 가능한 너비만큼 넓기 때문입니다.

그렇다면 그것을 합성 레이어에 넣을 때 텍스트만큼 넓어야 할까요, 아니면 뷰포트 전체만큼 넓어야 할까요? 실제로는 둘 다 구현할 수 있습니다. 이 장에서 소개하는 알고리즘은 더 작은 쪽을 택하지만, 실제 브라우저는 알고리즘에 따라 때때로 더 큰 쪽을 택하기도 합니다. 또한 텍스트를 담은 블록 요소에 배경색 같은 어떤 페인트 명령이라도 연결되어 있다면, 그 서피스는 반드시 뷰포트만큼 넓어야 한다는 점도 눈여겨보세요. 마찬가지로 인라인 자식이 여러 개라면 그들의 경계를 합집합한 것이 서피스 크기에 기여하게 됩니다.

## 잎을 합성하기

합성을 구현해 봅시다. 페인트 명령을 식별해 합성 레이어로 옮겨야 합니다. 그다음 이 합성 레이어들을 시각 효과와 결합하는 그리기 디스플레이 리스트를 만들어야 합니다. 단순하게 가기 위해, 모든 페인트 명령마다 합성 레이어를 하나씩 만드는 것부터 시작하겠습니다.

페인트 명령을 식별하기 위해 그것들에 모두 `PaintCommand` 상위 클래스를 주면 도움이 됩니다.

```python
class PaintCommand:
    def __init__(self, rect):
        self.rect = rect
        self.children = []
```

이제 각 페인트 명령은 `PaintCommand`의 하위 클래스가 되어야 합니다. 그러려면 클래스를 선언할 때 상위 클래스 이름을 적고 생성자에서도 특별한 문법을 써야 합니다.

```python
class DrawLine(PaintCommand):
    def __init__(self, x1, y1, x2, y2, color, thickness):
        super().__init__(skia.Rect.MakeLTRB(x1, y1, x2, y2))
        # ...
```

시각 효과에도 상위 클래스를 줄 수 있습니다.

```python
class VisualEffect:
    def __init__(self, rect, children):
        self.rect = rect.makeOffset(0.0, 0.0)
        self.children = children
        for child in self.children:
            self.rect.join(child.rect)
```

시각 효과에는 자식이 있으므로 그것들을 생성자에 넘길 뿐 아니라 그 `rect` 필드들도 우리 것에 더해야 한다는 점에 주의하세요. 저는 `makeOffset` 함수로 원본 `rect`의 사본을 만들고, 그다음 `join` 메서드로 그것을 키워 모든 자식까지 포함하게 합니다.

각 페인트 명령과 시각 효과 클래스를 이 두 새 클래스 중 하나의 하위 클래스가 되도록 수정하세요. `class` 줄에서 상위 클래스를 선언하고, `__init__` 메서드에서 `super()` 문법으로 상위 클래스 생성자도 호출하도록 하세요.

이제 `tree_to_list`로 모든 페인트 명령을 나열할 수 있습니다.

```python
class Browser:
    def composite(self):
        all_commands = []
        for cmd in self.active_tab_display_list:
            all_commands = tree_to_list(cmd, all_commands)
        paint_commands = [cmd for cmd in all_commands
            if isinstance(cmd, PaintCommand)]
```

다음으로 페인트 명령을 레이어로 묶어야 합니다. 우선 가장 단순한 방법으로, 각 페인트 명령을 자신만의 `CompositedLayer`에 넣읍시다.

```python
class Browser:
    def __init__(self):
        # ...
        self.composited_layers = []

    def composite(self):
        self.composited_layers = []
        # ...
        for cmd in paint_commands:
            layer = CompositedLayer(self.skia_context, cmd)
            self.composited_layers.append(layer)
```

여기서 `CompositedLayer`는 그저 _디스플레이 아이템_ 의 리스트(와 그것들이 그려질 서피스)를 저장할 뿐입니다.[^16]

```python
class CompositedLayer:
    def __init__(self, skia_context, display_item):
        self.skia_context = skia_context
        self.surface = None
        self.display_items = [display_item]
```

이제 합성 레이어들을 결합하는 그리기 디스플레이 리스트가 필요합니다. 이를 만들기 위해 각 합성 레이어에서 위로 걸어 올라가면서 그 레이어에 적용되는 모든 시각 효과의 사슬을 만들고, 사슬 맨 아래에 `DrawCompositedLayer`를 둡니다.

먼저 그 조상 시각 효과들에 쉽게 접근하고 비교할 수 있도록 디스플레이 리스트 트리에 부모 포인터를 추가합시다.

```python
def add_parent_pointers(nodes, parent=None):
    for node in nodes:
        node.parent = parent
        add_parent_pointers(node.children, node)

class Browser:
    def composite(self):
        add_parent_pointers(self.active_tab_display_list)
        # ...
```

다음으로 레이어의 페인트 명령의 조상들을 각각 _복제_ 하고 새 자식을 주입해야 하므로, 시각 효과 클래스들에 새 `clone` 메서드를 추가합시다. `Blend`의 경우 같은 매개변수를 가지되 새 자식을 가진 새 `Blend`를 만듭니다.

```python
class Blend(VisualEffect):
    # ...
    def clone(self, child):
        return Blend(self.opacity, self.blend_mode, [child])
```

우리 브라우저는 페인트 명령을 복제하지 않을 것입니다. 그것들은 전부 합성 레이어 안에 있게 되므로 페인트 명령에는 `clone`을 구현할 필요가 없습니다.

이제 그리기 디스플레이 리스트를 만들 수 있습니다. 각 합성 레이어마다 (곧 정의할) `DrawCompositedLayer` 명령을 만듭니다. 그다음 디스플레이 리스트를 거슬러 올라가면서, 그 합성 레이어에 적용되는 각 시각 효과로 그 `DrawCompositedLayer`를 감쌉니다.

```python
class Browser:
    def __init__(self):
        # ...
        self.draw_list = []

    def paint_draw_list(self):
        self.draw_list = []
        for composited_layer in self.composited_layers:
            current_effect = \
                DrawCompositedLayer(composited_layer)
            if not composited_layer.display_items: continue
            parent = composited_layer.display_items[0].parent
            while parent:
                current_effect = \
                    parent.clone(current_effect)
                parent = parent.parent
            self.draw_list.append(current_effect)
```

`paint_draw_list`의 코드는 각 합성 레이어에서 위로 걸어 올라가며 그것에 적용된 모든 효과를 다시 만들 뿐입니다. 이것으로 대체로 동작하겠지만, 한 효과가 둘 이상의 합성 레이어에 적용된다면 그 효과가 여러 개의 동일한 효과로 바뀌어 각 합성 레이어에 따로 적용되고 맙니다. 이는 올바르지 않은데, [11장](https://browser.engineering/visual-effects.html)에서 이야기했듯이 연산 순서가 중요하기 때문입니다.

복제된 효과를 재사용해 이를 고칩시다.

```python
class Browser:
    def paint_draw_list(self):
        new_effects = {}
        self.draw_list = []
        for composited_layer in self.composited_layers:
            # ...
            while parent:
                if parent in new_effects:
                    new_parent = new_effects[parent]
                    new_parent.children.append(current_effect)
                    break
                else:
                    current_effect = \
                        parent.clone(current_effect)
                    new_effects[parent] = current_effect
                    parent = parent.parent
            if not parent:
                self.draw_list.append(current_effect)
```

됐습니다! 이제 디스플레이 리스트를 합성 레이어와 그리기 디스플레이 리스트로 나눴으니, 브라우저의 나머지 부분이 그것들을 래스터화와 그리기에 사용하도록 갱신해야 합니다.

래스터화부터 시작합시다. 래스터화 단계에서 브라우저는 합성 레이어 목록을 순회하며 각각을 래스터화해야 합니다.

```python
class Browser:
    def raster_tab(self):
        for composited_layer in self.composited_layers:
            composited_layer.raster()
```

`raster` 안에서 합성 레이어는 자신을 래스터화할 서피스를 할당해야 하는데, 그러려면 자신이 얼마나 큰지 알아야 합니다. 그것은 자신의 모든 페인트 명령의 경계 상자를 합집합한 것, 즉 `rect` 필드입니다.

```python
class CompositedLayer:
    # ...
    def composited_bounds(self):
        rect = skia.Rect.MakeEmpty()
        for item in self.display_items:
            rect.join(item.rect)
        # ...
```

이 합성 레이어의 항목들을 담을 만큼만 딱 큰 서피스를 만들겠습니다. 이렇게 하면 필요한 GPU 메모리가 줄어듭니다. 다만 까다로운 예외 사례들이 있습니다. 예를 들어 Skia가 보기 좋게 만들거나 픽셀 격자에 맞추기 위해 선이나 안티에일리어싱된 텍스트를 여러 픽셀에 걸쳐 래스터화하는 방식 같은 것입니다.[^17] 그러니 그것을 고려해 각 변에 픽셀 하나씩을 더 넣읍시다.

```python
    def composited_bounds(self):
        # ...
        rect.outset(1, 1)
        return rect
```

이제 그 경계로 서피스를 만들 수 있습니다.

```python
class CompositedLayer:
    def raster(self):
        bounds = self.composited_bounds()
        if bounds.isEmpty(): return
        irect = bounds.roundOut()

        if not self.surface:
            self.surface = skia.Surface.MakeRenderTarget(
                self.skia_context, skia.Budgeted.kNo,
                skia.ImageInfo.MakeN32Premul(
                    irect.width(), irect.height()))
            assert self.surface
        canvas = self.surface.getCanvas()
```

합성 레이어를 래스터화하려면 그 모든 디스플레이 아이템을 이 서피스에 그리면 됩니다. 유일하게 까다로운 부분은 합성 경계의 `top`과 `left`만큼 오프셋을 주어야 한다는 것인데, 서피스 경계에는 그 오프셋이 포함되어 있지 않기 때문입니다.

```python
class CompositedLayer:
    def raster(self):
        # ...
        canvas.clear(skia.ColorTRANSPARENT)
        canvas.save()
        canvas.translate(-bounds.left(), -bounds.top())
        for item in self.display_items:
            item.execute(canvas)
        canvas.restore()
```

래스터화 단계는 이것으로 끝입니다. 그리기 단계를 위해서는 먼저 `DrawCompositedLayer` 명령을 구현해야 합니다. 이 명령은 그릴 합성 레이어를 받습니다.

```python
class DrawCompositedLayer(PaintCommand):
    def __init__(self, composited_layer):
        self.composited_layer = composited_layer
        super().__init__(
            self.composited_layer.composited_bounds())

    def __repr__(self):
        return "DrawCompositedLayer()"
```

`DrawCompositedLayer`를 실행하는 것은 간단합니다. 올바른 오프셋을 반영해 그 서피스를 부모 서피스에 그리기만 하면 됩니다.

```python
class DrawCompositedLayer(PaintCommand):
    def execute(self, canvas):
        layer = self.composited_layer
        bounds = layer.composited_bounds()
        layer.surface.draw(canvas, bounds.left(), bounds.top())
```

래스터화에 비해 브라우저의 `draw` 단계는 만족스러울 만큼 단순합니다. 그저 그리기 디스플레이 리스트를 실행하기만 하면 됩니다.

```python
class Browser:
    def draw(self):
        # ...
        canvas.save()
        canvas.translate(0,
            self.chrome.bottom - self.active_tab_scroll)
        for item in self.draw_list:
            item.execute(canvas)
        canvas.restore()
        # ...
```

남은 것은 이 메서드들을 연결하는 일뿐입니다. `raster_and_draw`의 이름을 (이제 추가로 합성 단계가 있다는 것을 상기시키기 위해) `composite_raster_and_draw`로 바꾸고 새 메서드 두 개를 추가합시다. (그에 해당하는 더티 플래그와 호출 지점의 이름도 잊지 말고 바꾸세요.)

```python
class Browser:
    def composite_raster_and_draw(self):
        # ...
        self.composite()
        self.raster_chrome()
        self.raster_tab()
        self.paint_draw_list()
        self.draw()
        # ...
```

정말 단순하고 우아하죠! 이제 매 프레임마다 우리는 그저 디스플레이 리스트를 합성 레이어와 그리기 디스플레이 리스트로 나누고, 각각을 자기 단계에서 실행할 뿐입니다. 이제 초매끄러운 애니메이션까지 절반쯤 왔습니다. 남은 것은 프레임 사이에 디스플레이 리스트가 크게 바뀌지 않았다면 레이아웃과 래스터화 단계를 건너뛰는 것입니다.

Chromium이 이 개념들을 어떻게 구현하는지에 대한 더 자세한 내용과 정보는 Chrome 개발자 블로그의 [블로그](https://developer.chrome.com/docs/chromium/renderingng-data-structures#display_lists_and_paint_chunks) [글들](https://developer.chrome.com/docs/chromium/renderingng-data-structures#compositor-frames)을 참고하세요. 다른 브라우저도 대체로 비슷한 일을 합니다. ## CSS 트랜지션

레이어를 다시 래스터화하지 않는 열쇠는 어떤 레이어가 바뀌었고 어떤 레이어가 바뀌지 않았는지 아는 것입니다. 지금 우리는 기본적으로 항상 모든 레이어가 바뀌었다고 가정하고 있지만, 이상적으로는 프레임 사이에 정확히 무엇이 바뀌었는지 알고 싶습니다. 브라우저는 이를 위해 온갖 복잡한 방법을 쓰지만,[^18] 단순하게 가기 위해 합성에 딱 맞는 CSS 기능 하나를 구현합시다. 바로 [CSS 트랜지션](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Transitions/Using_CSS_transitions)입니다.

CSS 트랜지션은 애니메이션을 구현하는 데 사용했던 `requestAnimationFrame` 루프를 "브라우저 안으로" 옮깁니다. 웹 페이지는 애니메이션할 속성과 애니메이션 지속 시간을 정의하는 CSS [`transition`](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Transitions/Using_CSS_transitions) 속성만 추가하면 됩니다. `div`의 불투명도 변화를 2초 동안 애니메이션하라고 말하는 방법은 다음과 같습니다.

```
div { transition: opacity 2s; }
```

이제 어떤 이유로든, 예를 들어 style 속성을 바꿔서 `div`의 `opacity` 속성이 바뀔 때마다 브라우저가 옛 값과 새 값 사이를 2초 동안 매끄럽게 보간합니다. [예제](https://browser.engineering/examples/example13-opacity-transition.html)가 여기 있습니다.

> 🔗 대화형 위젯: [example13-opacity-transition.html](https://browser.engineering/examples/example13-opacity-transition.html)

(여러분의 브라우저에서 예제를 불러오려면 [여기](https://browser.engineering/examples/example13-opacity-transition.html)를 클릭하세요)

시각적으로는 JavaScript 애니메이션과 거의 똑같아 보입니다.[^19] 하지만 브라우저가 그 애니메이션을 _이해하고 있으므로_ 애니메이션이 실행되는 방식을 최적화할 수 있습니다. 예를 들어 `opacity`는 그리기 디스플레이 리스트에 들어가는 `Blend` 명령에만 영향을 주므로, 브라우저는 이 애니메이션에 레이아웃이나 래스터화가 필요 없고 페인트와 그리기만 필요하다는 것을 압니다.

CSS 트랜지션을 구현하려면 앞선 예제의 JavaScript 변수 `current_frame`과 `change_per_frame` 같은 애니메이션 상태를 브라우저 안에 표현해야 합니다. 여러 요소가 동시에 애니메이션될 수 있으므로, 각 노드에 애니메이션되는 속성을 키로 하는 `animations` 딕셔너리를 저장합시다.[^20]

```python
class Text:
    def __init__(self, text, parent):
        # ...
        self.style = {}
        self.animations = {}

class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.style = {}
        self.animations = {}
```

애니메이션하기에 가장 단순한 종류는 `opacity` 같은 수치 속성입니다.

```python
class NumericAnimation:
    def __init__(self, old_value, new_value, num_frames):
        self.old_value = float(old_value)
        self.new_value = float(new_value)
        self.num_frames = num_frames

        self.frame_count = 1
        total_change = self.new_value - self.old_value
        self.change_per_frame = total_change / num_frames
```

JavaScript에서와 비슷하게, 프레임 수를 늘리고 새 값을 계산해 반환하는 `animate` 메서드가 필요합니다.

```python
class NumericAnimation:
    def animate(self):
        self.frame_count += 1
        if self.frame_count >= self.num_frames: return
        current_value = self.old_value + \
            self.change_per_frame * self.frame_count
        return str(current_value)
```

이 애니메이션 객체는 스타일 값이 바뀔 때마다 만들 텐데, 그것은 `style`에서 각 노드의 옛 스타일과 새 스타일을 비교(diff)해 감지할 수 있습니다.

```python
def style(node, rules):
    old_style = node.style

    # ...

    if old_style:
        transitions = diff_styles(old_style, node.style)
```

이 `diff_styles` 함수는 `transition` 속성에 언급되어 있으면서 옛 스타일과 새 스타일에서 값이 다른 모든 속성을 찾을 것입니다. 그러니 먼저 `transition` 값을 파싱해야 합니다.

첫 번째 난관은, 짜증스럽게도 지금 우리 CSS 파서가 `opacity 2s`를 유효한 CSS 값으로 인식하지 못한다는 것입니다. 값을 단어 하나로 파싱하기 때문이죠. 지정된 `chars` 집합에 속하는 문자를 제외한 모든 문자열을 인식하도록 파서를 개선합시다.

```python
class CSSParser:
    def until_chars(self, chars):
        start = self.i
        while self.i < len(self.s) and self.s[self.i] not in chars:
            self.i += 1
        return self.s[start:self.i]

    def pair(self, until):
        # ...
        val = self.until_chars(until)
        # ...
        return prop.casefold(), val.strip()
```

CSS 규칙 본문 안에서 속성 값은 세미콜론이나 닫는 중괄호가 나올 때까지 이어집니다.

```python
class CSSParser:
    def body(self):
        while self.i < len(self.s) and self.s[self.i] != "}":
            try:
                prop, val = self.pair([";", "}"])
                # ...
```

이제 CSS 속성을 파싱하니, 트랜지션이 있는 속성들을 파싱해 낼 수 있습니다.[^21]

```python
def parse_transition(value):
    properties = {}
    if not value: return properties
    for item in value.split(","):
        property, duration = item.split(" ", 1)
        frames = int(float(duration[:-1]) / REFRESH_RATE_SEC)
        properties[property] = frames
    return properties
```

이제 `diff_style`은 `transition`에 언급된 모든 속성을 순회하며 어떤 것이 바뀌었는지 볼 수 있습니다. 이 함수는 트랜지션 대상 속성만 담은 딕셔너리를 반환하며, 각 속성을 옛 값, 새 값, 지속 시간(역시 프레임 단위)에 대응시킵니다.[^22]

```python
def diff_styles(old_style, new_style):
    transitions = {}
    for property, num_frames in \
        parse_transition(new_style.get("transition")).items():
        if property not in old_style: continue
        if property not in new_style: continue
        old_value = old_style[property]
        new_value = new_style[property]
        if old_value == new_value: continue
        transitions[property] = \
            (old_value, new_value, num_frames)
    return transitions
```

다시 `style` 안으로 돌아와, 트랜지션 대상 속성마다 새 애니메이션 객체를 만들려고 합니다. `opacity`만 지원하겠습니다.

```python
def style(node, rules, tab):
    if old_style:
        transitions = diff_styles(old_style, node.style)
        for property, (old_value, new_value, num_frames) \
            in transitions.items():
            if property == "opacity":
                tab.set_needs_render()
                animation = NumericAnimation(
                    old_value, new_value, num_frames)
                node.animations[property] = animation
                node.style[property] = animation.animate()
```

`transition`에 나열된 속성의 값이 바뀔 때마다 애니메이션을 만들고 실행할 준비를 합니다.[^23]

애니메이션을 실행한다는 것은 페이지의 모든 활성 애니메이션을 순회하며 그것들의 `animate`를 호출한다는 뜻입니다. CSS 트랜지션은 `requestAnimationFrame` 애니메이션과 비슷하므로, `requestAnimationFrame` 콜백을 처리한 직후에 애니메이션을 실행합시다.

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        self.js.interp.evaljs("__runRAFHandlers()")

        for node in tree_to_list(self.nodes, []):
            for (property_name, animation) in \
                node.animations.items():
                # ...
```

이 루프 안에서 두 가지를 해야 합니다. 첫째, 애니메이션의 `animate` 메서드를 호출하고 새 값을 노드의 `style`에 저장합니다. 둘째, 그것이 렌더링 입력을 바꾸므로 나중에 렌더링이 필요하다는 더티 플래그를 설정합니다.[^24] 브라우저 스레드와 메인 스레드 사이의 전체 렌더링 주기가 그림 2에 정리되어 있습니다.

![그림 2: 브라우저 스레드와 메인 스레드 사이의 렌더링 주기.](multi-threaded-rendering-loop-2.gif)

*그림 2: 브라우저 스레드와 메인 스레드 사이의 렌더링 주기.*

그런데 애니메이션이 활성일 때마다 그냥 `needs_render`를 설정하면 되는 것처럼 단순하지는 않습니다. `needs_render`를 설정한다는 것은 `style`을 다시 실행한다는 뜻이고, 그러면 애니메이션이 속성 값을 바꿨다는 것을 알아채고 _새_ 애니메이션을 시작해 버립니다! 애니메이션 중에는 `layout`과 `paint`는 실행하되 `style`은 실행하고 _싶지 않습니다_.[^25]

```python
class Tab:
    def run_animation_frame(self, scroll):
        for node in tree_to_list(self.nodes, []):
            for (property_name, animation) in \
                node.animations.items():
                value = animation.animate()
                if value:
                    node.style[property_name] = value
                    self.set_needs_layout()
```

`set_needs_layout`을 구현하려면 단일 `needs_render` 플래그를 `needs_style`, `needs_layout`, `needs_paint`라는 세 플래그로 대체해야 합니다. 우리 구현에서는 파이프라인 앞쪽의 더티 플래그를 설정하면 그 뒤의 모든 것도 실행되므로,[^26] `set_needs_render`는 여전히 `needs_style` 플래그만 설정합니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.needs_style = False
        self.needs_layout = False
        self.needs_paint = False
        # ...

    def set_needs_render(self):
        self.needs_style = True
        self.browser.set_needs_animation_frame(self)
```

이제 `style` 단계가 아니라 `layout`과 `paint` 단계의 플래그만 설정하는 `set_needs_layout` 메서드를 작성할 수 있습니다.

```python
class Tab:
    def set_needs_layout(self):
        self.needs_layout = True
        self.browser.set_needs_animation_frame(self)
```

이 새 더티 플래그들을 지원하려면 `render`가 시작할 때 `needs_render`를 확인하는 대신 각 단계의 플래그를 확인해야 합니다.[^27]

```python
class Tab:
    def render(self):
        self.browser.measure.time('render')

        if self.needs_style:
            # ...
            self.needs_layout = True
            self.needs_style = False

        if self.needs_layout:
            # ...
            self.needs_paint = True
            self.needs_layout = False
    
        if self.needs_paint:
            # ...
            self.needs_paint = False

        self.browser.measure.stop('render')
```

자, 이 모든 작업을 마쳤으니 이제 우리 브라우저는 CSS만으로 애니메이션을 지원합니다. 그리고 중요하게도, 브라우저가 불투명도 애니메이션을 최적화해 레이아웃을 피할 수 있게 되었습니다.

### 더 알아보기

CSS 트랜지션은 JavaScript의 DOM 갱신으로 유발되는 애니메이션을 추가하는 데 훌륭합니다. 그런데 그저 페이지 UI의 일부일 뿐 시각적 전환과 연결되지 않은 애니메이션은 어떨까요? (예를 들어 버튼이나 커서의 맥박치는 불투명도 애니메이션 같은 것 말입니다.) 이는 JavaScript 없이 [CSS 애니메이션](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Animations/Using_CSS_animations)으로 CSS에서 직접 표현할 수 있습니다.

불투명도 데모의 CSS 애니메이션 버전은 [여기](https://browser.engineering/examples/example13-opacity-animation.html)에서 볼 수 있습니다.

이 기능을 구현하려면 새로운 `@keyframes` 문법과 `animation` CSS 속성을 파싱해야 합니다. `@keyframes`가 시작점과 끝점을 선언적으로 정의한다는 점을 눈여겨보세요. 역방향은 그저 키프레임을 거꾸로 가는 것이므로, 덕분에 애니메이션을 무한히 번갈아 반복할 수 있습니다. JavaScript로 애니메이션을 만들고 관리할 수 있게 해 주는 [Web Animations API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API)도 있습니다.

## 합성 애니메이션

이제 마침내 특정 애니메이션을 실행할 때 (레이아웃과) 래스터화를 피하는 방법을 브라우저에 가르칠 준비가 되었습니다. 이런 애니메이션은 매 프레임 래스터화를 피하는 합성 최적화와 호환되므로 _합성 애니메이션_ 이라고 부릅니다. 불투명도 애니메이션에서 `raster`와 `composite`를 피하는 것은 개념적으로 단순합니다. 무엇이 애니메이션되고 있는지 추적하고, 매 프레임마다 `paint`, `paint_draw_list`, `draw`만 다시 실행하면 됩니다.

이를 구현하는 것은 들리는 것보다 어렵습니다. _새_ 디스플레이 리스트를 _옛_ 합성 레이어와 _새_ 그리기 디스플레이 리스트로 나눠야 합니다. 그러려면 새 디스플레이 리스트와 옛 디스플레이 리스트가 어떤 관계인지, 디스플레이 리스트의 어떤 부분이 바뀌었는지 알아야 합니다. 이를 위해 각 디스플레이 아이템에 `node` 필드를 추가해, 그것을 페인트한 노드를 일종의 식별자로 저장하겠습니다.[^28]

```python
class VisualEffect:
    def __init__(self, rect, children, node=None):
        # ...
        self.node = node

class Blend(VisualEffect):
    def __init__(self, opacity, blend_mode, node, children):
        super().__init__(skia.Rect.MakeEmpty(), children, node)
        # ...

    def clone(self, child):
        return Blend(self.opacity, self.blend_mode,
                     self.node, [child])
```

이제 애니메이션이 실행되되 다른 것은 바뀌지 않았을 때, 이 노드들을 사용해 그리기 디스플레이 리스트의 어떤 디스플레이 아이템을 갱신해야 하는지 판단하겠습니다.

먼저, 합성 애니메이션이 실행되면 스타일이 바뀐 `Element`를 `composited_updates`라는 새 배열에 저장합니다. 이 경우 `needs_layout`이 아니라 `needs_paint` 플래그만 설정하겠습니다.

```python
class Tab:
    def __init__(self, browser):
        # ...
        self.composited_updates = []

    def run_animation_frame(self, scroll):
        for node in tree_to_list(self.nodes, []):
            for (property_name, animation) in \
                node.animations.items():
                value = animation.animate()
                if value:
                    node.style[property_name] = value
                    self.composited_updates.append(node)
                    self.set_needs_paint()
```

이제 페인트 단계만 필요한 프레임을 `commit`할 때 `composited_updates`를 브라우저로 보내고, 브라우저는 그것을 이용해 합성과 래스터화를 건너뜁니다. 각 애니메이션 갱신에 대해 보낼 데이터는 `Element`와 `Blend`입니다.

이를 위해 몇 단계가 필요합니다. 먼저 `Blend`를 페인트할 때 그것을 `Element`에 기록합니다.

```python
def paint_visual_effects(node, cmds, rect):
    # ...
    blend_op = Blend(opacity, blend_mode, cmds)
    node.blend_op = blend_op
    return [blend_op]
```

다음으로 `CommitData`에 합성 갱신 목록을 추가합니다(각 항목은 `Element`와 `Blend` 포인터를 담습니다).

```python
class CommitData:
    def __init__(self, url, scroll, height,
        display_list, composited_updates):
        # ...
        self.composited_updates = composited_updates
```

마지막으로 새 정보를 커밋합니다.[^29]

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        needs_composite = self.needs_style or self.needs_layout

        self.render()

        composited_updates = None
        if not needs_composite:
            composited_updates = {}
            for node in self.composited_updates:
                composited_updates[node] = node.blend_op
        self.composited_updates = []

        commit_data = CommitData(
            # ...
            composited_updates,
        )
```

이제 브라우저 스레드 차례입니다. 먼저 `needs_composite`, `needs_raster`, `needs_draw` 더티 플래그와 그에 해당하는 `set_needs_composite`, `set_needs_raster`, `set_needs_draw` 메서드를 추가하세요(그리고 옛 더티 플래그는 제거하세요).

```python
class Browser:
    def __init__(self):
        # ...
        self.needs_composite = False
        self.needs_raster = False
        self.needs_draw = False

    def set_needs_raster(self):
        self.needs_raster = True
        self.needs_draw = True

    def set_needs_composite(self):
        self.needs_composite = True
        self.needs_raster = True
        self.needs_draw = True

    def composite_raster_and_draw(self):
        if not self.needs_composite and \
            not self.needs_raster and \
            not self.needs_draw:
            self.lock.release()
            return
        
        if self.needs_composite:
            self.composite()
        if self.needs_raster:
            self.raster_chrome()
            self.raster_tab()
        if self.needs_draw:
            self.draw()
```

그다음 `handle_down`처럼 현재 `set_needs_raster_and_draw`를 호출하는 곳에서는 `set_needs_raster`를 호출해야 합니다.

```python
class Browser:
    def handle_down(self):
        # ...
        self.set_needs_raster()
```

`commit`에서 넘어온 데이터를 사용해 `set_needs_composite`를 호출할지 `set_needs_draw`를 호출할지 결정하고, 갱신 내용을 `composited_updates`에 저장하세요.

```python
class Browser:
    def __init__(self):
        # ...
        self.composited_updates = {}

    def commit(self, tab, data):
        # ...
        if tab == self.active_tab:
            # ...
            self.composited_updates = data.composited_updates
            if self.composited_updates == None:
                self.composited_updates = {}
                self.set_needs_composite()
            else:
                self.set_needs_draw()
```

이제 그리기 단계를 생각해 봅시다. 보통 우리는 합성 레이어로부터 그리기 디스플레이 리스트를 만듭니다. 하지만 이제 그것만으로는 충분하지 않은데, 합성 레이어가 _옛_ 디스플레이 리스트에서 왔기 때문입니다. 그냥 `paint_draw_list`를 다시 실행하면 옛 그리기 디스플레이 리스트를 얻게 됩니다! `composited_updates`를 바탕으로 새 디스플레이 리스트를 반영하도록 `draw_list`를 갱신해야 합니다.

그러기 위해, `composited_updates`에 갱신된 시각 효과가 있으면 그것을 가져오는 `get_latest` 메서드를 정의합시다.

```python
class Browser:
    def get_latest(self, effect):
        node = effect.node
        if node not in self.composited_updates:
            return effect
        if not isinstance(effect, Blend):
            return effect
        return self.composited_updates[node]
```

`paint_draw_list`에서 `get_latest`를 쓰는 것은 한 줄이면 됩니다.

```python
class Browser:
    def paint_draw_list(self):
        for composited_layer in self.composited_layers:
            while parent:
                new_parent = self.get_latest(parent)
                # ...
```

`paint_draw_list`의 나머지 `while` 루프에서도 새 효과를 만들 때 `parent` 대신 `new_parent`를 참조하도록 갱신하세요(다만 합성 레이어에서 위로 걸어 올라갈 때는 그대로 둡니다).

이제 그리기 디스플레이 리스트가 새 디스플레이 리스트를 기반으로 하게 되고, 우리의 예제 불투명도 애니메이션처럼 그리기 단계만 필요한 애니메이션은 이제 아주 매끄럽게 실행될 것입니다.

마지막으로 한 가지, 탭을 바꿀 때 합성 자료 구조를 비워야 합니다. 모든 것을 한 번에 비우는 `clear_data` 메서드를 뽑아내 그렇게 합시다.

```python
class Browser:
    def clear_data(self):
        self.active_tab_scroll = 0
        self.active_tab_url = None
        self.display_list = []
        self.composited_layers = []
        self.composited_updates = {}

    def set_active_tab(self, tab):
        # ...
        self.clear_data()
```

### 더 알아보기

우리 브라우저의 시각 효과 애니메이션은 이제 효율적이고 _합성되지만_, [12장](https://browser.engineering/scheduling.html#threaded-scrolling)의 의미에서 _스레드화_ 되지는 않았습니다. 애니메이션은 여전히 메인 스레드에서 똑딱이며, 느린 JavaScript나 다른 작업이 작업 큐를 막고 있으면 애니메이션이 끊깁니다. 이는 실제 브라우저에서 중요한 문제이므로 거의 모든 브라우저가 스레드화된 불투명도, 변환, 필터 애니메이션을 지원하며, 일부는 특정 종류의 클립 애니메이션도 지원합니다. 우리 브라우저에 스레드화된 애니메이션을 추가하는 것은 연습문제 13-3으로 남겨 두었습니다.

그렇긴 해도 "합성된(composited)"과 "스레드화된(threaded)"을 동의어처럼 쓰는 것을 흔히 듣게 됩니다. 대부분의 브라우저에서 합성이 스레드화의 _전제 조건_ 이기 때문입니다. 그 이유는 효율적으로 애니메이션하려면 대개 어차피 텍스처를 합성해야 하고, GPU 텍스처에 대한 애니메이션을 브라우저에서 배관 작업으로 표현하는 것이 "디스플레이 리스트의 일부"에 대한 애니메이션보다 훨씬 쉽기 때문입니다.

그렇다고 디스플레이 리스트를 애니메이션하는 것이 불가능하지는 않으며, 몇몇 브라우저는 그것을 시도했습니다. 예를 들어 Mozilla의 [WebRender](https://hacks.mozilla.org/2017/10/the-whole-web-at-maximum-fps-how-webrender-gets-rid-of-jank/) 프로젝트의 목표 하나는 캐시된 합성 레이어를 완전히 없애고, 디스플레이 리스트에서 직접 GPU로 60Hz로 래스터화하고 그림으로써 모든 애니메이션을 수행하는 것입니다. 이를 _직접 렌더링(direct render)_ 접근법이라고 합니다. 실제로는 어떤 GPU가 다른 GPU보다 빠르기 때문에, 현재의 GPU 기술로 이 목표를 달성하기는 어렵습니다. 그래서 브라우저들은 대신 직접 렌더링과 합성의 혼합 쪽으로 서서히 진화하고 있습니다.

모든 현대 브라우저가 스레드화된 애니메이션을 갖고 있지만, 이 글을 쓰는 시점에 Chromium과 WebKit은 둘 다 `compositing` 단계를 메인 스레드에서 수행하는 반면 우리 브라우저는 브라우저 스레드에서 한다는 점이 흥미롭습니다. 이 영역에서 우리 브라우저는 실제로 실제 브라우저보다 앞서 있는 셈입니다! Chromium에서 합성이 (아직) 다른 스레드에서 일어나지 않는 이유는, 거기까지 가려면 합성 알고리즘 전체를 다시 설계해야 했기 때문입니다. 이는 극도로 어려운 것으로 드러났는데, 옛 아키텍처가 렌더링 엔진의 거의 모든 측면과 깊이 얽혀 있었기 때문입니다. 그 작업은 [2021년에야 완료되었으니](https://developer.chrome.com/docs/chromium/renderingng#compositeafterpaint), 어쩌면 머지않아 Chromium에서도 이 작업이 스레드화될지도 모릅니다.

## 합성 최적화하기

이 시점에서 우리 브라우저는 불필요한 레이아웃과 래스터화를 피하면서 합성 애니메이션을 성공적으로 실행합니다. 하지만 실제 브라우저와 비교하면 합성 레이어가 _너무_ 많습니다. 페인트 명령마다 하나씩이니까요! 이는 GPU 메모리와 시간의 큰 낭비입니다. 각 합성 레이어는 서피스를 할당하고, 그 각각이 GPU 메모리를 할당해 붙들고 있습니다. GPU 메모리는 제한되어 있으므로 가능하면 덜 쓰고 싶습니다.

그러기 위해 합성 레이어를 더 적게 쓰고 싶습니다. 가장 단순하게 할 수 있는 일은, 디스플레이 리스트에서 조상 시각 효과 집합이 정확히 같은 페인트 명령들을 같은 합성 레이어에 넣는 것입니다.

구현해 봅시다. 합성 레이어에 새 메서드 두 개, `add`와 `can_merge`가 필요합니다. `add` 메서드는 그저 합성 레이어에 새 디스플레이 아이템을 추가합니다.

```python
class CompositedLayer:
    def add(self, display_item):
        self.display_items.append(display_item)
```

하지만 `can_merge` 메서드로 판단해 서로 호환되는 디스플레이 아이템만 같은 합성 레이어에 추가해야 합니다. 어떤 디스플레이 아이템은 합성 레이어에 이미 있는 것들과 부모가 같다면 병합할 수 있습니다.

```python
class CompositedLayer:
    def can_merge(self, display_item):
        return display_item.parent == \
            self.display_items[0].parent
```

이제 이 메서드들을 `composite`에서 쓰고 싶습니다. 기본적으로 페인트 명령마다 새 합성 레이어를 만드는 대신, `composited_layers`를 거꾸로[^31] 훑으면서 그 명령을 병합해 넣을 합성 레이어를 찾습니다.[^32]

```python
class Browser:
    def composite(self):
        for cmd in paint_commands:
            for layer in reversed(self.composited_layers):
                if layer.can_merge(cmd):
                    layer.add(cmd)
                    break
            else:
                # ...
```

이 구현으로 여러 페인트 명령이 때때로 같은 합성 레이어에 들어가게 되지만, 조상 효과가 _정확히_ 일치하지 않으면 그렇게 되지 않습니다.

애니메이션되지 않는 디스플레이 리스트 _서브트리_ 전체를 같은 합성 레이어에 넣으면 더 잘할 수 있습니다. 그러면 애니메이션되지 않는 시각 효과를 래스터화 단계에 넣을 수 있어서 합성 레이어 수가 더욱 줄어듭니다.

이를 구현하기 위해 새 `needs_compositing` 필드를 추가합시다. 이 값은 시각 효과가 그리기 디스플레이 리스트에 들어가야 하면 `True`, 합성 레이어에 들어가야 하면 `False`입니다. 대부분의 시각 효과에는 `False`로 설정하겠습니다.

```python
class VisualEffect:
    def __init__(self, rect, children):
        self.needs_compositing = False
```

합성이 무언가를 애니메이션하는 데 도움이 될 때 `True`로 설정해야 합니다. 실제 브라우저는 온갖 복잡한 휴리스틱을 쓰지만, 단순하게 가기 위해 애니메이션 여부와 관계없이 `Blend`(실제로 무언가를 할 때만이고, 아무 일도 하지 않는 경우는 제외)에 대해서만 `True`로 설정합시다.

```python
class Blend(VisualEffect):
    def __init__(self, opacity, blend_mode, node, children):
        # ...
        if self.should_save:
            self.needs_compositing = True
```

자손 중 하나라도 합성이 필요하다면 그 시각 효과도 합성이 필요하다고 표시해야 _합니다_. 한 효과가 그리기 단계에 있다면 그 위의 효과들도 그래야 하기 때문입니다.

```python
class VisualEffect:
    def __init__(self, rect, children, node=None):
        # ...
        self.needs_compositing = any([
            child.needs_compositing for child in self.children
            if isinstance(child, VisualEffect)
        ])
```

이제 레이어는 벌거벗은 페인트 명령이 아니라 합성되지 않은 명령들의 서브트리를 담을 수 있습니다.

```python
class Browser:
    def composite(self):
        # ...
        non_composited_commands = [cmd
            for cmd in all_commands
            if isinstance(cmd, PaintCommand) or \
                not cmd.needs_compositing
            if not cmd.parent or cmd.parent.needs_compositing
        ]
        # ...
        for cmd in non_composited_commands:
            # ...
```

리스트 컴프리헨션 안의 여러 `if` 문은 `and`로 결합됩니다.

이제 우리 합성 알고리즘은 훨씬 적은 레이어를 만듭니다! 애니메이션되지 않는 콘텐츠를 잘 묶어 합성 레이어 수를 줄이고(GPU 메모리를 아낍니다), 애니메이션이 아닌 작업을 가능한 한 그리기가 아니라 래스터화에서 하도록 합니다(합성 애니메이션을 더 빠르게 만듭니다).

이 시점에서 합성 알고리즘과 그것이 콘텐츠에 미치는 영향이 꽤 복잡해지고 있습니다. 무슨 일이 벌어지는지 이해하는 데 도움이 되도록 시각적 디버깅을 더 추가해 두면 아주 유용할 것입니다. 좋은 방법 하나는 `CompositedLayer` 콘텐츠 주위에 빨간 테두리를 그리는 [플래그](https://docs.python.org/3/library/argparse.html)[^33]를 브라우저에 추가하는 것입니다. 이는 `CompositedLayer.raster`에 아주 간단히 추가할 수 있습니다.

```python
class CompositedLayer:
    def raster(self):
        # ...
        if SHOW_COMPOSITED_LAYER_BORDERS:
            border_rect = skia.Rect.MakeXYWH(
                1, 1, irect.width() - 2, irect.height() - 2)
            DrawOutline(border_rect, "red", 1).execute(canvas)
```

불투명도 트랜지션 [예제](https://browser.engineering/examples/example13-opacity-transition.html)의 합성 레이어는 그림 5와 같이 보여야 합니다(레이어가 두 개인 것을 눈여겨보세요).

### 더 알아보기

주로 단순함을 위해 우리 브라우저는 애니메이션 여부와 관계없이 `Blend` 시각 효과를 합성합니다. 하지만 사실 특정 시각 효과를 항상 합성하는 데는 몇 가지 좋은 이유가 있습니다.

첫째, 애니메이션을 더 빨리 시작할 수 있습니다. 래스터화가 먼저 일어날 필요가 없기 때문입니다. 합성 이유가 바뀔 때마다 브라우저는 합성을 다시 하고 새 서피스를 다시 래스터화해야 합니다.

둘째, 합성은 때때로 시각적 부작용을 갖습니다. 이상적으로는 합성된 텍스처가 화면에서 합성되지 않은 것과 정확히 똑같아 보여야 합니다. 하지만 [서브픽셀 렌더링](https://en.wikipedia.org/wiki/Subpixel_rendering), 이미지 크기 조절 필터 알고리즘, 블렌딩, 안티에일리어싱처럼 픽셀에 민감한 래스터 기술의 세부 사항 때문에 항상 그럴 수는 없습니다. 예를 들어 부동소수점 정밀도 차이 때문에 일부 픽셀에서 미묘한 색 차이가 관찰되는 것은 흔한 일입니다. 콘텐츠를 "미리 합성"해 두면 합성이 시작될 때 페이지에서 시각적 도약이 일어나는 것을 피할 수 있습니다.

실제 브라우저는 미리 합성을 알리는 목적으로 [`will-change`](https://developer.mozilla.org/en-US/docs/Web/CSS/will-change) CSS 속성을 지원합니다.

## 겹침과 변환

우리가 구현한 합성 알고리즘은 많은 경우 훌륭하게 동작합니다. 안타깝게도 서로 _겹치는_ 디스플레이 리스트 명령에 대해서는 올바르게 동작하지 않습니다. 예를 들어 설명해 보겠습니다.

그림 6처럼 흰 배경 앞에 연한 파란 사각형이 있고 그것을 연한 초록 사각형이 겹치고 있다고 생각해 봅시다.

*그림 6: 합성 그리기 오류로 이어질 수 있는 겹침의 예.*

이제 파란 사각형에는 불투명도 애니메이션을 주고 초록 사각형에는 주지 않으려 한다고 합시다. 그러면 파란 사각형은 자신만의 합성 레이어로 갑니다. 그런데 초록 사각형은 어떨까요? 초록 사각형은 배경과 같은 조상 시각 효과를 갖습니다. 하지만 초록 사각형을 배경과 같은 합성 레이어에 넣고 싶지는 않은데, 파란 사각형이 배경과 초록 사각형 _사이에_ 그려져야 하기 때문입니다.

따라서 초록 사각형은 자신만의 합성 레이어로 가야 합니다. 이를 _합성의 겹침 이유(overlap reason for compositing)_ 라고 하며, 모든 실제 브라우저가 마주하는 주요 난관이자 추가 메모리 사용과 속도 저하의 잠재적 원인입니다.

겹침을 고려하도록 합성 알고리즘을 수정합시다. 기본적으로 어떤 디스플레이 아이템이 어느 합성 레이어로 갈지 고려할 때, 그것이 기존 합성 레이어와 겹치는지도 확인합니다. 겹친다면 이 디스플레이 아이템을 위해 새 `CompositedLayer`를 시작합니다.

```python
class Browser:
    def composite(self):
        # ...
        for cmd in non_composited_commands:
            for layer in reversed(self.composited_layers):
                if layer.can_merge(cmd):
                    # ...
                elif skia.Rect.Intersects(
                    layer.composited_bounds(),
                    cmd.rect):
                    layer = CompositedLayer(self.skia_context, cmd)
                    self.composited_layers.append(layer)
                    break
```

다만 이 코드를 _테스트_ 하기가 조금 어려운데, 우리 브라우저가 아직 시각 효과의 일부로 요소를 움직이거나 키우는[^34] 방법을 전혀 지원하지 않아서 아무것도 겹치지 않기 때문입니다. 이런! 실제 브라우저에는 겹침을 유발하는 시각 효과가 많은데, (애니메이션에서) 가장 중요한 것이 _변환(transform)_ 입니다. 변환은 DOM 서브트리가 페인트한 결과를 화면에서 옮길 수 있게 해 줍니다.[^35] 게다가 변환은 GPU에서 효율적으로 실행될 수 있습니다.

`transform` CSS 속성은 꽤 강력해서 3D 공간에서 [어떤 선형 변환](https://developer.mozilla.org/en-US/docs/Web/CSS/transform)이든 적용할 수 있게 해 주지만, 여기서는 기본적인 2D 이동에 머무르겠습니다. 그것만으로도 파란 사각형과 초록 사각형 예제와 비슷한 것을 구현하기에 충분합니다.[^36]

```
<div style="background-color:lightblue;
            transform:translate(50px, 50px)">Underneath</div>
<div style="background-color:lightgreen;
            transform:translate(0px, 0px)">On top</div>
```

이 변환들을 지원하는 것은 간단합니다. 먼저 속성 값을 파싱합시다.[^37]

```python
def parse_transform(transform_str):
    if transform_str.find('translate(') < 0:
        return None
    left_paren = transform_str.find('(')
    right_paren = transform_str.find(')')
    (x_px, y_px) = \
        transform_str[left_paren + 1:right_paren].split(",")
    return (float(x_px[:-2]), float(y_px[:-2]))
```

그다음 새 `Transform` 시각 효과를 추가하는 코드를 `paint_visual_effects`에 넣습니다.

```python
def paint_visual_effects(node, cmds, rect):
    translation = parse_transform(
        node.style.get("transform", ""))
    # ...
    return [Transform(translation, rect, node, [blend_op])]
```

이 `Transform` 디스플레이 아이템은 편리하게도 Skia 캔버스에 내장된 `translate` 메서드를 호출하기만 합니다.

```python
class Transform(VisualEffect):
    def __init__(self, translation, rect, node, children):
        super().__init__(rect, children, node)
        self.self_rect = rect
        self.translation = translation

    def execute(self, canvas):
        if self.translation:
            (x, y) = self.translation
            canvas.save()
            canvas.translate(x, y)
        for cmd in self.children:
            cmd.execute(canvas)
        if self.translation:
            canvas.restore()

    def clone(self, child):
        return Transform(self.translation, self.self_rect,
            self.node, [child])

    def __repr__(self):
        if self.translation:
            (x, y) = self.translation
            return "Transform(translate({}, {}))".format(x, y)
        else:
            return "Transform(<no-op>)"
```

`click`에서 이동을 고려하도록 히트 테스팅 알고리즘도 고쳐야 합니다. 레이아웃 객체의 위치를 클릭 지점과 그냥 비교하는 대신, 이동 오프셋을 포함해 사용자가 보는 좌표계에서의 _절대_ 경계를 계산해 그것과 비교합니다. 그런 경계를 계산하는 헬퍼 메서드 두 개를 쓰겠습니다. 첫 번째는 rect를 이동을 통해 매핑하고, 두 번째는 노드 트리를 거슬러 올라가며 발견되는 각 이동을 통해 매핑합니다.

```python
def map_translation(rect, translation):
    if not translation:
        return rect
    else:
        (x, y) = translation
        matrix = skia.Matrix()
        matrix.setTranslate(x, y)
        return matrix.mapRect(rect)

def absolute_bounds_for_obj(obj):
    rect = skia.Rect.MakeXYWH(
        obj.x, obj.y, obj.width, obj.height)
    cur = obj.node
    while cur:
        rect = map_translation(rect,
            parse_transform(
                cur.style.get("transform", "")))
        cur = cur.parent
    return rect
```

그리고 `click`에서 그것을 사용합니다.

그런데 위 예제를 불러와 보면 여전히 잘못 보일 것입니다. 파란 사각형이 초록 사각형 _아래에_ 있어야 하는데 위에 있습니다.[^38]

그것은 우리가 겹침을 테스트할 때 디스플레이 아이템의 `composited_bounds`를 합성 레이어의 `composited_bounds`와 비교하기 때문입니다. 즉 디스플레이 아이템의 원래 위치를 비교하는 것이지 이동된 버전을 비교하는 것이 아닙니다. 대신 절대 경계를 계산해야 합니다.

```python
class Browser:
    def composite(self):
        for cmd in non_composited_commands:
            for layer in reversed(self.composited_layers):
                if layer.can_merge(cmd):
                    # ...
                elif skia.Rect.Intersects(
                    layer.absolute_bounds(),
                    local_to_absolute(cmd, cmd.rect)):
                    # ...
```

`absolute_bounds` 메서드는 다음과 같습니다.

```python
class CompositedLayer:
    def absolute_bounds(self):
        rect = skia.Rect.MakeEmpty()
        for item in self.display_items:
            rect.join(local_to_absolute(item, item.rect))
        return rect
```

`local_to_absolute`를 구현하려면 먼저 `Transform`에 새 `map` 메서드가 필요합니다. 이 메서드는 변환의 "내용" 좌표계의 rect를 받아 변환 후 공간의 rect를 출력합니다. 예를 들어 변환이 `translate(20px, 0px)`였다면, rect에 대해 `map`을 호출한 결과는 그것을 _x_ 방향으로 20픽셀 이동시킬 것입니다.

```python
class Transform(VisualEffect):
    def map(self, rect):
        return map_translation(rect, self.translation)
```

`Blend`의 경우 클리핑을 위한 특수 처리를 넣어 둘 만합니다.

```python
class Blend(VisualEffect):
    def map(self, rect):
        if self.children and \
           isinstance(self.children[-1], Blend) and \
           self.children[-1].blend_mode == "destination-in":
            bounds = rect.makeOffset(0.0, 0.0)
            bounds.intersect(self.children[-1].rect)
            return bounds
        else:
            return rect
```

이제 디스플레이 아이템의 절대 경계를 계산할 수 있습니다. 그 합성 경계를 자신에게 적용된 모든 시각 효과를 통해 매핑하면 됩니다. 이는 `absolute_bounds_for_obj`와 아주 비슷해 보이지만, 레이아웃 객체 트리가 아니라 디스플레이 리스트에서 동작합니다.

```python
def local_to_absolute(display_item, rect):
    while display_item.parent:
        rect = display_item.parent.map(rect)
        display_item = display_item.parent
    return rect
```

이제 파란 사각형이 초록 사각형 아래에 있어야 하며, 겹침 테스트가 완성되었습니다. 이제 [이 예제](https://browser.engineering/examples/example13-transform-overlap.html)를 올바르게 렌더링할 수 있을 것입니다.

그런데 생각해 볼 만한 상황이 하나 더 있습니다. 텍스트가 많이 든 거대한 합성 레이어가 있는데 그 레이어의 작은 부분만 화면에 보이고 나머지는 잘려 나간다고 합시다. 그러면 `absolute_bounds`는 클립 연산을 고려하지만 `composited_bounds`는 그렇지 않으므로, 필요한 것보다 훨씬 큰 합성 레이어를 만들고 사용자가 결코 보지 않을 픽셀을 래스터화하는 데 많은 시간을 낭비하게 됩니다.

그 클립들을 `composited_bounds`에도 적용해 이를 고칩시다.[^39] 먼저 각 아이템의 절대 경계를 계산한 다음 그것을 다시 지역 공간으로 매핑하면, 각 디스플레이 아이템에 대해 "클립된 지역 rect"를 계산하는 효과가 납니다.

```python
class CompositedLayer:
    def composited_bounds(self):
        rect = skia.Rect.MakeEmpty()
        for item in self.display_items:
            rect.join(absolute_to_local(
                item, local_to_absolute(item, item.rect)))
        rect.outset(1, 1)
        return rect
```

이를 위해 `absolute_to_local`을 구현해야 합니다.

```python
def absolute_to_local(display_item, rect):
    parent_chain = []
    while display_item.parent:
        parent_chain.append(display_item.parent)
        display_item = display_item.parent
    for parent in reversed(parent_chain):
        rect = parent.unmap(rect)
    return rect
```

그리고 그것은 다시 `unmap`에 의존합니다. `Blend`의 경우 아무 일도 하지 않아야 하지만, `Transform`의 경우 그저 역방향 이동입니다.

```python
def map_translation(rect, translation, reversed=False):
    # ...
    else:
        # ...
        if reversed:
            matrix.setTranslate(-x, -y)
        else:
            matrix.setTranslate(x, y)

class Transform(VisualEffect):
    def unmap(self, rect):
        return map_translation(rect, self.translation, True)
```

### 더 알아보기

합성의 겹침 이유는 코드를 복잡하게 만들 뿐 아니라, 브라우저와 웹 개발자가 주의하지 않으면 엄청난 양의 GPU 메모리 사용과 추가 합성 레이어를 관리하느라 생기는 페이지 속도 저하로 이어질 수 있습니다. 이런 일이 일어나는 한 가지 경로는, 한 요소가 다른 요소와 겹쳐서 추가 합성 레이어가 생기고, 그것이 다시 세 번째 요소와 겹쳐서 또 하나가 생기고, 이런 식으로 이어지는 것입니다. 이 현상을 _레이어 폭발(layer explosion)_ 이라고 합니다. 우리 브라우저의 알고리즘은 조상 효과가 호환되는 한 여러 디스플레이 아이템을 병합할 수 있으므로 대체로 이 문제를 피하지만, 실제로는 콘텐츠를 효율적으로 병합하기 어려운 복잡한 상황들이 있습니다.

겹침 외에도 합성이 원치 않는 부작용을 일으켜 성능 문제로 이어지는 상황이 있습니다. 예를 들어 메모리가 넉넉하지 않은 기기 같은 특정 상황에서 합성 스크롤을 _끄되_ 시각 효과 애니메이션에는 여전히 합성을 쓰고 싶다고 합시다. 그런데 그 애니메이션이 스크롤러 아래의 콘텐츠에 있다면 어떻게 될까요? 실제로는 그냥 포기하고 스크롤러를 합성해 버리지 않고서는 이 상황을 올바르게 구현하기가 매우 어려울 수 있습니다.

## 연습문제

**13-1 _`background-color`_.** `background-color` CSS 속성의 애니메이션을 구현하세요. 모든 색 채널에 적용되는 새로운 종류의 보간을 정의해야 합니다.

**13-2 _이징 함수_.** 우리 브라우저는 시작 값과 끝 값 사이의 선형 보간만 구현하지만, 다른 [이징 함수](https://developer.mozilla.org/en-US/docs/Web/CSS/easing-function)도 많습니다(사실 실제 브라우저의 기본값은 선형이 아니라 `cubic-bezier(0.25, 0.1, 0.25, 1.0)`입니다). 이 이징 함수와 한두 개를 더 구현하세요.

**13-3 _합성되고 스레드화된 애니메이션_.** 우리 브라우저는 변환과 스크롤을 지원하지만 완전히 합성되고 스레드화되지는 않았으며, 변환 트랜지션 애니메이션도 지원하지 않습니다. 이것들을 구현하세요. (힌트: 변환의 경우 `opacity`와 같은 패턴을 따르기만 하면 됩니다. 스크롤의 경우 `handle_down`에서 더 적은 더티 플래그를 설정하면 됩니다.) 이제 [변환과 불투명도를 동시에 애니메이션하는 예제](https://browser.engineering/examples/example13-transform-transition.html)가 래스터화 없이 동작해야 하고, 그 페이지에서 스크롤해도 래스터화가 일어나지 않아야 합니다.

**13-4 _너비/높이 애니메이션_.** (먼저 연습문제 6-2를 해야 합니다.) `width`와 `height`를 애니메이션 가능하게 만드세요. 픽셀 값(문자열의 "px" 접미사)을 파싱하고 만들어 내는 `NumericAnimation`의 변형이 필요합니다. `width`와 `height`는 레이아웃을 유발하므로, 그것들을 애니메이션할 때 반드시 `needs_layout`이 설정되게 하세요. 브라우저에서 width를 애니메이션하면 줄바꿈이 바뀌는지 확인하세요. width 애니메이션을 구현하고 나면 [width 트랜지션 예제](https://browser.engineering/examples/example13-width-transition.html)가 동작해야 합니다.[^40]

**13-5 _CSS 애니메이션_.** [CSS 애니메이션](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Animations/Using_CSS_animations) API의 기본을 구현하세요. 특히 `browser.engineering` 웹사이트의 [두](https://browser.engineering/examples/example13-opacity-animation.html) [데모](https://browser.engineering/examples/example13-width-animation.html)를 구현하기에 충분할 만큼의 `animation` CSS 속성과 `@keyframe` 파싱을 구현하세요.

**13-6 _변환 애니메이션에서의 겹침 테스트_.** (먼저 연습문제 13-3을 해야 합니다.) 우리 브라우저는 겹침이 생겼다 사라지게 만드는 변환 애니메이션이 있을 때 현재 겹침 테스트를 올바르게 하지 못합니다. 먼저 그 버그를 드러내는 데모를 만들고, 그다음 고치세요. 고치는 한 가지 방법은 애니메이션되는 변환 디스플레이 아이템을 만날 때마다 "겹침 가정 모드"에 들어가는 것입니다. 이는 (지금 당장은 겹치지 않더라도) 이후의 모든 디스플레이 아이템이 애니메이션되는 그것과 겹친다고 가정하므로, 리스트에서 애니메이션되는 것보다 앞에 있는 어떤 `CompositedLayer`에도 병합될 수 없다는 뜻입니다. 또 다른 방법은 브라우저 스레드에서 매 애니메이션 프레임마다 겹침 테스트를 실행하고, 결과가 이전 프레임과 다르면 합성과 래스터화를 다시 하는 것입니다.[^41]

**13-7 _희소한 합성 레이어 피하기_.** 우리 브라우저의 알고리즘은 현재 조상 효과가 호환되는 페인트 청크를 항상 병합합니다. 하지만 이는 비효율적인 상황으로 이어질 수 있습니다. 예를 들어 웹 페이지에서 시각적으로 아주 멀리 떨어진 두 페인트 청크(하나는 맨 위, 다른 하나는 수천 픽셀 아래)가 같은 `CompositedLayer`에 들어가는 경우입니다. 이는 대부분 낭비되는 GPU 메모리인 거대한 `skia.Surface`를 만들어 내므로 아주 나쁠 수 있습니다. 그 문제를 줄이는 한 가지 방법은 `skia.Surface`의 전체 면적을 어떤 고정된 값보다 크게 만드는 페인트 청크 병합을 중단하는 것입니다. 그것을 구현하세요.[^42]

**13-8 _짧은 디스플레이 리스트_.** 실제 브라우저에서는 단색 하나뿐이거나 몇 개의 단순한 페인트 명령만 있는 `CompositedLayer`를 만나는 일이 비교적 흔합니다.[^43] 페인트 명령이 고정된 개수(이를테면 세 개)보다 적은 `CompositedLayer`에는 `skia.Surface`를 저장하지 않고 대신 그것들을 직접 실행하는 최적화를 구현하세요. 다시 말해 그런 `CompositedLayer`의 `raster`는 아무 일도 하지 않고 `draw`가 대신 페인트 명령을 실행합니다.

**13-9 _히트 테스팅_.** 지금은 클릭을 처리할 때 각 레이아웃 객체의 경계를 (`absolute_bounds_for_obj`를 통해) 절대 좌표로 변환해 클릭 위치와 비교합니다. 하지만 그 대신 레이아웃 트리를 순회하며 클릭 위치를 지역 좌표로 변환할 수도 있습니다. 그것을 대신 구현하세요. 각 레이아웃 객체에 클릭 위치를 받아 변환을 반영하고 자식의 `hit_test` 메서드를 재귀 호출하는 `hit_test` 메서드를 정의하면 편리할 것입니다.[^44]

**13-10 _`z-index`_.** 지금은 HTML 문서에서 뒤에 나오는 요소가 앞의 요소 "위에" 그려집니다. `z-index` CSS 속성은 그 순서를 바꿉니다. `z-index`가 더 큰 요소가 위에 그려지며(같으면 현재 순서로 결정하고, 기본 `z-index`는 0입니다), `z-index`가 효과를 가지려면 요소의 `position` 속성이 (기본값인) `static`이 아닌 다른 값이어야 합니다. `z-index` 지원을 추가하세요. 추가 도전으로 `z-index` 속성을 가진 [중첩 요소](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Positioning/Understanding_z_index/The_stacking_context) 지원도 추가해 보세요.

**13-11 _애니메이션 스크롤_.** 실제 브라우저에는 스크롤 중에 일어나는 여러 종류의 애니메이션이 있습니다. 예를 들어 아래쪽 방향키를 누르거나 스크롤바의 아래쪽 화살표를 누르면, 우리 브라우저가 현재 구현한 즉각적인 스크롤 대신 기분 좋은 애니메이션 스크롤이 일어납니다. 모바일에서는 터치 상호작용이 마찰이 있는 스크롤 관성 물리 모델에 따라 "플링(fling)" 스크롤을 일으키는 경우가 많습니다. `<body>` 요소에 [`scroll-behavior`](https://developer.mozilla.org/en-US/docs/Web/CSS/scroll-behavior) CSS 속성을 구현하고, 그것을 사용해 스크롤을 메인 스레드 애니메이션에 위임함으로써 `handle_down`에서 애니메이션 스크롤을 유발하세요.[^45] 새 `ScrollAnimation` 클래스와 `run_animation_frame`의 로직 일부를 구현해야 합니다. 이제 [변환 트랜지션](https://browser.engineering/examples/example13-transform-transition.html) 예제에서 스크롤이 매끄러워야 하는데, 그 예제가 `scroll-behavior`를 사용하기 때문입니다.[^46]

**13-12 _불투명도와 그리기_.** `DrawCompositedLayer` 명령이 `Blend(alpha=0.5)` 안에서 일어나면 지금은 서피스 복사가 두 번 있을 수 있습니다. 먼저 합성 레이어의 래스터 버퍼를 임시 버퍼로 복사하고, 그다음 거기에 불투명도를 적용해 루트 서피스로 복사하는 것이죠. 이는 불필요하며, 실제로 `Surface`에 대한 Skia의 [`draw`](https://kyamagu.github.io/skia-python/reference/skia.Surface.html#skia.Surface.draw) API는 불투명도를 적용할 수 있게 해 줍니다. 이 상황이 일어날 때 이 둘을 하나의 `draw` 명령으로 합치도록 브라우저를 최적화하세요. (이는 실제 브라우저에서 중요한 최적화입니다.)

CPU에서는 업로드 단계와 컴파일 단계가 필요 없고, 래스터화와 그리기에 쓸 메모리도 더 많습니다. 물론 GPU와 CPU 양쪽에 많은 최적화가 있으므로, 주어진 페이지를 래스터화하고 그릴 최선의 방법을 고르는 일은 꽤 복잡할 수 있습니다.
