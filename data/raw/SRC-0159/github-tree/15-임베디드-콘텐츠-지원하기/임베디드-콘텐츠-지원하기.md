우리 브라우저는 복잡한 스타일, 시각 효과, 애니메이션을 렌더링할 수 있지만, 그 모든 것은 기본적으로 텍스트에만 적용됩니다. 그런데 웹 페이지에는 이미지부터 다른 웹 페이지까지 텍스트가 아닌 다양한 _임베디드 콘텐츠_ 가 들어 있습니다. 임베디드 콘텐츠 지원은 브라우저 아키텍처, 성능, 보안, 열린 정보 접근에 강력한 영향을 미치며, 웹의 역사 전반에 걸쳐 핵심적인 역할을 해 왔습니다.

## 이미지

이미지는 [1993년 초](http://1997.webhistory.org/www.lists/www-talk.1993q1/0182.html)까지 거슬러 올라가는, 웹에서 확실히 가장 인기 있는 임베디드 콘텐츠입니다.[^1][^2] 이미지는 `<img>` 태그를 통해 웹 페이지에 포함되며, 다음과 같이 생겼습니다.

```
<img src="https://browser.engineering/im/hes.jpg">
```

이 특정 예제는 그림 1과 같이 렌더링됩니다.

![그림 1: 1969년 하이퍼텍스트 편집 시스템을 사용하는 컴퓨터 운용자. (Wikipedia의 Gregory Lloyd, CC BY-SA 4.0 International.)](hes.jpg)

*그림 1: 1969년 하이퍼텍스트 편집 시스템을 사용하는 컴퓨터 운용자. ([Wikipedia](https://commons.wikimedia.org/wiki/File:HypertextEditingSystemConsoleBrownUniv1969.jpg)의 Gregory Lloyd, [CC BY-SA 4.0 International](https://creativecommons.org/licenses/by-sa/4.0/deed.en).)*

다행히 이미지를 구현하는 것은 그리 어렵지 않으니 바로 시작합시다. 우리 브라우저에서 이미지를 표시하는 데는 네 단계가 있습니다.

1. URL에서 이미지를 내려받습니다.

2. 이미지를 메모리의 버퍼로 디코딩합니다.

3. 페이지에 이미지를 배치합니다.

4. 디스플레이 리스트에 이미지를 페인트합니다.

URL에서 이미지를 내려받는 것부터 시작합시다. 당연히 그것은 HTTP를 통해 일어나고, 우리에겐 이미 `request` 함수가 있습니다. 다만 지금까지 내려받은 콘텐츠(HTML, CSS, JavaScript)는 모두 텍스트였던 반면, 이미지는 보통 이진 데이터 형식을 사용합니다. `request`를 확장해 이진 데이터를 지원해야 합니다.

변경은 아주 사소합니다. `makefile`에 `"r"` 플래그를 넘기는 대신, 이진 모드를 나타내는 `"b"` 플래그를 넘기면 됩니다.

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
        response = s.makefile("b")
        # ...
```

이제 `response`에서 읽을 때마다 텍스트 데이터를 담은 `str`이 아니라 이진 데이터의 `bytes`를 얻게 되므로, HTTP 파서 코드 일부가 데이터를 명시적으로 `decode`하도록 바꿔야 합니다.

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
        statusline = response.readline().decode("utf8")
        # ...
        while True:
            line = response.readline().decode("utf8")
            # ...
        # ...
```

본문을 읽을 때는 `decode` 호출을 추가하지 _않았다는_ 점에 주의하세요. 본문이 실제로 이진 데이터일 수 있고, 그 이진 데이터를 브라우저에 그대로 반환하고 싶기 때문입니다. 이제 텍스트 데이터를 원하는 기존의 모든 `request` 호출은 응답을 `decode`해야 합니다. 예를 들어 `load`에서는 다음과 비슷하게 해야 합니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        headers, body = url.request(self.url, payload)
        body = body.decode("utf8", "replace")
        # ...
```

`decode`의 두 번째 인자로 `replace`를 넘겨서, 유효하지 않은 문자가 있으면 예외를 던지는 대신 특수 문자 �로 대체하라고 Python에 알려 줍니다.

`XMLHttpRequest_send` 안과 `load`의 여러 다른 곳을 포함해, 브라우저에서 `request`를 호출하는 모든 곳에 이 변경을 반드시 적용하세요.

다만 이미지를 내려받을 때는 `decode`를 호출하지 _않고_ 이진 데이터를 그대로 사용하겠습니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        images = [node
            for node in tree_to_list(self.nodes, [])
            if isinstance(node, Element)
            and node.tag == "img"]
        for img in images:
            src = img.attributes.get("src", "")
            image_url = url.resolve(src)
            assert self.allowed_request(image_url), \
                "Blocked load of " + str(image_url) + " due to CSP"
            header, body = image_url.request(url)
```

이미지를 내려받았으면 그것을 Skia `Image` 객체로 바꿔야 합니다. 다음 코드가 필요합니다.

```python
class Tab:
    def load(self, url, payload=None):
        for img in images:
            # ...
            img.encoded_data = body
            data = skia.Data.MakeWithoutCopy(body)
            img.image = skia.Image.MakeFromEncoded(data)
```

여기에는 까다로운 단계가 두 개 있습니다. 요청된 데이터가 `MakeWithoutCopy` 메서드로 Skia `Data` 객체가 되고, 그다음 `MakeFromEncoded`로 이미지가 됩니다.

`MakeWithoutCopy`를 썼기 때문에 `Data` 객체는 기존 `body`에 대한 참조만 저장하고 그 데이터를 소유하지 않습니다. 이는 필수적인데, 인코딩된 이미지 데이터는 어쩌면 수 메가바이트로 클 수 있고 그 데이터를 복사하는 것은 메모리와 시간의 낭비이기 때문입니다. 하지만 그 말은 `body`가 가비지 컬렉션되면 `data`가 무효가 된다는 뜻이기도 합니다. 그래서 `body`를 `encoded_data` 필드에 저장하는 것입니다.[^3]

이 내려받기와 디코딩 단계는 둘 다 실패할 수 있습니다. 그런 일이 생기면 "깨진 이미지" 자리 표시자를 불러오겠습니다([Wikipedia의 것](https://commons.wikimedia.org/wiki/File:Broken_Image.png)을 썼습니다).

```python
BROKEN_IMAGE = skia.Image.open("Broken_Image.png")

class Tab:
    def load(self, url, payload=None):
        for img in images:
            try:
                # ...
                assert img.image, \
                    "Failed to recognize image format for " + \
                        str(image_url)
            except Exception as e:
                print("Image", img.attributes.get("src", ""),
                    "crashed", e)
                img.image = BROKEN_IMAGE
```

이제 이미지를 내려받아 저장했으니 그것을 사용해야 합니다. Skia의 `drawImageRect` 함수를 호출하기만 하면 됩니다.

```python
class DrawImage(PaintCommand):
    def __init__(self, image, rect):
        super().__init__(rect)
        self.image = image

    def execute(self, canvas):
        canvas.drawImageRect(self.image, self.rect)
```

다만 `drawImageRect`의 내부는 조금 복잡해서 자세히 살펴볼 가치가 있습니다. `Image` 객체가 `MakeFromEncoded` 메서드로 만들어진다는 점을 떠올려 보세요. 그 이름은 우리가 내려받은 이미지가 원시 이미지 바이트가 아니라는 것을 상기시켜 줍니다. 실제로 여러분이 아는 모든 이미지 형식(JPG, PNG를 비롯한 수많은 잘 알려지지 않은 것들)은 다양한 정교한 알고리즘으로 이미지 데이터를 인코딩합니다. 따라서 이미지는 사용되기 전에 _디코딩_ 되어야 합니다.[^4]

Skia는 디코딩에 다양한 영리한 최적화를 적용합니다. 이미지를 최종 크기로 곧바로 디코딩하거나, 디코딩된 이미지를 가능한 한 오래 캐시하는 것 같은 것들이죠.[^5] 원시 이미지 데이터가 꽤 클 수 있기 때문입니다.[^6] 픽셀 하나는 보통 4바이트로 저장되므로, (요즘 휴대폰에 있는) 1200만 화소 카메라는 이미지 하나에 48메가바이트의 원시 데이터를 만들어 냅니다.

이미지 디코딩이 그렇게 비쌀 수 있기 때문에, Skia에는 디코딩에 쓸 수 있는 여러 알고리즘도 있습니다. 그중 일부는 더 빠르지만 결과 이미지가 더 나빠 보입니다.[^7] 예를 들어 빠르고 단순한 "최근접 이웃(nearest neighbor)" 알고리즘이 있고, 더 느리지만 품질이 좋은 "쌍선형(bilinear)"이나 심지어 "[Lanczos](https://en.wikipedia.org/wiki/Lanczos_resampling)" 알고리즘도 있습니다.[^8]

웹 페이지 작성자가 이 성능 병목을 제어할 수 있도록, 어떤 알고리즘을 쓸지 나타내는 [`image-rendering`](https://developer.mozilla.org/en-US/docs/Web/CSS/image-rendering) CSS 속성이 있습니다. 그것을 `DrawImage`의 인자로 추가합시다.[^9]

```python
def parse_image_rendering(quality):
   if quality == "high-quality":
       return skia.SamplingOptions(skia.CubicResampler.Mitchell())
   elif quality == "crisp-edges":
       return skia.SamplingOptions(
           skia.FilterMode.kNearest, skia.MipmapMode.kNone)
   else:
       return skia.SamplingOptions(
           skia.FilterMode.kLinear, skia.MipmapMode.kLinear)

class DrawImage(PaintCommand):
    def __init__(self, image, rect, quality):
        # ...
        self.quality = parse_image_rendering(quality)

    def execute(self, canvas):
        canvas.drawImageRect(self.image, self.rect, self.quality)
```

그런데 이 인자가 어디서 오는지 이야기하려면, 더 일반적으로는 내려받은 이미지를 우리 브라우저에서 실제로 보려면, 먼저 이미지를 브라우저의 레이아웃 트리에 추가해야 합니다.

### 더 알아보기

HTTP `Content-Type` 헤더는 웹 서버가 브라우저에게 문서가 텍스트를 담고 있는지 이진 데이터를 담고 있는지 알려 주게 해 줍니다. 이 헤더는 [MIME 타입](https://developer.mozilla.org/en-US/docs/Web/HTTP/Basics_of_HTTP/MIME_types)이라는 값을 담습니다. HTML, CSS, JavaScript에 대한 `text/html`, `text/css`, `text/javascript`, PNG와 JPEG 이미지에 대한 `image/png`와 `image/jpeg`, 그리고 여러 폰트·비디오·오디오·데이터 형식에 대한 [수많은 것들](https://www.iana.org/assignments/media-types/media-types.xhtml)이 있습니다.[^10] 흥미롭게도 위 코드에서 우리는 이미지 형식을 지정할 필요가 없었습니다. 많은 이미지 형식이 ["매직 바이트"](https://www.netspi.com/blog/technical/web-application-penetration-testing/magic-bytes-identifying-common-file-formats-at-a-glance/)로 시작하기 때문입니다. 예를 들어 PNG 파일은 항상 바이트 137 뒤에 "PNG"라는 글자로 시작합니다. 이 매직 바이트는 흔히 웹 서버가 제공하는 MIME 타입보다 신뢰할 만해서, 그런 "형식 스니핑"은 브라우저와 그 지원 라이브러리 안에서 흔합니다.

## 임베디드 레이아웃

앞선 장들의 경험에 비추어 보면, 우리 브라우저의 레이아웃과 페인트 과정에 이미지를 어떻게 추가할지 짐작할 수 있을 것입니다. `ImageLayout` 클래스를 만들고, `BlockLayout`의 `recurse` 메서드에 새 `image` 분기를 추가하고, `ImageLayout`의 `paint` 메서드에서 `DrawImage` 명령을 만들어 내야 합니다.

그렇게 하다 보면 `<input>` 요소에 대해 아주 비슷한 일을 했던 것이 떠오를 수 있습니다. 실제로 텍스트 영역과 버튼은 이미지와 매우 비슷합니다. 둘 다 DOM의 잎 노드이고, 줄 안에 놓이며, 텍스트 베이스라인의 영향을 받고, 맞춤 콘텐츠를 페인트합니다.[^11] 워낙 비슷하니 같은 코드를 재사용해 봅시다.

기존 `InputLayout`을 대부분의 기존 코드를 담은 `EmbedLayout`이라는 상위 클래스와, 입력에 특화된 코드를 담은 새 하위 클래스 `InputLayout`으로 나눕시다.[^12]

```python
class EmbedLayout:
    def __init__(self, node, parent, previous, frame):
        # ...

    def layout(self):
        self.zoom = self.parent.zoom
        self.font = font(self.node.style, self.zoom)
        if self.previous:
            space = self.previous.font.measureText(" ")
            self.x = \
                self.previous.x + space + self.previous.width
        else:
            self.x = self.parent.x
```

```python
class InputLayout(EmbedLayout):
    def __init__(self, node, parent, previous):
        super().__init__(node, parent, previous)

    def layout(self):
        super().layout()
```

아이디어는 `EmbedLayout`이 모든 종류의 임베디드 콘텐츠를 위한 공통 레이아웃 코드를 제공하고, `InputLayout` 같은 하위 클래스가 그 콘텐츠 타입에 특화된 코드를 제공한다는 것입니다. 임베디드 콘텐츠 타입마다 너비와 높이가 다를 수 있으므로 그것은 각 하위 클래스에서 일어나야 하며, `paint`의 정의도 마찬가지입니다.

```python
class InputLayout(EmbedLayout):
    def layout(self):
        # ...
        self.width = dpx(INPUT_WIDTH_PX, self.zoom)
        self.height = linespace(self.font)
        self.ascent = -self.height
        self.descent = 0

    def paint(self):
        # ...
```

이제 `ImageLayout`은 대부분의 동작을 `EmbedLayout`에서 상속받되 너비와 높이는 이미지 자체에서 가져올 수 있습니다.

```python
class ImageLayout(EmbedLayout):
    def __init__(self, node, parent, previous):
        super().__init__(node, parent, previous)

    def layout(self):
        super().layout()
        self.width = dpx(self.node.image.width(), self.zoom)
        self.img_height = dpx(self.node.image.height(), self.zoom)
        self.height = max(self.img_height, linespace(self.font))
        self.ascent = -self.height
        self.descent = 0
```

이미지의 높이가 요소의 폰트 크기에 의존한다는 점을 눈여겨보세요. 이상해 보이지만 실제로 이미지 레이아웃은 이렇게 동작합니다. 아주 작은 이미지 하나만 있는 줄도 텍스트를 담을 만큼 키가 큽니다.[^13] 그 근본적인 이유는, 인라인 레이아웃의 한 종류로서 이미지가 관련 텍스트와 함께 흐르도록 설계되었기 때문입니다. 즉 이미지의 아래쪽이 [텍스트 베이스라인](https://browser.engineering/text.html#text-of-different-sizes)에 맞춰져야 합니다. 위 코드에서 `img_height`를 저장하는 이유도 그것입니다.

또한 위 코드에서 `EmbedLayout` 하위 클래스에 새 `ascent`와 `descent` 필드를 도입했습니다. 이는 어센트와 디센트에 대한 기존 레이아웃 코드를 대신해 `LineLayout` 레이아웃에서 쓰기 위한 것입니다. 그러려면 `TextLayout`에도 그 필드를 도입해야 합니다.

```python
class LineLayout:
    def layout(self):
        # ...
        max_ascent = max([-child.ascent 
                          for child in self.children])
        baseline = self.y + max_ascent

        for child in self.children:
            if isinstance(child, TextLayout):
                child.y = baseline + child.ascent / 1.25
            else:
                child.y = baseline + child.ascent
        max_descent = max([child.descent
                           for child in self.children])
        self.height = max_ascent + max_descent

class TextLayout:
    def layout(self):
        # ...
        self.ascent = self.font.getMetrics().fAscent * 1.25
        self.descent = self.font.getMetrics().fDescent * 1.25
```

        rect = skia.Rect.MakeLTRB(
            self.x, self.y + self.height - self.img_height,
            self.x + self.width, self.y + self.height)

이제 `BlockLayout`에서 `ImageLayout`을 만들어야 합니다. 입력 요소는 `input` 메서드에서 만들어지므로 대체로 비슷한 `image` 메서드를 만듭니다. 그런데 `input` 자체가 대체로 `word`의 중복이므로 중복이 많아질 것입니다. 이 메서드들에서 다른 부분은 새 인라인 자식의 너비를 계산하는 부분뿐이고, 나머지 로직 대부분은 공유됩니다.

대신 공유되는 코드를 `text`, `image`, `input`이 호출할 수 있는 새 메서드로 리팩터링합시다. 먼저 이 메서드들은 모두 인라인 뒤에 얼마나 많은 공간[^14]을 남길지 결정하기 위해 폰트가 필요합니다. 그것을 위한 함수를 만듭시다.

```python
def font(style, zoom):
    weight = style["font-weight"]
    variant = style["font-style"]
    size = float(style["font-size"][:-2]) * 0.75
    font_size = dpx(size, zoom)
    return get_font(font_size, weight, variant)
```

줄 레이아웃을 처리하는 공유 코드도 있습니다. 그것을 새 `add_inline_child` 메서드에 넣읍시다. HTML 노드, 요소, 인스턴스화할 레이아웃 클래스(그리고 `TextLayout`만을 위한 `word` 매개변수)를 넘겨야 합니다.

```python
class BlockLayout:
    def add_inline_child(self, node, w, child_class, word=None):
        if self.cursor_x + w > self.x + self.width:
            self.new_line()
        line = self.children[-1]
        previous_word = line.children[-1] if line.children else None
        if word:
            child = child_class(node, word, line, previous_word)
        else:
            child = child_class(node, line, previous_word)
        line.children.append(child)
        self.cursor_x += w + \
            font(node.style, self.zoom).measureText(" ")
```

이제 `word`와 `input`을 만족스럽게 다시 정의할 수 있습니다.

```python
class BlockLayout:

        w = node_font.measureText(word)
        self.add_inline_child(node, w, TextLayout, word)

    def input(self, node):
        w = dpx(INPUT_WIDTH_PX, self.zoom)
        self.add_inline_child(node, w, InputLayout) 
```

## 이미지 크기 바꾸기

지금까지 화면에서 이미지의 크기는 픽셀 단위의 크기이며, 확대되었을 수도 있습니다.[^16] 하지만 실제로 작성자가 임베디드 콘텐츠의 크기를 제어할 수 있는 것은 대체로 값진 일입니다. 이를 하는 방법은 여러 가지가 있지만,[^17] 한 가지는 특별한 `width`와 `height` 속성입니다.[^18]

이 두 속성이 _모두_ 있으면 꽤 쉽습니다. 요소를 배치할 때 그것들을 읽기만 하면 됩니다. `image`에서도

```python
class BlockLayout:
    def image(self, node):
        if "width" in node.attributes:
            w = dpx(int(node.attributes["width"]), self.zoom)
        else:
            w = dpx(node.image.width(), self.zoom)
        # ...
```

그리고 `ImageLayout`에서도요.

```python
class ImageLayout(EmbedLayout):
    def layout(self):
        # ...
        width_attr = self.node.attributes.get("width")
        height_attr = self.node.attributes.get("height")
        image_width = self.node.image.width()
        image_height = self.node.image.height()

        if width_attr and height_attr:
            self.width = dpx(int(width_attr), self.zoom)
            self.img_height = dpx(int(height_attr), self.zoom)
        else:
            self.width = dpx(image_width, self.zoom)
            self.img_height = dpx(image_height, self.zoom)
        # ...
```

이는 아주 잘 동작하지만 큰 결함이 하나 있습니다. `width`와 `height`의 비율이 원본 이미지 크기의 비율과 다르면 이미지가 이상하게 늘어나게 됩니다. 의도적일 때도 있지만 보통은 실수입니다. 그래서 브라우저는 작성자가 `width`와 `height` 중 _하나만_ 지정하고 다른 하나는 이미지의 _종횡비_ 로 계산하게 해 줍니다.[^19]

이 종횡비 조정을 구현하는 것은 쉽습니다.

```python
class ImageLayout(EmbedLayout):
    # ...
    def layout(self):
        # ...
        aspect_ratio = image_width / image_height

        if width_attr and height_attr:
            # ...
        elif width_attr:
            self.width = dpx(int(width_attr), self.zoom)
            self.img_height = self.width / aspect_ratio
        elif height_attr:
            self.img_height = dpx(int(height_attr), self.zoom)
            self.width = self.img_height * aspect_ratio
        else:
            # ...
        # ...
```

우리 브라우저는 로드된 이미지 크기로부터 종횡비를 계산하지만, 이미지가 로드되기 전에는 그것을 알 수 없습니다. 이미지를 비동기적으로 로드하고 이미지 크기가 레이아웃 매개변수에 [반응할 수 있는](https://developer.mozilla.org/en-US/docs/Learn/CSS/CSS_layout/Responsive_Design) 실제 브라우저에서는 이것이 문제입니다. 종횡비를 모르면 이미지가 로드될 때 [레이아웃이 흔들릴](https://web.dev/cls/) 수 있는데, 이는 사용자에게 짜증스러운 일입니다. [`aspect-ratio` 속성](https://developer.mozilla.org/en-US/docs/Web/CSS/aspect-ratio)은 웹 페이지가 이 문제를 해결하는 한 가지 방법입니다.

## 대화형 위젯

지금까지 우리 브라우저에는 두 종류의 임베디드 콘텐츠가 있습니다. 이미지와 입력 요소입니다. 둘 다 중요하고 널리 쓰이지만,[^20] 지도, PDF, 광고, 소셜 미디어 컨트롤 같은 복잡한 임베디드 콘텐츠 사용 사례가 요구하는 맞춤 설정성[^21]과 유연성을 제공하지는 못합니다. 그래서 현대 브라우저에서 이런 것들은 `<iframe>` 요소를 사용해 _한 웹 페이지 안에 다른 웹 페이지를 내장_ 함으로써 처리됩니다.[^22]

의미론적으로 `<iframe>`은 `Tab` 안의 `Tab`과 비슷합니다. 자신만의 HTML 문서, CSS, 스크립트를 갖습니다. 그리고 레이아웃 면에서 `<iframe>`은 `width`와 `height` 속성을 가진 `<img>` 태그와 아주 비슷합니다. 그래서 기본적인 iframe을 구현하려면 다음 세 가지 큰 차이만 처리하면 됩니다.

- iframe에는 _브라우저 크롬이 없습니다_. 따라서 모든 페이지 이동은 페이지 안에서(`<a>` 요소나 스크립트를 통해) 일어나거나, `<iframe>` 요소를 _담고 있는_ 웹 페이지에서 일어나는 이동의 부수 효과로 일어나야 합니다. iframe 안의 링크를 클릭하면 최상위 페이지가 아니라 그 iframe이 이동합니다.

- iframe은 _렌더링 이벤트 루프를 공유할 수 있습니다_.[^23] 실제 브라우저에서 [교차 출처](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy) iframe은 흔히 "사이트 격리"되어, [보안상의 이유로](https://www.chromium.org/Home/chromium-security/site-isolation/) 자신만의 CPU 프로세스를 갖습니다. 우리 브라우저에서는 (중첩된 것도 포함해 — 그렇습니다, iframe은 iframe을 담을 수 있습니다!) 모든 iframe이 같은 렌더링 이벤트 루프를 쓰게 하겠습니다.

- 교차 출처 iframe은 담고 있는 페이지와 _스크립트가 격리됩니다_. 즉 iframe 안의 스크립트는 담고 있는 페이지의 변수나 DOM에 [접근할 수 없고](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy#cross-origin_script_api_access), 담고 있는 페이지의 스크립트도 iframe의 변수나 DOM에 접근할 수 없습니다. 다만 동일 출처 iframe은 접근할 수 있습니다.

이 차이들은 곧 다루겠지만, 우선 `Tab` 안의 `Tab`이라는 아이디어부터 작업해 봅시다. 우리가 할 일은 `Tab` 클래스를 두 조각으로 나누는 것입니다. `Tab`은 이벤트 루프와 스크립트 환경을 소유하고, `Frame`이 나머지를 합니다.

이런 복잡한 리팩터링은 어느 정도 자세히 계획해 두는 것이 좋습니다. `Tab`은 다음을 합니다.

- 이벤트를 처리하기 위해 `Browser`와 `Frame` 사이를 중개합니다.

- 프레임 간 통신을 중계합니다.

- 애니메이션 프레임과 렌더링을 시작합니다.

- 탭의 모든 프레임에 대한 디스플레이 리스트를 페인트하고 소유합니다.

- 접근성 트리를 구성하고 소유합니다.

- 브라우저 스레드로 커밋합니다.

그리고 새로운 `Frame` 클래스는 다음을 합니다.

- 자신의 HTML 문서에 대한 DOM, 레이아웃 트리, 스크롤 오프셋을 소유합니다.

- 자신의 DOM과 레이아웃 트리에 대해 스타일과 레이아웃을 실행합니다.

- 자신의 HTML 문서에 대한 로딩과 (포커스, 히트 테스팅 등의) 이벤트 처리를 구현합니다.

이 두 클래스를 만들고 메서드를 그에 맞게 나누세요.

당연히 모든 `Frame`에는 자신의 `Tab`에 대한 참조가 필요합니다. 부모 프레임과 대응하는 `<iframe>` 요소에도 접근할 수 있으면 편리합니다.

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        self.tab = tab
        self.parent_frame = parent_frame
        self.frame_element = frame_element
        # ...
```

이제 `Frame`이 어떻게 만들어지는지 봅시다. 첫 번째 자리는 `Tab`의 `load` 메서드로, _루트 프레임_ 을 만들어야 합니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.root_frame = None

    def load(self, url, payload=None):
        self.history.append(url)
        # ...
        self.root_frame = Frame(self, None, None)
        self.root_frame.load(url, payload)
```

`load`의 알맹이가 이제 `Frame` 안에 있다는 점에 주의하세요. `Frame`이 HTML 트리를 소유하기 때문입니다. `Frame`은 `<iframe>` 요소를 위해 자식 `Frame`을 만들 수도 _있습니다_.

```python
class Frame:
    def load(self, url, payload=None):
        # ...
        iframes = [node
                   for node in tree_to_list(self.nodes, [])
                   if isinstance(node, Element)
                   and node.tag == "iframe"
                   and "src" in node.attributes]
        for iframe in iframes:
            document_url = url.resolve(iframe.attributes["src"])
            if not self.allowed_request(document_url):
                print("Blocked iframe", document_url, "due to CSP")
                iframe.frame = None
                continue
            iframe.frame = Frame(self.tab, self, iframe)
        # ...
```

iframe은 하위 자원(과 하위 프레임!)을 가질 수 있어서 로드가 느릴 수 있으므로, 스크립트와 마찬가지로 비동기적으로 로드해야 합니다.

```python
class Frame:
    def load(self, url, payload=None):
        for iframe in iframes:
            # ...
            task = Task(iframe.frame.load, document_url)
            self.tab.task_runner.schedule_task(task)
```

그리고 비동기적이므로 아직 로드되지 않은 iframe을 렌더링하려 하지 않도록 로드 여부를 기록해야 합니다.

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.loaded = False

    def load(self, url, payload=None):
        self.loaded = False
        ...
        self.loaded = True
```

이제 하나의 탭 안에 프레임 트리가 생겼습니다. 그런데 때때로 임의의 프레임에 직접 접근해야 하므로, 각 프레임에 식별자도 부여합시다. 이를 _윈도 ID_ 라고 부르겠습니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.window_id_to_frame = {}
```

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.window_id = len(self.tab.window_id_to_frame)
        self.tab.window_id_to_frame[self.window_id] = self
```

이제 프레임이 만들어지고 있으니, 그 프레임들을 화면에 렌더링하는 작업을 해 봅시다.

### 더 알아보기

꽤 오랫동안 브라우저는 [Java 애플릿](https://en.wikipedia.org/wiki/Java_applet)이나 [Flash](https://en.wikipedia.org/wiki/Adobe_Flash) 같은 _플러그인_ 형태의 임베디드 콘텐츠도 지원했습니다. 하지만 플러그인은 보통 자신만의 렌더링, 샌드박싱, UI 기본 요소를 구현했기 때문에 [성능, 보안, 접근성 문제](https://developer.mozilla.org/en-US/docs/Learn/HTML/Multimedia_and_embedding/Other_embedding_technologies#the_embed_and_object_elements)가 있었습니다. 시간이 지나면서 새로운 API들이 웹 네이티브 콘텐츠와 "비웹" 플러그인 사이의 간극을 좁혔고,[^24] 그래서 플러그인은 점점 드물어졌습니다. 개인적으로 저는 그것이 좋은 일이라고 생각합니다. 웹은 정보를 모두에게 접근 가능하게 만드는 것이고, 그러려면 임베디드 콘텐츠를 포함해 열린 표준이 필요하기 때문입니다.

## iframe 렌더링

렌더링은 `Tab`과 그 `Frame`들로 나뉩니다. `Frame`이 스타일과 레이아웃을 하고, `Tab`이 접근성과 페인트를 합니다.[^25] 그 분할을 구현해야 하고, `Tab`에서 각 `Frame`의 렌더링을 유발하는 코드도 추가해야 합니다.

렌더링 파이프라인을 나누는 것부터 시작합시다. 여기서 주된 메서드는 여전히 `Tab`의 `run_animation_frame`과 `render`이며, 이들이 로드된 모든 iframe을 순회합니다.

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        for (window_id, frame) in self.window_id_to_frame.items():
            if not frame.loaded:
                continue
            frame.js.dispatch_RAF(frame.window_id)
            # ...

    def render(self):
        self.browser.measure.time('render')

        for id, frame in self.window_id_to_frame.items():
            if frame.loaded:
                frame.render()

        if self.needs_accessibility:
            # ...

        if self.needs_paint:
            # ...

        # ...
```

이 코드에서 새로운 `dispatch_RAF` 메서드를 썼습니다.

```python
class JSContext:
    def dispatch_RAF(self):
        self.interp.evaljs("window.__runRAFHandlers()")
```

`needs_accessibility`, `pending_hover`를 비롯한 플래그들이 여전히 `Tab`에 있다는 점에 주의하세요. 그것들은 `Tab`이 맡은 렌더링 부분과 관련되기 때문입니다. 반면 스타일과 레이아웃은 이제 `Frame`에서 일어납니다.

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.needs_style = False
        self.needs_layout = False

    def set_needs_render(self):
        self.needs_style = True
        self.tab.needs_accessibility = True
        self.tab.set_needs_paint()

    def set_needs_layout(self):
        self.needs_layout = True
        self.tab.needs_accessibility = True
        self.tab.set_needs_paint()

    def render(self):
        if self.needs_style:
            # ...

        if self.needs_layout:
            # ...
```

다시 말하지만, 이 더티 플래그들은 프레임이 맡은 렌더링 부분과 관련되므로 `Frame`으로 옮깁니다.

이미지와 달리 iframe에는 [_고유 크기(intrinsic size)_](https://developer.mozilla.org/en-US/docs/Glossary/Intrinsic_Size)가 _없습니다_. `<iframe>` 요소의 레이아웃 크기는 그 내용에 의존하지 않습니다.[^26] 즉 부모 프레임과 자식 프레임 사이에 결정적으로 중요한 추가 통신이 필요합니다. 프레임이 얼마나 넓고 높게 배치되어야 할까요? 이는 `iframe` 요소의 속성과 CSS로 정의됩니다.

```python
class BlockLayout:
    def layout_mode(self):
        # ...
        elif self.node.tag in ["input", "img", "iframe"]:
            return "inline"

    def recurse(self, node):
        else:
            # ...
            elif node.tag == "iframe" and \
                 "src" in node.attributes:
                self.iframe(node)
            # ...

    def iframe(self, node):
        if "width" in self.node.attributes:
            w = dpx(int(self.node.attributes["width"]),
                    self.zoom)
        else:
            w = IFRAME_WIDTH_PX + dpx(2, self.zoom)
        self.add_inline_child(node, w, IframeLayout, self.frame)

    def should_paint(self):
        return isinstance(self.node, Text) or \
            (self.node.tag not in \
                ["input", "button", "img", "iframe"])
```

`IframeLayout` 레이아웃 코드는 비슷하며 `EmbedLayout`을 상속받되 종횡비 코드는 없습니다.

```python
class IframeLayout(EmbedLayout):
    def __init__(self, node, parent, previous, parent_frame):
        super().__init__(node, parent, previous, parent_frame)

    def layout(self):
        # ...
        if width_attr:
            self.width = dpx(int(width_attr) + 2, self.zoom)
        else:
            self.width = dpx(IFRAME_WIDTH_PX + 2, self.zoom)

        if height_attr:
            self.height = dpx(int(height_attr) + 2, self.zoom)
        else:
            self.height = dpx(IFRAME_HEIGHT_PX + 2, self.zoom)
        self.ascent = -self.height
        self.descent = 0
```

추가된 2픽셀은 나중에 각 변에 1픽셀씩 테두리를 위한 공간을 마련해 줍니다.

`width`가 지정되지 않으면 iframe은 [기본값](https://www.w3.org/TR/CSS2/visudet.html#inline-replaced-width)을 사용한다는 점에 주의하세요. 이는 오래전 당시의 평균 화면 크기를 바탕으로 정해진 것입니다.

```python
IFRAME_WIDTH_PX = 300
IFRAME_HEIGHT_PX = 150
```

그런데 이 코드는 _부모_ 프레임에서 실행됩니다. 이 너비와 높이를 _자식_ 프레임으로 전달해서 자식이 레이아웃 중에 자기 너비와 높이를 알 수 있게 해야 합니다. 그러니 자식 프레임에 그것을 위한 필드를 추가합시다.

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.frame_width = 0
        self.frame_height = 0
```

그리고 부모 프레임이 배치될 때 그 값들을 설정할 수 있습니다.

```python
class IframeLayout(EmbedLayout):
    def layout(self):
        # ...
        if self.node.frame and self.node.frame.loaded:
            self.node.frame.frame_height = \
                self.height - dpx(2, self.zoom)
            self.node.frame.frame_width = \
                self.width - dpx(2, self.zoom)
```

조건문은 CSP에 의해 iframe이 차단된 (드문) 경우를 처리하기 위한 것일 뿐입니다.

여기서 자식 프레임에 `set_needs_render`를 호출하지 않는 것이 놀라울 수 있습니다. 그것은 지름길입니다. `width`와 `height` 속성은 `setAttribute`로만 바뀔 수 있고, `zoom`은 `zoom_by`와 `reset_zoom`에서만 바뀔 수 있습니다. 다만 그 모든 핸들러는 새 메서드를 통해 모든 프레임을 무효화해야 하며, 이제 사라진 `Tab`의 기존 `set_needs_render`를 쓰면 안 됩니다. 이 호출 지점들을 모두 그 메서드를 호출하도록 갱신하세요(모든 프레임의 스타일에 영향을 주는 다크 모드 변경도 포함해서요).

```python
class Tab:
    def set_needs_render_all_frames(self):
        for id, frame in self.window_id_to_frame.items():
            frame.set_needs_render()
```

물론 루트 프레임은 창 전체를 채웁니다.

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.root_frame.frame_width = WIDTH
        self.root_frame.frame_height = self.tab_height
```

여기에 까다로운 의존 순서가 있다는 점에 주의하세요. 자식 프레임이 레이아웃할 때 최신 너비와 높이를 갖도록 부모 프레임이 자식보다 먼저 레이아웃해야 합니다. 그 순서는 딕셔너리가 삽입 순서로 정렬되는 Python(3.7 이상)에서는 보장되지만, 다른 언어로 따라 하고 있다면 렌더링하기 전에 프레임을 정렬해야 할 수도 있습니다.

이제 프레임에 스타일이 적용되고 배치되었으니 페인트만 하면 됩니다. 레이아웃이나 스타일과 달리 탭 안의 모든 프레임은 하나로 통합된 디스플레이 리스트를 만들어 내므로 재귀적으로 작업해야 합니다. `Tab`이 루트 `Frame`을 페인트하게 하겠습니다.

```python
class Tab:
    def render(self):
        if self.needs_paint:
            self.display_list = []
            paint_tree(self.root_frame.document, self.display_list)
            self.needs_paint = False
```

대부분의 레이아웃 트리 `paint` 메서드는 바꿀 필요가 없지만, `IframeLayout`을 페인트하려면 `paint_tree`에서 자식 프레임을 페인트해야 합니다.

```python
def paint_tree(layout_object, display_list):
    cmds = layout_object.paint()

    if isinstance(layout_object, IframeLayout) and \
        layout_object.node.frame and \
        layout_object.node.frame.loaded:
        paint_tree(layout_object.node.frame.document, cmds)
    else:
        for child in layout_object.children:
            paint_tree(child, cmds)

    cmds = layout_object.paint_effects(cmds)
    display_list.extend(cmds)
```

다만 그 명령들을 디스플레이 리스트에 넣기 전에 테두리를 추가하고, 사용 가능한 시각 영역을 넘는 iframe 내용을 잘라 내고, 좌표계를 변환해야 합니다.

```python
class IframeLayout(EmbedLayout):
    def paint_effects(self, cmds):
        # ...

        diff = dpx(1, self.zoom)
        offset = (self.x + diff, self.y + diff)
        cmds = [Transform(offset, rect, self.node, cmds)]
        inner_rect = skia.Rect.MakeLTRB(
            self.x + diff, self.y + diff,
            self.x + self.width - diff, self.y + self.height - diff)
        internal_cmds = cmds
        internal_cmds.append(Blend(1.0, "destination-in", None, [
                          DrawRRect(inner_rect, 0, "white")]))
        cmds = [Blend(1.0, "source-over", self.node, internal_cmds)]
        paint_outline(self.node, cmds, rect, self.zoom)
        cmds = paint_visual_effects(self.node, cmds, rect)
        return cmds
```

`Transform`은 자식 프레임 내용을 옮겨서 그 왼쪽 위 모서리가 올바른 자리에서 시작하게 하고,[^27] `ClipRRect`는 iframe 내용을 테두리 안쪽으로 잘라 내며, `paint_outline`은 테두리를 추가합니다. 외곽선을 유발하려면 브라우저 CSS 파일에 다음을 추가하기만 하면 됩니다.

```css
iframe { outline: 1px solid black; }
```

마지막으로 접근성 트리에도 iframe을 추가합시다. 디스플레이 리스트와 마찬가지로 접근성 트리도 모든 프레임에 걸쳐 전역입니다. iframe이 `iframe` 노드를 만들게 할 수 있습니다.

```python
class AccessibilityNode:
    def __init__(self, node):
        else:
            elif node.tag == "iframe":
                self.role = "iframe"
```

그런 노드를 `build`하려면 그 프레임으로 재귀하기만 하면 됩니다.

```python
class AccessibilityNode:
   def build_internal(self, child_node):
        if isinstance(child_node, Element) \
            and child_node.tag == "iframe" and child_node.frame \
            and child_node.frame.loaded:
            child = AccessibilityNode(child_node.frame.nodes)
        # ... 
```

이제 iframe이 화면에 나타납니다. 다음 단계는 그것과 상호작용하는 것입니다.

### 더 알아보기

iframe 이전에는 [`<frameset>`과 `<frame>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/frameset) 요소가 있었습니다. `<frameset>`은 `<body>` 태그를 대체하고 브라우저 창을 여러 `<frame>`으로 나눴습니다. 이는 이 책에서 소개한 것과는 다른 초기의 대안적 레이아웃 시스템이었습니다. 프레임은 내비게이션과 접근성이 혼란스러웠고 `<iframe>`의 유연함도 없었으므로 요즘은 별로 쓰이지 않습니다. "iframe"이라는 이름은 어떤 면에서 이 요소들을 참조하는데, "인라인 프레임(inline frame)"의 줄임말입니다.

## iframe 입력 이벤트

이제 iframe이 화면에 렌더링되니 사용자 입력으로 고리를 닫아 봅시다. iframe 안의 것을 클릭하는 지원과, 그 안에서 탭으로 이동하거나 스크롤하는 지원을 추가하려고 합니다.

큰 틀에서 이벤트 핸들러는 그저 루트 프레임에 위임합니다.

```python
class Tab:
    def click(self, x, y):
        self.render()
        self.root_frame.click(x, y)
```

iframe이 클릭되면 클릭을 자식 프레임으로 넘기고 곧바로 반환합니다. iframe이 클릭 이벤트를 잡아 두기 때문입니다. 자식 프레임으로 재귀할 때 (절대) _x_, _y_ 클릭 위치에서 iframe의 절대 _x_, _y_ 오프셋을 뺀다는 점을 눈여겨보세요.

```python
class Frame:
    def click(self, x, y):
        # ...
        while elt:
            # ...
            elif elt.tag == "iframe":
                abs_bounds = \
                    absolute_bounds_for_obj(elt.layout_object)
                border = dpx(1, elt.layout_object.zoom)
                new_x = x - abs_bounds.left() - border
                new_y = y - abs_bounds.top() - border
                elt.frame.click(new_x, new_y)
                return
```

이제 `<a>` 요소를 클릭하는 것이 동작하며, 이는 프레임이 새 페이지로 이동하게 만들 수 있다는 뜻입니다. 그리고 `Frame`이 `Tab`이 갖고 있던 모든 로딩과 내비게이션 로직을 갖고 있으므로, 더 이상 아무것도 바꾸지 않아도 그냥 동작합니다!

이제 [iframe 예제](https://browser.engineering/examples/example15-iframe.html)를 불러올 수 있을 것입니다. 그림 5에 나온 이미지처럼 보여야 합니다.

다른 상호작용들도 동작하게 만들어 봅시다. 요소에 포커스하는 것부터 시작하죠. _탭당 하나의 요소에만_ 포커스할 수 있으므로 `focus`는 여전히 `Tab`에 저장하겠지만, 포커스된 요소가 있는 iframe도 저장해야 합니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        self.focus = None
        self.focused_frame = None
```

iframe이 어떤 요소에 포커스하려 할 때는 자신을 포커스된 iframe으로 설정하는데, 그전에 이전에 포커스되었던 iframe의 포커스를 해제해야 합니다.

```python
class Frame:
    def focus_element(self, node):
        # ...
        if self.tab.focused_frame and self.tab.focused_frame != self:
            self.tab.focused_frame.set_needs_render()
        self.tab.focused_frame = self
        # ...
```

이전에 포커스되었던 iframe이 포커스 외곽선 그리기를 멈추도록 그 프레임을 다시 렌더링해야 합니다.

또 다른 상호작용은 현재 프레임의 포커스 가능한 요소들을 순환하기 위해 `Tab`을 누르는 것입니다. `advance_tab` 로직을 `Frame`으로 옮기고 `Tab`에서 그것으로 전달하기만 합시다.[^28]

```python
class Tab:
    def advance_tab(self):
        frame = self.focused_frame or self.root_frame
        frame.advance_tab()
```

텍스트 입력과 버튼 상호작용에 쓰이는 `keypress`와 `enter`에도 똑같이 하세요.

지원해야 할 또 다른 큰 상호작용은 스크롤입니다. 각 `Frame`에 스크롤 오프셋을 저장하겠습니다.

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        self.scroll = 0
```

그런데 [13장](https://browser.engineering/animations.html)에서 떠올려 보면, 반응성을 개선하기 위해 스크롤은 `Browser` 안과 `Tab` 안 양쪽에서 일어납니다. 그것만으로도 이미 꽤 복잡했으므로, 단순하게 가기 위해 루트 프레임에 대해서만 스레드화된 스크롤을 지원하겠습니다. 브라우저 스레드가 루트 프레임이 포커스되어 있는지 알 수 있도록 새 커밋 매개변수가 필요합니다.

```python
class CommitData:
    def __init__(self, url, scroll, root_frame_focused, height,
        display_list, composited_updates, accessibility_tree, focus):
        # ...
        self.root_frame_focused = root_frame_focused

class Tab:
    def run_animation_frame(self, scroll):
        root_frame_focused = not self.focused_frame or \
                self.focused_frame == self.root_frame
        # ...
        commit_data = CommitData(
            # ...
            root_frame_focused,
            # ...
        )
        # ...
```

`Browser` 스레드는 이 정보를 `commit`에서 저장해 두었다가 사용자가 스크롤을 요청할 때 사용합니다.

```python
class Browser:
    def commit(self, tab, data):
        # ...
            self.root_frame_focused = data.root_frame_focused

    def handle_down(self):
        self.lock.acquire(blocking=True)
        if self.root_frame_focused:
            # ...
        task = Task(self.active_tab.scrolldown)
        self.active_tab.task_runner.schedule_task(task)
        self.lock.release()
```

탭이 스크롤 요청을 받으면 포커스된 프레임을 스크롤합니다.

```python
class Tab:
    def scrolldown(self):
        frame = self.focused_frame or self.root_frame
        frame.scrolldown()
        self.set_needs_paint()
```

루트 프레임이 아닌 프레임이 스크롤되면 그냥 `needs_composite`를 설정해 브라우저가 처음부터 다시 래스터화하게 하겠습니다.

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        for (window_id, frame) in self.window_id_to_frame.items():
            if frame == self.root_frame: continue
            if frame.scroll_changed_in_frame:
                needs_composite = True
                frame.scroll_changed_in_frame = False
        # ...
```

스크롤에는 미묘한 점이 하나 더 있습니다. 스크롤한 뒤에는 사용자가 페이지의 마지막 항목보다 더 아래로 스크롤하는 것을 막기 위해 스크롤 위치를 _제한(clamp)_ 하고 싶습니다. 지금 `clamp_scroll`은 최대 스크롤 양을 결정하는 데 창 높이를 사용합니다. 그 함수를 `Frame` 안으로 옮겨 현재 프레임의 높이를 쓸 수 있게 합시다.

```python
class Frame:
    def scrolldown(self):
        self.scroll = self.clamp_scroll(self.scroll + SCROLL_STEP)

    def clamp_scroll(self, scroll):
        height = math.ceil(self.document.height + 2*VSTEP)
        maxscroll = height - self.frame_height
        return max(0, min(scroll, maxscroll))
```

모든 곳에서 `clamp_scroll` 메서드를 반드시 사용하세요. 예를 들어 `scroll_to`에서요.

```python
class Frame:
    def scroll_to(self, elt):
        # ...
        self.scroll = self.clamp_scroll(new_scroll)
```

지원해야 할 접근성 호버 상호작용도 여럿 있습니다. 이는 어려운데, 접근성 상호작용이 정보가 제한된 브라우저 스레드에서 일어나기 때문입니다.

- 접근성 트리는 iframe이 어디에 있는지 모르므로, 프레임 안으로 들어갈 때 호버 좌표를 어떻게 변환할지 모릅니다.

- 또한 iframe이 얼마나 큰지 모르므로, iframe 경계 밖으로 잘려 나간 것들을 무시하지 못합니다.[^29]

- 또한 프레임이 얼마나 스크롤되었는지 모르므로, 스크롤된 프레임에 맞춰 조정하지 못합니다.

이 정보를 저장하기 위해 `AccessibilityNode`의 하위 클래스를 만들겠습니다.

```python
class FrameAccessibilityNode(AccessibilityNode):
    pass
```

각 `iframe` 노드 아래에 그런 노드를 하나씩 만들겠습니다.

```python
class AccessibilityNode:
    def build_internal(self, child_node):
        if isinstance(child_node, Element) \
            and child_node.tag == "iframe" and child_node.frame \
            and child_node.frame.loaded:
            child = FrameAccessibilityNode(child_node)
```

`FrameAccessibilityNode`를 히트 테스트할 때는 프레임의 경계를 사용해 프레임 경계 밖의 클릭을 무시하고, 클릭을 프레임의 좌표에 맞춰 조정합니다(프레임의 확대된 테두리를 빼는 것을 눈여겨보세요).

```python
class FrameAccessibilityNode(AccessibilityNode):
    def __init__(self, node, parent=None):
        super().__init__(node, parent)
        self.scroll = self.node.frame.scroll
        self.zoom = self.node.layout_object.zoom

    def hit_test(self, x, y):
        bounds = self.bounds[0]
        if not bounds.contains(x, y): return
        new_x = x - bounds.left() - dpx(1, self.zoom)
        new_y = y - bounds.top() - dpx(1, self.zoom) + self.scroll
        node = self
        for child in self.children:
            res = child.hit_test(new_x, new_y)
            if res: node = res
        return node
```

이제 히트 테스팅은 동작하겠지만, 화면에 그려질 때 호버된 노드의 경계는 여전히 잘못되어 있습니다. 그것을 위해 `AccessibilityNode`의 절대 화면 사각형을 반환하는 메서드가 필요합니다. 그리고 그 메서드는 다시 접근성 트리를 거슬러 올라갈 부모 포인터가 필요하므로, 그것부터 추가합시다.

```python
class AccessibilityNode:
    def __init__(self, node, parent=None):
        # ...
        self.parent = parent

    def build_internal(self, child_node):
        if isinstance(child_node, Element) \
            and child_node.tag == "iframe" and child_node.frame \
            and child_node.frame.loaded:
            child = FrameAccessibilityNode(child_node, self)
        else:
            child = AccessibilityNode(child_node, self)
        # ...
```

이제 절대 좌표로 매핑하는 메서드를 만들 준비가 되었습니다. 이 메서드는 모든 경계 `Rect`를 순회하며 그것들을 루트까지 매핑합니다. `FrameAccessibilityNode`에는 특수 처리가 있다는 점에 주의하세요. 그 자체 경계는 그 iframe을 담고 있는 프레임의 좌표 공간에 있기 때문입니다.

```python
class AccessibilityNode:
    def absolute_bounds(self):
        abs_bounds = []
        for bound in self.bounds:
            abs_bound = bound.makeOffset(0.0, 0.0)
            if isinstance(self, FrameAccessibilityNode):
                obj = self.parent
            else:
                obj = self
            while obj:
                obj.map_to_parent(abs_bound)
                obj = obj.parent
            abs_bounds.append(abs_bound)
        return abs_bounds
```

이 메서드는 경계를 조정하기 위해 `map_to_parent`를 호출합니다. 대부분의 접근성 노드는 부모와 같은 좌표 공간에 있으므로 아무것도 할 필요가 없습니다.

```python
class AccessibilityNode:
    def map_to_parent(self, rect):
        pass
```

반면 `FrameAccessibilityNode`는 iframe의 위치와 클리핑에 맞춰 조정합니다.

```python
class FrameAccessibilityNode(AccessibilityNode):
    def map_to_parent(self, rect):
        bounds = self.bounds[0]
        rect.offset(bounds.left(), bounds.top() - self.scroll)
        rect.intersect(bounds)
```

이제 노드 위로 마우스를 올리면 우리 접근성 서브시스템이 그것을 읽어 줄 것입니다.

좋습니다. 이제 우리 브라우저의 모든 사용자 상호작용 형태가 프레임 트리를 제대로 재귀합니다. iframe에 기능을 더 추가할 때가 되었습니다.

### 더 알아보기

우리 브라우저는 브라우저 스레드에서 루트 프레임만 스크롤할 수 있지만, 실제 브라우저는 iframe을 포함해 가능한 한 많은 스크롤이 브라우저 스레드에서 일어나도록 [많은 공을 들였습니다](https://developer.chrome.com/articles/renderingng/#threaded-scrolling-animations-and-decode). 어려운 부분은 컨테이닝 블록, [쌓임 순서](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Positioning/Understanding_z_index/The_stacking_context), [스크롤 바](https://developer.mozilla.org/en-US/docs/Web/CSS/overflow), 변환, iframe의 수많은 난해한 조합을 처리하는 것입니다. 브라우저 스레드에서 스크롤하려면 이 모든 복잡한 상호작용이 메인 스레드에서 브라우저 스레드로 전달되고 양쪽에서 올바르게 해석되어야 합니다.

## iframe 스크립트

이제 사용자가 iframe과 상호작용합니다. 그런데 스크립트가 iframe과 상호작용하는 것은 어떨까요? 물론 각 프레임은 _이미_ 스크립트를 실행할 수 있습니다. 하지만 지금은 각 `Frame`이 자신만의 `JSContext`를 갖고 있어서 이 스크립트들이 서로 제대로 상호작용할 수 없습니다. 대신 _동일 출처_ iframe은 같은 JavaScript 컨텍스트에서 실행되어 서로의 전역 변수에 접근하고, 서로의 함수를 호출하고, 서로의 DOM을 수정할 수 있어야 합니다. 그림 7에 나와 있습니다. 그것을 구현해 봅시다.

![그림 7: 같은 탭 안의 여러 프레임이 하나의 JSContext를 공유할 수 있습니다.](browser-tab-frame-jscontext-2.gif)

*그림 7: 같은 탭 안의 여러 프레임이 하나의 `JSContext`를 공유할 수 있습니다.*

두 프레임의 JavaScript 환경이 상호작용하려면 그것들을 같은 `JSContext`에 두어야 합니다. 그러니 각 `Frame`이 자신만의 `JSContext`를 갖는 대신, `JSContext`를 출처를 JavaScript 컨텍스트에 대응시키는 딕셔너리로 `Tab`에 저장하겠습니다.

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.origin_to_js = {}

    def get_js(self, url):
        origin = url.origin()
        if origin not in self.origin_to_js:
            self.origin_to_js[origin] = JSContext(self, origin)
        return self.origin_to_js[origin]
```

그러면 각 `Frame`은 `Tab`에게 자신의 JavaScript 컨텍스트를 요청합니다.

```python
class Frame:
    def load(self, url, payload=None):
        # ...
        self.js = self.tab.get_js(url)
        # ...
```

이제 여러 페이지의 스크립트가 하나의 JavaScript 컨텍스트를 씁니다. 그런데 이제 그것들의 변수를 어떻게든 각자의 네임스페이스에 두어야 합니다. 열쇠는 `Window` 타입의 `window` 전역이 될 것입니다. 브라우저에서 이는 [전역 객체](https://developer.mozilla.org/en-US/docs/Glossary/Global_object)를 가리키며, `a` 같은 전역 변수를 쓰는 대신 항상 `window.a`라고 쓸 수 있습니다.[^30] 구현을 단순하게 유지하기 위해, 우리 브라우저에서 스크립트는 항상 `window`를 통해 변수와 함수를 참조해야 합니다.[^31] 런타임에서도 똑같이 해야 합니다.

```javascript
window.console = { log: function(x) { call_python("log", x); } }

// ...

window.Node = function(handle) { this.handle = handle; }

// ...
```

`runtime.js` 파일의 모든 함수와 변수에 대해 똑같이 하세요. 하나라도 놓치면 다음과 같은 오류가 납니다.

```
dukpy.JSRuntimeError: ReferenceError: identifier 'Node'
    undefined
    duk_js_var.c:1258
    eval src/pyduktape.c:1 preventsyield
```

이 오류가 보이면 `Node` 대신 `window.Node`라고 써야 할 곳을 찾아야 한다는 뜻입니다. 클래스 앞에 `window`를 붙이도록 `EVENT_DISPATCH_JS`도 수정해야 합니다.

```python
EVENT_DISPATCH_JS = \
    "new window.Node(dukpy.handle)" + \
    ".dispatchEvent(new window.Event(dukpy.type))"
```

> **참고**
>
> 이전 장들의 데모도 동작하려면 비슷하게 고쳐야 합니다. 예를 들어 `setTimeout`은 `window.setTimeout`으로 바꿔야 할 수 있습니다.

여러 프레임의 스크립트가 하나의 JavaScript 컨텍스트 안에서 잘 지내게 하기 위해, `window_1`, `window_2` 같은 여러 개의 `Window` 객체를 만들겠습니다. 어떤 프레임의 스크립트를 실행하기 전에 `window`를 그 프레임의 `Window` 객체로 설정해서, 스크립트가 올바른 `Window`를 쓰게 하겠습니다.[^32]

우선 `JSContext`를 만들 때 `Window` 클래스를 정의합시다.

```python
class JSContext:
    def __init__(self, tab, url_origin):
        self.url_origin = url_origin
        # ...
        self.interp.evaljs("function Window(id) { this._id = id };")
```

이제 프레임이 만들어져 `JSContext`를 쓰려 할 때, 먼저 `window` 객체를 만들어 달라고 요청해야 합니다.

```python
class JSContext:
    def add_window(self, frame):
        code = "var window_{} = new Window({});".format(
            frame.window_id, frame.window_id)
        self.interp.evaljs(code)

class Frame:
    def load(self, url, payload=None):
        # ...
        self.js = self.tab.get_js(url)
        self.js.add_window(self)
        # ...
```

JavaScript를 실행하기 전에 `window` 전역이 어떤 윈도를 가리키는지 바꾸고 싶습니다.

```python
class JSContext:
    def wrap(self, script, window_id):
        return "window = window_{}; {}".format(window_id, script)
```

이를 사용해, 예를 들어 각 `Frame`의 초기 런타임 환경을 설정할 수 있습니다.

```python
class JSContext:
    def add_window(self, frame):
        # ...
        self.interp.evaljs(self.wrap(RUNTIME_JS, frame.window_id))
```

`evaljs`를 쓸 때마다 `wrap`을 호출해야 하는데, 그 말은 많은 메서드에 윈도 ID 인자를 추가해야 한다는 뜻이기도 합니다. 예를 들어 `run`에는 `window_id` 매개변수를 추가하겠습니다.

```python
class JSContext:
    def run(self, script, code, window_id):
        try:
            code = self.wrap(code, window_id)
            self.interp.evaljs(code)
        except dukpy.JSRuntimeError as e:
            print("Script", script, "crashed", e)
```

그리고 `load` 메서드에서 그 인자를 넘깁니다.

```python
class Frame:
    def load(self, url, payload=None):
        for script in scripts:
            # ...
            task = Task(self.js.run, script_url, body,
                self.window_id)
            # ...
```

여러 디스패치 API도 마찬가지입니다. 예를 들어 이벤트를 디스패치하려면 `window_id`가 필요합니다.

```python
class JSContext:
    def dispatch_event(self, type, elt, window_id):
        # ...
        code = self.wrap(EVENT_DISPATCH_JS, window_id)
        do_default = self.interp.evaljs(code,
            type=type, handle=handle)
```

마찬가지로 `click`, `submit_form`, `keypress`에도 윈도 ID 인자를 넘겨야 하는데, 그 코드 조각들은 생략했습니다. `runtime.js` 파일을 수정해 `LISTENERS`를 `window` 객체에 저장하도록 했어야 한다는 점에 주의하세요. 그러면 각 `Frame`이 디스패치할 자신만의 이벤트 리스너 집합을 갖게 됩니다.

```javascript
window.LISTENERS = {}

// ...


window.Node.prototype.dispatchEvent = function(evt) {
    var type = evt.type;
    var handle = this.handle
    var list = (window.LISTENERS[handle] &&
        window.LISTENERS[handle][type]) || [];
    for (var i = 0; i < list.length; i++) {
        list[i].call(this, evt);
    }
    return evt.do_default;
}
```

`requestAnimationFrame`에도 똑같이 해서, 윈도 ID를 전달하고 코드가 `window`를 올바르게 참조하도록 감싸세요.

JavaScript에서 브라우저를 호출할 때는 JavaScript가 자신이 호출하는 윈도 ID를 넘겨야 합니다.

```javascript
window.document = { querySelectorAll: function(s) {
    var handles = call_python("querySelectorAll", s, window._id);
    return handles.map(function(h) { return new window.Node(h) });
}}
```

그러면 브라우저 쪽에서 그 윈도 ID를 사용해 `Frame` 객체를 가져올 수 있습니다.

```python
class JSContext:
    def querySelectorAll(self, selector_text, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        selector = CSSParser(selector_text).selector()
        nodes = [node for node
                 in tree_to_list(frame.nodes, [])
                 if selector.matches(node)]
        return [self.get_handle(node) for node in nodes]
```

`innerHTML`과 `style`에도 비슷한 것이 필요합니다. 해당 `Frame`에 `set_needs_render`를 호출해야 하기 때문입니다.

마지막으로, JavaScript에서 브라우저로의 호출과 나중에 브라우저에서 JavaScript로의 호출이 모두 관여하는 `setTimeout`과 `XMLHttpRequest`에서도 마찬가지로 JavaScript에서 윈도 ID를 넘기고, JavaScript로 되돌아 호출할 때 그 윈도 ID를 써야 합니다. 이 절의 코드 변경 상당수는 반복적이어서 생략했습니다. 필요한 모든 위치는 코드베이스에서 `evaljs`를 검색해 찾을 수 있습니다.

이제 서로 다른 프레임을 격리했습니다. 다음으로 그것들이 상호작용하게 해 봅시다.

### 더 알아보기

동일 출처 iframe은 서로의 상태에 접근할 수 있지만 교차 출처 iframe은 그럴 수 없습니다. 그런데 잘 알려지지 않은 [`domain`](https://developer.mozilla.org/en-US/docs/Web/API/Document/domain) 속성은 iframe이 자신의 출처를 바꿔서, 어떤 경우에는 동일 출처 상태로 들어가거나 나올 수 있게 해 줍니다. 개인적으로 저는 이것이 잘못된 기능이라고 생각합니다. 안전하게 구현하기가 어렵고 여러 샌드박싱 기법과 충돌하기 때문입니다. 언젠가 웹에서 제거되기를 바랍니다. 대신 iframe이 더 나은 보안과 성능을 얻기 위해 공유를 줄이겠다고 선택할 수 있는 [여러 헤더](https://html.spec.whatwg.org/multipage/browsers.html#origin-isolation)가 있습니다.

## 프레임 간 통신

이제 여러 `Frame`의 JavaScript를 하나의 `JSContext`에서 실행하게 만들었고, 서로의 상태를 건드리지 않도록 어느 정도 격리했습니다. 그런데 이 작업의 요점은 동일 출처 프레임 사이에 _어느 정도_ 상호작용을 허용하는 것입니다. 이제 그것을 해 봅시다.

두 프레임이 상호작용하는 가장 단순한 방법은 `Window` 객체의 `parent` 속성을 통해 서로의 상태에 접근하는 것입니다. 두 프레임의 출처가 같다면, 이를 통해 한 프레임이 다른 프레임의 메서드를 호출하고, 변수에 접근하고, 브라우저 상태를 수정할 수 있습니다. 이 동일 출처 프레임들이 `JSContext`를 공유하게 만들어 두었으므로 구현하기가 그리 어렵지 않습니다. 기본적으로 윈도 ID에서 그 부모 프레임의 윈도 ID로 가는 방법이 필요합니다.

```python
class JSContext:
    # ...
    def parent(self, window_id):
        parent_frame = \
            self.tab.window_id_to_frame[window_id].parent_frame
        if not parent_frame:
            return None
        return parent_frame.window_id
```

JavaScript 쪽에서는 이제 윈도 ID로부터 `Window` 객체를 찾아야 합니다. 방법은 여러 가지가 있지만 가장 쉬운 것은 전역 맵을 두는 것입니다.

```python
class JSContext:
    def __init__(self, tab, url_origin):
        # ...
        self.interp.evaljs("WINDOWS = {}")
```

각 윈도가 만들어질 때 전역 맵에 추가하겠습니다.

```python
class JSContext:
    def add_window(self, frame):
        # ...
        self.interp.evaljs("WINDOWS[{}] = window_{};".format(
            frame.window_id, frame.window_id))
```

이제 `window.parent`가 이 전역 맵에서 올바른 `Window` 객체를 찾을 수 있습니다.

```html
Object.defineProperty(Window.prototype, 'parent', {
  configurable: true,
  get: function() {
    var parent_id = call_python('parent', window._id);
    if (parent_id != undefined) {
        var parent = WINDOWS[parent_id];
        if (parent === undefined) parent = new Window(parent_id);
        return parent;
    }
  }
});
```

부모 프레임이 현재 프레임과 출처가 달라서 같은 `JSContext`에서 실행되고 있지 않다면 `WINDOWS` 조회가 실패할 수 있다는 점에 주의하세요. 그런 경우 이 코드는 그 ID를 가진 새 `Window` 객체를 반환합니다. 하지만 iframe은 출처를 넘어 서로의 문서에 접근하는 것이 (또는 안전하지 않은 여러 다른 API를 호출하는 것이) 허용되지 않으므로, 이 상황을 확인하고 예외를 던지는 메서드를 추가합시다.

```python
class JSContext:
    def throw_if_cross_origin(self, frame):
        if frame.url.origin() != self.url_origin:
            raise Exception(
                "Cross-origin access disallowed from script")
```

그다음 문서에 접근하는 모든 `JSContext` 메서드에서 이 메서드를 사용하세요.[^33]

```python
class JSContext:
    def querySelectorAll(self, selector_text, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...

    def setAttribute(self, handle, attr, value, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...

    def innerHTML_set(self, handle, s, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...

    def style_set(self, handle, s, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...
```

그래서 동일 출처 iframe은 `parent`를 통해 통신할 수 있습니다. 그런데 교차 출처 iframe은 어떨까요? 그것들이 서로의 변수에 접근하거나 서로의 메서드를 호출하게 하는 것은 안전하지 않으므로, 대신 브라우저는 [_메시지 전달_](https://en.wikipedia.org/wiki/Message_passing)이라는 형태를 허용합니다. 이는 공유 상태나 락 없이도 서로 다른 두 이벤트 루프 사이에 구조화된 통신을 하는 기법입니다.

JavaScript에서 메시지 전달은 이렇게 동작합니다. 대화하고 싶은 `Window` 객체에서 [`postMessage` API](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)를 호출하되, 첫 번째 매개변수로 메시지 자체를, 두 번째로 `*`를 넘깁니다.[^34]

```
window.parent.postMessage("...", '*')
```

이는 첫 번째 인자[^35]를 부모 프레임으로 보내고, 부모 프레임은 자신의 `Window` 객체에서 `message` 이벤트를 처리해 그 메시지를 받을 수 있습니다.

```
window.addEventListener("message", function(e) {
    console.log(e.data);
});
```

이 두 번째 코드 조각의 `window`는 받는 쪽 `Window`이며, 첫 번째 조각의 `window`와는 다른 `Window`라는 점에 주의하세요.

_수신자_ 쪽부터 시작해 `postMessage`를 구현해 봅시다. 이 이벤트는 `Node`가 아니라 `Window`에서 일어나므로 새 `WINDOW_LISTENERS` 배열이 필요합니다.

```javascript
window.WINDOW_LISTENERS = {}
```

각 리스너는 `MessageEvent` 객체와 함께 호출됩니다.

```javascript
window.MessageEvent = function(data) {
    this.type = "message";
    this.data = data;
}
```

이벤트 리스너와 디스패치 코드는 `Node`의 것과 같되 `Window`에 있고 `WINDOW_LISTENERS`를 사용한다는 점만 다릅니다. 그 메서드들을 그냥 복제하면 됩니다.

```javascript
Window.prototype.addEventListener = function(type, listener) {
    // ...
}

Window.prototype.dispatchEvent = function(evt) {
    // ...
}
```

수신자 쪽은 이것으로 끝입니다. 이제 송신자 쪽을 해 봅시다. 먼저 `postMessage` API 자체를 구현합시다. 여기서 `this`는 수신자, 즉 대상 윈도라는 점에 주의하세요.

```javascript
Window.prototype.postMessage = function(message, origin) {
    call_python("postMessage", this._id, message, origin)
}
```

브라우저에서 `postMessage`는 `Tab`에 작업을 예약합니다.

```python
class JSContext:
    def postMessage(self, target_window_id, message, origin):
        task = Task(self.tab.post_message,
            message, target_window_id)
        self.tab.task_runner.schedule_task(task)
```

작업을 예약하는 것은 `postMessage`가 비동기 API이기 때문에 필요합니다. 동기적으로 메시지를 보내려면 여러 `JSContext`나 심지어 여러 프로세스를 동기화해야 할 수 있는데, 그러면 오버헤드가 크고 아마 교착 상태가 생길 것입니다.

그 작업은 대상 프레임을 찾아 디스패치 메서드를 호출합니다.

```python
class Tab:
    def post_message(self, message, target_window_id):
        frame = self.window_id_to_frame[target_window_id]
        frame.js.dispatch_post_message(
            message, target_window_id)
```

그러면 그것이 방금 작성한 JavaScript `dispatchEvent` 메서드를 호출합니다.

```python
POST_MESSAGE_DISPATCH_JS = \
    "window.dispatchEvent(new window.MessageEvent(dukpy.data))"

class JSContext:
    def dispatch_post_message(self, message, window_id):
        self.interp.evaljs(
            self.wrap(POST_MESSAGE_DISPATCH_JS, window_id),
            data=message)
```

이제 `postMessage`로 프레임 간에,[^36] 서로 다른 `JSContext`에서 실행되는 교차 출처 프레임 사이에도 안전하게 메시지를 보낼 수 있을 것입니다.

### 더 알아보기

광고는 흔히 iframe으로 제공되며 웹의 샌드박싱, 임베딩, 애니메이션 기본 요소를 많이 사용합니다. 즉 광고는 성능과 [사용자 경험](https://en.wikipedia.org/wiki/User_experience) 문제의 만만치 않은 원천입니다. 예를 들어 광고 [분석](https://en.wikipedia.org/wiki/Web_analytics)은 광고 경제에 중요하지만, 많은 코드를 실행하고 많은 데이터를 측정해야 합니다. [Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API) 같은 일부 웹 API는 기본적으로 분석 계산을 더 효율적으로 만들기 위해 존재합니다. 그리고 물론 광고 차단기는 아마 가장 인기 있는 [브라우저 확장 프로그램](https://en.wikipedia.org/wiki/Browser_extension)일 것입니다.

## 격리와 타이밍

iframe은 [10장](https://browser.engineering/security.html)에서 이야기한 것 위에 완전히 새로운 층의 보안 과제를 더합니다. 한 웹 페이지를 다른 웹 페이지에 내장하는 능력은 두 페이지가 서로를 신뢰하지 않을 때 그에 상응하는 보안 위험을 만듭니다. 신뢰할 수 없는 페이지를 여러분의 페이지에 내장하는 경우와, 반대로 공격자가 여러분의 페이지를 자신의 악의적인 페이지에 내장하는 경우 모두에서요. 두 경우 모두 우리는 다른 프레임이 유발하는 보안·프라이버시 위험으로부터 여러분의 페이지를 보호하고 싶습니다.[^37]

출발점은 교차 출처 iframe이 JavaScript를 통해 서로에게 직접 접근할 수 없다는 것입니다. 좋습니다. 그런데 [버퍼 오버런](https://en.wikipedia.org/wiki/Buffer_overflow) 같은 JavaScript 엔진의 버그 때문에 iframe이 그 보호를 우회할 수 있다면 어떨까요? 안타깝게도 이런 버그는 충분히 흔해서 브라우저는 그것을 방어해야 합니다. 예를 들어 요즘 브라우저는 서로 다른 출처의 프레임을 [서로 다른 운영체제 프로세스](https://www.chromium.org/Home/chromium-security/site-isolation/)에서 실행하고, 운영체제 기능을 사용해 그 프로세스가 가진 접근 권한을 제한합니다.

우리 브라우저의 `Tab` 전체 디스플레이 리스트처럼 브라우저의 다른 부분들은 여러 프레임의 콘텐츠를 섞습니다. 즉 래스터화기의 버그가 한 프레임이 래스터화기를 장악해 궁극적으로 다른 프레임에서 온 데이터를 읽게 만들 수 있습니다. 꽤 복잡한 공격처럼 보이겠지만 전에도 일어난 적이 있어서, 현대 브라우저는 [샌드박싱](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/sandboxing.md) 기법으로 이를 막습니다. 예를 들어 Chromium은 래스터화기를 자신만의 프로세스에 두고, `seccomp`라는 Linux 기능으로 그 프로세스가 할 수 있는 시스템 호출을 제한할 수 있습니다. 버그가 래스터화기를 장악하더라도 그 래스터화기는 네트워크로 데이터를 빼낼 수 없어서 비공개 데이터 유출을 막습니다.

이런 격리와 샌드박싱 기능은 [12장](https://browser.engineering/scheduling.html)에서 추가한 브라우저 스레드가 "단순명료"한 것과 같은 의미에서 "단순명료"해 보일 수 있습니다. 실제로는 브라우저 API가 워낙 많아서 구현이 미묘한 문제로 가득하고 결국 극도로 복잡해집니다. 예를 들어 Chromium은 [_사이트 격리_](https://www.chromium.org/Home/chromium-security/site-isolation/)의 첫 구현을 출시하는 데 여러 해가 걸렸습니다.

사이트 격리는 [_스펙터_ 와 _멜트다운_](https://meltdownattack.com/)이라 불리는 CPU 캐시 타이밍 공격 때문에 최근 몇 년 사이 훨씬 더 중요해졌습니다. 요약하면 이 공격들은 특정 CPU 연산에 걸리는 시간을 측정함으로써 공격자가 메모리의 임의 위치를, 두 프레임이 같은 프로세스에 있다면 다른 프레임의 데이터까지 읽을 수 있게 해 줍니다. 민감한 콘텐츠를 (각자의 메모리 주소 공간을 갖는) 서로 다른 CPU 프로세스에 두는 것은 이런 공격에 대한 좋은 방어입니다.

그렇긴 해도 이런 종류의 _타이밍 공격_ 은 미묘할 수 있고, 아직 발견되지 않은 것들이 분명히 더 있습니다. 이 위협을 무디게 하기 위해 브라우저는 현재 타이밍 공격에 보통 필요한 정확한 타이밍 데이터를 제공할 수 있는 _고정밀 타이머_ 에 대한 접근을 막고 있습니다. 예를 들어 브라우저는 `Date.now`나 `setTimeout` 같은 API의 정확도를 낮춥니다.

더 나쁜 것은, 타이머처럼 보이지 않지만 타이머로 쓸 수 있는 브라우저 API가 있다는 점입니다.[^38] 이런 API는 유용하므로 브라우저가 그것을 없애고 싶어 하지는 않지만, 애초에 시계가 아니므로 "정확도를 낮출" 방법도 없습니다. 브라우저는 이제 특히 `SharedArrayBuffer` 사용을 허용하기 위해 부모 _와_ 자식 프레임의 HTTP 응답 양쪽에 [특정 선택적 HTTP 헤더](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer#security_requirements)가 있어야 한다고 요구하지만, 이것도 완벽한 해결책은 아닙니다.

### 더 알아보기

`SharedArrayBuffer` 문제는 제가 [이 책의 웹사이트](https://browser.engineering)에 내장된 브라우저 위젯에 [JavaScript 지원을 추가할](https://browserbook.substack.com/p/javascript-in-javascript) 때 문제를 일으켰습니다. 저는 `JSContext`에서 브라우저로 동기 호출을 허용하기 위해 `SharedArrayBuffer`를 쓰고 있었는데, 그러려면 브라우저가 보안상의 이유로 제한하는 API가 필요했습니다. 보안 헤더를 설정하는 것으로는 해결되지 않았는데, 14장이 YouTube 비디오를 내장하고 있고 제가 이 글을 쓰는 시점에 YouTube는 그 헤더를 보내지 않기 때문입니다. 결국 저는 브라우저 위젯을 내장하지 않고 [독자에게 요청하여](http://browser.engineering/scripts.html#outline) 새 브라우저 창을 열게 하는 방식으로 이 문제를 우회했습니다.

## 요약

이 장에서는 브라우저가 이미지와 iframe 같은 임베디드 콘텐츠 사용 사례를 어떻게 다루는지 소개했습니다. 핵심을 다시 정리하면 다음과 같습니다.

- HTML이 아닌 _임베디드 콘텐츠_(이미지, 비디오, 캔버스, iframe, 입력 요소, 플러그인)를 웹 페이지에 내장할 수 있습니다.

- 임베디드 콘텐츠에는 이미지 디코딩 시간 같은 고유한 성능 문제가 따라오며, 맞춤 최적화가 필요합니다.

- iframe은 특히 중요한 종류의 임베디드 콘텐츠로, 시간이 지나면서 복잡한 콘텐츠를 웹 페이지에 쉽게 내장하는 표준 방법으로서 브라우저 플러그인을 대체했습니다.

- iframe은 렌더링, 이벤트 처리, 내비게이션, 보안 등 웹의 모든 복잡함을 브라우저의 임베디드 콘텐츠 처리에 끌어들입니다. 다만 이 복잡함은 정당한데, 광고, 비디오, 소셜 미디어 버튼 같은 중요한 교차 출처 사용 사례를 가능하게 하기 때문입니다.

그리고 이 장에서 보셨기를 바라지만, 이 기능들 중 어느 것도 구현하기가 그리 어렵지는 않습니다. 다만 연습문제에서 보게 되겠지만, 그것들을 _잘_ 구현하려면 세부 사항에 많은 주의를 기울여야 합니다.

이 장의 브라우저를 시험해 보려면 [여기](https://browser.engineering/widgets/lab15-browser.html)를 클릭하세요.

## 연습문제

**15-1 _canvas 요소_.** [`<canvas>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/canvas) 요소, [`getContext`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/getContext) API의 2D 부분, [`CanvasRenderingContext2D`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D)의 일부 그리기 명령을 구현하세요. 캔버스 레이아웃은 기본 너비와 높이를 포함해 iframe과 똑같습니다. `getContext("2d")`가 호출되면 적절한 크기의 Skia 서피스를 할당하고 캔버스에 그리는 API 일부를 구현해야 합니다.[^39] 대부분의 API 메서드를 Skia의 대응물로 옮기는 것은 어렵지 않을 것입니다.

**15-2 _배경 이미지_.** 요소는 [`background-image`](https://developer.mozilla.org/en-US/docs/Web/CSS/background-image)를 가질 수 있습니다. 이 CSS 속성의 기본, 즉 `background-image` 속성에 대한 `url(...)` 값을 구현하세요. `background-image` 속성이 실제로 어떤 요소에서도 사용되지 않는다면 이미지를 로드하지 않도록 하세요. 더 큰 도전으로, 웹 페이지가 [`background-size`](https://developer.mozilla.org/en-US/docs/Web/CSS/background-size) CSS 속성으로 배경 이미지의 크기를 설정할 수 있게도 해 보세요.

**15-3 _`object-fit`_.** [`object-fit`](https://developer.mozilla.org/en-US/docs/Web/CSS/object-fit) CSS 속성을 구현하세요. 이 속성은 `<img>` 요소 안의 이미지가 컨테이너 요소에 대해 어떻게 크기가 조절될지 결정합니다. 종횡비가 다른 이미지를 잘라 내야 합니다.

**15-4 _지연 로딩_.** 이미지를 내려받는 데는 꽤 많은 데이터가 쓰일 수 있습니다.[^40] 브라우저는 기본적으로 페이지의 모든 이미지를 즉시 내려받지만, `img` 요소의 [`loading` 속성](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/img#loading)은 이미지가 페이지의 보이는 영역에 가까울 때만 내려받도록 브라우저에 지시할 수 있습니다. 이런 종류의 최적화를 일반적으로 [지연 로딩](https://developer.mozilla.org/en-US/docs/Web/Performance/Lazy_loading)이라고 합니다. `loading`을 구현하세요. 이미지 로딩이 끝나기 전과 후 모두 페이지가 올바르게 배치되도록 하세요.

**15-5 _iframe 종횡비_.** [`aspect-ratio`](https://developer.mozilla.org/en-US/docs/Web/CSS/aspect-ratio) CSS 속성을 구현하고, 그것을 사용해 `width`나 `height` 중 하나만 지정되었을 때(또는 연습문제 15-4를 했다면 이미지가 아직 로드되지 않았을 때) iframe과 이미지에 암묵적 크기를 제공하세요.

**15-6 _이미지 자리 표시자_.** 지연 로딩 위에 아직 로드되지 않은 이미지의 자리 표시자 스타일을 구현하세요. 이는 `width`나 `height`가 지정되지 않은 한 0×0 크기를 설정함으로써 이루어집니다. `alt` 속성이 없거나 비어 있으면 "깨진 이미지"를 숨기는 지원도 추가하세요.[^41]

**15-7 _미디어 쿼리_.** [`width`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/width) 미디어 쿼리를 구현하세요. iframe 안에서도 동작하는지 확인하세요. 부모 프레임이 iframe의 너비를 바꿨을 때도 동작하는지 확인하세요.

**15-8 _`postMessage`의 대상 출처_.** [`postMessage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)의 `targetOrigin` 매개변수를 구현하세요. 이 매개변수는 메시지를 받을 수 있는 프레임 출처를 나타내는 문자열입니다.

**15-9 _다중 프레임 포커스_.** 우리 브라우저에서 `Tab`을 누르면 포커스된 프레임의 요소들을 순환합니다. 하지만 그 말은 키보드만으로는 다른 프레임의 포커스 가능한 요소에 접근할 수 없다는 뜻입니다. 한 프레임의 포커스 가능한 요소를 모두 순회한 뒤 프레임 사이를 이동하도록 고치세요.

**15-10 _iframe 방문 기록_.** iframe이 브라우저 방문 기록에 영향을 주도록 하세요. 예를 들어 iframe 안의 링크를 클릭한 다음 뒤로 가기 버튼을 누르면 그 iframe 안에서 뒤로 가야 합니다. 사용자가 여러 프레임의 링크를 여러 순서로 클릭해도 동작하도록 하세요.[^42]

**15-11 _스크립트가 추가하거나 제거한 iframe_.** `innerHTML` API는 iframe을 추가하거나 제거할 수 있지만, 우리 브라우저는 그런 일이 일어나도 그것을 로드하거나 언로드하지 않습니다. 이를 고치세요. 새 iframe은 로드되고 옛 것은 언로드되어야 합니다.

**15-12 _`X-Frame-Options`_.** 웹 페이지가 iframe 안에 나타나는 것을 금지하는 [이 헤더](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Frame-Options)를 구현하세요.

[^11]: 이미지는 _텍스트_ 와 꼭 같지는 않습니다. 텍스트 노드는 여러 줄에 걸쳐 나뉠 수 있는 연속된 텍스트 전체일 수 있는 반면, 이미지는 [원자적 인라인](https://drafts.csswg.org/css-display-3/#atomic-inline)이기 때문입니다. 이 장의 다른 임베디드 콘텐츠 타입들도 원자적 인라인입니다.

[^12]: 실제 브라우저에서 입력 요소는 보통 _위젯_ 이라고 불리는데, 때때로 CSS가 관여하는 [특별한 렌더링 규칙](https://html.spec.whatwg.org/multipage/rendering.html#widgets)이 많기 때문입니다.

[^13]: 실제로 이미지 하나만 있고 텍스트나 CSS가 전혀 없는 페이지도 폰트, 즉 기본 폰트의 영향을 레이아웃에서 받습니다. 이는 웹 개발자들이 흔히 혼란스러워하는 지점입니다. 실제 브라우저에서는 `display` CSS 속성으로 이미지를 블록이나 다른 레이아웃 모드로 강제해 이를 피할 수 있습니다.

[^14]: 그렇습니다, 실제 브라우저도 이렇게 합니다.

[^15]: 비디오에서는 "코덱"이라고 부르지만 이미지에서는 "형식"이라고 부릅니다. 참 알 수 없죠.

[^16]: 이 절의 기능을 도입하기 전에도 확대 때문에 이미지가 원래 크기와 다른 크기로 렌더링될 수 있다는 점에 주의하세요.

[^17]: 예를 들어 연습문제 6-2에서 만난 `width`와 `height` CSS 속성이 있습니다(`width`와 `height` 속성(attribute)과 혼동하지 마세요!).

[^18]: 이미지가 이런 속성을 가진 것은 대체로 역사적인 이유입니다. CSS가 존재하기 전에 만들어졌기 때문입니다.

[^19]: 구현하기 쉬운데도 실제 웹 브라우저의 이 기능은 2021년에야 모든 브라우저에 도달했습니다. 그전까지 개발자들은 [`padding-top` 꼼수](https://web.dev/aspect-ratio/#the-old-hack-maintaining-aspect-ratio-with-padding-top) 같은 것에 의존했습니다. 때로는 설계상의 누락을 고치는 데 오랜 시간이 걸립니다.

[^20]: [`<canvas>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/canvas) 요소 같은 변형들도 마찬가지입니다. 네트워크에서 이미지를 로드하는 대신, JavaScript가 API를 통해 `<canvas>` 요소에 그릴 수 있습니다. 이미지와 달리 `<canvas>` 요소에는 고유 크기가 없지만, 그 점만 빼면 레이아웃 면에서 꽤 비슷합니다.

[^21]: 사실 웹 페이지가 입력 요소의 모습을 맞춤 설정할 수 있게 하려는 [진행 중인 작업](https://open-ui.org/)이 있으며, 이는 [커스텀 요소](https://developer.mozilla.org/en-US/docs/Web/Web_Components)와 [폼](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/attachInternals)을 지원하는 이전 작업 위에 쌓여 있습니다. 이 문제는 플랫폼 독립성, 접근성, 스크립팅, 스타일 지정과 얽혀 있어 꽤 어렵습니다.

[^22]: 또는 PDF 같은 경우를 위해 `embed`와 `object` 태그를 통해서도요. 여기서는 그것들을 다루지 않겠습니다.

[^23]: 예를 들어 iframe이 그것을 내장한 웹 페이지와 출처가 같다면, iframe 안의 스크립트는 부모 DOM에 동기적으로 접근할 수 있습니다. 즉 그 iframe을 다른 스레드나 CPU 프로세스에 두는 것이 기본적으로 불가능해지고, 실제로 같은 렌더링 이벤트 루프에 놓이게 됩니다.

[^24]: 예를 들어 지난 10년 사이 `<canvas>` 요소는 하드웨어 가속 3D 콘텐츠 지원을 얻었고, [WebAssembly](https://en.wikipedia.org/wiki/WebAssembly)는 네이티브에 가까운 속도로 실행될 수 있습니다.

[^25]: 왜 렌더링 파이프라인을 이렇게 나눌까요? 접근성 트리와 디스플레이 리스트는 궁극적으로 메인 스레드에서 브라우저 스레드로 전달되어 어차피 하나로 합쳐지기 때문입니다. 반면 DOM, 스타일, 레이아웃 트리는 스레드 사이를 오가지 않으므로 뒤섞이지 않습니다.

[^26]: 과거에 iframe에 고유 크기를 부여하려는 시도가 있었지만, 어떤 브라우저도 구현하지 않아 HTML 명세에서 [제거되었습니다](https://github.com/whatwg/html/issues/331). 부모 프레임과 레이아웃이 조율되는 "매끄러운(seamless)" iframe에 대한 좋은 사용 사례가 있으므로 [앞으로](https://github.com/w3c/csswg-drafts/issues/1771) 바뀔 수도 있습니다.

[^27]: 이 책은 [CSS 박스 모델](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Box_Model/Introduction_to_the_CSS_box_model)의 세부 사항을 다루지 않지만, iframe의 `width`와 `height` 속성은 _콘텐츠 박스_ 를 가리키며 테두리 너비를 더하면 _테두리 박스_ 가 됩니다. 그 결과 우리가 구현한 것은 다소 부정확합니다.

[^28]: 여러 프레임이 관여할 때 이는 특별히 사용자 친화적인 탭 순환 구현은 아닙니다. 더 나은 버전은 연습문제 15-9를 보세요.

[^29]: 프레임 기반 `click`은 이미 올바르게 동작한다는 점을 눈여겨보세요. 클릭이 `iframe` 요소의 경계와 교차하지 않으면 iframe으로 재귀하지 않기 때문입니다. 그리고 iframe이 있기 전에는 그럴 필요가 없었는데, SDL 창 시스템이 이미 그것을 해 주었기 때문입니다.

[^30]: JavaScript API로 여러 전역 네임스페이스를 노출하려는 [여러 제안](https://github.com/tc39/proposal-shadowrealm)이 있습니다. 이 장에서 그런 기능이 있다면 확실히 편했을 텐데요. 모든 곳에 `window`를 쓰지 않아도 되니까요!

[^31]: 이는 스크립트의 모든 전역 변수도, 브라우저 API가 아니더라도, 똑같이 해야 한다는 뜻입니다.

[^32]: 어떤 JavaScript 엔진은 전역 객체를 바꾸는 API를 지원하지만, 우리가 쓰는 DukPy 라이브러리는 그렇지 않습니다. `with`라는 표준 JavaScript 연산자가 어느 정도 그런 일을 하기는 _하지만_, 규칙이 복잡하고 여기서 우리가 원하는 것과 딱 맞지도 않습니다. 요즘은 권장되지도 않습니다.

[^33]: 실제 브라우저에서 이는 보안으로는 한참 부족하다는 점에 주의하세요. 실제 브라우저는 `runtime.js` 코드 전체를 아주 신중하게 잠그고 모든 JavaScript API를 촘촘히 감사해야 할 것입니다.

[^34]: 두 번째 매개변수는 출처 제한과 관련이 있습니다. 연습문제 15-8을 보세요.

[^35]: 실제 브라우저에서는 숫자나 객체처럼 문자열이 아닌 데이터도 넘길 수 있습니다. 이는 [구조화된 복제(structured cloning)](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm)라는 _직렬화_ 알고리즘을 통해 동작하는데, 이는 (DOM 노드 같은 것은 제외하고) 대부분의 JavaScript 객체를 바이트 열로 변환해 수신 프레임이 그것을 다시 JavaScript 객체로 되돌릴 수 있게 해 줍니다. DukPy는 객체에 대해 구조화된 복제를 기본 지원하지 않으므로 우리 브라우저도 이를 지원하지 않습니다.

(이 특정 예제는 동일 출처 `postMessage`를 사용합니다. 서로 다른 포트에서 로컬 HTTP 서버 두 개를 띄우고 `example15-img.html` iframe 문서의 URL을 두 번째 포트를 가리키도록 바꾸면 교차 출처를 로컬에서 테스트할 수 있습니다.)

[^37]: 웹사이트는 `X-Frame-Options` 헤더로 자신이 iframe에 담기는 것을 막을 수 있습니다.

[^38]: 예를 들어 [SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer) API는 두 JavaScript 스레드가 동시에 실행되며 메모리를 공유할 수 있게 해 주는데, 이는 [시계를 만드는](https://security.stackexchange.com/questions/177033/how-can-sharedarraybuffer-be-used-for-timing-attacks) 데 쓰일 수 있습니다.

[^41]: `alt` 텍스트가 제공되었다면 브라우저는 그 이미지가 웹사이트의 의미에 중요하다고 가정할 수 있고, 따라서 로드에 실패하면 사용자가 콘텐츠 일부를 놓치고 있다고 알려 주어야 하기 때문입니다. 하지만 그렇지 않다면 깨진 이미지 아이콘은 아마 보기 흉한 잡동사니일 뿐입니다.
