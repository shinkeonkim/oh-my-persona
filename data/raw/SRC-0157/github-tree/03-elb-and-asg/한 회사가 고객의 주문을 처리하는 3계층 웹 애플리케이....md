## Question

한 회사가 고객의 주문을 처리하는 3계층 웹 애플리케이션을 운영하고 있습니다. 웹 계층은 Application Load Balancer 뒤에 있는 Amazon EC2 인스턴스들로 구성되어 있습니다. 처리 계층은 EC2 인스턴스들로 구성되어 있습니다. 회사는 Amazon Simple Queue Service(Amazon SQS)를 사용하여 웹 계층과 처리 계층을 분리했습니다. 스토리지 계층은 Amazon DynamoDB를 사용합니다. 피크 시간대에 일부 사용자들이 주문 처리 지연 및 중단을 보고하고 있습니다. 회사는 이러한 지연 시간 동안 EC2 인스턴스들이 CPU 사용률 100%로 실행되고 있으며, SQS 대기열이 가득 차는 것을 확인했습니다. 피크 시간대는 가변적이고 예측할 수 없습니다. 회사는 애플리케이션의 성능을 개선해야 합니다.
어떤 솔루션이 이러한 요구 사항을 충족할까요?

- [ ] A. Amazon EC2 Auto Scaling에 예약된 스케일링을 사용하여 피크 사용 시간 동안 처리 계층 인스턴스를 스케일 아웃합니다. CPU 사용률 메트릭을 사용하여 스케일링 시기를 결정합니다.
- [ ] B. DynamoDB 백엔드 티어 앞에 Amazon ElastiCache for Redis를 사용합니다. 타겟 활용도를 메트릭으로 사용하여 확장 시기를 결정합니다.
- [ ] C. Amazon CloudFront 배포를 추가하여 웹 계층에 대한 응답을 캐시합니다. HTTP 대기 시간을 메트릭으로 사용하여 확장 시기를 결정합니다.
- [ ] D. Amazon EC2 Auto Scaling 대상 추적 정책을 사용하여 처리 계층 인스턴스를 확장합니다. ApproximateNumberOfMessages 속성을 사용하여 확장 시기를 결정합니다.

## Answer

정답: D

## Explanation

EC2 Auto Scaling의 대상 추적 정책(Target Tracking Policy)을 사용하고 SQS의 ApproximateNumberOfMessages 지표를 기반으로 확장하면, 큐에 쌓인 처리 대기 메시지 수에 비례하여 처리 계층 인스턴스를 자동으로 확장합니다. 이 방식은 실제 처리 부하를 직접 반영하므로 가장 정확한 확장 시점을 결정합니다.

오답 분석

A: 예약된 스케일링(Scheduled Scaling)은 트래픽 패턴이 일정한 경우에 유용하지만, 예측 불가능한 트래픽 급증에는 대응이 늦어 SQS 큐에 메시지가 계속 쌓일 수 있습니다.

B: ElastiCache for Redis는 읽기 성능 캐싱에 유용하지만, SQS 큐에 쌓이는 메시지 처리 지연과 처리 계층의 CPU 100% 문제를 직접 해결하지 못합니다.

C: Amazon CloudFront는 정적/동적 콘텐츠의 엣지 캐싱에 유용하지만, 백엔드 처리 계층의 주문 처리 과부하 문제를 해결하는 솔루션이 아닙니다.
