## Question

회사의 HTTP 애플리케이션은 NLB(Network Load Balancer) 뒤에 있습니다. NLB의 대상 그룹은 웹 서비스를 실행하는 여러 EC2 인스턴스와 함께 Amazon EC2 Auto Scaling 그룹을 사용하도록 구성됩니다.
회사는 NLB가 애플리케이션에 대한 HTTP 오류를 감지하지 못한다는 것을 알게 됩니다. 이러한 오류는 웹 서비스를 실행하는 EC2 인스턴스를 수동으로 다시 시작해야 합니다. 회사는 사용자 지정 스크립트나 코드를 작성하지 않고 애플리케이션의 가용성을 개선해야 합니다.
솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 합니까?

- [ ] A. 회사 애플리케이션의 URL을 제공하여 NLB에서 HTTP 상태 확인을 활성화합니다.
- [ ] B. EC2 인스턴스에 cron 작업을 추가하여 1분에 한 번씩 로컬 애플리케이션의 로그를 확인합니다. HTTP 오류가 감지된 경우 애플리케이션이 다시 시작됩니다.
- [ ] C. NLB를 Application Load Balancer로 교체합니다. 회사 애플리케이션의 URL을 제공하여 HTTP 상태 확인을 활성화합니다. 비정상 인스턴스를 교체하도록 Auto Scaling 작업을 구성합니다.
- [ ] D. NLB에 대한 UnhealthyHostCount 지표를 모니터링하는 Amazon CloudWatch 경보를 생성합니다. 경보가 ALARM 상태일 때 비정상 인스턴스를 교체하도록 Auto Scaling 작업을 구성합니다.

## Answer

정답: C

## Explanation

NLB를 ALB(Application Load Balancer)로 교체하면 HTTP 수준(OSI 7계층)의 정밀한 상태 확인과 콘텐츠 기반 라우팅이 가능해집니다. ALB는 HTTP GET 요청을 대상에 보내고 응답 상태 코드(200 등)를 확인하여 애플리케이션 수준의 건강 상태를 정확히 판단합니다. 또한 응답 본문의 특정 문자열 매칭(matcher), 경로 기반 라우팅, 호스트 기반 라우팅 등 7계층의 지능적인 트래픽 관리가 가능합니다. 핵심적으로, Auto Scaling 그룹의 상태 확인 유형을 ELB로 설정하면, ALB가 비정상으로 판단한 인스턴스를 Auto Scaling이 자동으로 종료하고 새 인스턴스로 교체합니다. 이로써 커스텀 스크립트 없이 HTTP 오류 감지와 인스턴스 교체가 모두 자동화됩니다. HTTP 애플리케이션에는 ALB가 NLB보다 더 적합한 로드 밸런서입니다.

오답 분석

A: NLB도 HTTP/HTTPS 상태 확인을 구성할 수 있지만(기본 프로토콜은 TCP), 이 보기의 근본적인 문제는 Auto Scaling 작업이 구성되어 있지 않다는 점입니다. NLB가 비정상 인스턴스를 감지하더라도 Auto Scaling 그룹이 ELB 상태 확인을 기반으로 비정상 인스턴스를 자동으로 교체하도록 구성되지 않으면, 여전히 수동 재시작이 필요합니다. 또한 HTTP 애플리케이션에는 ALB의 7계층 기능(경로 기반 라우팅, 호스트 기반 라우팅, HTTP 헤더 검사 등)이 더 적합합니다.

B: cron 작업을 EC2 인스턴스에 추가하여 로그를 확인하고 애플리케이션을 재시작하는 것은 사용자 지정 스크립트를 작성하는 것입니다. 문제에서 '사용자 지정 스크립트나 코드를 작성하지 않아야 한다(without writing custom scripts or code)'는 요구사항이 명시적으로 존재하므로, 이 접근 방식은 직접적으로 위배됩니다.

D: CloudWatch 경보로 NLB의 UnhealthyHostCount 메트릭을 모니터링하는 접근 방식은, NLB의 상태 확인 결과에 의존합니다. NLB의 기본 상태 확인이 TCP인 경우, TCP 포트가 열려 있기만 하면 정상으로 판단하므로 HTTP 수준 오류(5xx 에러 등)를 감지하지 못합니다. 근본적으로 HTTP 오류 감지 문제가 해결되지 않은 상태에서 경보를 설정하는 것은 효과가 없습니다.
