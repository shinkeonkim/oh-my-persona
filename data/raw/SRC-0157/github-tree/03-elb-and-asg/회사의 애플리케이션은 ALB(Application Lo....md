## Question

회사의 애플리케이션은 ALB(Application Load Balancer) 뒤의 Amazon EC2 인스턴스에서 실행됩니다. 인스턴스는 여러 가용 영역에 걸쳐 Amazon EC2 Auto Scaling 그룹에서 실행됩니다. 매월 1일 자정에 월말 재무 계산 일괄 처리가 실행되면 애플리케이션이 훨씬 느려집니다. 이로 인해 EC2 인스턴스의 CPU 사용률이 즉시 100%에 도달하여 애플리케이션이 중단됩니다.
애플리케이션이 워크로드를 처리하고 다운타임을 방지할 수 있도록 하기 위해 솔루션 설계자는 무엇을 권장해야 합니까?

- [ ] A. ALB 앞에 Amazon CloudFront 배포를 구성합니다.
- [ ] B. CPU 사용률을 기반으로 EC2 Auto Scaling 단순 조정 정책을 구성합니다.
- [ ] C. 월별 일정을 기반으로 EC2 Auto Scaling 예약 조정 정책을 구성합니다.
- [ ] D. EC2 인스턴스에서 일부 워크로드를 제거하도록 Amazon ElastiCache를 구성합니다.

## Answer

정답: C

## Explanation

매월 1일 자정에 정기적으로 발생하는 예측 가능한 트래픽 급증에 대해, 예약된 조정(Scheduled Scaling)을 사용하면 해당 시간 전에 미리 인스턴스를 원하는 수만큼 확장하여 충분한 용량을 사전 확보할 수 있습니다. 월별 일정(cron 표현식)으로 매월 1일 자정 이전에 용량을 늘리고, 배치 처리 완료 후 축소하는 일정을 설정할 수 있습니다. 이렇게 하면 CPU 100% 도달 및 애플리케이션 중단을 예방할 수 있습니다.

오답 분석

A: Amazon CloudFront는 정적/동적 웹 콘텐츠를 엣지 로케이션에서 캐싱하여 전송 속도를 높이는 CDN입니다. 월말 재무 계산과 같은 백엔드 배치 처리의 CPU 부하를 줄이는 데는 효과적이지 않으며, 서버 측 계산 집약적 워크로드에 CDN은 무의미합니다.

B: 단순 조정 정책(Simple Scaling)은 CloudWatch 경보가 트리거된 후에 반응적으로 인스턴스를 추가합니다. 문제에서 CPU 사용률이 즉시 100%에 도달한다고 했으므로, 인스턴스 추가가 시작되기도 전에 이미 애플리케이션이 중단됩니다. 사전 확장이 필요합니다.

D: Amazon ElastiCache는 인메모리 캐싱 서비스(Redis, Memcached)로, 데이터베이스 읽기 쿼리 결과를 캐싱하여 DB 부하를 줄이는 데 유용합니다. 그러나 월말 재무 계산 배치 처리는 CPU 집약적 연산이므로, 캐싱으로는 CPU 부하를 직접 줄일 수 없습니다.
