## Question

회사는 Application Load Balancer 뒤의 Amazon EC2 인스턴스에서 중요한 비즈니스 애플리케이션을 실행하고 있습니다. EC2 인스턴스는 Auto Scaling 그룹에서 실행되며 Amazon RDS DB 인스턴스에 액세스합니다.
EC2 인스턴스와 DB 인스턴스가 모두 단일 가용 영역에 있기 때문에 설계가 운영 검토를 통과하지 못했습니다. 솔루션 설계자는 두 번째 가용 영역을 사용하도록 설계를 업데이트해야 합니다.
애플리케이션의 가용성을 높이는 솔루션은 무엇입니까?

- [ ] A. 각 가용 영역에서 서브넷을 프로비저닝합니다. 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성합니다. 각 네트워크에 대한 연결로 DB 인스턴스를 구성합니다.
- [ ] B. 두 가용 영역에 걸쳐 확장되는 두 개의 서브넷을 프로비저닝합니다. 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성합니다. 각 네트워크에 대한 연결로 DB 인스턴스를 구성합니다.
- [ ] C. 각 가용 영역에서 서브넷을 프로비저닝합니다. 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성합니다. 다중 AZ 배포를 위해 DB 인스턴스를 구성합니다.
- [ ] D. 두 가용 영역에 걸쳐 확장되는 서브넷을 프로비저닝합니다. 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성합니다. 다중 AZ 배포를 위해 DB 인스턴스를 구성합니다.

## Answer

정답: C

## Explanation

AWS에서 서브넷은 반드시 단일 가용 영역(AZ)에 속하는 네트워크 세그먼트이므로, 각 AZ에 별도의 서브넷을 프로비저닝해야 합니다. Auto Scaling 그룹을 두 AZ에 걸쳐 EC2 인스턴스를 배포하도록 구성하면, 한 AZ 장애 시 다른 AZ의 인스턴스가 ALB를 통해 서비스를 계속 제공합니다. RDS DB 인스턴스를 Multi-AZ로 구성하면, AWS가 자동으로 다른 AZ에 동기식 대기(Synchronous Standby) 복제본을 생성하고, 주(Primary) DB에 장애 발생 시 60~120초 내에 대기 DB로 자동 장애 조치(failover)가 수행됩니다. Multi-AZ RDS는 DNS 엔드포인트가 자동으로 대기 인스턴스로 전환되므로 애플리케이션 코드 변경이 필요 없습니다.

오답 분석

A: 각 AZ에 서브넷을 프로비저닝하고 Auto Scaling 그룹을 구성하는 부분은 올바르지만, DB 인스턴스를 '각 네트워크에 대한 연결'로 구성하는 것은 RDS Multi-AZ 배포가 아닙니다. RDS Multi-AZ는 자동 장애 조치, 동기식 복제, DNS 자동 전환을 내장 제공하지만, 수동 연결 구성으로는 이러한 자동화된 고가용성 기능을 구현할 수 없습니다.

B: AWS에서 서브넷은 두 가용 영역에 걸쳐 확장(span)될 수 없습니다. VPC의 서브넷은 항상 정확히 하나의 AZ에 속하는 CIDR 블록으로, 이는 AWS 네트워킹의 기본 설계 원칙입니다. 두 AZ를 사용하려면 반드시 각 AZ에 별도의 서브넷을 생성해야 합니다. 또한 DB 연결 구성도 Multi-AZ가 아닙니다.

D: 서브넷이 두 가용 영역에 걸쳐 확장될 수 없다는 점은 B와 동일합니다. 단일 서브넷은 단일 AZ에만 존재하므로 '두 AZ에 걸쳐 확장되는 서브넷'이라는 전제 자체가 AWS 아키텍처에서 불가능합니다. RDS Multi-AZ 구성은 올바르지만, 서브넷 구성이 잘못되었습니다.
