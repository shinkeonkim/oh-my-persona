## Question

한 회사가 Amazon EC2 인스턴스를 사용하여 퍼블릭 웹 애플리케이션에 대한 요청을 처리합니다. 이 애플리케이션은 URL 경로를 사용하여 여러 애플리케이션 페이지로 트래픽을 라우팅합니다. 그런데 예측할 수 없는 시점에 트래픽이 급증하기 시작합니다. 트래픽 급증으로 인해 웹 애플리케이션에 문제가 발생하고 가끔씩 사용할 수 없게 됩니다. 회사는 갑작스러운 트래픽 증가를 처리하기 위해 웹 애플리케이션의 확장성을 높여야 합니다.
이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

- [ ] A. 웹 애플리케이션 인스턴스의 Amazon Machine Image(AMI)를 생성합니다. AMI를 사용하여 최소 용량이 2개인 EC2 인스턴스로 구성된 Auto Scaling 그룹을 생성합니다. 애플리케이션 로드 밸런서를 생성합니다. Auto Scaling 그룹을 대상 그룹으로 설정합니다.
- [ ] B. 애플리케이션의 Docker 이미지를 생성합니다. Amazon Elastic Container Service(Amazon ECS)를 사용하여 Auto Scaling ECS 클러스터를 생성합니다. 관리형 확장을 활성화합니다. 네트워크 로드 밸런서를 생성합니다. ECS 클러스터를 대상 그룹으로 설정합니다.
- [ ] C. 웹 애플리케이션 인스턴스의 Amazon Machine Image(AMI)를 생성합니다. AMI를 사용하여 별도의 가용 영역에 두 개의 웹 애플리케이션 인스턴스를 더 생성합니다. 세 인스턴스를 모두 참조하도록 웹사이트 DNS 레코드를 업데이트합니다.
- [ ] D. 애플리케이션 로드 밸런서(ALB)를 생성합니다. 웹 애플리케이션 인스턴스를 대상으로 설정합니다. ALB 트래픽 지표를 기반으로 Amazon CloudWatch 알람을 생성합니다. 트래픽 급증 시 활성화되도록 알림을 구성합니다.

## Answer

정답: A

## Explanation

AMI를 생성하여 Auto Scaling 그룹과 ALB를 설정하면 트래픽 급증에 자동으로 대응할 수 있습니다. 최소 용량 2를 설정하여 고가용성을 보장하고, ALB는 URL 경로 기반 라우팅을 지원하여 기존 애플리케이션 구조에 적합합니다.

오답 분석

B: Docker 이미지를 생성하고 ECS 클러스터를 설정하는 것은 기존 EC2 기반 애플리케이션을 컨테이너화하는 추가 작업이 필요하며, NLB는 URL 경로 기반 라우팅을 지원하지 않습니다.

C: DNS 레코드를 세 인스턴스로 업데이트하는 것은 자동 확장이 불가능하며, 인스턴스 장애 시 자동으로 대응하지 못합니다.

D: ALB에 단일 인스턴스를 대상으로 설정하고 CloudWatch 알람만 생성하면 실제 자동 확장이 이루어지지 않아 트래픽 급증에 대응할 수 없습니다.
