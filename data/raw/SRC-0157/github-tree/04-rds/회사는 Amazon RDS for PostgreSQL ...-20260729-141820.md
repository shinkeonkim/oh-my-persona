## Question

회사는 Amazon RDS for PostgreSQL 단일 AZ DB 인스턴스에 모든 주문을 저장하는 온라인 쇼핑 애플리케이션을 호스팅합니다. 경영진은 단일 실패 지점을 제거하기를 원하며 솔루션 설계자에게 애플리케이션 코드를 변경하지 않고도 데이터베이스 다운타임을 최소화할 수 있는 접근 방식을 권장하도록 요청했습니다.
어떤 솔루션이 이러한 요구 사항을 충족합니까?

- [ ] A. 데이터베이스 인스턴스를 수정하고 다중 AZ 옵션을 지정하여 기존 데이터베이스 인스턴스를 다중 AZ 배포로 변환합니다.
- [ ] B. 새로운 RDS 다중 AZ 배포를 생성합니다. 현재 RDS 인스턴스의 스냅샷을 만들고 스냅샷으로 새 다중 AZ 배포를 복원합니다.
- [ ] C. 다른 가용 영역에서 PostgreSQL 데이터베이스의 읽기 전용 복제본을 생성합니다. Amazon Route 53 가중 레코드 세트를 사용하여 데이터베이스 전체에 요청을 분산합니다.
- [ ] D. 최소 그룹 크기가 2인 Amazon EC2 Auto Scaling 그룹에 RDS for PostgreSQL 데이터베이스를 배치합니다. Amazon Route 53 가중 레코드 세트를 사용하여 인스턴스 간에 요청을 분산합니다.

## Answer

정답: A

## Explanation

기존 데이터베이스 인스턴스를 수정하여 다중 AZ 옵션을 지정하면 애플리케이션 코드를 변경하지 않고도 고가용성을 확보할 수 있습니다. RDS 다중 AZ 배포는 동기식 복제를 통해 대기 인스턴스를 유지하며, 장애 발생 시 자동으로 대기 인스턴스로 장애 조치됩니다. DNS 엔드포인트가 자동으로 대기 인스턴스를 가리키도록 전환되므로 애플리케이션 코드 변경이 필요하지 않습니다.

오답 분석

B: 스냅샷을 찍어 새 RDS 배포로 복원하면 별도의 독립적인 인스턴스가 생성됩니다. 이는 자동 장애 조치를 제공하지 않으며, 데이터가 실시간으로 동기화되지 않아 단일 실패 지점을 제거하지 못합니다.

C: 읽기 전용 복제본은 비동기식 복제를 사용하며, 장애 시 자동 장애 조치를 제공하지 않습니다. 수동으로 승격해야 하며, Route 53 가중 레코드 세트로 요청을 분산하면 쓰기 트래픽 문제가 발생할 수 있습니다. 또한 애플리케이션 코드 변경이 필요합니다.

D: RDS for PostgreSQL 데이터베이스를 EC2 Auto Scaling 그룹에 배치하는 것은 RDS 관리형 서비스의 기능이 아니며, 데이터베이스를 EC2에서 직접 관리해야 하므로 운영 오버헤드가 크게 증가합니다.
