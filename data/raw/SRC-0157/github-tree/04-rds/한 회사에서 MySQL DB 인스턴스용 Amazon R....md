## Question

한 회사에서 MySQL DB 인스턴스용 Amazon RDS를 출시했습니다. 데이터베이스에 대한 대부분의 연결은 서버리스 애플리케이션에서 발생합니다. 데이터베이스에 대한 애플리케이션 트래픽은 임의의 간격으로 크게 변경됩니다. 수요가 많을 때 사용자는 애플리케이션에 데이터베이스 연결 거부 오류가 발생한다고 보고합니다.
최소한의 운영 오버헤드로 이 문제를 해결하는 솔루션은 무엇입니까?

- [ ] A. RDS Proxy에서 프록시를 생성합니다. RDS Proxy를 통해 DB 인스턴스를 사용하도록 사용자 애플리케이션을 구성합니다.
- [ ] B. 사용자 애플리케이션과 DB 인스턴스 간에 Amazon ElastiCache for Memcached를 배포합니다.
- [ ] C. I/O 용량이 더 큰 다른 인스턴스 클래스로 DB 인스턴스를 마이그레이션합니다. 새 DB 인스턴스를 사용하도록 사용자 애플리케이션을 구성합니다.
- [ ] D. DB 인스턴스에 대한 다중 AZ를 구성합니다. DB 인스턴스 간에 전환하도록 사용자 애플리케이션을 구성합니다.

## Answer

정답: A

## Explanation

Amazon RDS Proxy는 서버리스 애플리케이션에서 데이터베이스 연결을 효율적으로 관리하도록 설계되었습니다. 서버리스 애플리케이션의 트래픽이 임의 간격으로 크게 변동할 때, RDS Proxy의 연결 풀링 기능이 데이터베이스 연결을 재사용하고 관리하여 연결 거부 오류를 방지합니다. RDS Proxy를 통해 DB 인스턴스를 사용하도록 구성하면 코드 변경 없이 최소한의 운영 오버헤드로 문제를 해결할 수 있습니다.

오답 분석

B: ElastiCache for Memcached는 캐시 솔루션으로, 연결 풀링 문제를 해결하는 것이 아니라 읽기 부하를 줄이는 데 사용됩니다. 연결 거부 오류의 근본 원인인 과도한 동시 연결 수를 해결하지 못합니다.

C: 더 높은 I/O 용량의 인스턴스 클래스로 마이그레이션하면 데이터베이스 성능은 향상되지만, 서버리스 애플리케이션의 급격한 연결 수 변동에 따른 연결 관리 문제를 해결하지 못합니다.

D: Multi-AZ는 고가용성을 위한 것이며, 대기 인스턴스는 읽기 트래픽을 처리할 수 없습니다. 또한 애플리케이션이 DB 인스턴스 간에 전환하도록 구성하는 것은 올바른 Multi-AZ 사용 방법이 아닙니다.
