## Question

한 회사가 Auto Scaling 그룹의 Amazon EC2 인스턴스에서 웹 애플리케이션을 실행합니다. 애플리케이션은 PostgreSQL DB 인스턴스용 Amazon RDS에서 실행되는 데이터베이스를 사용합니다. 트래픽이 증가하면 애플리케이션 성능이 느려집니다. 트래픽이 많은 기간 동안 데이터베이스에 읽기 로드가 많이 발생합니다.
이러한 성능 문제를 해결하기 위해 솔루션 설계자는 어떤 조치를 취해야 합니까? (2개를 선택하세요.)

- [ ] A. DB 인스턴스에 대해 Auto Scaling을 활성화합니다.
- [ ] B. DB 인스턴스에 대한 읽기 전용 복제본을 생성합니다. 읽기 트래픽을 읽기 전용 복제본으로 보내도록 애플리케이션을 구성합니다.
- [ ] C. DB 인스턴스를 다중 AZ DB 인스턴스 배포로 변환합니다. 대기 DB 인스턴스에 읽기 트래픽을 보내도록 애플리케이션을 구성합니다.
- [ ] D. Amazon ElastiCache 클러스터를 생성합니다. ElastiCache 클러스터에서 쿼리 결과를 캐시하도록 애플리케이션을 구성합니다.
- [ ] E. EC2 인스턴스가 DB 인스턴스와 동일한 가용 영역에 프로비저닝되도록 Auto Scaling 그룹 서브넷을 구성합니다.

## Answer

정답: B, D

## Explanation

두 가지 솔루션을 결합하여 성능 문제를 해결합니다. 첫째, DB 인스턴스에 대한 읽기 전용 복제본을 생성하고 읽기 트래픽을 복제본으로 보내면 기본 데이터베이스의 읽기 부하를 분산할 수 있습니다. 둘째, Amazon ElastiCache 클러스터를 생성하여 자주 실행되는 쿼리 결과를 캐시하면 데이터베이스에 대한 읽기 요청 수 자체를 줄일 수 있습니다. 이 두 가지 접근 방식은 서로 보완적으로 동작합니다.

오답 분석

A: Amazon RDS DB 인스턴스는 Auto Scaling을 기본적으로 지원하지 않습니다. RDS는 스토리지 Auto Scaling은 지원하지만 컴퓨팅 인스턴스의 Auto Scaling은 지원하지 않습니다.

C: Multi-AZ DB 인스턴스 배포에서 대기 DB 인스턴스는 읽기 트래픽을 처리할 수 없습니다. 대기 인스턴스는 장애 조치를 위한 것이며, 읽기 요청을 처리하는 용도로 사용할 수 없습니다.

E: EC2 인스턴스를 DB 인스턴스와 동일한 가용 영역에 프로비저닝하면 네트워크 지연이 약간 줄어들 수 있지만, 데이터베이스의 읽기 부하 문제를 해결하지 못하며 고가용성도 저하됩니다.
