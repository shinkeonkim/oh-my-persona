## Question

전자상거래 회사가 AWS에서 애플리케이션을 실행합니다. 애플리케이션은 기본 데이터베이스에 대해 다중 AZ 모드의 Amazon Aurora PostgreSQL 클러스터를 사용합니다. 최근 판촉 캠페인 중에 애플리케이션에 과도한 읽기 로드 및 쓰기 로드가 발생했습니다. 사용자가 애플리케이션에 액세스하려고 할 때 시간 초과 문제가 발생했습니다.
솔루션 아키텍트는 애플리케이션 아키텍처의 확장성과 가용성을 높여야 합니다.
가동 중지 시간을 최소화하면서 이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

- [ ] A. Aurora 클러스터를 소스로 포함하는 Amazon EventBridge 규칙을 생성합니다. Aurora 클러스터의 상태 변경 이벤트를 기록하는 AWS Lambda 함수를 생성합니다. EventBridge 규칙의 대상으로 Lambda 함수를 추가합니다. 장애 조치할 추가 리더 노드를 추가합니다.
- [ ] B. Aurora 클러스터를 수정하고 ZDR(제로 다운타임 재시작) 기능을 활성화합니다. 클러스터에서 데이터베이스 활동 스트림을 사용하여 클러스터 상태를 추적합니다.
- [ ] C. Aurora 클러스터에 추가 리더 인스턴스를 추가합니다. Aurora 클러스터에 대한 Amazon RDS 프록시 대상 그룹을 생성합니다.
- [ ] D. Redis 캐시용 Amazon ElastiCache를 생성합니다. Write-around 방식의 AWS Database Migration Service(AWS DMS)를 사용하여 Aurora 클러스터에서 Redis로 데이터를 복제합니다.

## Answer

정답: C

## Explanation

Aurora 클러스터에 추가 리더 인스턴스를 추가하면 과도한 읽기 로드를 분산할 수 있으며, Amazon RDS Proxy를 함께 사용하면 데이터베이스 연결을 효율적으로 관리하여 쓰기 로드에 대한 연결 관리도 개선됩니다. RDS Proxy는 연결 풀링을 통해 데이터베이스 연결 수를 줄이고, 장애 조치 시에도 애플리케이션 연결을 유지합니다. 이 조합은 읽기와 쓰기 모두의 확장성을 최소 다운타임으로 향상시킵니다.

오답 분석

A: EventBridge와 Lambda를 사용한 상태 변경 이벤트 로깅은 모니터링에는 유용하지만, 데이터베이스의 읽기/쓰기 성능을 직접 개선하지는 않습니다. 리더 노드 추가만으로는 쓰기 로드 문제를 해결하지 못합니다.

B: ZDR(제로 다운타임 재시작)은 엔진 재시작 시 다운타임을 최소화하는 기능이며, 데이터베이스 활동 스트림은 감사용입니다. 두 기능 모두 확장성 문제를 해결하지 않습니다.

D: DMS를 사용한 Aurora에서 Redis로의 데이터 복제는 복잡한 설정이 필요하며, Write-around 방식으로는 쓰기 성능 문제를 해결하지 못합니다.
