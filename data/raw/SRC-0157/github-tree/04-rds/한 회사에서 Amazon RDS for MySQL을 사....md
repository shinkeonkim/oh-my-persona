## Question

한 회사에서 Amazon RDS for MySQL을 사용하여 중요한 애플리케이션을 배포하고 있습니다. 애플리케이션은 고가용성이어야 하며 자동으로 복구되어야 합니다. 이 회사는 최대 4시간 지연으로 대화형 사용자(트랜잭션 쿼리)와 일괄 보고(분석 쿼리)를 지원해야 합니다. 분석 쿼리는 트랜잭션 쿼리의 성능에 영향을 미치지 않아야 합니다.
어떤 솔루션이 이러한 요구 사항을 충족합니까?

- [ ] A. 하나의 대기 인스턴스가 있는 다중 AZ DB 인스턴스 배포에서 Amazon RDS for MySQL을 구성합니다. 트랜잭션 쿼리를 기본 DB 인스턴스로 지정합니다. 분석 쿼리를 다른 가용 영역에서 실행되는 보조 DB 인스턴스로 지정합니다.
- [ ] B. 두 개의 대기 인스턴스가 있는 다중 AZ DB 클러스터 배포에서 Amazon RDS for MySQL을 구성합니다. 트랜잭션 쿼리를 기본 DB 인스턴스로 지정합니다. 분석 쿼리를 리더 엔드포인트로 지정합니다.
- [ ] C. 여러 가용 영역에서 여러 읽기 복제본을 사용하도록 Amazon RDS for MySQL을 구성합니다. 트랜잭션 쿼리를 기본 DB 인스턴스로 지정합니다. 분석 쿼리를 다른 가용 영역의 복제본 중 하나로 지정합니다.
- [ ] D. 자동 백업이 활성화된 트랜잭션 쿼리의 기본 데이터베이스로 Amazon RDS for MySQL을 구성합니다. 자동 백업을 구성합니다. 매일 밤, 분석 쿼리를 지원하기 위해 가장 최근의 스냅샷에서 읽기 전용 데이터베이스를 만듭니다. 이전에 만든 데이터베이스를 종료합니다.

## Answer

정답: B

## Explanation

Multi-AZ DB 클러스터 배포는 두 개의 읽기 가능한 대기 인스턴스를 제공하여 고가용성(35초 이내 자동 장애 조치)과 읽기 쿼리 분리를 동시에 달성합니다. 트랜잭션 쿼리는 기본 DB 인스턴스로, 분석 쿼리는 리더 엔드포인트로 라우팅하여 성능 격리를 보장합니다. 복제 지연이 일반적으로 수십 밀리초 수준이므로 4시간 지연 요구 사항도 충족합니다.

오답 분석

A: 다중 AZ DB 인스턴스 배포의 보조 인스턴스(대기 인스턴스)는 읽기 트래픽을 처리할 수 없습니다. 대기 인스턴스는 장애 조치 목적으로만 사용되므로, 분석 쿼리를 보조 DB 인스턴스로 지정해도 실제 쿼리가 처리되지 않습니다.

C: 읽기 복제본은 분석 쿼리와 트랜잭션 쿼리 간의 성능 격리를 제공하지만, 읽기 복제본 자체는 고가용성과 자동 복구를 제공하지 않습니다. 기본 인스턴스에 별도로 Multi-AZ를 구성해야 하지만, 옵션 텍스트에는 이러한 구성이 포함되어 있지 않습니다.

D: 매일 밤 스냅샷에서 읽기 전용 데이터베이스를 생성하고 이전 데이터베이스를 종료하는 것은 운영 오버헤드가 높고 실시간에 가까운 데이터를 제공하지 못합니다.
