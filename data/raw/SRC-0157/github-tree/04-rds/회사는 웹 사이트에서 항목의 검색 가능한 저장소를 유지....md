## Question

회사는 웹 사이트에서 항목의 검색 가능한 저장소를 유지 관리합니다. 데이터는 1,000만 개 이상의 행을 포함하는 Amazon RDS for MySQL 데이터베이스 테이블에 저장됩니다. 데이터베이스에는 2TB의 범용 SSD 스토리지가 있습니다. 회사 웹 사이트를 통해 매일 이 데이터에 대한 수백만 건의 업데이트가 있습니다.
회사는 일부 삽입 작업이 10초 이상 걸리는 것을 발견했습니다. 회사는 데이터베이스 스토리지 성능이 문제라고 판단했습니다.
이 성능 문제를 해결하는 솔루션은 무엇입니까?

- [ ] A. 스토리지 유형을 프로비저닝된 IOPS SSD로 변경합니다.
- [ ] B. DB 인스턴스를 메모리 최적화 인스턴스 클래스로 변경합니다.
- [ ] C. DB 인스턴스를 버스트 가능한 성능 인스턴스 클래스로 변경합니다.
- [ ] D. MySQL 기본 비동기 복제로 다중 AZ RDS 읽기 복제본을 활성화합니다.

## Answer

정답: A

## Explanation

데이터베이스 스토리지 성능이 문제로 확인되었고 삽입 작업이 10초 이상 걸리므로, 스토리지 유형을 프로비저닝된 IOPS SSD로 변경하는 것이 가장 적합한 해결책입니다. 2TiB(≈2TB) gp2 볼륨은 기본 6,144 IOPS(3 IOPS/GiB × 2,048 GiB)를 제공하지만, IOPS 성능이 스토리지 용량에 연동되어 독립적으로 구성할 수 없습니다. 수백만 건의 일일 업데이트가 지속적으로 발생하는 환경에서는 gp2의 성능이 불충분하거나 예측하기 어려울 수 있습니다. 프로비저닝된 IOPS SSD(io1/io2)는 스토리지 용량과 독립적으로 IOPS를 설정하여 일관되고 예측 가능한 I/O 성능을 제공하여 이 문제를 해결합니다.

오답 분석

B: 메모리 최적화 인스턴스 클래스로 변경하면 메모리 관련 성능은 향상되지만, 문제가 스토리지 성능으로 확인되었으므로 근본적인 해결책이 아닙니다.

C: 버스트 가능 인스턴스 클래스(t 시리즈)는 일시적인 CPU 버스트에 적합하며, 스토리지 I/O 성능과는 관련이 없습니다. 오히려 성능이 저하될 수 있습니다.

D: 읽기 전용 복제본은 읽기 트래픽을 분산시키는 것으로, 삽입(쓰기) 작업의 스토리지 성능 문제를 해결하지 못합니다.
