## Question

회사에는 다양한 런타임으로 분당 최대 800회 AWS Lambda 함수를 호출하는 이벤트 기반 애플리케이션이 있습니다. Lambda 함수는 Amazon Aurora MySQL DB 클러스터에 저장된 데이터에 액세스합니다. 회사는 사용자 활동이 증가함에 따라 연결 시간 초과를 인지하고 있습니다. 데이터베이스는 과부하의 징후를 보이지 않습니다. CPU, 메모리 및 디스크 액세스 메트릭이 모두 낮습니다.
최소한의 운영 오버헤드로 이 문제를 해결하는 솔루션은 무엇입니까?

- [ ] A. 더 많은 연결을 처리하려면 Aurora MySQL 노드의 크기를 조정합니다. 데이터베이스 연결 시도에 대한 Lambda 함수의 재시도 논리를 구성합니다.
- [ ] B. Redis용 Amazon ElastiCache를 설정하여 데이터베이스에서 일반적으로 읽은 항목을 캐시합니다. 읽기를 위해 ElastiCache에 연결하도록 Lambda 함수를 구성합니다.
- [ ] C. Aurora 복제본을 리더 노드로 추가합니다. 라이터 엔드포인트가 아닌 DB 클러스터의 리더 엔드포인트에 연결하도록 Lambda 함수를 구성합니다.
- [ ] D. Amazon RDS 프록시를 사용하여 프록시를 생성합니다. DB 클러스터를 대상 데이터베이스로 설정합니다. DB 클러스터가 아닌 프록시에 연결하도록 Lambda 함수를 구성합니다.

## Answer

정답: D

## Explanation

Amazon RDS Proxy는 Lambda 함수와 같은 서버리스 애플리케이션에서 데이터베이스 연결을 효율적으로 관리하기 위해 설계되었습니다. RDS Proxy는 연결 풀링을 통해 데이터베이스 연결을 재사용하므로, 분당 최대 800회 호출되는 Lambda 함수가 각각 새로운 연결을 생성하는 대신 기존 연결을 공유할 수 있습니다. 데이터베이스의 CPU, 메모리, 디스크 메트릭이 모두 낮으므로 성능 문제가 아닌 연결 수 관리 문제이며, RDS Proxy가 이를 정확히 해결합니다.

오답 분석

A: Aurora MySQL 노드의 크기를 조정해도 연결 풀링 문제는 해결되지 않습니다. 데이터베이스 메트릭이 이미 낮으므로 리소스 부족이 아닌 연결 관리 문제입니다. 재시도 논리만으로는 근본적인 연결 과다 문제를 해결할 수 없습니다.

B: ElastiCache는 자주 읽는 데이터를 캐시하여 데이터베이스 부하를 줄이는 데 도움이 되지만, 이 시나리오에서는 데이터베이스 부하가 아닌 연결 수 관리가 문제입니다.

C: Aurora 복제본을 추가하면 읽기 부하를 분산할 수 있지만, 각 Lambda 호출이 여전히 새로운 연결을 생성하므로 연결 과다 문제는 해결되지 않습니다.
