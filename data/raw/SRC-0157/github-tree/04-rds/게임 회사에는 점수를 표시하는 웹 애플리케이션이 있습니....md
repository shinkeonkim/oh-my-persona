## Question

게임 회사에는 점수를 표시하는 웹 애플리케이션이 있습니다. 애플리케이션은 Application Load Balancer 뒤의 Amazon EC2 인스턴스에서 실행됩니다. 애플리케이션은 Amazon RDS for MySQL 데이터베이스에 데이터를 저장합니다. 사용자는 데이터베이스 읽기 성능으로 인해 긴 지연과 중단을 경험하기 시작했습니다. 회사는 애플리케이션 아키텍처의 변경을 최소화하면서 사용자 경험을 개선하고자 합니다.
솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 합니까?

- [ ] A. 데이터베이스 앞에서 Amazon ElastiCache를 사용합니다.
- [ ] B. 애플리케이션과 데이터베이스 간에 RDS 프록시를 사용합니다.
- [ ] C. 애플리케이션을 EC2 인스턴스에서 AWS Lambda로 마이그레이션합니다.
- [ ] D. MySQL용 Amazon RDS에서 Amazon DynamoDB로 데이터베이스를 마이그레이션합니다.

## Answer

정답: A

## Explanation

Amazon ElastiCache는 인메모리 캐시 솔루션으로, 자주 조회되는 데이터를 캐시에 저장하여 데이터베이스에 대한 읽기 요청 자체를 줄여줍니다. 게임 점수판과 같이 동일한 데이터가 반복적으로 조회되는 읽기 집약적 워크로드에서 데이터베이스 읽기 부하를 근본적으로 감소시켜 지연과 중단을 해결할 수 있습니다. 캐시 조회 로직을 애플리케이션에 추가해야 하지만, 기존 데이터베이스와 아키텍처를 그대로 유지하면서 캐시 레이어만 추가하는 것이므로 아키텍처 변경이 최소화됩니다.

오답 분석

B: RDS Proxy는 애플리케이션과 데이터베이스 사이에서 연결 풀링을 제공하여 커넥션 관리 오버헤드를 줄여주지만, 읽기 쿼리 자체는 여전히 데이터베이스에 도달합니다. 이 시나리오의 문제는 커넥션 수가 아니라 데이터베이스 읽기 성능(read performance) 자체이므로, RDS Proxy는 근본적인 해결책이 되지 못합니다.

C: EC2에서 Lambda로 마이그레이션하면 애플리케이션 아키텍처가 크게 변경되어야 하며, 데이터베이스 읽기 성능 문제를 직접 해결하지 못합니다.

D: Amazon DynamoDB로 마이그레이션하면 데이터 모델을 완전히 재설계해야 하므로 아키텍처 변경이 가장 큽니다.
