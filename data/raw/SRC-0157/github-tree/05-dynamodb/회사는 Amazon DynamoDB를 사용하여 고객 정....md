## Question

회사는 Amazon DynamoDB를 사용하여 고객 정보를 저장하는 쇼핑 애플리케이션을 실행합니다. 데이터 손상의 경우 솔루션 설계자는 15분의 RPO(복구 지점 목표)와 1시간의 RTO(복구 시간 목표)를 충족하는 솔루션을 설계해야 합니다.
이러한 요구 사항을 충족하기 위해 솔루션 설계자는 무엇을 권장해야 합니까?

- [ ] A. DynamoDB 전역 테이블을 구성합니다. RPO 복구의 경우 애플리케이션이 다른 AWS 리전을 가리키도록 합니다.
- [ ] B. DynamoDB 특정 시점으로 복구를 구성합니다. RPO 복구를 위해 원하는 시점으로 복원합니다.
- [ ] C. 매일 DynamoDB 데이터를 Amazon S3 Glacier로 내보냅니다. RPO 복구를 위해 S3 Glacier에서 DynamoDB로 데이터를 가져옵니다.
- [ ] D. 15분마다 DynamoDB 테이블에 대한 Amazon Elastic Block Store(Amazon EBS) 스냅샷을 예약합니다. RPO 복구의 경우 EBS 스냅샷을 사용하여 DynamoDB 테이블을 복원합니다.

## Answer

정답: B

## Explanation

DynamoDB 특정 시점 복구(Point-in-Time Recovery, PITR)는 테이블에 대한 변경사항을 지속적으로 백업하여 지난 35일 이내의 어느 시점으로든 초 단위 정밀도로 복원할 수 있습니다. PITR은 테이블의 쓰기 성능에 영향을 주지 않으며, 활성화만 하면 자동으로 백업이 수행됩니다. 15분 RPO는 PITR의 연속 백업으로 충족되며, 복원 작업은 테이블 크기에 따라 다르지만 일반적으로 수 분~수십 분 내에 완료되어 1시간 RTO도 충족합니다.

오답 분석

A: DynamoDB 전역 테이블은 다른 리전으로 밀리초 단위 실시간 복제를 제공하지만, 데이터 손상 시나리오에서는 손상된 데이터가 모든 리전으로 즉시 복제되므로 데이터 손상 복구에는 적합하지 않습니다. PITR과 달리 특정 시점으로 되돌릴 수 없습니다.

C: 매일 한 번 S3 Glacier로 내보내면 최대 24시간의 데이터 손실이 발생할 수 있어 15분 RPO 요구사항을 충족하지 못합니다. 또한 Glacier에서의 데이터 검색에 수 시간이 소요되어 1시간 RTO도 충족하기 어렵습니다.

D: DynamoDB는 관리형 서비스로 내부적으로 스토리지를 관리하며, 사용자가 EBS 볼륨에 직접 접근할 수 없습니다. 따라서 EBS 스냅샷으로 DynamoDB 테이블을 백업하거나 복원하는 것은 기술적으로 불가능합니다.
