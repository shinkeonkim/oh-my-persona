## Question

한 회사가 고객에게 거래 플랫폼을 제공합니다. 이 플랫폼은 Amazon API Gateway REST API, AWS Lambda 함수, Amazon DynamoDB 테이블을 사용합니다. 플랫폼에서 처리하는 각 거래는 Amazon DynamoDB에 거래 데이터를 저장하는 Lambda 함수를 호출합니다. 이 회사는 거의 실시간 분석을 위해 Amazon S3의 데이터 레이크로 거래 데이터를 수집하려고 합니다. 어떤 솔루션이 최소한의 운영 오버헤드로 이러한 요구 사항을 충족할까요?

- [ ] A. Amazon DynamoDB Streams를 사용하여 거래 데이터 변경 사항을 캡처합니다. DynamoDB Streams를 구성하여 Amazon S3에 데이터를 쓰는 Lambda 함수를 호출합니다.
- [ ] B. Amazon DynamoDB Streams를 사용하여 거래 데이터 변경 사항을 캡처합니다. DynamoDB Streams를 구성하여 Amazon Data Firehose에 데이터를 쓰는 Lambda 함수를 호출합니다. Data Firehose에서 Amazon S3에 데이터를 씁니다.
- [ ] C. DynamoDB 테이블에서 Amazon Kinesis Data Streams를 활성화하여 거래 데이터 변경 사항을 캡처합니다. Kinesis Data Streams를 구성하여 Amazon S3에 데이터를 쓰는 Lambda 함수를 호출합니다.
- [ ] D. DynamoDB 테이블에서 Amazon Kinesis Data Streams를 활성화하여 거래 데이터 변경 사항을 캡처합니다. Amazon Data Firehose의 입력이 될 데이터 스트림을 구성합니다. Data Firehose에서 Amazon S3로 데이터를 씁니다.

## Answer

정답: D

## Explanation

DynamoDB 테이블에서 Amazon Kinesis Data Streams를 활성화하면 테이블의 모든 데이터 변경을 실시간으로 캡처할 수 있습니다. Kinesis Data Streams를 Amazon Data Firehose의 입력으로 구성하면 Firehose가 자동으로 데이터를 배치 처리하여 S3에 전달합니다. 이 방식은 커스텀 Lambda 코드 작성이 필요 없어 운영 오버헤드가 가장 적습니다. 모든 구성요소가 완전 관리형 서비스입니다.

오답 분석

A: DynamoDB Streams → Lambda → S3 방식은 가능하지만, Lambda 함수를 직접 작성하고 유지 관리해야 하므로 D보다 운영 오버헤드가 더 큽니다.

B: DynamoDB Streams → Lambda → Data Firehose → S3 경로는 Lambda가 Firehose에 데이터를 전달하고 Firehose가 다시 S3에 쓰는 불필요한 중간 단계가 추가되어 복잡성과 비용이 증가합니다.

C: Kinesis Data Streams를 활성화한 후 Lambda로 S3에 쓰는 방식은 Lambda 코드 작성이 필요하여 D보다 운영 오버헤드가 큽니다.
