## Question

회사는 Amazon EC2 인스턴스에서 Java 기반 작업을 실행합니다. 작업은 매시간 실행되며 실행하는 데 10초가 걸립니다. 작업은 예약된 간격으로 실행되며 1GB의 메모리를 사용합니다.
작업이 사용 가능한 최대 CPU를 사용하는 짧은 순간을 제외하고 인스턴스의 CPU 사용률은 낮습니다. 회사는 작업 실행 비용을 최적화하려고 합니다.
이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

- [ ] A. AWS App2Container(A2C)를 사용하여 작업을 컨테이너화합니다. 0.5 vCPU(가상 CPU) 및 1GB 메모리를 사용하여 AWS Fargate에서 Amazon Elastic Container Service(Amazon ECS) 작업으로 작업을 실행합니다.
- [ ] B. 메모리가 1GB인 AWS Lambda 함수에 코드를 복사합니다. Amazon EventBridge 예약 규칙을 생성하여 매시간 코드를 실행합니다.
- [ ] C. AWS App2Container(A2C)를 사용하여 작업을 컨테이너화합니다. 기존 Amazon Machine Image(AMI)에 컨테이너를 설치합니다. 태스크가 완료되면 스케줄이 컨테이너를 중지하는지 확인합니다.
- [ ] D. 작업 완료 시 EC2 인스턴스를 중지하고 다음 작업이 시작될 때 EC2 인스턴스를 다시 시작하도록 기존 일정을 구성합니다.

## Answer

정답: B

## Explanation

Lambda 함수는 Java 런타임을 지원하며, 최대 10GB 메모리와 15분 실행 시간을 제공합니다. 시간당 10초만 실행되는 job에 Lambda는 실행 시간(10초)에 대해서만 과금되어 EC2의 상시 운영 비용 대비 극적인 비용 절감을 달성합니다. EventBridge 스케줄 규칙으로 정확히 1시간 간격의 cron 스케줄을 설정하면 자동으로 Lambda를 호출합니다. 서버리스로 EC2 인스턴스의 OS 패칭, 모니터링, 인스턴스 관리 등 모든 인프라 관리가 불필요하여 운영 효율성을 극대화합니다.

오답 분석

A: AWS App2Container로 컨테이너화하고 ECS Fargate에서 실행하면 Fargate 태스크 정의, 스케줄링 구성 등이 필요합니다. 10초 실행에 Fargate 태스크를 매시간 시작하는 것은 Lambda 대비 시작 시간이 길고 비용이 높습니다.

C: EC2 AMI에 컨테이너를 설치하고 스케줄로 시작/중지하면, EC2 인스턴스 부팅 시간(수 분)이 소요되고 인프라 관리 오버헤드가 존재합니다. 10초 실행을 위해 매시간 인스턴스를 부팅하는 것은 비효율적입니다.

D: EC2 인스턴스의 stop/start 스케줄링도 부팅 시간 지연과 인스턴스 관리 오버헤드가 발생합니다. Lambda의 밀리초 단위 시작 시간과 zero 관리 대비 운영 복잡성이 높습니다.
