## Question

회사는 AWS Lambda와 통합된 Amazon API Gateway API 백엔드를 사용하는 프론트엔드 애플리케이션을 호스팅합니다. API가 요청을 받으면 Lambda 함수는 많은 라이브러리를 로드합니다. 그런 다음 Lambda 함수는 Amazon RDS 데이터베이스에 연결하여 데이터를 처리하고 프론트엔드 애플리케이션에 데이터를 반환합니다. 회사는 회사 운영에 대한 변경 횟수를 최소화하면서 모든 사용자의 응답 대기 시간을 가능한 한 낮추고자 합니다.
이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

- [ ] A. API를 우회하여 쿼리 속도를 높이려면 프론트엔드 애플리케이션과 데이터베이스 사이에 연결을 설정합니다.
- [ ] B. 요청을 처리하는 Lambda 함수에 대해 프로비저닝된 동시성을 구성합니다.
- [ ] C. 유사한 데이터 세트를 더 빠르게 검색하기 위해 쿼리 결과를 Amazon S3에 캐시합니다.
- [ ] D. Lambda가 한 번에 설정할 수 있는 연결 수를 늘리려면 데이터베이스 크기를 늘립니다.

## Answer

정답: B

## Explanation

Lambda 함수의 provisioned concurrency를 설정하면 사전 초기화된 실행 환경이 준비되어 cold start 지연시간이 완전히 제거됩니다. Cold start는 Lambda가 새 실행 환경을 생성할 때 발생하며, 라이브러리 로딩과 데이터베이스 연결 초기화 등으로 수 초의 지연이 발생할 수 있습니다. Provisioned concurrency는 이러한 초기화 작업을 사전에 완료하여 한 자릿수 밀리초(single-digit milliseconds) 응답을 보장합니다. 이 설정이 API 호출 시 느린 응답 문제를 직접적으로 해결합니다.

오답 분석

A: 프론트엔드 애플리케이션에서 데이터베이스에 직접 연결하는 것은 보안상 위험하며(데이터베이스 자격 증명 노출), Lambda 기반 아키텍처의 근본적인 설계를 변경하는 것입니다. cold start 문제와 무관합니다.

C: 쿼리 결과를 S3에 캐싱하면 반복 쿼리의 응답 시간은 개선할 수 있지만, Lambda 함수의 cold start로 인한 초기 처리 지연은 해결되지 않습니다. 첫 호출 시의 느린 응답은 여전히 발생합니다.

D: 데이터베이스 크기를 증가시키면 더 많은 동시 연결을 지원할 수 있지만, Lambda 함수의 cold start 문제와는 무관합니다. 지연시간의 원인이 DB 연결 수가 아닌 Lambda 초기화에 있기 때문입니다.
